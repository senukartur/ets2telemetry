All eight are Node-safe: they never load native SQLite. Only the storage worker does ([storage](storage.md#storage-worker)).

```text
pipe bytes -> FrameDecoder('server') -> V1Consumer -> identity check -> live state, credit
                                                   \-> checkpoint, snapshots (with receipt labels), events, gaps -> DurableDelivery FIFO
                                                         -> sink observe (readings; the recorder samples them) | sink commit (items) -> DurableAckCursor -> ACK frame
                                                         -> samples op (5 s timer or 60 pending rows) -> appendSamples(uniqueSeconds), never an ACK
```

## Connection and validation

- **Hello.** One hello per connection with the service's `clientInstanceId` (one UUID per `V1Ingestion`, that is per service process). `durableEvents` is true only when a sink is configured, durable delivery is allowed (below), the selection is one of the `durableSelections` (every selection when the option is omitted) and `durableReady()` reports storage open (always when omitted; R10). It is decided at `connect`, when the hello is written: the native client sets its authority receipt, which names the plugin session, just before it emits `connect`. A live-only connection never sends `ack`.
- **Readiness (R10).** Live delivery never waits for storage: a connection made before storage opens is live-only. `durableAvailabilityChanged()` closes a current live-only connection that could now request durable delivery and reconnects once on the shortest backoff (250 ms) with a durable hello; it changes nothing when durable delivery is still not possible. The service calls it when its database opens (ET-015a PR-3), through `HistoryStorage`'s `onOpened`.
- **Validation.** Every frame passes the v1 `FrameDecoder` and `V1Consumer`: welcome, then exactly one checkpoint, then snapshots, events, gaps, clock replies and `end`. Any violation closes the connection as `incompatible` without a reconnection until the user selects a source again (E9). A service receive clock that runs backwards closes it the same way with the reason "Receive clock failure". This includes v0 and CAP0 frames, a duplicate or skipped `eventSeq`, an event on a live-only connection, a client message from the server and any frame after `end` in the same read.
- **Identity.** A game selection requires every envelope to equal the native broker's authority receipt (game, process ID, Windows session, process instance, plugin session) with origin `game`. A synthetic or replay selection requires the envelope origin to equal the selection, and the endpoint must match `TEST_PIPE_PATTERN_V1`, a desktop-local copy of the simulator's `\\.\pipe\ETS2Telemetry-SYNTHETIC-TEST-v1-{pid}-{uuid}` pattern (a test checks that the two stay identical).
- **Game connections.** `V1Ingestion` has no default native client: a game selection without the `connectGame` option or a broker configuration stays `unavailable`. The telemetry service supplies the broker's v1 mode ([service wiring](#service-wiring)).
- **Credit (E5).** The broker relays one frame per credit. Each frame is decoded, validated and applied synchronously, and its event or gap is queued, before the listener returns and the credit is granted. A credit never waits for storage.

## Live state (E2)

`V1SourceState` is service-internal. Since ET-010c only its whitelisted live projection leaves the service (see [Live projection](#live-projection-et-010c)); the clock mapping, the last `end`, the delivery cursor, continuity and durable status never do. The v0-retirement PR switches the live path.

| Field | Meaning |
| --- | --- |
| `status`, `reason`, `fresh` | `waiting`, `connected`, `paused`, `stale`, `disconnected`, `incompatible` or `unavailable`, with a fixed reason text |
| `observation` | The latest checkpoint or snapshot: source, `seq`, capture, state, status (delivery cursor, loss counters, game mode), continuity, `hydration` (true for the checkpoint) and the receive time |
| `clockMapping` | The local source-to-service clock mapping, when measured |
| `lastEnd` | The last `end` received, kept across reconnections |
| `durable` | `off`, `pending`, `active` or `failed` with a fixed code. `off`: no sink, or the latest hello of the selection did not request durable delivery (a selection outside `durableSelections`, storage not ready or never opened) or none was sent yet. `pending` and `active` are reported only for a connection that requested durable delivery. `failed` is reported whenever durable delivery has failed for the service lifetime (or is blocked by `ACK_AHEAD_OF_STORAGE`), also on the live-only connections that follow, so the failure stays visible (ET-015a PR-3 review pass 1) |

- **Hydration.** A checkpoint replaces current state only. Its job, truck and trailer configuration never become an event, a commit or an ACK (REG-003, REG-004). A welcome alone is never fresh.
- **Freshness.** The receive time advances only when `state.boundaryOrder` advances (OD-5 S7), on the service's monotonic receive clock. The state is `stale` 500 ms after the last new boundary, `paused` when a fresh state reports a paused simulation, and `waiting` when the simulation is unavailable.

## Reconnection (E9)

| Event | Status | Next |
| --- | --- | --- |
| Hello or checkpoint not received within 5 s | `disconnected` | Reconnect |
| EOF or close | `disconnected` | Reconnect |
| `end` (`plugin-shutdown`, `sequence-exhausted`, `source-retired`) | `disconnected`, `lastEnd` kept | Reconnect; a retired session finds no discovery record and waits |
| Broker exit 2 (no discovery record) | `waiting` | Reconnect |
| Broker startup deadline or exit 4 before any receipt (transient) | `waiting` | Reconnect |
| Retryable durable failure, `ACK_AHEAD_OF_STORAGE`, durable unavailable | `disconnected` | Reconnect (durable, or live-only) |
| Schema, order or identity violation; other broker rejections | `incompatible` | None until a new selection |

Reconnection delays are 250, 500, 1000, 2000 and then 4000 ms. They restart only once a connection proves healthy: a live-only connection at its hydrated checkpoint, a durable connection at its first successful commit. A persistent retryable storage failure, which closes each durable connection before its first commit, therefore keeps backing off instead of making the plugin redeliver its retained store every 250 ms. A reconnection waits for the previous broker process to exit.

## Clock probes (E10)

After each checkpoint the ingestion sends one `clock.probe`, then at most one per second while no probe is outstanding. `V1Consumer.expectClockReply` registers each probe before it is written, with IDs 1, 2, 3, … per connection. The client clock is injectable (`nowNs`, default `process.hrtime.bigint`) with one `clientClockId` per service. `computeClockMapping` turns a reply into `ClockMapping`; a reply more than 1 s after its probe gives no mapping, still ends the outstanding probe, and only then may the next probe be sent. A mapping whose source clock differs from a new welcome's capture clock is dropped. The mapping never leaves the service and never mixes the source clock with the service clock (§11).

## Storage-commit ACK pipeline (E5–E8)

- **Queue (E5, R5).** Events and gaps of every connection enter one FIFO in stream order, together with each durable connection's checkpoint and snapshots (readings). One sink command runs at a time. At most `MAX_PENDING_COMMITS` = 512 coverage items are queued or in flight (ET-015c, below); one more closes its connection as retryable with `BACKLOG_FULL`, drops that connection's queued work, and the producer redelivers after the reconnection. Snapshots are queued only for a sink with `observe` and count against their own bound, `MAX_PENDING_READINGS` = 512 (more than 25 s at 20 Hz, above the 10 s storage deadline that fails the worker): the 513th closes the connection the same way. Readings never count against the coverage items, so snapshots cannot starve events, and they are never coalesced or thinned, because that would change the reading holes and jumps the reducer sees (T17).
- **One ended connection's leftover work plus a full redelivery fits (ET-015c, G11).** The coverage-item bound is 512, twice the producer's 256 retained entries ([native v1 transport](native-transport-v1.md#store-rules), I2). Items still queued, and the one in flight, from a connection that has already ended keep counting until they leave the FIFO; dropping them would reorder readings against the redelivered events, and not counting them would leave the queue unbounded. They were never acknowledged, so they cover entries the producer still retains: at most 256. The reconnection redelivers the retained entries, again at most 256, and its live events are admitted into the same 256 entries until an ACK releases some, which happens only after commits that have already left the queue. The leftovers of one ended connection plus a full redelivery plus live events therefore fit (a live delta gap item, which extends the trailing gap record without a new entry, fits only while the leftovers and the redelivery stay below 512), so such a reconnection is no longer closed with `BACKLOG_FULL` while the earlier work drains, and events are no longer lost as `offline` through a refused reconnection. Events the plugin observes between the disconnection and the next durable hello are still `offline` loss. Under ET-015a's bound of 256 such a redelivery was refused once or a few times, and even with nothing left over a full redelivery was refused when one live item arrived before its first commit finished. The queue can still fill, and a reconnection still be refused for a while as retryable `BACKLOG_FULL` (bounded and draining, never a livelock), in two cases: leftovers stacked from several connections that ended before the queue drained, and a true storage stall, in which a gap record that keeps growing while nothing commits adds a delta gap item at each extension (I3, I6) without a new entry. `MAX_PENDING_READINGS` stays 512.
- **Readings (R5).** At the head of the FIFO the sink's `observe` runs synchronously: the checkpoint (after it started the cursor) and each snapshot reach the recorder at their place among the commits, so a reading that arrives while a commit is in flight waits for that commit's result. A refused reading stops durable delivery like a failed commit.
- **Receipt label (R8).** The ingestion reads its UTC clock (`utcNow`, default `Date.now`) when an event or gap frame is decoded and passes the value with the item; the sink receives it as `commit(message, {receivedUtcMs})`. A slow commit therefore never shifts the label the reducer uses for a session without UTC labels (T15). Since ET-015b PR-3 (H13) a durable connection's checkpoint and snapshots carry such a label too (`DurableConnection.checkpoint(message, receivedUtcMs)` and `snapshot(message, receivedUtcMs)`), and the sink receives it as `observe(message, {receivedUtcMs})`.
- **Cursor (E6).** At each durable welcome the pipeline queues `openSession` behind earlier work. `openSession` stores the session (`upsertSession`) and returns the stored contiguous coverage C, and a new `DurableAckCursor(pluginSessionId, C)` starts. The checkpoint's `ackedThroughEventSeq` A begins the connection. If A > C (for example a restored database), durable delivery stops for that plugin session with `ACK_AHEAD_OF_STORAGE`: the ingestion reconnects live-only, and a live-only welcome of another plugin session lifts the block and reconnects durable.
- **Restore loss (R9).** Before that connection closes, the pipeline awaits the sink's optional `restoreLoss(pluginSessionId, C, A)`. The recorder stores one session-level completeness interval `{kind: 'restore-loss', firstEventSeq: C + 1, lastEventSeq: A, detail: {cause: 'ack-ahead-of-storage', storedThroughEventSeq: C, ackedThroughEventSeq: A}}` with `recordCompleteness(..., {ifAbsent: true})`, so a service restart in the same plugin session adds no second row. `V1_DURABLE_RESTORE_LOSS {code}` is logged with `RECORDED` or the failure code; a failure does not unblock the session. The plugin session stays live-only until it ends (E6); its open trip closes as `restart` at the next plugin session of that game.
- **Commit.** Each item is `cursor.received` and then committed by the sink. `committed`, `duplicate` and `covered` commit the range in the cursor. `conflict` keeps the stored row (§9); the key counts as committed and `V1_EVENT_CONFLICT` is logged at counts 1, 2, 4, 8, …. After every commit the storage's `committedThroughEventSeq` must equal the cursor's `throughEventSeq`; otherwise durable delivery fails with `COVERAGE_MISMATCH` and nothing is acknowledged.
- **ACK (E8).** `cursor.ack()` runs only after the commit, and its frame is written only while the connection that received the coverage is current, open and before `end`. A commit that finishes after a disconnect or `end` writes nothing; the next connection acknowledges the range again once it has been redelivered (§10). Receipt, parsing or validation is never grounds for an ACK.
- **Stop.** `stop()` drops queued work, waits for the one command in flight and commits, observes or acknowledges nothing afterwards; a session open that completes after it changes no status. Since ET-015b PR-3 it then writes the sink's pending samples unless durable delivery failed ([one-second samples](#one-second-samples-et-015b)). A second `stop()` returns the first one's promise.
- **Ingestion stop (R14).** `V1Ingestion.stop()` is split into `stopSource()`, which ends the source and waits for the owned broker process (the intake phase; nothing is acknowledged afterwards), and `flush()`, which is the pipeline's `stop()`. `stop()` runs both in order. Queued commits are dropped, not drained: the producer retains and redelivers them, and no ACK could be written after the source closed. The service runs them as two shutdown steps ([service wiring](#service-wiring)).

### Failure classes (E7)

`STORAGE_FAILURE_CLASS` lists every `StorageErrorCode` in [packages/storage](../packages/storage/src/api.ts), so a new code fails to compile until it is classified. A rejected sink promise or a malformed result is `INTERNAL`.

| Class | Codes | Behavior |
| --- | --- | --- |
| Retryable | `DATABASE_LOCKED`, `DISK_FULL`, `IO_ERROR`, `STORAGE_BUSY` | No ACK. The connection closes, its queued work is dropped and it reconnects durable on the backoff; the producer keeps what it has not seen acknowledged (5 minutes of disconnect retention). `V1_DURABLE_RETRY {code, count}` is logged at counts 1, 2, 4, 8, … per code |
| Unavailable for the service lifetime | `WORKER_FAILED`, `TIMEOUT`, `CONSTRAINT_VIOLATION`, `SESSION_CONFLICT`, `INVALID_INPUT`, `INTERNAL`, `PERMISSION_DENIED`, `DATABASE_CORRUPT`, `UNKNOWN_SESSION`, `UNKNOWN_TRIP`, `VALUE_OUT_OF_RANGE`, `STORAGE_CLOSED`, `DATA_PATH_INVALID`, `DATABASE_UNRECOGNIZED`, `SCHEMA_NEWER`, `PURPOSE_MISMATCH`, `DURABILITY_UNVERIFIED`, `BACKUP_FAILED`, `MIGRATION_FAILED`; pipeline codes `COVERAGE_MISMATCH` and `INTERNAL` | No ACK. Every queued item is dropped, the connection closes and reconnects live-only. `V1_DURABLE_UNAVAILABLE {code}` is logged once; `durable` reports `failed` with the code |

Storage marks `TIMEOUT` retryable, but a missed deadline fails the `StorageClient` closed and every later command gets `WORKER_FAILED`, so the pipeline treats it as unavailable. `CONSTRAINT_VIOLATION` includes a session whose origin the database purpose refuses, such as a synthetic source in history.

The trip recorder adds three sink codes, `TRIP_ORDER_VIOLATION`, `TRIP_COVERAGE_MISMATCH` and `TRIP_UNKNOWN_SESSION`, for a reducer result `ok: false` (R7). They are contract defects between the stream, storage and the reducer, so `RECORDER_FAILURE_CLASS` makes every one `unavailable` and `failureClass` consults it after the storage table; they are logged through `V1_DURABLE_UNAVAILABLE {code}`. A code that is neither a storage nor a recorder code is never retried.

## Durable sink (E1)

`StorageDurableSink` maps `openSession` to `upsertSession({message: welcome})` and `commit` to `commitEvent` or `commitGap` with the validated message, without trip effects. Its optional effects hook was removed in ET-015a (S-3): a synchronous hook got no commit result, so it could not adopt the reducer state only after the commit (T3). The trip recorder below replaces it.

The durable path is proven only against temporary synthetic-purpose databases in tests and, since ET-015a PR-3, against a synthetic or replay [recording target](#recording-gate-et-015a). By default the service passes no sink: the hello requests `durableEvents: false`, nothing is written to history and nothing is acknowledged. Committing to history with empty effects was rejected (E1): effects apply on first insert only, so such rows could never receive trips.

## Trip recorder (ET-015a)

`TripRecorderSink` (R2) implements `DurableSink` over the storage client and owns the reducer state. `DurableDelivery` stays the only FIFO and the only single-in-flight scheduler; the recorder adds no queue of its own. It follows the [caller contract](trips.md#caller-contract-for-et-015a):

| Sink member | What the recorder does |
| --- | --- |
| `openSession(welcome)` | `upsertSession` returns the stored coverage C. When the reducer knows no session of the welcome's game (`games[game].sessionId === null`, the first durable welcome per game in the recorder's lifetime; R15), it reads that game's stored open trips with `readTripSeeds` (R4). When the reducer still has a connection, it steps `disconnected` first (R6): the interval comes from the session's last item and reading, not from when the step runs, and the old connection's queued work preceded this welcome in the FIFO. Then it steps `session` with C and the seeds |
| `commit(message, {receivedUtcMs})` | Reads `committedThrough()`, steps the event or gap, commits it with the returned effects in one transaction and adopts the stepped state only on `committed`, `duplicate`, `covered` or `conflict` (T3). A retryable failure keeps the state, so the redelivered item is stepped from it again (R7). A gap whose `previouslyCoveredThrough` differs from the coverage read before the commit, or is missing, is not adopted and fails with `TRIP_COVERAGE_MISMATCH`. This is detection after the commit, not prevention: the gap row and its effects are already stored. Durable delivery stops (no ACK, live-only), and a later cold start seeds from those rows. Under the single-writer rule it should never happen; the mismatch is on the enablement list ([Pending](#pending)) |
| `observe(message, {receivedUtcMs})` | A checkpoint steps `checkpoint` and then its state as a reading; a snapshot steps a reading. The state is normalized with `normalizeV1State`, as the trip replay does. Since ET-015b PR-3 the adopted reading then goes through `sampleReading` with the trip view of its game and its receipt label (H2, H7, H13), and a sampled row joins the pending `SampleBuffer` |
| `restoreLoss(session, C, A)` | The `restore-loss` interval above, with `ifAbsent` (R9) |
| `samples` (ET-015b) | The pending rows for DurableDelivery: `pending()` (`{rows, losses}`), `write(maxRows, final)` (one plugin session's ended loss intervals, every one with `final`, with `recordCompleteness`, then at most `maxRows` of its rows with `appendSamples(…, {uniqueSeconds: true})`; each part leaves the buffer only once stored), `discard()` and `dropped()` |
| `view(game)` | The read-only `tripView` of the adopted state, for ET-015b's sample trip UUIDs (R17) |

A `conflict` result is adopted, as T3 says (R16). Ingestion commits contiguously, so a conflict can only hit an eventSeq at or below the coverage, where the reducer is a no-op; any later divergence fails closed through storage's `UNKNOWN_TRIP`. An `unavailable` failure stops durable delivery for the service lifetime, so the recorder is no longer called; the next service start cold-starts from seeds.

## One-second samples (ET-015b)

ET-015b PR-3 records one-second history samples through the trip recorder, under decisions H2, H5, H7–H13, H15 and H17 ([concept.md](../concept.md#et-015b-authorization--october-16-2026)). The pure sampler is [history-samples.ts](../packages/telemetry-core/src/history-samples.ts) ([trips](trips.md#one-second-sampler-et-015b)); storage's one-row-per-second guard is the `uniqueSeconds` option of `appendSamples` ([storage](storage.md#storage-api)). DurableDelivery stays the only scheduler (R2): the recorder only holds the rows.

```text
reading at the FIFO head -> TripRecorderSink.observe: step the reducer and adopt the reading
  -> sampleReading(sampler, {message, receivedUtcMs, view: tripView(state, reading's game)}) -> SampleBuffer (at most 300 rows)
DurableDelivery: first pending row arms a 5 s timer | 60 rows pending -> {kind: 'samples'} op at the FIFO tail
  -> samples.write(60): recordCompleteness(sample-loss) for ended dropped runs, then appendSamples(session, at most 60 rows, {uniqueSeconds: true})
stop(): drop queued work, wait for the command in flight, then write every pending row and loss run (samples.write(300, final))
```

| Constant | Value | Meaning |
| --- | --- | --- |
| `SAMPLE_FLUSH_MS` | 5,000 ms | A `samples` op is queued once the oldest pending row has waited this long; the timer is armed when rows become pending and no op is queued or running, and re-armed for rows left after a batch (H8) |
| `SAMPLE_BATCH_ROWS` | 60 | A `samples` op is queued at once when this many rows are pending, and one op writes at most this many rows of one plugin session (H8). A 60-row commit took 2.5 ms median and 3.8 ms at the 95th percentile in the [ET-013 measurement](storage.md#measured-size-et-013-pr-2) |
| `MAX_PENDING_SAMPLES` | 300 | Rows held while storage is behind (5 minutes at 1 Hz); beyond it the newest row is dropped (H9) |
| `MAX_LOSS_RUNS` | 16 | Pending loss runs per plugin session and source clock; a further run is merged into the latest one, whose interval then also spans the rows accepted between them and whose count stays the dropped rows (review pass 1) |

- **Sampling (H2, H7, H13).** After `observe` adopts a reading, the recorder calls `sampleReading` with the trip view of the reading's game from the adopted state and the reading's receipt label. A sample therefore names only a trip that a commit before it in the FIFO opened, and only while that trip is `active` without an untracked job. Its `utcMs` is the reading's `captureUtcUnixMs` (the label of the SDK frame that published the state), otherwise the receipt label; its `monotonicNs` is the message's capture time, so the two can be up to about 50 ms apart (the snapshot interval).
- **One op (H8, H10).** At most one `samples` op is queued or running. It joins the FIFO tail, so a coverage item queued after it waits behind one bounded batch, and it belongs to no connection: a connection's failure or overflow never drops it. Samples never count against the coverage-item or reading bounds (512 each), and a sample write never produces or advances an ACK.
- **Batches.** One write stores one plugin session: first the `sample-loss` interval of each of its ended dropped runs, then its oldest rows. Each part leaves the buffer only once stored, so a loss interval written before a failed row write is not written again. `pending()` reports rows and loss intervals apart; the batch trigger counts rows, and the timer runs while either is pending.
- **Bound (H9).** Beyond 300 pending rows the newest row is dropped (D7). Each contiguous dropped run of a plugin session on one capture clock becomes one session-level interval `{tripUuid: null, kind: 'sample-loss', startUtcMs, endUtcMs, startMonotonicNs, endMonotonicNs, sourceClockId, detail: {cause: 'sample-backlog', count}}` from its first and last dropped row. A run stays open while the buffer is full and ends when a row of its session is accepted again, when stored rows free room, or when a dropped row is on another clock. Only an ended run is written, except by the final write at `stop()`, so one contiguous outage gives one interval however often its rows or its interval fail and are retried (review pass 1). Taking a batch never ends a run: the batch keeps a snapshot, and storing the interval removes exactly that part, so rows dropped meanwhile remain as the rest of the run. At most 16 runs are kept per plugin session and clock, which also bounds the loss writes of one op. A loss interval does not change any trip's completeness: the same storage failure fails event commits as well.
- **Failures (H12).** A retryable code (`DATABASE_LOCKED`, `DISK_FULL`, `IO_ERROR`, `STORAGE_BUSY`) keeps the rows, leaves every connection open and the durable status unchanged, and the rows wait for the next timer even when a full batch is pending. Any other code, a rejected promise or a malformed result stops durable delivery for the service lifetime like a failed commit (`V1_DURABLE_UNAVAILABLE {code}`, the latest connection closes and reconnects live-only), and the pending rows are discarded. Any lifetime failure, also one from an event commit, discards them.
- **Orderly exit (H11).** `stop()`, called by the `recording-flush` step, clears the timer, drops queued items and a queued `samples` op, waits for the command in flight and then, unless durable delivery failed, writes every pending row and loss run, ended or not: one write per plugin session of at most 300 rows, its loss intervals first. The step keeps its 500 ms and the stop its 2,500 ms total; rows still unwritten when the step expires are lost, and the storage close still finishes the command in flight.
- **Synthetic only (H15).** Samples are written only by the recorder, which exists only for a synthetic or replay [recording target](#recording-gate-et-015a). The gate and its tripwire are unchanged.

| Situation | Rows lost | Recorded as |
| --- | --- | --- |
| Steady state | None; at most 5 s of rows plus one batch command are uncommitted | — |
| Recording process killed | The pending rows (normally the last 5 s, about 5–6 rows) and readings queued but not yet observed (normally none; at most 512 behind a stalled commit) | Only through an open trip's `consumer-restart` interval at the next start; otherwise missing seconds |
| Orderly exit | None unless the 500 ms step expires | Missing seconds |
| Retryable storage failure | None while at most 300 rows are pending | `V1_SAMPLES_RETRY` |
| Storage backlog beyond 300 rows | The newest rows | One session-level `sample-loss` interval per contiguous dropped run, however often it is retried; `V1_SAMPLES_DROPPED` |
| Unavailable storage | Every pending row | `V1_DURABLE_UNAVAILABLE`, `V1_SAMPLES_DISCARDED`; durable `failed` |
| Paused, unavailable, stale or disconnected seconds | No row by design (H5) | The reducer's trip `sample-loss` and `not-connected` intervals |

Diagnostics, fixed codes and numbers only: `V1_SAMPLES_RETRY {code, count}` at counts 1, 2, 4, 8, … per code; `V1_SAMPLES_DISCARDED {count}` once, with the rows discarded at the lifetime failure; `V1_SAMPLES_SKIPPED {count}`, the running total of rows storage skipped as already stored, logged when it reaches or passes 1, 2, 4, 8, …; `V1_SAMPLES_DROPPED {count}`, the running total of rows the bound dropped, at 1, 2, 4, 8, …; and `V1_SAMPLES_EXIT {rows, losses, code}` once at `stop()` when anything was pending, with the pending rows, the pending loss intervals and `WRITTEN`, the failure code or `INTERNAL`.

## Service wiring

PR-3 (E2, E9, E12) runs one `V1Ingestion` in the telemetry service beside the v0 `TelemetryIngestion`:

- **Recording runtime (ET-015c PR-1, G13).** Since ET-015c the service builds its v1 ingestion, the recording plan, the database (`HistoryStorage`) and, for a recording target, the trip recorder through `createRecordingRuntime` in [recording-runtime.ts](../apps/desktop/src/recording-runtime.ts). The entry point supplies its environment, LOCALAPPDATA, log, the physical storage worker, the broker's v1 mode and its live-state callback; it keeps v0 ingestion, captures, the storage probe and the probe-failure exit, which closes `runtime.history`. `register(shutdown)` adds the three recording steps below, and `start()` opens the database. The move changed no behaviour: `tests/unit/telemetry-service-v0.test.ts` passes with unchanged expectations.

- **Live-only (E2).** By default the service passes no durable sink ([recording gate](#recording-gate-et-015a)). Every hello asks for `durableEvents: false`, so the plugin copies no event and counts each one it observes as `noDurableConsumer` loss (OD-4); the service sends no ACK and writes no history row, and `durable` stays `off`. Clock probes run as described above. `V1SourceState` stays inside the service; since ET-010c its whitelisted projection rides on the live update (see [Live projection](#live-projection-et-010c)).
- **Selection.** Each `select` command, after the v0 ingestion has accepted it, also selects the same source for v1. A v1 failure is logged as `V1_SELECT_REJECTED` and never fails the v0 selection.
- **Game sources.** Only through the verified native broker in its v1 mode (`--protocol v1`), started by `NativePipeClient` in v1 mode ([native broker control](telemetry-service-v0.md#protocol-v1-mode)). The client accepts only the six-key receipt marked `protocolMajor: 1` and rejects a v0 receipt, and a v0 client rejects a v1 receipt. It sends the hello raw and every later client frame (`clock.probe` here; `ack` only with a sink) as tag `0x02` followed by the frame, apart from the `0x01` credits. A client frame whose length prefix does not match it or whose payload is outside 1–4,096 bytes closes the connection with the outcome `client-frame-rejected` before anything reaches the broker. The broker stages `client-frame` and `client-write` are known stage names. No Node code opens a game pipe.
- **Discovery directory (E12).** The v1 directory is derived from the validated v0 broker configuration that main sends with a selection: a directory named `v0` under a parent named `transport` gives its sibling `v1` (`%LOCALAPPDATA%\ETS2Telemetry\transport\v1`) with the same verified executable. Any other shape gives no configuration, so a v1 game source stays `unavailable` instead of guessing a directory. The main-to-service message is unchanged.
- **Fixtures.** A `synthetic` or `replay` selection connects v1 only to `ETS2TELEMETRY_SOURCE_PIPE_V1`, which must match `TEST_PIPE_PATTERN_V1`; without it v1 is `unavailable`. The envelope origin must equal the selection.
- **Two brokers.** A game selection now runs two broker processes, one per protocol, each with its own directory, policy and lock. A v1 broker that finds no `transport\v1` directory (a plugin without v1) reports `waiting` and exits 2; the ingestion retries on the backoff above.
- **Shutdown (R14).** The `v1-ingestion` step runs in the `intake` phase beside `ingestion` and `capture` with a 1,000 ms budget; it calls `stopSource()`, which ends the source and waits for the broker process, so nothing is acknowledged afterwards. The `recording-flush` step (ET-015a PR-3) is the only step of the `flush` phase, with a 500 ms budget; it calls `flush()`, which drops queued durable work and waits for the one storage command in flight, before the `storage` phase closes the database. Since ET-015b PR-3 it then writes the pending one-second samples (H11). Without a sink it has nothing to wait for. The phase maxima are 1,000 ms (`intake`) + 500 ms (`flush`) + 1,000 ms (`storage`) = 2,500 ms, exactly `SERVICE_STOP_BUDGET_MS`, inside main's 3,000 ms kill deadline.

## Recording gate (ET-015a)

PR-3 (R3, R10, R14) decides in [recording-policy.ts](../apps/desktop/src/recording-policy.ts) whether the service records, and where. Production records no real game history: `GAME_HISTORY_RECORDING` is `false` (a unit test is a tripwire on it), and only the separate enablement PR may change it, after the v0 retirement (D2), real-game v1 evidence, ET-015b, ET-015c and the S-1/S-2 decision in ET-016. S-1 is done: ET-016 PR-6 persists trip fuel used ([trips](trips.md#readings-accounting-t16-t17)); S-2 (late-attach trips, ET-016 PR-7) remains on the list.

`recordingPlan(env, {gameHistory})` returns the database and the durable selections:

| `ETS2TELEMETRY_RECORDING` | Database | Durable selections | Sink |
| --- | --- | --- | --- |
| Unset or empty | History, `%LOCALAPPDATA%\ETS2Telemetry\data\telemetry.sqlite` | None (`ets2` and `ats` only once `GAME_HISTORY_RECORDING` is true) | None: every hello is live-only, as before |
| `synthetic:<name>` or `replay:<name>`, name `[a-z0-9-]{1,64}` | `%LOCALAPPDATA%\ETS2Telemetry\synthetic\<name>.sqlite` with that purpose, **instead of** history; backups in `synthetic\backups` | Only the matching selection (`synthetic` or `replay`) | `TripRecorderSink` |
| Any other value | As unset; `RECORDING_TARGET_REJECTED` is logged once | As unset | As unset |

- **No path into history.** The value names a purpose and a file name only. The name pattern admits no separator, dot or capital, so it cannot leave the synthetic directory or name the history file, and `HistoryStorage` checks the name again before it builds the path (`DATA_PATH_INVALID` otherwise). A recording target never makes a game selection durable, even once game recording is enabled; the database's purpose trigger refuses any other origin as well (defence in depth). The service reads the variable from its own environment, which Electron's `utilityProcess.fork` inherits from main, so main.ts is unchanged.
- **Wiring.** With durable selections the service's recording runtime (`createRecordingRuntime`, since ET-015c PR-1) constructs `TripRecorderSink` over the `HistoryStorage` client (`recorderClient`), and passes `durableSelections` and `durableReady: () => history.state === 'open'` to `V1Ingestion`. Before the database opens, after a refused open or after a storage failure, every hello stays live-only, and a recorder command answers `STORAGE_CLOSED` (unavailable). When the open succeeds, `HistoryStorage` calls `onOpened`, and the service calls `durableAvailabilityChanged()`: a current live-only connection of a durable selection reconnects once with a durable hello (R10). Live delivery never waits for storage.
- **Diagnostics.** A target logs `RECORDING_TARGET {purpose}` before the open, and then the same `HISTORY_STORAGE_*` codes and facts as history mode; history mode itself logs exactly what it logged before. `RECORDING_TARGET_REJECTED` has no facts: the rejected value is never logged.
- **A refused target.** A target that cannot be opened (for example a read-only file, `PERMISSION_DENIED`) leaves the service live-only for its lifetime, like a refused history open; the file is not changed. Its v1 connections report `durable: off`, not `failed`: durable delivery was never requested, and the refusal itself is the logged `HISTORY_STORAGE_UNAVAILABLE {code}`. A synthetic-mode service with an ETS2 or ATS selection reports `off` too, unless durable delivery has already failed for the service lifetime, which reports `failed`. After a plain source disconnection, `active` remains until the next welcome. `failed` means that durable delivery was requested and then stopped.

## Recording status (ET-015c)

PR-3 (G2–G7, G9, G10, G12) makes the service report what its recording is doing. The service derives the status ([recording-status.ts](../apps/desktop/src/recording-status.ts), `deriveRecordingStatus`) and its recording runtime posts it to main as `{type: 'recording', status}` on the utilityProcess parent port. Main keeps it in `AppState.health.recording` ([application lifecycle](app-lifecycle.md#health-and-the-dashboard)) and never derives it itself; the live projection still carries no durable status (F2). The status holds fixed enums and counts only, never text, paths or identifiers.

**Shape (G2).** `{state: 'disabled'}`, `{state: 'unknown'}` (set by main only), or `{state, target, code, losses, trip}`. `target` is the database purpose (`history`, `synthetic` or `replay`), `code` a fixed code or null, `losses` the committed loss counts below, and `trip` the current trip of the game of the latest v1 observation (`phase`, the open trip's `completeness` or null, `untrackedJob`), or null before any observation.

**States (G3).** The first matching rule wins:

| # | Condition | State | Code |
| --- | --- | --- | --- |
| 1 | No trip recorder: production while `GAME_HISTORY_RECORDING` is `false`, and any service without a recording target | `disabled` | — |
| 2 | The database is `idle` or `opening` | `opening` | null |
| 3 | The database is unavailable (a refused open, a worker failure) or closed | `stopped` | The database's failure code, `STORAGE_CLOSED` without one |
| 4 | Durable delivery failed with `ACK_AHEAD_OF_STORAGE` | `live-only`: this plugin session continues live-only; a new plugin session ends it | `ACK_AHEAD_OF_STORAGE` |
| 4 | Durable delivery failed with any other code, for the service lifetime (G10) | `stopped` | That code (`PERMISSION_DENIED`, a recorder code, `COVERAGE_MISMATCH`, …) |
| 5 | The selection is not one of the plan's durable selections (no source chosen yet, or a game while recording to a synthetic target) | `not-recorded-source` | null |
| 6 | The pipeline's retry code is set (G9) | `retrying` | `DISK_FULL`, `IO_ERROR`, `DATABASE_LOCKED`, `STORAGE_BUSY` or `BACKLOG_FULL` |
| 7 | The durable cursor is `active` and v1 is `connected` | `recording` | null |
| 7 | The durable cursor is `active` and v1 is `paused` | `paused` | null |
| 8 | Otherwise, when this selection was recording or paused since it was selected | `interrupted` | null |
| 8 | Otherwise | `waiting` | null |

`recording` thus needs all three: the database open, the durable cursor active and fresh v1 data (connected or paused are the fresh v1 statuses). Rule 8 splits G3's last two rules by whether the selection was recording or paused (cursor active, fresh v1 data) since it was selected: a connection that has not recorded yet reads `waiting` whatever order its session open and checkpoint take, and one that recorded and lost its fresh data or its connection reads `interrupted` until it records again ([deviation](validation/et-015c.md#pr-3-the-recording-status-from-the-service-to-main-october-16-2026)). One exception: the "recorded" latch in `recording-runtime.ts` follows each synchronous ingestion state, not the settled status, so a cursor that is briefly `active` with fresh data just before a checkpoint finds the database behind the plugin (`ACK_AHEAD_OF_STORAGE`) latches it. Once a later plugin session lifts that block, the selection then reads `interrupted` instead of `waiting` until the new session's checkpoint, although it recorded nothing. Only the shown state is affected, never the stored data (PR-3 review pass 2).

**Retry code (G9).** `DurableDelivery.retryCode` is set by a retryable commit or sample failure and by a backlog bound (`BACKLOG_FULL`), and cleared only by the next successful commit or sample write, not by a reconnection or a session open. `DISK_FULL`, `IO_ERROR` and `DATABASE_LOCKED` stay retryable; recovery uses the existing reconnect backoff (at most 4 s) and the 5 s sample timer. Permission and the other unavailable codes give `stopped` for the service lifetime; there is no automatic re-open (ET-019).

**Codes.** The closed set `RECORDING_CODES`: the storage error codes, the trip recorder's `TRIP_ORDER_VIOLATION`, `TRIP_COVERAGE_MISMATCH` and `TRIP_UNKNOWN_SESSION`, and the pipeline's `BACKLOG_FULL`, `COVERAGE_MISMATCH` and `ACK_AHEAD_OF_STORAGE`. A compile-time check keeps it equal to them; any other code reads `INTERNAL`.

**Losses (G6).** Counted by the trip recorder from what storage committed, as non-negative safe integers that saturate:

| Counter | Counts |
| --- | --- |
| `lostEvents` | For each gap committed as a new row, the eventSeq values it newly covers (`lastEventSeq` − `previouslyCoveredThrough`); for each recorded restore loss, its released range (A − C) |
| `eventLoss`, `notConnected`, `sampleLoss`, `restoreLoss` | Completeness intervals of that kind: the `completeness.add` effects of commits stored as new rows, each `sample-backlog` interval `samples.write` stored, and each recorded restore loss |
| `droppedSamples` | One-second rows the 300-row pending bound dropped |

A `duplicate`, `covered` or `conflict` result counts nothing, since its effects were stored earlier or never. The counts belong to one service process. Main adds every earlier process's last counts to the current one's (`addLosses`, folded when a service fails, exits or restarts), so the totals count since ETS2Telemetry started; an application restart starts new totals. `{state: 'unknown'}` carries no losses, so while main reports `unknown` (after a service failure, exit or restart, or restart exhaustion) the dashboard shows no totals; main keeps them and adds them to the next service's report ([TD-005](technical-debt.md#td-005-loss-totals-hidden-while-the-recording-status-is-unknown)). **Known overcount:** a later service in the same plugin session counts a restore loss again, although storage keeps one row, because `recordCompleteness(…, {ifAbsent: true})` does not report whether it inserted. After such a service restart main's totals show `restoreLoss` 2 and `lostEvents` twice A − C; the database is correct, and the totals (and those PR-4 shows) are an upper bound in that case ([TD-004](technical-debt.md#td-004-restore-loss-counted-once-in-the-live-loss-totals)). The database stays authoritative; a journal of losses is ET-016.

**No outage interval (G7).** No `storage-unavailable` interval is written. An outage reaches history only through the producer's gap causes (`noDurableConsumer`, `offline`, `retentionExpired`) once storage records again; the live status shows it while it happens.

**Timeliness (G5).** The status is event-driven. The database, the ingestion (every state change and every retry code change), the trip recorder (every commit, observation, sample-loss interval and restore loss) and the selection report changes; the publisher computes the status once the I/O callbacks of that event loop turn and their promise jobs ran (`setImmediate`), so a session open and a checkpoint that finds the database behind the plugin give no passing `recording`. Likewise, a snapshot that makes the source connected and an event that overflows the commit backlog, applied in the same turn, give only `retrying BACKLOG_FULL`. A new status whose losses changed is sent at once; any other new status at most once per 250 ms, the latest one at the end of the interval. An unchanged status is never sent again, and there is no heartbeat: a hung service stays pending for ET-019. The first status is sent at start, before readiness; none is sent once the orderly stop began.

**Main (G4, G12).** Main accepts the message only from the current service, until that service fails, exits or restarts, and not while the application stops. The message must be exactly `{type, status}` and the status must pass `parseRecordingHealth` (exact keys per variant, known enums, a code from the closed set or null, safe non-negative integer losses). Anything else sets `unknown` and logs `RECORDING_STATUS_REJECTED {count}` at counts 1, 2, 4, 8, …; it is not fatal, unlike an unknown message type (`SERVICE_INVALID_MESSAGE`). A valid status reaches the dashboard through the existing `app:state` push and `app:get-state`, and the tray through its presenter. No IPC channel, bridge method or preload code is added.

**Diagnostics.** The status adds no service log line; the existing codes explain it: `HISTORY_STORAGE_UNAVAILABLE {code}` and `V1_DURABLE_UNAVAILABLE {code}` (`stopped`), `V1_DURABLE_ACK_AHEAD` and `V1_DURABLE_RESTORE_LOSS` (`live-only`), `V1_DURABLE_RETRY` and `V1_SAMPLES_RETRY` (`retrying`), `V1_SAMPLES_DROPPED` (`droppedSamples`), `V1_SOURCE_STATUS` (`waiting`, `paused`, `interrupted`) and `RECORDING_TARGET` (the target). Main adds `RECORDING_STATUS_REJECTED {count}`, and, only in its opt-in smoke timeline (an explicit diagnostic directory, ET-015c PR-4), one `RECORDING_STATUS` row with the status as flat facts at each change ([isolated smoke diagnostics](app-lifecycle.md#isolated-smoke-diagnostics)).

## Live projection (ET-010c)

The service keeps the latest v0 update and the latest v1 projection and publishes `withV1(v0, v1)` through the existing live subscriptions, which coalesce to at most 20 Hz (decision F1). The projection ([live-v1.ts](../apps/desktop/src/live-v1.ts), `liveV1Projection`) is an explicit whitelist (F2):

| Field | Content |
| --- | --- |
| `selection`, `status`, `reason`, `fresh` | As in `V1SourceState` |
| `observation.source`, `seq`, `capture` | The latest checkpoint's or snapshot's envelope fields |
| `observation.state` | The wire state's keys except `window` (fifteen of sixteen), listed one by one, so a new wire key never leaks by default |
| `observation.sourceStatus` | `gameMode` and `eventLoss` only; never the delivery cursor |
| `observation.receivedMonotonicMs`, `hydration` | The service receive time (advances only with a new SDK boundary) and the checkpoint flag |

It never carries the window or its handle, the message kind, continuity, the clock mapping, the last `end` or durable status. The projection is attached only to a v0 update of the same selection. The service republishes only for a change the projection shows: the selection, status, reason, freshness or a new observation object; a clock mapping or durable status update alone republishes nothing.

Main validates the projection in the upstream handler, before freshness and the overlay see it, and the dashboard preload validates it again (`parseLiveV1`: exact keys, the update's selection, one of the seven v1 statuses, a reason of 1–256 characters without control characters, `fresh` only with an observation and a `connected` or `paused` status, and `validateLiveObservationV1`, which applies the wire state rules and rejects a window). An invalid projection is stripped and the v0 update kept; main logs `LIVE_V1_REJECTED {count}` at occurrences 1, 2, 4, 8, … and never closes the channel for it. Main and the preload expire the projection 500 ms after its last new receipt key (plugin session, process instance, capture clock, SDK boundary and receipt time), independently of v0 (F3). Display rules are in [live telemetry fields](live-telemetry-fields.md#protocol-v1-rows-et-010c).

## Journal queries (ET-016)

ET-016 PR-3 (J2, J4, J11) answers the trip journal's reads in the service ([journal-service.ts](../apps/desktop/src/journal-service.ts)), through the client of the database the recording runtime opened (`runtime.history`): the history database in production, or the synthetic or replay recording target. There is no second connection or worker.

- **Messages.** Main sends `{type: 'journal', id, query}` on the parent port; the service answers `{type: 'journal', id, result}` with a value or a fixed code (`SERVICE_UNAVAILABLE`, `DATABASE_OPENING`, `DATABASE_UNAVAILABLE` with its `storageCode`, `BUSY`, `TIMEOUT`, `NOT_FOUND`, `FAILED`). The query is parsed again in the service: a trips filter, a trip UUID, or a UUID with a page whose limit is one of the read's allowed sizes (events and intervals 100 or 500, samples 300 or 3,600). A malformed message is answered `FAILED` when its id is valid and logged as `JOURNAL_REQUEST_REJECTED {count}` at counts 1, 2, 4, 8, …
- **One at a time, only while open.** The service runs one journal read at a time; a second one while it runs answers `BUSY`. It reads only while `history.state` is `open` and its orderly stop has not begun: `idle` or `opening` answers `DATABASE_OPENING`, `unavailable` answers `DATABASE_UNAVAILABLE` with the history failure code, and `closed` or a stopping service answers `SERVICE_UNAVAILABLE`. So at most one journal command is ever in the storage client's queue, and it waits behind at most the recorder's one command in flight; it never advances coverage or produces an ACK.
- **Results.** Trips, the detail, timeline and interval pages are the storage reads' values; a sample page is `listSamples` with the trip scope plus the open database's purpose and schema version (`history.database`) and the next cursor of a full page. Storage errors map to fixed codes: `UNKNOWN_TRIP` to `NOT_FOUND`, `STORAGE_BUSY` to `BUSY`, `TIMEOUT` to `TIMEOUT`, `WORKER_FAILED` and `STORAGE_CLOSED` to `DATABASE_UNAVAILABLE` with the history failure code (or `SERVICE_UNAVAILABLE` while stopping), and everything else, including `JOURNAL_ANSWER_INVALID`, to `FAILED`.
- **A bad page.** A journal answer that broke the journal contract fails only that read in the storage client; the client and the recorder keep running. `HistoryStorage` logs it as `JOURNAL_ANSWER_INVALID {command, count}` at counts 1, 2, 4, 8, … A read that misses the client's 10 s deadline still fails the client closed and stops recording for the service lifetime, as any storage command does; every journal read is bounded for that reason ([journal](journal.md#data-source-and-purposes-j2-j3)).

Main's side (the queue, the 15 s deadline, retirement and the strict reply check) is described under [journal routing](journal.md#routing-and-bounds-j4).

## Diagnostics

Fixed codes and numbers only, through the `diagnose` option: `V1_DURABLE_RETRY {code, count}`, `V1_DURABLE_UNAVAILABLE {code}` (including the recorder codes), `V1_DURABLE_ACK_AHEAD {code}`, `V1_DURABLE_RESTORE_LOSS {code}` (ET-015a: `RECORDED` or the failure code), `V1_EVENT_CONFLICT {count}` and, since ET-015b PR-3, `V1_SAMPLES_RETRY`, `V1_SAMPLES_DISCARDED`, `V1_SAMPLES_SKIPPED`, `V1_SAMPLES_DROPPED` and `V1_SAMPLES_EXIT` ([one-second samples](#one-second-samples-et-015b)); by default the service has no sink, so they occur only with a recording target. The recording gate adds `RECORDING_TARGET {purpose}` and `RECORDING_TARGET_REJECTED` ([above](#recording-gate-et-015a)). The telemetry service adds `V1_SOURCE_STATUS {status, selection, durable, count}`, logged when the status changes, at occurrences 1, 2, 4, 8, … of each status, so a reconnection loop cannot fill the bounded log; `NATIVE_BROKER_V1_EXIT` with the same fixed facts and coalescing as the v0 `NATIVE_BROKER_EXIT`; and `V1_SELECT_REJECTED`. Since ET-015c PR-3 the service posts the [recording status](#recording-status-et-015c) without a log line of its own, and main logs `RECORDING_STATUS_REJECTED {count}` for an invalid one. No message content, identifiers or paths are logged.

# Synthetic protocol v0 simulator

ET-005a reuses the accepted [protocol 0.0](protocol/v0.md) without extending it.
The simulator is a Node CLI, independent of Electron and the SCS SDK. The
simulator is the pipe server; the test consumer is the client, matching the
planned plugin/service direction. ET-006a's actual desktop ingestion is pending.

From the repository root, using the [pinned toolchain](setup.md):

```powershell
npm run build --workspace @ets2telemetry/telemetry-simulator
node tools/telemetry-simulator/dist/cli.cjs replay tests/fixtures/simulator-v0/reconnect.json
npm run smoke --workspace @ets2telemetry/telemetry-simulator
npm test -- tests/unit/simulator-v0.test.ts
```

`replay` writes deterministic JSON lines to stdout; it does not open a pipe.
`smoke` creates an actual Windows Named Pipe, performs the v0 hello exchange,
consumes two fixture connections, validates every received message, and closes
its handles. Real-time writes are scheduled from each connection's start, so
timer and write latency do not accumulate across steps. The smoke checks the
first scheduled gap of at least 20 ms, measured from that connection's first
message, against half to one second more than its fixture time; shorter gaps are
below timer resolution and are reported as `cadence: null`. It also reports
freshness at each connection's last receive instant (fresh, stale after the
probe deadline, stale after disconnect). `serve <fixture.json>` prints its
private endpoint and waits for an explicit test client; each client connection
receives the next scripted connection segment. Ctrl+C cancels owned handles.
Both modes have a five-second total deadline and one-second handshake/write
deadlines. A source fixture with gaps longer than this smoke budget should use
deterministic `replay`; this CLI does not support long-running live simulation.

`src/scenario.ts` exports `validateScenario`, `replay`, and the typed `Scenario`
interface. `src/pipe.ts` exports `startPipe` and `consumePipe`; `src/cadence.ts`
exports the smoke `checkCadence` rule; `SnapshotProbe`
is a narrow bounded test observer. These are source interfaces for ET-006a,
not a production discovery or authentication interface.

## Fixture rules

The [reconnect fixture](../tests/fixtures/simulator-v0/reconnect.json) has an
independently authored [expectation file](../tests/fixtures/simulator-v0/reconnect.expected.json).
Its source, IDs, clocks, state and omission counters are deterministic. Expectations
were specified from sequence/counter rules, not generated by executing replay.
The fixture has an initial absent app, current-state hydration, a road stop with
unchanged values at a new capture boundary, pause, disconnect, missing readings,
truck/configuration change, refueling, game-time reset, and reconnect. These are
current observations, not trip/accounting outcomes. A separate unit scenario
hydrates a copied job with unknown currency and an exact large expected-income
value; disappearance of that job produces no delivery/cancellation claim.

Every fixture declares `origin: "synthetic"`, game (`ets2` or `ats`), scenario ID,
seed, and ordered steps. Fixture files are parsed with the protocol's strict
JSON parser, so duplicate keys are rejected instead of silently keeping the last
value. `reading.atMs` and other step `atMs` values are controlled
elapsed milliseconds (0 through one day). A reading supplies speed in m/s, fuel
in liters, simulation status, configuration revision, nullable truck ID, exact
decimal game minutes and optionally a complete wire job availability object.
Unknown scenario, step and reading object fields are rejected; nested job and
diagnostic objects use the unchanged strict v0 validator. Retained input is
rebuilt from declared bounded values only, including fresh arrays without
caller metadata. Configuration equality is semantic: reordering JSON keys
does not count as an offline transition.
`null` speed/fuel become unavailable; numeric zero remains available. Other
unmodeled channels explicitly report unavailable. The illustrative SDK mean
0.3 L/km maps through the accepted helper to 30 L/100km; it is not a trip mean.

Seeded SHA-256 labels produce stable project-owned UUID syntax for plugin,
process, source capture, and game clocks. A decreasing game-minute observation
rotates the seeded game clock ID. These identifiers and placeholder PID/session
metadata are synthetic, not authenticated Windows process identities. Source
capture nanoseconds, source UTC labels, game minutes, and local receive times
are separate domains. A checkpoint copies current state at its own boundary and
labels that capture UTC; it does not replay offline readings as historical data.

Each source reading consumes a session sequence even offline; welcome and
checkpoint consume their own sequences. Offline state retains one current
value. Replacing an earlier offline reading increments `coalescedSnapshots`;
simulation/configuration changes observed offline increment `offlineTransitions`.
The first reading has no prior observation; comparing it with the placeholder
initial state is not a transition. These fixture counting boundaries do not finalize ET-003/ET-004a producer policy.
The `diagnostic` step uses copied v0 observations. It emits only when the fixture
explicitly enables `diagnostics` and a client opts in; disabled/offline
observations increment `lostObservations` without payload retention. Copied
diagnostics are labeled synthetic and never imply durable recording.

The test probe uses local receive time to mark values stale after 500 ms or
immediately on disconnect/error. Identical values in a newly received valid
snapshot remain fresh. Reconnect clears the old state/freshness; welcome alone
remains unhydrated and stale until a new checkpoint. The local receive clock
must remain monotonic across reconnects. This is a test observer policy, not a completed ET-006a
freshness or ET-015 sampling policy.

## Isolation and bounds

Endpoints are generated per run as
`\\.\pipe\ETS2Telemetry-SYNTHETIC-TEST-v0-<pid>-<random-uuid>`.
The test client rejects other prefixes and never searches production discovery.
Every emitted source must be synthetic; valid frames are checked with the
accepted encoder before serving. No database is opened or written, no game
directory is accessed, and no SDK function is called. Stdout is the only replay
output; callers own any explicitly redirected files. There is no configurable
history path, endpoint override, production identity, or disk spool.

Input files are at most 2 MiB; scenarios at most 1,000 steps; wire runs and test
observers at most 2,000 messages; a pipe run's input frames at most 16 MiB.
The CLI opens a fixture once and reads at most 2 MiB plus one overflow-probe
byte from that handle. It decodes UTF-8 and parses JSON only after enforcing
the byte cap; path replacement or growth after opening cannot waive this cap.
Writes are serial with a per-write deadline; there is no pending event queue.
Before serving, the accepted consumer guard also checks every scripted connection's
identity, ordering, capture time, continuity and diagnostic opt-in. The test
client requires checkpoint hydration and waits for clean EOF and socket close.
Cancellation, absent clients, malformed hello, and a paused reader retire the
owned pipe. All test sockets have explicit cleanup. This finite replay tool
retains its bounded script in memory; it is not the native callback queue.

Node test pipes do not establish the production protected DACL, remote rejection,
peer/token verification, discovery collision controls or executable provenance.
Those remain ET-004a. The real-pipe smoke validates encoding and transport only.

## Pending acceptance

REG-003/009/010/011 have partial synthetic coverage in
[simulator-v0.test.ts](../tests/unit/simulator-v0.test.ts). REG-001/002/004/008
recording/accounting outcomes remain pending even though this tool can represent
some corresponding current observations. ET-006a must demonstrate the actual

transactional deduplication, production history, sanitized CAP-01 replay,

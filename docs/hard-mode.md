# Hard Mode persisted-settings verification (ET-026)

Owner decision, October 21, 2026: Hard Mode verifies **observed persisted settings**. Settings not yet written by the game, and transient changes between observations, are not claimed as detected. This is not anti-cheat evidence. Current settings status is separate from a delivered trip's qualification. The observed ETS2 1.61.1.9s mapping supersedes the earlier cvar aliases in the mockup.

## Rules

All twelve configured rules must pass. Boolean comparisons are exact; numeric minimum/maximum comparisons allow an absolute tolerance of `1e-6` in the raw cvar unit. Unknown, malformed and conflicting values never pass. Identical numeric duplicates are harmless. Parsing accepts bounded `uset key "value"` directives, surrounding whitespace, `#`/`//` trailing comments and finite decimal/exponent numbers; partial/non-finite numbers are rejected. Unknown cvars are not retained.

The doubles flag describes simplified double-trailer placements; either valid flag passes with Normal difficulty. Parking uses configuration only: actual parking at delivery, including `autoParkUsed`, does not affect qualification.

## Read-only evidence

Electron main resolves Documents privately. The shared service observer inspects only the active authenticated game target through the verified native client's fixed `--inspect-profile-process` mode. A retained process handle verifies user, Windows session, creation FILETIME, liveness and game image before and after one fixed COM `Win32_Process.CommandLine` query. Native parsing returns only the verified executable and absolute `-homedir` override, or null for a successfully inspected command line without an override; raw command lines never leave the child. The log creation header must match that process within five seconds.

Profile identity is the UTF-8 hex of the latest ordered `New profile selected` marker, matched against a later loaded-save path in the same selection generation. A new selection or unfinished transition invalidates preceding save evidence. `/home/profiles/<id>/save/` selects local storage; `/steam/profiles/<id>/save/` selects Cloud. A stale `Profile type: PC_steam_cloud` marker cannot override a newer local save path, as the owner's Cloud-to-local conversion demonstrated. No latest-mtime, process-name-only or single-folder heuristic is used. Missing or conflicting evidence fails closed.

Local profile files live at `<Documents>/<Game>/profiles/<id>/config.cfg` and `config_local.cfg`. Cloud uses `<Documents>/<Game>/steam_profiles/<id>/config_local.cfg` and exactly one `<Steam>/userdata/<account>/<appid>/remote/profiles/<id>/config.cfg`. Steam's root comes from the existing bounded registry discovery; appids are ETS2 `227300` and ATS `270880`. Explicit game `-homedir` overrides are read from the verified process command line. Encrypted saves are never opened. Cloud-off is not required.

A five-second guard reads canonical file/directory identities, size and high-resolution modification/change metadata, plus bounded newly appended log bytes. Ordinary log appends do not reread settings or retire proof. Full settings-byte and local/Cloud candidate verification is attempted initially, 60 monotonic seconds after the preceding full attempt, and after relevant changes; an unchanged optional read failure does not trigger five-second byte retries. Config verification retains two equal bounded reads; log reads use explicit positions, streaming ordered markers and incomplete UTF-8/line buffers. Replacement, truncation, conflicting transitions or unproven identity retires old evidence before replacement verification. Missing settings alone does not destroy independently verified profile identity.

An admitted observation remains valid while its authenticated source and observed generation are unchanged. A failed or slow periodic byte verification retains prior proof only when independent process, log and metadata guards establish that generation. Both evidence providers share a required-guard deadline of the successful guard operation's start plus five seconds of cadence and two seconds for completion. An independent timer and synchronous evidence/retention checks revoke both proofs if blocked work prevents the next guard; heartbeats, probes and optional settings work never renew that deadline. A failed required guard supplies unknown immediately; later recovery never restores a lost trip qualification. Source/process/clock changes retire work synchronously. Profile/save checks also run after pre-FIFO checkpoint, timer/game-clock, simulation and relevant job/config boundaries: they suspend profile eligibility, coalesce a cheap tail check and require a later causal probe without invalidating otherwise unchanged Hard Mode settings. Explicit same-source supersession preserves admitted settings while cancelled work drains; independent errors and the original bounded verification deadline still fail closed. Triggering and queued older events cannot borrow later profile proof.

Successful process inspection is cached by authenticated OS lifetime (game, PID, Windows session, creation FILETIME and user tag), including reconnects and stale/null oscillation. The first inspection attempt is immediate; unsuccessful attempts retry after 5/15/30/60 seconds, then every 60 seconds. Cancellation and retirement preserve that backoff, and every actual start counts toward the limit of eight starts per rolling five minutes across the observer. One child/physical operation remains owned until actual close/drain, under a two-second deadline; retired results cannot publish. The bounded lifetime cache fails closed on saturation and never evicts a success to permit another query. Restarting the utility begins a new observation lifetime. There are no steady-state native queries after success and no PowerShell process inspection.

Bounds remain 256 profile entries, 32 account entries, 256 Cloud profiles total, 256 KiB per config and 8 KiB per log line. Initial reconstruction and each catch-up are bounded to 4 MiB; an incrementally observed log may grow beyond that total without rereading its prefix. Polling can notice a file change up to five seconds later. Metadata-preserving edits between full byte verifications and transient unwritten settings are outside the detection guarantee. Canonical redirections and Cloud ambiguity still fail closed; isolated shared-open tests do not establish all real OneDrive behavior. Fixed privacy-safe diagnostics contain no paths, identities, hashes, job data or file text.

## Recording and durability

A passing read is not published as proof until a validated same-source/clock `clock.reply` answers a probe sent after file-read completion. The ingestion retains the existing validated probe's client send time and source receipt time privately. Comparing the client send time with file completion uses only client `hrtime`; the event occurrence is required to be strictly after the source receipt watermark. No client/source clock-origin or rate equivalence is assumed. An old, unsolicited, mismatched, missing or late reply supplies no proof. Read plus causal boundary share the unchanged two-second deadline; failure/unknown is published immediately. The monitor never infers a causal boundary from the latest received snapshot.

The delivery FIFO synchronously captures evidence when a coverage item is admitted, before queued/session/storage awaits, and releases it when the item commits or is dropped/stopped. Its existing 512-item bound is unchanged. Each capture retains the first later unsafe observation while pending/in flight; one failed attempt's frozen capture remains for retry. The recorder freezes a private boolean freshness verdict at synchronous intake from the monitor's generation-eligible evidence, and freezes the equivalent verdict when a monitor observation is offered. Storage strictly validates these internal command fields; missing proof cannot establish a passing observation. It preserves the verdict across queue/write delay and retry, without comparing commit UTC with observation UTC or comparing clocks across processes. Session/source occurrence/redelivery/binding checks still apply, and false freshness never discards failing/unknown evidence or its original values. The recorder reads that retained loss immediately before posting the event transaction, with no intervening await, so an observation applied before an opening row exists cannot disappear. Typed commit metadata carries the frozen opening observation and the first pending loss separately; opening evidence stays intact while loss/latest are initialized in the same transaction before ACK. Ordered observer publications replace the latest audit in actual publication order, even if UTC moves backwards. Frozen intake/pending-loss reapplications, closing audits and queued gaps preserve the already-published latest assessment while independently latching first loss. A new opening initializes its audit from the opening capture and retained pending loss; later observer publications replace latest. No UTC comparison, persisted ordering field or cross-process clock mapping selects latest. Failure evidence retains the original numeric values even without positive source proof. The observation carries the current source capture watermark. An event older than that watermark, a redelivered opening, missing occurrence time, missing/mismatched session, retired observation or unproven binding cannot gain present-day file evidence. Historical and checkpoint-opened trips remain unqualified. Cold recorder/session opening first persists an interruption for existing open trips, even when the process/profile/plugin session and binding digest are unchanged; an initial unknown before storage opened cannot be forgotten.

Observation writes use the existing bounded serialized storage client and carry no telemetry ACK. At most one observation write and one pending loss are retained by the recorder; later passing settings cannot overwrite a pending failure. Trip opening/closing audit changes run in the same transaction as ordinary trip effects, without adding effects or enlarging the sixteen-effect bound. Failed transactions change neither event coverage nor trip audit. Duplicates return before audit effects. New gaps record interruption in their transaction. First loss is irreversible, independently of outcome or recording completeness.

Schema `0003-hard-mode` adds `is_hard_mode INTEGER NOT NULL DEFAULT 0 CHECK (is_hard_mode IN (0,1))` and nullable valid JSON `hard_mode_details`, capped at 16,384 characters. INTEGER preserves SQLite STRICT semantics. Versions 1/2 and their frozen fixture bytes are unchanged; old rows become false/null. Typed version-1 audit data contains opening/latest assessments, a SHA-256 binding digest, source categories, observation times, the nullable `manualDelivery` compatibility field and first loss with the **original detected value**, reason, rule and time. New audits leave `manualDelivery` null; saved audits and qualification are never recalculated. Names, account IDs, absolute paths and raw configs are excluded. Only an explicitly delivered trip with all observed settings evidence intact gets true; open/cancelled/unresolved trips stay false.

## UI and IPC

`getHardModeStatus()` and `refreshHardMode()` use fixed `hard-mode:status` and `hard-mode:refresh` channels, accept no arguments and are limited to the trusted dashboard main frame. Replies are strictly validated in main and preload. Check again requests full verification immediately, bypassing the automatic minute schedule, coalesces concurrent work and permits at most one manual start per second; it returns current status while work completes. The dashboard's one outstanding poll reads the result. Assessment publications and trip-detail updates use separate strictly validated private service/main envelopes. The monitor sends only the canonical bounded remaining lifetime (0–3,000,000,000ns) as a service publication lease. A one-second memory-only heartbeat renews that lease while the authenticated source and admitted evidence remain eligible, preserving the original observation timestamp and causal watermark. It performs no file/native queries and cannot resurrect invalidated evidence. Main consumes that relative duration on its own monotonic clock, gates it on readiness/stopping and retires proof/trip state on service failure, exit or restart. Trip-only posts update trip details without renewing assessment expiry; malformed/missing positive lifetime metadata fails closed, and trip details remain available after assessment expiry. It never derives cache eligibility from an assessment UTC label. The overlay bridge has no Hard Mode method; since ET-070 the existing main→overlay projection carries only a display enum and a pass count derived from this same gated status (active only on a pass, lost on the trip's first loss, otherwise not active), revalidated in the overlay preload ([minimal overlay](minimal-overlay.md#hard-mode-indicator)). Invalid or expired replies become unknown; no configuration path/name reaches the renderer.

ET-047 (owner decision, October 23, 2026) moves Hard Mode to a dedicated Drive page between Live and Journal. Live's instrument card spans the available content width. The page shows the status/count/progress, source/observation age, all twelve detected/required/state/reason/cvar entries, retained first loss, Check again and persisted/read-only caveats inline. Ordinary page scrolling keeps all information reachable. There is no checklist drawer or View checklist trigger; this supersedes the October 21 presentation requirement. Optional noninteractive parameter hints still work on hover/focus with Escape dismissal and normal Tab order. One dashboard-lifetime controller serves the page and global status, so navigation grants no new qualification or proof. Lost status retains the first violating value and time even after all current rules pass.

All Hard Mode app text uses the accepted ET-029 typed EN/RU dictionaries with explicit selected-language view/component inputs, including hot changes on the Hard Mode page. Only UI labels/status/explanations are translated: SDK cargo/city/company/truck names, raw numeric/cvar evidence and stored audit/protocol enums remain unchanged. Qualifying journal rows show `HM`; localized trip details show opening/latest audit and first loss, including legacy parking-loss reasons. The JSON export is [format 2](journal-export.md#hard-mode-format-2-et-026). A future server dispatch maps `is_hard_mode` to the same boolean; no server exists or is implemented here.

`GAME_HISTORY_RECORDING` remains true. Real history enablement and all other cards' game/performance gates are unchanged. See [validation](validation/et-026.md) and [regression registry](regression-registry-history.md#et-026-hard-mode).

## Conservative loss and measurement limits

The accepted policy has no grace period after an actual failure or required unknown. Failed initial process inspection supplies no proof; bounded retries can recover the current display but never an already lost trip qualification. Failed periodic work alone does not invalidate independently unchanged evidence. Hard Mode observes persisted settings and is not continuous runtime detection or anti-cheat protection. Real ETS2/ATS, TruckersMP, Cloud/OneDrive behavior, startup-query reliability and CPU/frame-time comparisons remain unverified; synthetic checks cannot establish those results.

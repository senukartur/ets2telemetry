# Hard Mode persisted-settings verification (ET-026)

Owner decision, October 21, 2026: Hard Mode verifies **observed persisted settings**. Settings not yet written by the game, and transient changes between observations, are not claimed as detected. This is not anti-cheat evidence. Current settings status is separate from a delivered trip's qualification. The observed ETS2 1.61.1.9s mapping supersedes the earlier cvar aliases in the mockup.

## Rules

All twelve configured rules must pass. Boolean comparisons are exact; numeric minimum/maximum comparisons allow an absolute tolerance of `1e-6` in the raw cvar unit. Unknown, malformed and conflicting values never pass. Identical numeric duplicates are harmless. Parsing accepts bounded `uset key "value"` directives, surrounding whitespace, `#`/`//` trailing comments and finite decimal/exponent numbers; partial/non-finite numbers are rejected. Unknown cvars are not retained.

## Read-only evidence

Electron main resolves the real Documents directory, including redirection, and passes it privately to the telemetry utility process. The service accepts no renderer-supplied path or assessment. The reader queries the authenticated pipe peer's PID through a fixed read-only Windows process query, checks executable/game and creation time, and matches the current log's creation header to that process (five-second timestamp allowance). The process facts are checked again after reading. The telemetry source's session/process identity remains part of the binding.

Profile identity is the UTF-8 hex of the latest ordered `New profile selected` marker, matched against a later loaded-save path in the same selection generation. A new selection or unfinished transition invalidates preceding save evidence. `/home/profiles/<id>/save/` selects local storage; `/steam/profiles/<id>/save/` selects Cloud. A stale `Profile type: PC_steam_cloud` marker cannot override a newer local save path, as the owner's Cloud-to-local conversion demonstrated. No latest-mtime, process-name-only or single-folder heuristic is used. Missing or conflicting evidence fails closed.

Local profile files live at `<Documents>/<Game>/profiles/<id>/config.cfg` and `config_local.cfg`. Cloud uses `<Documents>/<Game>/steam_profiles/<id>/config_local.cfg` and exactly one `<Steam>/userdata/<account>/<appid>/remote/profiles/<id>/config.cfg`. Steam's root comes from the existing bounded registry discovery; appids are ETS2 `227300` and ATS `270880`. Explicit game `-homedir` overrides are read from the verified process command line. Encrypted saves are never opened. Cloud-off is not required.

The service polls **bytes**, including when an mtime changed without different content. Initial log `uset` values are never substituted for later file contents. Node/libuv shared-open reads are tested against an isolated log held by another Node writer. The reader checks file identity, two equal bounded byte reads and metadata stability. It canonicalizes Documents/game roots, accepts placeholders retaining their canonical path, and honestly refuses unsupported file redirections rather than treating every Windows ReparsePoint as a symlink. This does not establish every real OneDrive placeholder behavior.

Bounds: at most 256 profile entries per discovery, 32 account entries and 256 Cloud profile entries total, 256 KiB per config, 8 KiB per line, 4 MiB per log, one observation in flight, two-second observation deadline and no scan more frequently than once per second. Refresh coalesces with an observation already in flight and obeys the same minimum interval. A timed-out underlying read cannot start a second concurrent scan; its result is retired. Log replacement/truncation, source transitions and expired observation coverage produce unknown evidence. Filesystem work is asynchronous and never runs inside ingestion callbacks. Poll throttling and coverage expiry use client monotonic time, never UTC. Expired coverage publishes an interruption even without a new gameplay coverage event. Passing proof retains the file-read completion age when a later causal reply arrives; UTC rollback cannot renew coverage or suppress scanning. UTC remains an audit label only.

## Recording and durability

A passing read is not published as proof until a validated same-source/clock `clock.reply` answers a probe sent after file-read completion. The ingestion retains the existing validated probe's client send time and source receipt time privately. Comparing the client send time with file completion uses only client `hrtime`; the event occurrence is required to be strictly after the source receipt watermark. No client/source clock-origin or rate equivalence is assumed. An old, unsolicited, mismatched, missing or late reply supplies no proof. Read plus causal boundary share the unchanged two-second deadline; failure/unknown is published immediately. The monitor never infers a causal boundary from the latest received snapshot.

The delivery FIFO synchronously captures evidence when a coverage item is admitted, before queued/session/storage awaits, and releases it when the item commits or is dropped/stopped. Its existing 512-item bound is unchanged. Each capture retains the first later unsafe observation while pending/in flight; one failed attempt's frozen capture remains for retry. The recorder freezes a private boolean freshness verdict at synchronous intake from the monitor's monotonic-aged evidence, and freezes the equivalent verdict when a monitor observation is offered. Storage strictly validates these internal command fields; missing proof cannot establish a passing observation. It preserves the verdict across queue/write delay and retry, without comparing commit UTC with observation UTC or comparing clocks across processes. Session/source occurrence/redelivery/binding checks still apply, and false freshness never discards failing/unknown evidence or its original values. The recorder reads that retained loss immediately before posting the event transaction, with no intervening await, so an observation applied before an opening row exists cannot disappear. Typed commit metadata carries the frozen opening observation and the first pending loss separately; opening evidence stays intact while loss/latest are initialized in the same transaction before ACK. Ordered observer publications replace the latest audit in actual publication order, even if UTC moves backwards. Frozen intake/pending-loss reapplications, closing audits and queued gaps preserve the already-published latest assessment while independently latching first loss. A new opening initializes its audit from the opening capture and retained pending loss; later observer publications replace latest. No UTC comparison, persisted ordering field or cross-process clock mapping selects latest. Failure evidence retains the original numeric values even without positive source proof. The observation carries the current source capture watermark. An event older than that watermark, a redelivered opening, missing occurrence time, missing/mismatched session, expired observation or unproven binding cannot gain present-day file evidence. Historical and checkpoint-opened trips remain unqualified. Cold recorder/session opening first persists an interruption for existing open trips, even when the process/profile/plugin session and binding digest are unchanged; an initial unknown before storage opened cannot be forgotten.

Observation writes use the existing bounded serialized storage client and carry no telemetry ACK. At most one observation write and one pending loss are retained by the recorder; later passing settings cannot overwrite a pending failure. Trip opening/closing audit changes run in the same transaction as ordinary trip effects, without adding effects or enlarging the sixteen-effect bound. Failed transactions change neither event coverage nor trip audit. Duplicates return before audit effects. New gaps record interruption in their transaction. First loss is irreversible, independently of outcome or recording completeness.

Schema `0003-hard-mode` adds `is_hard_mode INTEGER NOT NULL DEFAULT 0 CHECK (is_hard_mode IN (0,1))` and nullable valid JSON `hard_mode_details`, capped at 16,384 characters. INTEGER preserves SQLite STRICT semantics. Versions 1/2 and their frozen fixture bytes are unchanged; old rows become false/null. Typed version-1 audit data contains opening/latest assessments, a SHA-256 binding digest, source categories, observation times, explicit manual-delivery availability and first loss with the **original detected value**, reason, rule and time. Names, account IDs, absolute paths and raw configs are excluded. Only an explicitly delivered trip with all observed evidence intact and manual completion gets true; open/cancelled/unresolved trips stay false.

## UI and IPC

`getHardModeStatus()` and `refreshHardMode()` use fixed `hard-mode:status` and `hard-mode:refresh` channels, accept no arguments and are limited to the trusted dashboard main frame. Replies are strictly validated in main and preload. Refresh schedules the bounded read and returns the current status; the dashboard's one outstanding poll reads the result. Assessment publications and trip-detail updates use separate strictly validated private service/main envelopes. The monitor sends only the canonical bounded remaining lifetime (0–3,000,000,000ns) from its own monotonic observation/read-completion anchor, retaining causal-bind age. Main consumes that relative duration on its own monotonic clock, gates it on readiness/stopping and retires proof/trip state on service failure, exit or restart. Trip-only posts update trip details without renewing assessment expiry; malformed/missing positive lifetime metadata fails closed, and trip details remain available after assessment expiry. It never derives cache eligibility from an assessment UTC label. The overlay bridge is unchanged. Invalid or expired replies become unknown; no configuration path/name reaches the renderer.

ET-047 (owner decision, October 23, 2026) moves Hard Mode to a dedicated Drive page between Live and Journal. Live's instrument card spans the available content width. The page shows the status/count/progress, source/observation age, all twelve detected/required/state/reason/cvar entries, retained first loss, Check again and persisted/read-only/manual-delivery caveats inline. Ordinary page scrolling keeps all information reachable. There is no checklist drawer or View checklist trigger; this supersedes the October 21 presentation requirement. Optional noninteractive parameter hints still work on hover/focus with Escape dismissal and normal Tab order. One dashboard-lifetime controller serves the page and global status, so navigation grants no new qualification or proof. Lost status retains the first violating value and time even after all current rules pass.

All Hard Mode app text uses the accepted ET-029 typed EN/RU dictionaries with explicit selected-language view/component inputs, including hot changes on the Hard Mode page. Only UI labels/status/explanations are translated: SDK cargo/city/company/truck names, raw numeric/cvar evidence and stored audit/protocol enums remain unchanged. Qualifying journal rows show `HM`; localized trip details show opening/latest audit, manual-delivery proof and first loss. The JSON export is [format 2](journal-export.md#hard-mode-format-2-et-026). A future server dispatch maps `is_hard_mode` to the same boolean; no server exists or is implemented here.

`GAME_HISTORY_RECORDING` remains false. Real history enablement and all other cards' game/performance gates are unchanged. See [validation](validation/et-026.md) and [regression registry](regression-registry.md#et-026-hard-mode).

## Conservative loss and measurement limits

The accepted policy has no grace period: one required unknown observation irreversibly disqualifies the open trip, including a transient process-query timeout, a changing-file read race or an over-limit log. Restoration cannot recover that trip. This deliberately accepts false disqualification under the observed persisted-setting model; it does not claim continuous runtime detection or anti-cheat protection. The real-reader/monitor/recorder regression includes one failed process probe followed by restored passing observations and manual delivery.

A successful production scan queries the verified process twice, so the one-second minimum cadence can spawn up to two PowerShell/Get-CimInstance processes per second. The two sequential process queries each have a 1500ms bound, but share the unchanged 2000ms overall read-plus-causal-bind deadline; their worst-case sum alone exceeds that deadline. The three-second coverage lifetime can also expire while a read and post-read probe binding are still pending, before replacement proof is available. These are deliberate fail-closed limits, not guarantees that every compliant scan completes. CPU/frame-time impact has not been measured in real gameplay. The log remains capped at 4MiB; larger files fail closed as unknown and lose qualification. Each scan calls readStableFile on the log twice, and each call performs two full reads of up to 4MiB: four bounded full-log reads. A concurrent append during a stable read can fail closed as Changing file. Actual log growth, I/O/CPU cost and the rate of these races or timeout losses remain unmeasured; optimizing them is deferred until measured without weakening final process identity verification. These limits are not resolved by a grace period, larger deadlines or a new native API in this task.

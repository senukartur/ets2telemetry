# Hard Mode persisted-settings verification (ET-026)

Owner decision, October 21, 2026: Hard Mode verifies **observed persisted settings**. Settings not yet written by the game, and transient changes between observations, are not claimed as detected. This is not anti-cheat evidence. Current settings status is separate from a delivered trip's qualification. The observed ETS2 1.61.1.9s mapping supersedes the earlier cvar aliases in the mockup.

## Rules

All twelve configured rules must pass. Boolean comparisons are exact; numeric minimum/maximum comparisons allow an absolute tolerance of `1e-6` in the raw cvar unit. Unknown, malformed and conflicting values never pass. Identical numeric duplicates are harmless. Parsing accepts bounded `uset key "value"` directives, surrounding whitespace, `#`/`//` trailing comments and finite decimal/exponent numbers; partial/non-finite numbers are rejected. Unknown cvars are not retained.

## Read-only evidence

Electron main resolves Documents privately. The shared service observer inspects only the active authenticated game target through the verified native client's fixed `--inspect-profile-process` mode. A retained process handle verifies user, Windows session, creation FILETIME, liveness and game image before and after one fixed COM `Win32_Process.CommandLine` query. Native parsing returns only the verified executable and absolute `-homedir` override, or null for a successfully inspected command line without an override; raw command lines never leave the child. The log creation header must match that process within five seconds.

Profile identity is the UTF-8 hex of the latest ordered `New profile selected` marker, matched against a later loaded-save path in the same selection generation. A new selection or unfinished transition invalidates preceding save evidence. `/home/profiles/<id>/save/` selects local storage; `/steam/profiles/<id>/save/` selects Cloud. A stale `Profile type: PC_steam_cloud` marker cannot override a newer local save path, as the owner's Cloud-to-local conversion demonstrated. No latest-mtime, process-name-only or single-folder heuristic is used. Missing or conflicting evidence fails closed.

Local profile files live at `<Documents>/<Game>/profiles/<id>/config.cfg` and `config_local.cfg`. Cloud uses `<Documents>/<Game>/steam_profiles/<id>/config_local.cfg` and exactly one `<Steam>/userdata/<account>/<appid>/remote/profiles/<id>/config.cfg`. Steam's root comes from the existing bounded registry discovery; appids are ETS2 `227300` and ATS `270880`. Explicit game `-homedir` overrides are read from the verified process command line. Encrypted saves are never opened. Cloud-off is not required.

A five-second guard reads canonical file/directory identities, size and high-resolution modification/change metadata, plus bounded newly appended log bytes. Ordinary log appends do not reread settings or retire proof. Full settings-byte and local/Cloud candidate verification is attempted initially, 60 monotonic seconds after the preceding full attempt, and after relevant changes; an unchanged optional read failure does not trigger five-second byte retries. Config verification retains two equal bounded reads; log reads use explicit positions, streaming ordered markers and incomplete UTF-8/line buffers. Replacement, truncation, conflicting transitions or unproven identity retires old evidence before replacement verification. Missing settings alone does not destroy independently verified profile identity.

An admitted observation remains valid while its authenticated source and observed generation are unchanged. A failed or slow periodic byte verification retains prior proof only when independent process, log and metadata guards establish that generation. Both evidence providers share a required-guard deadline of the successful guard operation's start plus five seconds of cadence and two seconds for completion. An independent timer and synchronous evidence/retention checks revoke both proofs if blocked work prevents the next guard; heartbeats, probes and optional settings work never renew that deadline. A failed required guard supplies unknown immediately; new trips record its reason separately without treating it as a settings violation. Source/process/clock changes retire work synchronously. Profile/save checks also run after pre-FIFO checkpoint, timer/game-clock, simulation and relevant job/config boundaries: they suspend profile eligibility, coalesce a cheap tail check and require a later causal probe without invalidating otherwise unchanged Hard Mode settings. Explicit same-source supersession preserves admitted settings while cancelled work drains; independent errors and the original bounded verification deadline still fail closed. Triggering and queued older events cannot borrow later profile proof.

Successful process inspection is cached by authenticated OS lifetime (game, PID, Windows session, creation FILETIME and user tag), including reconnects and stale/null oscillation. The first inspection attempt is immediate; unsuccessful attempts retry after 5/15/30/60 seconds, then every 60 seconds. Cancellation and retirement preserve that backoff, and every actual start counts toward the limit of eight starts per rolling five minutes across the observer. One child/physical operation remains owned until actual close/drain, under a two-second deadline; retired results cannot publish. The bounded lifetime cache fails closed on saturation and never evicts a success to permit another query. Restarting the utility begins a new observation lifetime. There are no steady-state native queries after success and no PowerShell process inspection.

Bounds remain 256 profile entries, 32 account entries, 256 Cloud profiles total, 256 KiB per config and 8 KiB per log line. Initial reconstruction and each catch-up are bounded to 4 MiB; an incrementally observed log may grow beyond that total without rereading its prefix. Polling can notice a file change up to five seconds later. Metadata-preserving edits between full byte verifications and transient unwritten settings are outside the detection guarantee. Canonical redirections and Cloud ambiguity still fail closed; isolated shared-open tests do not establish all real OneDrive behavior. Fixed privacy-safe diagnostics contain no paths, identities, hashes, job data or file text.

## Recording and durability

A passing read is not published as proof until a validated same-source/clock `clock.reply` answers a probe sent after file-read completion. The ingestion retains the existing validated probe's client send time and source receipt time privately. Comparing the client send time with file completion uses only client `hrtime`; the event occurrence is required to be strictly after the source receipt watermark. No client/source clock-origin or rate equivalence is assumed. An old, unsolicited, mismatched, missing or late reply supplies no proof. Read plus causal boundary share the unchanged two-second deadline; failure/unknown is published immediately. The monitor never infers a causal boundary from the latest received snapshot.

New trips use audit version 2 in the existing `hard_mode_details` JSON column. A delivered trip qualifies exactly when `known = passingChecks + failingChecks > 0` and `passingChecks * 100 >= known * 95`, using integer arithmetic. Each passing check requires all twelve rules to pass; a verified rule failure is one failing check. Unavailable, changing, malformed or unproven evidence is unknown and excluded from the denominator. Neither opening nor final settings must pass separately. Open, cancelled and unresolved trips remain unqualified; the ratio can recover before delivery. No offline checks are invented.

The existing five-second scheduled verification, including guards that prove cached settings unchanged, supplies at most one completed check. Initial acquisition can supply the first check. Manual refresh, status polling, probes, health heartbeats, coverage reapplication and missed intervals supply no extra checks; manual refresh does not postpone the automatic cadence. File metadata or byte changes trigger re-verification, not a fabricated rule failure. Identical rewrites, unrelated cvars and new save directories can temporarily withdraw current proof, then recover without permanent rejection.

The delivery FIFO freezes current evidence at intake before queued/storage awaits. Publications update latest in actual publication order, independent of UTC corrections; frozen opening/closing/gap reapplication cannot replace a newer published endpoint. A job boundary owns a bounded aggregate from synchronous intake, including time queued behind earlier FIFO work. The reducer hands it to the actual new or existing member; an identical resend or cargo pickup does not discard its checks or count another initial seed. Terminal delivery/cancellation ends that intake interval. A retained capture shares its member checkpoint through same-session retry. A replacement session retires the previous failed owner while preserving an already queued boundary from the new session. The recorder retains one in-flight write and one cumulative pending aggregate, scoped to one raw recording member and source session. A producer-lifetime UUID and cumulative sequence/count checkpoint make retries idempotent, including a committed write whose response was lost. Coalescing retains every designated check and only bounded first/latest diagnostics. Closing flushes its applicable checks before posting the terminal transaction. If an optional observation write fails while ordinary recording remains healthy, its retained checkpoint commits inside the next ordinary event/gap transaction. Observation writes carry no telemetry ACK; opening/closing effects and audit still commit atomically with event coverage before ACK, and duplicates do not reapply them.

A verified logical trip adds the member counters before applying the one global threshold, including checks from progress later abandoned by save restoration. Existing profile/canonical-job association and ambiguity rules are unchanged. Unknown/source/process/session transitions are diagnostics, not permanent v2 losses. The logical trip's original member determines its policy: version-1 continuations retain the old strict interruption policy. Historical v1 audit bytes, qualification and frozen migration fixtures stay unchanged; they are never silently upgraded.

The bounded v2 audit retains opening/latest assessments, binding, `passingChecks`, `failingChecks`, `unknownChecks`, one last checkpoint, and `firstDiagnostic`/`latestDiagnostic` endpoints. Endpoints retain UTC labels, fixed reason codes and original offending rule/values when available: settings changing/unavailable, profile verification, source change, required guard deadline, session transition, storage failure or verified rule failure. These diagnostics survive independently of retained logs. `firstLoss` and `manualDelivery` are null in v2; neither vetoes its ratio. V1 validation and interpretation remain strict. The existing 16,384-character column bound and SQL schema are unchanged. Names, account IDs, paths, command lines and raw configs are excluded.

## UI and IPC

`getHardModeStatus()` and `refreshHardMode()` use fixed `hard-mode:status` and `hard-mode:refresh` channels, accept no arguments and are limited to the trusted dashboard main frame. Replies are strictly validated in main and preload. Check again requests full verification immediately, bypassing the automatic minute schedule, coalesces concurrent work and permits at most one manual start per second; it returns current status while work completes. The dashboard's one outstanding poll reads the result. Assessment publications and trip-detail updates use separate strictly validated private service/main envelopes. The monitor sends only the canonical bounded remaining lifetime (0–3,000,000,000ns) as a service publication lease. A one-second memory-only heartbeat renews that lease while the authenticated source and admitted evidence remain eligible, preserving the original observation timestamp and causal watermark. It performs no file/native queries and cannot resurrect invalidated evidence. Main consumes that relative duration on its own monotonic clock, gates it on readiness/stopping and retires proof/trip state on service failure, exit or restart. Trip-only posts update trip details without renewing assessment expiry; malformed/missing positive lifetime metadata fails closed, and trip details remain available after assessment expiry. It never derives cache eligibility from an assessment UTC label. The overlay bridge is unchanged. Invalid or expired replies become unknown; no configuration path/name reaches the renderer.

ET-047 (owner decision, October 23, 2026) moves Hard Mode to a dedicated Drive page between Live and Journal. Live's instrument card spans the available content width. The page shows the status/count/progress, source/observation age, all twelve detected/required/state/reason/cvar entries, trip pass/known ratio, threshold, unknown count, diagnostics and Check again and persisted/read-only caveats inline. Ordinary page scrolling keeps all information reachable. There is no checklist drawer or View checklist trigger; this supersedes the October 21 presentation requirement. Optional noninteractive parameter hints still work on hover/focus with Escape dismissal and normal Tab order. One dashboard-lifetime controller serves the page and global status, so navigation grants no new qualification or proof. V2 trip statistics remain separate from current rule status and show the exact denominator; below-threshold trips can recover. Historical v1 loss text remains available only for its original audits.

All Hard Mode app text uses the accepted ET-029 typed EN/RU dictionaries with explicit selected-language view/component inputs, including hot changes on the Hard Mode page. Only UI labels/status/explanations are translated: SDK cargo/city/company/truck names, raw numeric/cvar evidence and stored audit/protocol enums remain unchanged. Qualifying journal rows show `HM`; localized trip details show opening/latest audit, v2 counters/diagnostics, and historical v1 loss including legacy parking reasons. The JSON export is [format 5](journal-export.md#hard-mode-statistics-format-5). A future server dispatch maps `is_hard_mode` to the same boolean; no server exists or is implemented here.

`GAME_HISTORY_RECORDING` remains true. Real history enablement and all other cards' game/performance gates are unchanged. See [validation](validation/et-026.md) and [regression registry](regression-registry-history.md#et-026-hard-mode).

## Conservative loss and measurement limits

New audits use the inclusive 95% known-check threshold; unknown evidence is explicitly excluded and shown separately. A small known denominator can therefore qualify. Version-1 audits retain their original irreversible-loss policy. Failed initial process inspection supplies no proof; bounded retries can recover current verification. Failed periodic work alone does not invalidate independently unchanged evidence. Hard Mode observes persisted settings and is not continuous runtime detection or anti-cheat protection. Real ETS2/ATS, TruckersMP, Cloud/OneDrive behavior, startup-query reliability and CPU/frame-time comparisons remain unverified; synthetic checks cannot establish those results.

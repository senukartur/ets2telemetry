# Minimal overlay (ET-008, layouts ET-012a)

The prototype adds a separate transparent telemetry window anchored inside the selected game's client rectangle. ET-008 drew a fixed 300 × 132 DIP speed/fuel widget at the top left; since ET-012a the window has one of four layouts with its own size and anchor and shows the sections chosen in the settings ([below](#layouts-and-sections-et-012a)). ETS2 defaults to km/h and liters; ATS defaults to mph and US gallons (3.785411784 L). Canonical v0 values remain m/s and L. Missing readings are `—`; stale captures show dimmed dashes and never last-known values (see [section states](#section-states)). These conversions follow the contract and ET-000 defaults; real SDK units still require CAP-01 evidence. Since ET-011b the units come from the persisted per-game profile (`metric` or `us-customary`, with the same defaults) and the conversions from `packages/telemetry-core`. A saved profile change republishes the overlay from main's stored freshness output without renewing SDK or window freshness; see [settings](settings.md#dashboard-and-overlay).

## Layouts and sections (ET-012a)

The layout and the enabled sections are saved settings ([settings](settings.md#overlay-settings-et-012a)); coordinator decisions L1–L15 are in [concept.md](../concept.md#et-012a-authorization--october-15-2026). Main builds the whole display projection (`overlayPresentation` in `apps/desktop/src/overlay-presentation.ts`); the overlay renderer only arranges the formatted strings and receives no telemetry, geometry or settings authority. Its bridge is still only `subscribeOverlay`.

### Geometry

Main converts the game's physical client rectangle to DIP with `screen.screenToDipRect` as before, then `overlayBounds(layout, client)` (`apps/desktop/src/overlay-geometry.ts`) places the window. Margins are 16 DIP; the strip sits 8 DIP below the top edge. With client area `(cx, cy, cw, ch)`:

| Layout | Window | Position | Fits when |
| --- | --- | --- | --- |
| Strip (default) | width `floor(min(1280, cw − 32))`, height 38 | top centre: `x = round(cx + (cw − width) / 2)`, `y = round(cy + 8)` | width ≥ 480 and ch ≥ 54 |
| Card | 300 × 360 | top right: `x = round(cx + cw − 316)`, `y = round(cy + 16)` | cw ≥ 332 and ch ≥ 392 |
| Cluster | 440 × 220 | bottom left: `x = round(cx + 16)`, `y = round(cy + ch − 236)` | cw ≥ 472 and ch ≥ 252 |
| Minimal HUD | 320 × 320 | top left: `x = round(cx + 16)`, `y = round(cy + 16)` | cw ≥ 352 and ch ≥ 352 |

For example, a 1920 × 1080 client area at (0, 0) gives the strip {320, 8, 1280, 38}, the card {1604, 16, 300, 360}, the cluster {16, 844, 440, 220} and the HUD {16, 16, 320, 320}. A layout that does not fit, or whose box is not fully inside one display, hides the overlay; a fixed layout is never shrunk. Main creates the overlay window at the saved layout's nominal size (strip 1280 × 38). A saved layout change, or a late settings read that brings another layout, republishes the projection and re-places the window from the last observation the controller holds. It renews no SDK or window freshness. A visible overlay that moves re-asserts the topmost level without activation, as every placement change does, and a hidden overlay is never shown or raised by it.

### Layouts

Each layout has its own minimal CSS in `apps/desktop/src/renderer.css` (no Tailwind, no shadcn base layer, no web fonts, no `backdrop-filter`) and inline SVG icons from the pinned `lucide-react`. The root is transparent; only each layout's surface paints `rgba(10, 17, 24, .88)`.

- **Strip**: one 38 px row at the top centre with an icon per section, the groups Driving, Fuel, Job and Time separated by thin dividers, and a small "SDK mean" caption beside the SDK consumption. Items wrap whole onto a clipped second line when the row is too narrow, so trailing items drop out rather than overlap.
- **Card**: top right; a header with the game and tags, then one labelled row per section. Long labels shorten before values do.
- **Cluster**: bottom left; a round speed gauge with an engine RPM ring and a gear badge, and a side panel with the other sections. The gauge appears only when speed, gear or RPM is enabled. The ring uses a fixed 0–3000 rpm display scale (decision L12) because neither protocol v0 nor v1 carries the SDK's `rpm.limit`.
- **Minimal HUD**: top left; shadowed text lines without a background.

### Section states

Main formats each enabled section that the protocol in use carries with telemetry-core in the displayed game's unit profile, exactly as the dashboard's Live telemetry card does ([live telemetry fields](live-telemetry-fields.md#overlay)). Decisions L5 and L6:

- A disabled section, or one whose fields the protocol in use does not carry, is left out.
- While the projection is **current**, a section with a value shows it. A section without data is hidden, never shown as zero. Speed and fuel, the ET-008 baseline, keep a visible `—` instead (REG-009: unavailable differs from zero).
- While it is **not current** (stale, no signal, disconnected, or an origin/game mismatch), every carried, enabled section shows a dimmed `—`, so the layout does not jump and no stale value looks current. No last-known value is kept.

The root is dimmed (`is-dim`) whenever freshness is not `current`. Tags: **Paused** while current telemetry reports a paused game, **No signal** while freshness is `unavailable`, and **Synthetic** or **Replay** for fixture origins. The preload's 500 ms quiet-channel fallback turns every shown section into a placeholder and keeps the layout. The legacy `speed`, `fuel`, `speedUnit` and `fuelUnit` fields stay in the projection. The runtime smoke reads the state from the `overlay-root` data attributes and the speed and fuel number and unit from the separate `overlay-speed`, `overlay-speed-unit`, `overlay-fuel` and `overlay-fuel-unit` elements ([CI](ci.md#overlay-smoke-dom-contract-et-012a)).

## Ownership and authorization

The utilityProcess still owns ingestion, source validation and the fixed native broker; its SQLite worker remains the isolated scaffold probe. Main consumes exactly one service port and fans out to independent bounded dashboard and overlay subscriptions. Each has one outstanding delivery, one replaceable latest update and a maximum 20 Hz delivery rate. Credits acknowledge callback consumption only. They are neither v0 wire acknowledgements nor durable storage acknowledgements. Dashboard unsubscribe/reload cannot close the upstream or overlay subscription. History sampling is not implemented.

The dashboard retains its existing bridge and source selection; ET-011a appends the application-state and exit methods described in [the application lifecycle](app-lifecycle.md#health-and-the-dashboard). The overlay has a separate sandboxed, context-isolated preload exposing only frozen `window.overlay.subscribeOverlay`. Its projected payload contains display strings, units, source/origin/status/freshness and, since ET-012a, the saved layout, a paused flag and the formatted sections, without SDK observations, geometry, HWNDs, paths or source-selection commands. Main accepts its subscribe/unsubscribe messages only from the current overlay main frame. Popups and navigation are denied. No renderer receives Node.js or filesystem access.

The overlay uses the fixed Electron session partition `ets2telemetry-overlay`, separate from the dashboard's default session. The partition has no `persist:` prefix, so its session is in memory and has its own browser context. Reload and bounded renderer recovery reuse the existing overlay window and session. This separates the contexts that Chromium can use for renderer reuse; actual process separation and dashboard responsiveness during an overlay stall require runtime checks of distinct positive OS process IDs, distinct session identities and dashboard DOM progress, including after reload under `--renderer-process-limit=1`. Construction-boundary Node tests protect the session configuration and reload behavior without proving process isolation. The telemetry service, SQLite worker and read-only IPC boundary retain their existing ownership.

The overlay is constructed hidden, transparent, nonfocusable and outside the taskbar. Mouse ignoring is enabled before loading/showing; authorized display uses `showInactive()`. There is no editing or always-visible mode. Explicit synthetic/replay selections can populate the hidden renderer and identify their origin; they cannot authorize native window visibility.

## Z-order

Main makes the overlay topmost with `setAlwaysOnTop(true, 'screen-saver')` immediately after construction, not with the constructor's `alwaysOnTop` option. On Windows, every level other than normal becomes plain `WS_EX_TOPMOST`. However, Electron's default `floating` level, which the constructor option uses, and the levels `torn-off-menu`, `modal-panel`, `main-menu` and `status` also stack the window directly behind the taskbar (`Shell_TrayWnd`). While a borderless full-screen window such as the game is foreground, the shell makes the taskbar non-topmost. A topmost window placed after a non-topmost window loses its topmost status ([`SetWindowPos`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos)). The overlay then stays below the game. This was the October 13, 2026 defect; see [ET-008 validation](validation/et-008.md#topmost-loss-behind-a-borderless-game-october-13-2026).

The controller re-asserts the level after every `showInactive()` and every placement change: it calls `setAlwaysOnTop(true, 'screen-saver')`, then `moveTop()`. While the overlay is visible, each update also reads `isAlwaysOnTop()`. On Windows, Chromium derives that value from the HWND's actual `WS_EX_TOPMOST` style, so the controller restores a style that something external cleared. A loss observed at show or while visible records one fact-only `OVERLAY_TOPMOST_RESTORED` diagnostic with `phase` `show` or `visible` per shown period. Both calls use `SWP_NOACTIVATE`. On Windows, Electron 44.7.0's `moveTop()` calls `SetWindowPos(HWND_TOP, …)` with `SWP_NOMOVE | SWP_NOSIZE`, so it changes only the z-order and never the bounds that placement computed ([MoveTop](https://github.com/electron/electron/blob/v44.7.0/shell/browser/native_window_views.cc#L1055-L1069)). The window keeps `WS_EX_NOACTIVATE`, nonfocusability and mouse ignoring. The controller never calls `show()` or `focus()`. A hidden overlay is never raised, because Electron's `moveTop()` also passes `SWP_SHOWWINDOW`. Foreground/minimize/expiry/source gates still hide it first. Returning to the game after focusing the dashboard is therefore a hide-then-show transition that re-asserts topmost. The dashboard is never topmost.

## Placement and freshness

Main reuses `currentGameClientBounds`: explicit ETS2/ATS selection, matching game-origin identity, valid fresh client bounds, foreground and non-minimized state are required. SDK freshness is independent of window freshness. Main applies 500 ms SDK and 250 ms window deadlines measured on its own receipt clock. Capture/session/process/clock identity keys prevent equal SDK captures from renewing metrics; window receipts expire separately. No `performance.now()` values are compared across processes. A fresh window can authorize a visible overlay with explicit stale, blank metrics.

Physical signed client bounds are converted through [Electron `screen.screenToDipRect(null, rect)`](https://www.electronjs.org/docs/latest/api/screen#screenscreentodiprectwindow-rect-windows), which chooses the display nearest the rectangle. Game DPI is not used as a coordinate divisor. Geometry is recomputed when physical bounds change; display addition/removal/metrics changes hide the overlay until a new window receipt and invalidate cached conversion. Small/invalid/offscreen rectangles and conversion failures hide it. The layout's box must fit inside the client area and an available display ([geometry](#geometry)).

Selection requests immediately hide the old placement. Pending requests suppress upstream observations, and sender/frame/document/child/request generations are rechecked after broker verification. Retired ports cannot publish. Service/port failure invalidates current data; upstream recovery has at most two attempts per 60 seconds. Overlay renderer reload/failure hides and retires its channel; renderer recovery is separately bounded. Overlay consumers have a 500 ms credit deadline, and the preload blanks quiet current readings after 500 ms. SDK expiry does not terminate a healthy quiet channel. Since ET-011a, closing the dashboard hides it to the tray: the overlay, its subscription, the upstream channel and the v0 service keep running, and the overlay keeps following the game until an explicit exit. The overlay refuses close requests until then. The ET-008 G02 session observation that the overlay disappeared when the owner closed the main window is historical and predates this change. See [the application lifecycle](app-lifecycle.md#close-to-tray); recording behavior remains ET-015.

While source verification is pending, main publishes a blank initial state for the committed source and hides placement. The requested source label enters both consumer caches only after the ownership checks pass and the source IPC send succeeds. A quiet service therefore hydrates a reloaded dashboard and overlay with the committed source even when verification is retired or dispatch throws. Retired verification does not roll back or republish state, so it cannot overwrite a newer selection, service-failure/replacement publication or application stop. These label changes do not renew SDK or window receipt authority; new observations remain necessary for current metrics and visibility.

When the upstream sliding budget is exhausted, main keeps one cancellable 60-second cooldown before rechecking the unchanged budget and scheduling the existing 250 ms retry. Every acquisition and retry requires the same current ready service child, an application that is not stopping and no active upstream port. Another budget refusal retains one further cooldown. Intentional upstream close, application stop, service-generation replacement or an accepted connection cancels the pending timer. This restores a channel in the existing service without restarting a renderer, native broker or service process. Both dashboard and overlay remain stale until the current upstream publishes new data; equal SDK captures and expired window receipts cannot renew their independent freshness or visibility authority.

Main records `MAIN_CHANNEL_CLOSED` for unexpected loss of the current service live channel and `MAIN_CHANNEL_RECOVERY_COOLDOWN` when the recovery budget refuses an attempt, with the 60,000 ms wait. Neither diagnostic guesses the cause of channel loss. Retired-port notifications and intentional shutdown/service retirement do not produce channel-loss or cooldown diagnostics.

Overlay preload channel recovery has its own sliding budget of two attempts per 60 seconds and a 250 ms retry delay. When that budget is exhausted, the same subscribed document retains one cancellable 60-second cooldown, then rechecks ownership, listener, absent port and the monotonic budget before scheduling a retry. If the budget still refuses the attempt, it waits another cooldown. Unsubscribe or a replacement port cancels the pending wait; retired ports and subscription owners cannot renew timers, consumption credits or readings. Metrics remain stale and blank until a new projected delivery arrives. A recovered channel does not renew SDK capture freshness or native window authority, and it does not restart a renderer, service or native process.

Main records `OVERLAY_CHANNEL_CLOSED` when the active overlay channel closes unexpectedly, and hides the overlay. The diagnostic states the closure without asserting a cause: credit expiry, malformed credit and port loss can all close a channel. Intentional unsubscribe, document reload, renderer retirement and application shutdown retire channel identity before closing it and do not produce this diagnostic.

The preload's quiet-channel deadline measures time since the last projected delivery, independently of main's SDK receipt deadline. If current projections for one capture arrive at 0/200/400 ms and subsequent deliveries are suppressed, main expires the capture at 500 ms while the preload fallback blanks at 900 ms. Healthy delivery sends main's stale projection earlier. This bounded delivery-age fallback does not renew SDK or window authority, and it does not establish measured display latency. A blocked renderer cannot repaint until it resumes; main hides on its channel closure/credit expiry.

## Validation boundary

Node tests cover units/zeros/missing/stale values, independent clocks, equal captures, signed/mixed-scale placement through a mocked Electron API, topology invalidation, foreground/minimize/source gates, trusted frames, async selection, independent credits, port retirement and shutdown. Monotonic fake-clock regressions cover the third consumer and upstream losses, repeated cooldown recovery within each sliding limit, cancellation, retired owners and service generations, budget rechecks and factual closure diagnostics. Recovered upstream data still requires current SDK and window authority. These accelerated checks do not establish 60-second runtime stability. Controller and main-construction tests protect the topmost level, its order after `showInactive()` and placement, restoration after an external loss and the absence of activation. The hidden-overlay smoke requires the actual hidden HWND to be topmost. Neither layer can reproduce a full-screen game making the taskbar non-topmost; only an actual session establishes the overlay above the game. Controlled synthetic renderer fixtures are useful for DOM, isolation and recovery checks while the native overlay stays hidden. They do not establish actual mixed-DPI conversion, input pass-through, focus behavior or game compatibility.

Follow [manual prototype setup](manual-plugin-setup.md) for the maintained SDK DLL, build and launch commands. See [ET-008 validation](validation/et-008.md). Actual ETS2/ATS single-player/TruckersMP windowed and borderless sessions (Convoy is deferred by the October 12, 2026 owner decision), elevation, monitor removal, latency, resource use and frame-time impact remain pending. Since ET-012a, `tests/unit/overlay-geometry.test.ts`, `overlay-presentation.test.ts`, `overlay-view.test.ts` and `overlay-sections.test.ts` cover the per-layout geometry, the section projection and the view model, and the controller tests cover each layout's anchor, re-placement on a layout change and hiding when a layout does not fit. Whether each layout is visible and readable above a real game remains pending in [ET-012a validation](validation/et-012a.md). Exclusive fullscreen, rendering hooks, arbitrary game memory access, overlay editing or dragging, recording and server functionality are outside this package.

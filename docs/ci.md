# Windows CI and regression infrastructure

ET-022 provides [Windows CI](../.github/workflows/windows-ci.yml) for pull requests, pushes to `main`, and manual dispatch. ET-024 limits automatic runs as described in [Triggers and draft checks](#triggers-and-draft-checks). Clean hosted execution and the deliberate failing-assertion/restoration sequence passed as recorded in [ET-022 validation](validation/et-022.md). The final current PR head still needs its own check/review association before owner merge. These runs do not establish branch protection or game compatibility.

The explicitly selected x64 `windows-2022` image uses Visual Studio 2022 with `Visual Studio 17 2022`, not the local Visual Studio 2026 generator. Image updates may change MSVC and SDK patch versions; each run records image identity and vendor versions. Node 24.19.0, npm 11.17.0, Electron 44.7.0 and Playwright 1.64.0 are pinned. CMake 4.3.1 is acquired explicitly before tool verification and configuration; the runner's CMake 3.31.6 does not satisfy the existing native minimum of 4.3. Action revisions are pinned to exact commits (checkout v5, setup-node v5, cache v4, upload-artifact v4). The [runner manifest](https://github.com/actions/runner-images/blob/main/images/windows/Windows2022-Readme.md) documents VS 2022 support.

`scripts/ci/Install-CMake.ps1` is restricted to GitHub Actions. It downloads the official [Kitware CMake 4.3.1 Windows x86_64 ZIP](https://github.com/Kitware/CMake/releases/download/v4.3.1/cmake-4.3.1-windows-x86_64.zip), verifies SHA256 `03a610be931546474e46a442d171ef10532f4fc847de9cf76b7a8065bbef6a23` before expansion, and checks `cmake version 4.3.1`. The [vendor checksum manifest](https://github.com/Kitware/CMake/releases/download/v4.3.1/cmake-4.3.1-SHA-256.txt) and GitHub release asset digest agree with that pin; the independently downloaded manifest SHA256 is `e101d7dacb65463f86fa1c04bf15181368f258f29a3dad4969de8f44ba6dcbd3`. Acquisition uses a fresh runner temporary directory and adds its `bin` to the current process PATH and `GITHUB_PATH`; no MSI/global installation or owner-host PATH change occurs. `.local/ci/cmake-toolchain.json` retains source, archive hash, observed version and executable path. The tool archive is not shared through dependency caches. The second hosted run passed all 122 tests, then exposed the runner's older CMake; that failed run remains part of the acceptance history rather than weakening the native requirement.

Every run installs the lockfile into a clean workspace, installs the separate lint lockfile and runs ESLint with zero allowed errors or warnings, runs PSScriptAnalyzer over tracked PowerShell files with zero allowed findings, runs typecheck and the full Node-safe Vitest corpus, builds desktop and native x64, runs CTest, executes a bounded development Electron smoke, makes the actual Forge/Squirrel artifact, inspects packaged bytes/native paths, and executes the packaged smoke from an unrelated working directory. Vitest never imports Electron or native SQLite. Lint (ET-023a) runs before the build for fast feedback; its toolchain, TypeScript 6 API rationale and rule exceptions are in [setup](setup.md#linting). The lint step measured 17-18 s on hosted runners; [ET-023a validation](validation/et-023a.md) records the controlled failure and restore runs. PowerShell script analysis (ET-023b) follows it; the hash-pinned module, Windows PowerShell 5.1 engine and rule exceptions are in [setup](setup.md#powershell-script-analysis). No test filtering or retries are enabled.

Caching is configured only for downloaded npm archives and Electron distributions. Before ET-024, every hosted run ended with `Path Validation Error: Path(s) specified in the action for caching do(es) not exist` and saved nothing: npm did not use `~\AppData\Local\npm-cache` on the runner, and Electron's installer ignores `ELECTRON_CACHE` (it reads `electron_config_cache`), so `.local/cache/electron` was never created. The job now sets `npm_config_cache` and `electron_config_cache` to `.local/cache/npm` and `.local/cache/electron` inside the workspace and caches exactly those paths. GitHub saves a cache only after a successful job, and a cache saved on `main` is visible to all PR branches, while a PR-branch cache is visible only to that PR. ET-024 measurements on dispatch runs [38167660898](https://github.com/senukartur/ets2telemetry/actions/runs/38167660898) (cold, saved ~212 MB in 4 s) and [38167962488](https://github.com/senukartur/ets2telemetry/actions/runs/38167962488) (cache hit, restored in 4 s) show `npm ci` taking 17 s cold and 14 s warm. The restore costs about what it saves, so the cache gives no measurable speedup; it is kept as protection against registry/CDN download failures, not as a time saving. The largest step is Forge make/inspection (68–108 s across these runs); whole-job time varied from 169 s to 236 s between runners for the same work. Keys include both lockfiles (root and `tools/lint`), Windows/x64, Node 24.19.0 ABI 137 and Electron 44.7.0 ABI 149. No `node_modules`, native build tree, SQLite binding compiled for another runtime, packaged artifact, profile or database is cached. This is deliberately stricter than [setup-node's default download caching](https://github.com/actions/setup-node/blob/main/docs/advanced-usage.md).

## Triggers and draft checks

| Event | Behavior |
| --- | --- |
| PR opened, updated or reopened while **draft** | Workflow run is created but the job is skipped (no runner minutes). A skipped job is not a passed check |
| PR marked **Ready for review**, or updated while ready | Full job on the PR merge result |
| PR or `main` push changing only `**.md` or `docs/**` | No run at all; GitHub reports no check for that commit |
| Push to `main` touching anything else | Full job plus extended regressions |
| Manual dispatch | Full job on the selected branch head; extended regressions unless `extended=false` |

Any change outside `**.md` and `docs/**` (code, tests, fixtures, scripts, workflow, `package*.json`, config) runs the full job. GitHub evaluates path filters against the whole PR diff, so a PR that later gains a code change runs normally. Documentation-only PRs rely on the focused document checks in [TESTING.md](../TESTING.md). If required status checks are ever enabled, a path-filtered workflow reports no check and would leave such PRs waiting.

To check a draft head without marking it ready, dispatch the workflow on the task branch:

```powershell
gh workflow run windows-ci.yml --ref <task-branch> -f extended=false
gh run list --workflow windows-ci.yml --branch <task-branch> --limit 1
```

A dispatch run checks the branch head itself, not the PR merge result with current `main`. GitHub attaches it to the head commit (visible in the commit's checks and the Actions list), but the PR check list keeps showing the skipped pull-request job for that commit, so record the dispatch run link in the PR or ledger. The final-head gate is therefore the pull-request run triggered by **Ready for review** (or a later push while ready). If that run fails, fix the branch or return the PR to draft (`gh pr ready <number> --undo`).

## Bounded runtime checks

Run from the repository root on Windows with pinned Node on PATH, after `npm run build` / `npm run make` respectively:

```powershell
./scripts/ci/Invoke-RuntimeSmoke.ps1 -Mode development
./scripts/ci/Invoke-RuntimeSmoke.ps1 -Mode packaged
```

Each mode launches once under the existing Windows Job Object: 60 seconds maximum, 16 processes, 2 GiB committed memory, 25% system CPU and kill-on-close. The owner retains the Job until all descendants exit; a forced cleanup/timeout fails. Playwright launch keeps its 20-second deadline and normal close has 8 seconds. Release sandbox, context isolation, narrow frozen bridge and Node isolation remain enabled. [Playwright Electron support is experimental](https://playwright.dev/docs/api/class-electron); the prior ET-001 launch timeout remains unexplained and is not erased by later success.

Readiness proves Electron main → utilityProcess → storage worker → actual bundled better-sqlite3 N-API write, close, reopen, read. Successful close must report normal app/service exit, worker stop and removal of the temporary probe. This does not test production history, migrations or game telemetry. Paths for TEMP, profiles, APPDATA and LOCALAPPDATA are unique per mode/run; no real user history or game files are accepted. Development and packaged checks remain sequential inside the job to stay within desktop resource caps.

Evidence remains under `.local/ci/<mode>-<uuid>`: expected/actual assertions, candidate identity, Node/Electron/Playwright versions, bounded app/service/Job logs, screenshot and trace. Trace collection failure also fails the smoke. A launch failure can prevent trace creation; the Job stdout/stderr and failure metadata remain available. Abandoned synthetic files are retained for diagnosis rather than deleting evidence before upload. Hosted workspace disposal removes them; local users can remove their exact owned run directory after reviewing it. Test helper owners clean their own synthetic fixtures; `tests/unit/test-resources.test.ts` exercises parallel uniqueness and preservation of a second owner during cleanup.

The wrapper also writes a distinct `wrapper-result.json`. A missing, malformed, failed or mismatched driver receipt fails even if the Job exits zero; a nonzero Job fails even when the driver reports success. The wrapper never overwrites driver evidence or invents worker/security/runtime observations after an early crash. Its receipt records actual Job exit, owned PID and log paths, observed Node version and pinned Playwright metadata; absent Electron runtime observations remain null. Inert `tests/unit/runtime-receipt.test.ts` protects these failure paths without launching Electron. ET-022's first local packaged launch timed out at the unchanged 20-second deadline with an unhandled Playwright promise rejection and no driver receipt; a separately recorded same-cap DEBUG diagnostic succeeded. That failure remains visible and is not a clean-pass claim or justification for retries.

Hosted smoke failures are compared in [the smoke failure record](validation/ci-smoke-window-stall.md). Dispatch run [38624116941](https://github.com/senukartur/ets2telemetry/actions/runs/38624116941) failed the development scaffold smoke because the Electron main process stopped dispatching for about 17.7 s right after creating its windows; Playwright saw no page within 10 s. Its cause is unknown: the Job records no CPU accounting and main records no event-loop timing, so CPU starvation under the 25% cap cannot be told apart from a native block. That record proposes diagnostics; deadlines, retries and Job limits are unchanged.

Pushes to `main` and manual dispatch with `extended: true` add actual existing watchdog fixtures and uninstall-residue regressions. These do not run an installer. ET-003 adds isolated AddressSanitizer console targets for the accepted v0 parser corpus and the fake-host SDK adapter. CI configures a separate `native/telemetry-plugin/build-asan` tree, builds only those two instrumented test targets and runs their bounded CTest cases; the game DLL remains uninstrumented. CTest diagnostics from both build trees are uploaded. Local and current hosted outcomes belong in [ET-003 validation](validation/et-003.md); adding the workflow step alone is not a passed hosted check. Production crash/ACK recovery, historical migrations, capture replay, fuzzing, sustained recording and full domain/protocol branch coverage remain pending. The [scenario registry](regression-registry.md) distinguishes pending feature requirements from partial protection.

ET-002b PR-2 adds the `protocol-v1-asan-test` console target to that ASan build list, so the existing `-R asan-contract` selection also runs `protocol-v1-asan-contract` on the shared protocol v1 corpus.

Job timeout is 20 minutes. The clean and restored hosted jobs measured 199 and 200 seconds respectively; feedback under 10 minutes remains a target for future runs. `versions.json` records elapsed time from toolchain verification through final collection. GitHub job duration includes earlier checkout/setup overhead and is the end-to-end timing source. Always-uploaded 14-day evidence includes JUnit results, runtime runs, package inspection and CTest diagnostics; workflow command logs contain build/install/vendor output. Current private-repository protection limitations still apply. Superseded runs are cancelled; cancellation is not a passed check.

## ET-006a native client and live smoke (implementation candidate)

The hosted job also builds separate console AddressSanitizer client/fixture targets and runs the `native-pipe-client-asan-*` entries (`-R '^native-pipe-client-asan-'`) with the matching MSVC runtime on PATH. The client fixture is registered as one CTest entry per case: `native-pipe-client-<case>` in the ordinary build and `native-pipe-client-asan-<case>` in the ASan build. Each entry selects its case through `ETS2TELEMETRY_CLIENT_TEST_CASE`, and the entries share a resource lock because the fixture's endpoint names are fixed per user and session. The lock applies only within one `ctest` invocation, so do not run client suites concurrently: Release and ASan in parallel, or two worktrees at once, collide on the same endpoint names. Most cases finish well under a second. `quiet`, `quiet-exit`, `partial-prefix` and `partial-payload` each wait out a fixed 5-5.5 s broker or fixture window. Each entry has its own hang backstop: 20 s, or 30 s for those four cases, doubled under ASan. The `*-case-list` entry fails if the registered names differ from the fixture's case list. Each case prints `case <name> ms=<n>` on stderr. The production broker remains uninstrumented. Local ASan controls failed during the recorded Avast scan interference investigation; a hosted result is a separate environment result and does not erase those failures. No antivirus exclusions are required or configured by this workflow.

The maintained client adds a fixed project-owned native broker for connected-pipe identity checks and bounded raw I/O. Ingestion, validation and subscriptions stay in the utilityProcess. The broker is built as part of npm run build using the documented CMake/MSVC toolchain. Its source-bound build receipt and executable are staged under ignored .local/package-native/telemetry-client and packaged as resources/telemetry-client; static inspection compares native bytes, x64 PE identity and source hashes. No generated binary is committed. See native-transport-boundary-v0.md and the feature validation record for final checks and pending real-game evidence.

Alongside the unchanged bounded scaffold probe, the candidate adds the following commands from the repository root:

```powershell
./scripts/ci/Invoke-RuntimeSmoke.ps1 -Mode development -Scenario telemetry
./scripts/ci/Invoke-RuntimeSmoke.ps1 -Mode packaged -Scenario telemetry
```

These use an explicitly isolated synthetic Windows pipe and the same 60-second/16-process/2-GiB/25%-CPU Windows Job Object limits with zero retries. The intended assertions exercise source-to-renderer speed/fuel, six-second renderer stall with changed values and subscription recovery, invalid source rejection, three renderer reloads, one deliberately terminated owned service followed by supervised reconnect/new ports, and stale readings after disconnect. The diagnostic main event is opt-in under isolated smoke configuration and is not a renderer command. The killed service's exact original temporary SQLite probe may remain as retained crash evidence; the replacement service must remove its normal-shutdown probe. Ordinary scaffold smokes still require zero remaining probes, unchanged SQLite 42/security assertions and normal shutdown. Actual outcomes must be recorded before acceptance; neither this planned harness nor synthetic telemetry establishes game support.

The third reload, `renderer-reload-delayed-commit`, holds the replacement document's navigation request for 2 s through a Playwright route. The replaced document's 250 ms re-subscribe therefore always reaches main before the commit. The step requires current values and exactly one new `DASHBOARD_PRECOMMIT_SUBSCRIPTION_RETIRED` main event for that reload. Without it, a late commit on the CPU-capped hosted runner left the dashboard without a subscription and failed intermittently with `page.waitForFunction: Timeout 10000ms exceeded` after the second reload. See [the renderer reload race record](validation/renderer-reload-subscription-race.md).

## ET-008 hidden overlay projection checks (implementation candidate)

The original development/packaged scaffold and telemetry recovery journeys remain separate. ET-008 adds two sequential bounded journeys, after the corresponding build/make:

```powershell
./scripts/ci/Invoke-RuntimeSmoke.ps1 -Mode development -Scenario overlay
./scripts/ci/Invoke-RuntimeSmoke.ps1 -Mode packaged -Scenario overlay
```

Each launch retains the same isolated profile, TEMP/APPDATA/LOCALAPPDATA, diagnostics, unrelated working directory and current-commit receipt, with the unchanged 60-second Windows Job, 16-process, 2-GiB, 25%-CPU caps, 20-second launch, 10-second window/status observations, 8-second close and zero retries. The separate scenario avoids extending the existing telemetry recovery journey. All native, sanitizer, static package and PowerShell gates remain in the workflow.

The synthetic named-pipe fixture explicitly has unavailable game-window metadata and cannot authorize native placement. The harness selects the exact dashboard and `renderer/index.html?view=overlay` main-frame URLs, checks every expected window's sandbox/context-isolation/no-Node settings, preserves the dashboard's three-key bridge, and checks the overlay's frozen sole `subscribeOverlay` method with no dashboard bridge. Read-only Electron main evaluation confirms the synthetic overlay stays hidden and nonfocusable at every observation. The same evaluation records `isAlwaysOnTop()`, which on Windows reads the HWND's actual `WS_EX_TOPMOST` style: the hidden overlay must already be topmost and the dashboard must not be. The overlay receipt rejects a missing, non-boolean or false overlay value and a topmost dashboard at startup, every phase and both stalls. This does not reproduce the taskbar-ordering defect, because hosted runners have no foreground full-screen window; see [the minimal overlay](minimal-overlay.md#z-order). Coherent DOM assertions cover ETS2 metric units, explicit synthetic origin, 90 km/h and 73 L, changed 72 km/h and 71 L, missing readings distinct from zero, held-open silence becoming stale, resume, and disconnected unavailable readings. Separate overlay and dashboard reloads and six-second credit stalls must recover while preserving the other consumer and the one upstream source connection. Source identity and raw phase/window observations are retained, including partial evidence on failure.

Each stall holds the owned renderer at a DevTools `debugger` statement through a separate Chrome DevTools Protocol session ([`Debugger.paused`](https://chromedevtools.github.io/devtools-protocol/tot/Debugger/#event-paused), [`Debugger.resume`](https://chromedevtools.github.io/devtools-protocol/tot/Debugger/#method-resume)). While paused, that renderer's main thread runs no page tasks: no port messages, consumption credits, timers or rendering. Unlike the earlier busy loop, it consumes no CPU, so the Job's hard CPU cap cannot starve the independent renderer, service, main process or driver. The harness waits for the pause event and checks that the paused frame holds its unique marker, then changes the source and observes the other renderer's 72 km/h and 71 L. Only the driver resumes the renderer, and no earlier than six seconds after the barrier on its high-resolution clock. An observation received before the resume request is therefore definitely pending. The receipt records start/change/observation/resume-request/completion order on the driver's monotonic clock, actual start/end on the stalled renderer's separate monotonic clock, the pause method and reason, pending-at-observation, the unchanged single source connection and hidden/security flags. Observation must precede the resume request, and both the driver hold and the renderer's elapsed time must be at least six seconds. A failure-path cleanup resume is recorded separately and never satisfies the resume-request field. If the renderer shares a process with the other window, the pause also freezes the other window and the gate fails; a controlled local experiment confirmed this. The overlay must then recover its current projection after port-credit expiry; the symmetric dashboard stall retains direct overlay-during-stall evidence. The two stalls occupy 12 seconds of the unchanged 60-second Job allowance; this arithmetic is not a measured overall run duration. Actual runtime and timeout outcomes remain part of each run's evidence.

The overlay receipt additionally requires every phase, security/window observation, source identity, both stall-start/order/timing proofs, recovery result, normal app/service exit and zero remaining probes; a successful Job or missing overlay result cannot pass it. Its pure validator, barrier orchestration, coherent observations and isolated pipe controls are tested in `tests/unit/overlay-smoke-source.test.ts`. Observations made only after a stall or after its resume request, absent barriers, malformed timing, a missing resume time, a CPU-spinning or non-`debugger` pause, stalls or holds shorter than six seconds and source reconnection cannot satisfy the receipt. Original scaffold/telemetry receipt rules are unchanged. The wrapper binds the scenario into the Job receipt as well as driver/wrapper receipts.

These are hidden-renderer projection and isolation checks. `hidden-overlay-dom.png` captures that DOM; it does not establish an OS-visible overlay, game-following placement, click-through, foreground/focus behavior, mixed DPI, monitor removal, real game compatibility, display latency or frame-time performance. Those checks remain pending against the real-game candidate. Adding this harness/workflow is not an executed or passed UI/hosted check; actual runs and their candidate identities must be recorded separately before acceptance.

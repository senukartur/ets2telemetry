## Advisory AI review

The separate [Claude code review](ai-review.md) workflow comments on non-draft pull requests and on owner `@claude` requests. It runs on Ubuntu and requires a Claude secret. It is advisory only and is not a required check; the Windows jobs below remain the CI merge gate.

ET-022 provides [Windows CI](../.github/workflows/windows-ci.yml) for pull requests, pushes to `main`, and manual dispatch. ET-024 limits automatic runs as described in [Triggers and draft checks](#triggers-and-draft-checks). Clean hosted execution and the deliberate failing-assertion/restoration sequence passed as recorded in [ET-022 validation](validation/et-022.md). The final current PR head still needs its own check/review association before owner merge. These runs do not establish branch protection or game compatibility.

The explicitly selected x64 `windows-2022` image uses Visual Studio 2022 with `Visual Studio 17 2022`, not the local Visual Studio 2026 generator. Image updates may change MSVC and SDK patch versions; each run records image identity and vendor versions. Node 24.19.0, npm 11.17.0, Electron 44.7.0 and Playwright 1.64.0 are pinned. CMake 4.3.1 is acquired explicitly before tool verification and configuration; the runner's CMake 3.31.6 does not satisfy the existing native minimum of 4.3. Action revisions are pinned to exact commits (checkout v5, setup-node v5, cache v4, upload-artifact v4). The [runner manifest](https://github.com/actions/runner-images/blob/main/images/windows/Windows2022-Readme.md) documents VS 2022 support.

`scripts/ci/Install-CMake.ps1` is restricted to GitHub Actions. It downloads the official [Kitware CMake 4.3.1 Windows x86_64 ZIP](https://github.com/Kitware/CMake/releases/download/v4.3.1/cmake-4.3.1-windows-x86_64.zip), verifies SHA256 `03a610be931546474e46a442d171ef10532f4fc847de9cf76b7a8065bbef6a23` before expansion, and checks `cmake version 4.3.1`. The [vendor checksum manifest](https://github.com/Kitware/CMake/releases/download/v4.3.1/cmake-4.3.1-SHA-256.txt) and GitHub release asset digest agree with that pin; the independently downloaded manifest SHA256 is `e101d7dacb65463f86fa1c04bf15181368f258f29a3dad4969de8f44ba6dcbd3`. Acquisition uses a fresh runner temporary directory and adds its `bin` to the current process PATH and `GITHUB_PATH`; no MSI/global installation or owner-host PATH change occurs. `.local/ci/cmake-toolchain.json` retains source, archive hash, observed version and executable path. The tool archive is not shared through dependency caches. The second hosted run passed all 122 tests, then exposed the runner's older CMake; that failed run remains part of the acceptance history rather than weakening the native requirement.

Every run installs the lockfile into a clean workspace, installs the separate lint lockfile and runs ESLint with zero allowed errors or warnings, runs PSScriptAnalyzer over tracked PowerShell files with zero allowed findings, runs typecheck and the full Node-safe Vitest corpus, builds desktop and native x64, runs CTest, executes a bounded development Electron smoke, makes the actual Forge/Squirrel artifact, inspects packaged bytes/native paths, and executes the packaged smoke from an unrelated working directory. Since October 17, 2026 pull requests package without the Squirrel maker and skip the development smokes (owner decisions E1 and E2, [ET-019t speed-up](#et-019t-speed-up-october-17-2026)); pushes to `main` and dispatch still run both. Before the ET-028 artifact partition these steps ran in three parallel jobs: lint, PowerShell analysis, typecheck and the Vitest suites in one, the build, native CTest, chains, smokes and Forge make in another, and the native AddressSanitizer console tests in the third; see [Job layout](#job-layout). Vitest never imports Electron or native SQLite. Lint (ET-023a) runs first in the tests job, on its own runner, for fast feedback; its toolchain, TypeScript 6 API rationale and rule exceptions are in [setup](setup.md#linting). The lint step measured 17-18 s on hosted runners; [ET-023a validation](validation/et-023a.md) records the controlled failure and restore runs. PowerShell script analysis (ET-023b) follows it; the hash-pinned module, Windows PowerShell 5.1 engine and rule exceptions are in [setup](setup.md#powershell-script-analysis). No test filtering or retries are enabled.

Caching is configured only for downloaded npm archives and Electron distributions. Before ET-024, every hosted run ended with `Path Validation Error: Path(s) specified in the action for caching do(es) not exist` and saved nothing: npm did not use `~\AppData\Local\npm-cache` on the runner, and Electron's installer ignores `ELECTRON_CACHE` (it reads `electron_config_cache`), so `.local/cache/electron` was never created. The job now sets `npm_config_cache` and `electron_config_cache` to `.local/cache/npm` and `.local/cache/electron` inside the workspace and caches exactly those paths. GitHub saves a cache only after a successful job, and a cache saved on `main` is visible to all PR branches, while a PR-branch cache is visible only to that PR. ET-024 measurements on dispatch runs [38167660898](https://github.com/senukartur/ets2telemetry/actions/runs/38167660898) (cold, saved ~212 MB in 4 s) and [38167962488](https://github.com/senukartur/ets2telemetry/actions/runs/38167962488) (cache hit, restored in 4 s) show `npm ci` taking 17 s cold and 14 s warm. The restore costs about what it saves, so the cache gives no measurable speedup; it is kept as protection against registry/CDN download failures, not as a time saving. The largest step is Forge make/inspection (68–108 s across these runs); whole-job time varied from 169 s to 236 s between runners for the same work. Keys include both lockfiles (root and `tools/lint`), Windows/x64, Node 24.19.0 ABI 137 and Electron 44.7.0 ABI 149. No `node_modules`, native build tree, SQLite binding compiled for another runtime, packaged artifact, profile or database is cached. This is deliberately stricter than [setup-node's default download caching](https://github.com/actions/setup-node/blob/main/docs/advanced-usage.md).

## Triggers and draft checks

| Event | Behavior |
| --- | --- |
| PR opened, updated or reopened while **draft** | Workflow run is created but all participating jobs and the aggregate are skipped (no runner minutes). A skipped job is not a passed check |
| PR marked **Ready for review**, or updated while ready | `windows-build` packages/inspects the PR merge checkout; `windows-runtime` runs packaged runtime/UI checks only (E1, E2). Tests/ASan run independently; the hosted installer is deliberately skipped. `Windows x64 scaffold` aggregates the participating results |
| PR or `main` push changing only `**.md` or `docs/**` | No run at all; GitHub reports no check for that commit |
| Push to `main` touching anything else | `windows-build` makes/inspects the Squirrel output; `windows-installer` runs the [hosted lifecycle](#et-018-installer-lifecycle); `windows-runtime` runs development/packaged runtime/UI checks and extended regressions. Tests/ASan and the scaffold aggregate remain required |
| Manual dispatch | Selected branch checkout: `windows-build` makes/inspects, `windows-installer` runs the hosted lifecycle of the build that was made (since ET-055 PR-5 also the staging lifecycle of a dispatch on any other branch, which builds staging; the side-by-side scenario on `main` only, [side-by-side](#side-by-side-installer-lifecycle-et-055-pr-5)), and `windows-runtime` runs development/packaged runtime/UI checks regardless of `extended`, adding extended regressions unless `extended=false`. Tests/ASan and the scaffold aggregate remain required |

Any change outside `**.md` and `docs/**` (code, tests, fixtures, scripts, workflow, `package*.json`, config) runs every participating job and the three required checks. GitHub evaluates path filters against the whole PR diff, so a PR that later gains a code change runs normally. Documentation-only PRs rely on the focused document checks in [TESTING.md](TESTING.md). The `Protect main` ruleset requires all three checks, and a path-filtered workflow reports none for such a PR, so a documentation-only PR is merged with the admin bypass described in [branch protection](agent-rules.md#branch-protection--october-16-2026).

To check a draft head without marking it ready, dispatch the workflow on the task branch:

```powershell
gh workflow run windows-ci.yml --ref <task-branch> -f extended=false
gh run list --workflow windows-ci.yml --branch <task-branch> --limit 1
```

A dispatch run checks the branch head itself, not the PR merge result with current `main`. GitHub attaches it to the head commit (visible in the commit's checks and the Actions list), but the PR check list keeps showing the skipped pull-request job for that commit, so record the dispatch run link in the PR or ledger. The final-head gate is therefore the pull-request run triggered by **Ready for review** (or a later push while ready). If that run fails, fix the branch or return the PR to draft (`gh pr ready <number> --undo`).

### Build channels (ET-055 PR-4)

Which channel each trigger builds ([build channels](setup.md#build-channels-et-055), UP13):

| Trigger | Channel | How |
| --- | --- | --- |
| Pull request (ready) | Staging, the default | `ETS2TELEMETRY_BUILD_CHANNEL` stays unset. The package is `out/ETS2Telemetry Desktop Staging-win32-x64` with the staging plugin, pipes and data root, and the version is `<package.json version>-stg.000000` |
| Push to `main`, dispatch on `main` | Production, for the release artifact | The step **Build production on main** (`if: github.ref == 'refs/heads/main'`) in `windows-build`, `windows-runtime` and `windows-installer` writes `ETS2TELEMETRY_BUILD_CHANNEL=production` to `GITHUB_ENV`; the resolver accepts it because the job runs on a GitHub-hosted runner (`GITHUB_ACTIONS=true` and `RUNNER_ENVIRONMENT=github-hosted`) |
| Dispatch on any other branch | Staging, the default, as a staging release artifact | As a pull request: `ETS2TELEMETRY_BUILD_CHANNEL` stays unset. The maker still runs, and the Setup is uploaded as `windows-installer-staging-<run>-<attempt>`. Until ET-055 PR-5 the hosted installer job ran a notice step instead of the lifecycle; since PR-5 it runs the staging lifecycle, without the side-by-side step. Since the owner decision of October 28, 2026 ([below](#et-055-release-workflow-dispatch-only)) the step **Staging run number on a branch dispatch** in the same three jobs sets `ETS2TELEMETRY_STAGING_RUN_NUMBER`, so the version is `<package.json version>-stg.<6-digit run number>` and the artifact, with `release-identity.json`, can be released as staging. A dispatch on a tag keeps `-stg.000000` |
| `windows-tests` | Neither | Vitest removes the build variables first (`tests/shared/build-channel-environment.ts`), and the tests name the channel they check |
| `windows-asan`, `windows-extended.yml` | Production, passed explicitly | They configure their own native test trees with `cmake` directly and `-DETS2TELEMETRY_CHANNEL=production`, because CMake's own default is staging, and package nothing |
| `windows-soak.yml` (dispatch-only) | Staging, the default | `npm run native:configure` and `npm run package` with the variable unset |

`npm run native:configure -- -G 'Visual Studio 17 2022'` configures the plugin tree for the resolved channel. The drivers never guess the channel: `Invoke-RuntimeSmoke.ps1`, `Invoke-SessionEndSmoke.ps1`, the session-end package hash, `compiled-artifact.mjs` and the installer lifecycle read it from the desktop build evidence (`node scripts/build-channel.mjs --built`), and the packaged smokes also check the package's own broker evidence. The smokes then expect that channel's package folder, executable, isolated data root (`<LOCALAPPDATA>\ETS2Telemetry` or `...\ETS2TelemetryStaging`), plugin file, display name in user-facing copy and application version (`scripts/ci/smoke-build.mjs`). The compiled-artifact manifest records the channel, and a restore accepts only that channel's package folder. The native chain tests take the pipe prefix from the channel of `native/telemetry-plugin/build`.

Consequences:

- A packaging regression that affects only production names shows first on the `main` push; the golden tests in `tests/unit/channel-identity.test.ts` pin the production values on every PR (plan risk R2). A branch dispatch checks the staging path only, so the production path of a change is first exercised after its merge.
- The installer artifact is named after the channel the build evidence names (step **Name the built channel and Setup**): `windows-installer-<run>-<attempt>` with the production Setup on `main`, `windows-installer-staging-<run>-<attempt>` with the staging Setup on a branch dispatch. The production artifact comes only from a `main` run. Never install an artifact of a branch dispatch as production: it is a staging build. Since October 28, 2026 the release workflow may release it as staging.
- `tests/unit/ci-build-channel-workflow.test.ts` asserts these conditions in the workflow text: the three production steps and their `refs/heads/main` condition, the channel-named artifact and Setup, and (since ET-055 PR-5) the lifecycle for the built channel, the side-by-side step on `main` only and the staging build job.
- Since ET-055 PR-5, `main` builds staging as well, in the separate job `windows-staging-build`, for the staging and side-by-side installer lifecycles ([below](#side-by-side-installer-lifecycle-et-055-pr-5)); the uploaded `windows-installer-<run>-<attempt>` still holds the production Setup only.
- `release-identity.json` records `builtBy` with the run id (`GITHUB_RUN_ID`) of the run that built it.

The three required check names remain unchanged; `Windows x64 scaffold` is an `always()` aggregate. The same triggers/path filters/concurrency group apply. Draft PRs skip execution. On PRs only the explicitly nonparticipating installer job may be skipped; every other missing, skipped, failed or cancelled participating dependency fails the aggregate.

Consumers install the same lockfile but restore the exact producer bytes, including development's `better-sqlite3/prebuilds/win32-x64.node`, after installation. `compiled-artifact.mjs` verifies effective source SHA and actual checkout SHA (including a PR merge checkout), a SHA-256/size manifest, all required roots, regular files, unique bounded relative paths and no extra/missing payload files before any copy. Destination links are refused. The same-run, same-attempt artifact transfers desktop dist, staged plugin, simulator dist, native Release executable/DLL/evidence files (including the separate required `native/telemetry-plugin/build/cap0-host/Release/eurotrucks2.exe`), portable package, the native SQLite binding and, for non-PR events, maker output. No compiled payload is taken from a dependency cache or another run. The official `actions/download-artifact` v4 tag was verified at `d3f86a106a0bac45b974a628896c90dbdf5c8093`; upload retains its existing pin. Both consumers retain isolated run roots and every 60-second runtime Job/resource/security/cleanup predicate.

### Artifact identity and rerun procedure

The artifact name is `windows-compiled-${{ github.run_id }}-${{ github.run_attempt }}`. Consumers accept only the producer payload from the **same workflow run and the same attempt**. GitHub keeps a run ID across reruns but increments the attempt number ([variables reference](https://docs.github.com/en/actions/reference/workflows-and-actions/variables)). There is no fallback to another run or earlier attempt, and a missing payload fails the consumer and aggregate.

For recovery, use **Re-run all jobs**, or start a fresh complete workflow dispatch on the intended branch. Do not use **Re-run failed jobs** or rerun an isolated consumer: its new attempt requests a new artifact name while a reused successful producer has only the previous attempt's artifact. Re-running all jobs republishes and verifies the payload in one attempt. GitHub documents [full and partial reruns](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs); a rerun retains the original event SHA/ref, so a fresh dispatch is needed to check a newer branch head. Record every failed/cancelled attempt and the complete replacement outcome; partial success or retries do not erase a failure or prove its cause. The final automatic PR gate still belongs to the intended final source.

The manifest's `source` and `checkout` fields have different purposes. On `pull_request`, `source` labels `github.event.pull_request.head.sha`, while `checkout` records actual `git rev-parse HEAD`: the default event merge commit. The producer compiles the PR head integrated with its base, and consumers must match that same merge checkout and source label. File hashes prove the transferred bytes match the producer; they do not claim those bytes were compiled from the standalone head tree. On dispatch, the event selects the branch commit and the default checkout uses it; both identities normally match. Pushes use their event commit. See GitHub's [pull-request event identity](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request) and the [pinned checkout behavior](https://github.com/actions/checkout/blob/fbc6f3992d24b796d5a048ff273f7fcc4a7b6c09/README.md). Record the observed source/checkout pair with the completed run evidence rather than inferring a head-only test from the source label.

### Worker independence and required checks

The job **Windows x64 extended campaigns** belongs to a separate workflow, `windows-extended.yml`, which runs on pushes to `main` and by dispatch, never on pull requests. It is not a required check, and its result does not change the Windows CI run; see [ET-019 extended campaigns](#et-019-extended-campaigns).

The tests job needs no CMake and no native build: the Node-safe suite and the storage suite ran before `npm run build` in the single job too, and the storage suite bundles its own worker. Its steps moved from the scaffold job without changes: same commands, reporters, JUnit files and the storage step's 5-minute limit.

The AddressSanitizer job uses no output of the compiled-artifact producer or its consumers. Both CMake trees build their targets from the checkout, including the uninstrumented `snapshot-transport-test-plugin` and `snapshot-transport-hooked-test-plugin` DLLs that the ASan DLL cases load, and the tests read their fixtures from `tests/fixtures`. The job installs no npm dependencies and restores no cache; pinned Node is set up only for `scripts/ci/versions.mjs`, which writes this job's own `versions.json`. The two ASan steps moved without changes: same commands, target lists, CTest selections and per-test deadlines, in the same order, with no filter or retry. Since ET-019t the two build commands also pass CMake's `--parallel` and the two CTest commands `--output-junit`; targets, selections and per-test deadlines are unchanged. Because the Release and ASan client suites now run on different machines, the endpoint-name collision described in [the ET-006a section](#et-006a-native-client-and-live-smoke-implementation-candidate) cannot occur between them.

A run passes only when all three required checks pass, including the fail-closed scaffold aggregate over all participating workers. A cancelled or unexpected skipped worker is not a passed check. The `Protect main` ruleset requires those three check names; the scaffold aggregate covers its five worker dependencies. The owner approved adding `Windows x64 tests` on October 17, 2026 (U5), and the coordinator added it that day after the job first reported on a Ready run (#103, run 39030712000).

### ET-019t speed-up (October 17, 2026)

This dated section retains the original heavy-scaffold owner and six-smoke inventory. The current [job layout](#job-layout) supersedes its job ownership/inventory; its E1/E2 event-selection decisions remain in effect.

Before ET-019t, PR runs took 13.6–14.5 minutes of wall time: the scaffold job 785–865 s and the AddressSanitizer job 426–506 s ([ET-019t validation](validation/et-019t.md) lists the runs and steps). The scaffold job was the critical path. ET-019t changes four things and no test selection:

- **Third job (C2).** Lint, PowerShell analysis, typecheck, the Node-safe suite and the storage suite, 240–300 s of the scaffold job's hosted time, run in `windows-tests` (above).
- **Parallel MSBuild (C1).** `npm run native:build`, `scripts/build-native-client.mjs` and both AddressSanitizer builds pass CMake's `--parallel` without a job count. For Visual Studio generators CMake then adds `/m` to the MSBuild command line (confirmed locally with `-v:diag`: `MSBuild.exe /m /p:Configuration=Release …`), so MSBuild builds independent projects of a solution in parallel. Review round 1 replaced the first form, `-- /m`, because arguments after `--` go to MSBuild, so extra CMake arguments appended through npm broke, and Git Bash rewrites a bare `/m` to `M:/` (MSBuild error MSB1008). The serial plugin Release build took 116 s and the plugin ASan build 137 s. CTest itself stays serial: no `-j`.
- **CTest JUnit (C4).** All four CTest runs write `--output-junit` files under `.local/ci` with an absolute path, because CTest resolves a relative path against the build tree: `ctest-client-release.xml` and `ctest-plugin-release.xml` in the scaffold job, `ctest-plugin-asan.xml` and `ctest-client-asan.xml` in the AddressSanitizer job.
- **Seeded journal case (C3).** The storage case with more than 5,000 money amounts (66–117 s hosted) seeds its fines; see [ET-019t validation](validation/et-019t.md).

Two further reductions were **adopted by owner decision on October 17, 2026**:

- **E1.** On `pull_request` events the scaffold job runs `npm run package` and `npm run inspect:package` (step "Forge package and static native package inspection") instead of the Squirrel `npm run make` (step "Forge maker and static native package inspection"). Squirrel took about 74 s and nothing in a PR run consumes its output: `inspect:package` and the packaged smokes read `out/ETS2Telemetry Desktop-win32-x64`, which `electron-forge package` writes on its own and `make` writes before running the maker. The maker output `out/make` is read by no CI step. Pushes to `main` and every manual dispatch still run `npm run make`.
- **E2.** On `pull_request` events the scaffold job runs only the six packaged runtime smokes; the six development-mode smokes (80–86 s) run on pushes to `main` and on every manual dispatch.

Per event:

| Event | Forge step | Development smokes | Packaged smokes | Extended regressions |
| --- | --- | --- | --- | --- |
| `pull_request` (ready) | `npm run package` + inspection | skipped | all six | skipped |
| `push` to `main` | `npm run make` + inspection | all six | all six | run |
| `workflow_dispatch`, `extended=true` | `npm run make` + inspection | all six | all six | run |
| `workflow_dispatch`, `extended=false` | `npm run make` + inspection | all six | all six | skipped |

The conditions are step-level `if: github.event_name == 'pull_request'` and `!= 'pull_request'`, not the `extended` input. The input exists only for dispatch, while the owner decision ties E1 and E2 to the event: a push to `main` and every dispatch, including the `extended=false` draft check, must keep the full make and both smoke sets. An event condition says that directly; folding it into `extended` would either drop the development smokes from `extended=false` dispatches or change what that input means. The job-level draft skip, the triggers, the concurrency group and the three check names are unchanged. A draft head checked by dispatch therefore runs more than its later Ready run, never less.

**Projection, not a measurement.** From the before-step durations: the scaffold job on a PR drops the moved steps (240–300 s), the Squirrel maker (about 74 s), the development smokes (80–86 s) and part of the serial MSBuild time (C1, an expected 60–75 s), so it falls to about 4–7 minutes; the tests job is about 3–4.5 minutes, with the storage suite shortened by C3; the AddressSanitizer job, about 6.5–8 minutes with the parallel build, becomes the longest, so a PR run is expected to take about 7–8.5 minutes of wall time. ## Bounded runtime checks

Run from the repository root on Windows with pinned Node on PATH, after `npm run build` / `npm run make` respectively:

```powershell
./scripts/ci/Invoke-RuntimeSmoke.ps1 -Mode development
./scripts/ci/Invoke-RuntimeSmoke.ps1 -Mode packaged
```

Each mode launches once under the existing Windows Job Object: 60 seconds maximum, 16 processes, 2 GiB committed memory, 25% system CPU and kill-on-close. The owner retains the Job until all descendants exit; a forced cleanup/timeout fails. Playwright launch keeps its 20-second deadline and normal close has 8 seconds. Release sandbox, context isolation, narrow frozen bridge and Node isolation remain enabled. [Playwright Electron support is experimental](https://playwright.dev/docs/api/class-electron); the prior ET-001 launch timeout remains unexplained and is not erased by later success.

Readiness proves Electron main → utilityProcess → storage worker → actual bundled better-sqlite3 N-API write, close, reopen, read. Three diagnostics help explain a stalled launch. They are observations only: they change no deadline, retry, Job limit or pass condition. The [resource evidence](#resource-evidence-et-019-pr-11) below is recorded the same way, but its receipt fields must be present and plausible.

- **Job CPU series.** The smoke wrapper calls `BoundedProcess.Run` with CPU sampling enabled, which writes `job/cpu.jsonl`. The first line records the wall-clock start, logical processor count and the 25% rate. Each following line, about every 100 ms, records cumulative Job CPU time, active Job processes and whole-system busy and idle time. `scripts/ci/job-cpu-summary.mjs` adds a per-second summary to `job-result.json` under `cpu`, in processors used (CPU ms per wall ms): `capProcessors` is the hard cap, 0.5 on a two-processor runner. A Job running at its cap during a stall points to starvation. A busy system with an idle Job points to outside load. Both idle points to a block inside the application. A missing or invalid series is recorded as `cpu.error` and does not fail the smoke. Other `BoundedProcess` callers are unchanged and write no series.
- **Main-process timeline.** Only when `ETS2TELEMETRY_DIAGNOSTIC_DIR` is set, which the smokes always do, main logs `DASHBOARD_WINDOW_CREATED`, `OVERLAY_WINDOW_CREATED`, `<DASHBOARD|OVERLAY>_LOAD_STARTED`, `<DASHBOARD|OVERLAY>_LOAD_FINISHED` with the renderer PID, and `CHILD_PROCESS_GONE` for any GPU or utility process. A 250 ms main-process timer logs `MAIN_EVENT_LOOP_LAG` with `gapMs` when it fires more than 1 s late. In Electron, main's event loop is also Chromium's browser UI thread, so the event is written only after a stall ends, at its end time, and `gapMs` gives its length. None of these names match the smoke's failure-event pattern. Default user logs contain none of them.
- **Driver phases.** `result.json` holds `phases`: wall and monotonic driver times for launch, tracing start, page discovery, dashboard readiness, journey completion or failure, tracing stop and close. If page discovery fails, `pagesAtRendererPagesFailure` lists the URLs Playwright had seen.

### Resource evidence (ET-019 PR-11)

Since ET-019 PR-11 (October 19, 2026) every runtime smoke records resource evidence: development, packaged and installed mode, every scenario. The values are measured, not gated (ET-019 plan decision D3, measure, then gate): no threshold fails a run. `Test-RuntimeReceipt` fails only a receipt whose values are missing or implausible, with the reason `RESOURCE_EVIDENCE_INCOMPLETE_OR_INVALID`. The wrapper always names its `job-result.json` for that check; a caller that names none keeps the earlier rules.

- **Job peak memory** (`job-result.json`, `memory`). With sampling enabled, `BoundedProcess.Run` queries the Job's extended limit information once after the run, after the Job is terminated and before its handle closes, and writes `job/memory.json`. A failed query writes no file; a write that fails midway can leave a partial or empty file, which the wrapper records as `JOB_MEMORY_INVALID` and the receipt check rejects. `peakProcessMemoryBytes` is `PeakProcessMemoryUsed`, the largest committed memory of any one process ever in the Job. `peakJobMemoryBytes` is `PeakJobMemoryUsed`, the largest committed memory of the whole Job. The Job also holds the Node driver and its helpers, such as the `journal` scenario's Vite build of its seed script, so both are upper bounds for the application. The receipt check requires whole bytes from 1 MiB to the Job's 2 GiB limit, the process peak not above the Job peak, and no other field.
- **Cold-launch phases** (`result.json`, `coldLaunch`). The first launch of the run, in whole milliseconds after the main process was created (Electron's `process.getCreationTime()`, read through Playwright; the driver's launch request only if that is unavailable). `launchRequestedToOriginMs` is the time from the driver's launch request to that origin. It is recorded as measured: the launch request is a V8 `Date`, coarse to the system timer tick (about 15.6 ms), while the origin is the kernel's creation time, so a healthy launch can measure slightly below zero. The receipt check allows that skew down to -1,000 ms. Each phase is the first occurrence of a row the application already logs, or a driver read; no product hook was added:

  | Phase | Source |
  | --- | --- |
  | `mainStarted` | main `APP_START` |
  | `mainReady` | main `SERVICE_START_REQUESTED`, the first row of the `whenReady` handler. Under Playwright, Electron's `ready` event waits until Playwright has attached, so this includes the attach |
  | `serviceReady` | main `SERVICE_READY` |
  | `storageProbeVerified` | service `STORAGE_VERIFIED` |
  | `historyStorageOpened` | service `HISTORY_STORAGE_OPENED`: the history database, or the synthetic target of `recording` and `journal`. In `refusal`, which opens none, it is null with `HISTORY_STORAGE_OPENED_NOT_LOGGED` |
  | `firstWindowShown` | main `DASHBOARD_WINDOW_CREATED`; the dashboard is created visible, so its creation is its first show |
  | `dashboardLoaded` | main `DASHBOARD_LOAD_FINISHED` |
  | `rendererFirstPaint`, `rendererFirstContentfulPaint` | The dashboard document's Paint Timing entries, read right after the ready text is visible, waiting at most 2 s for the contentful paint |
  | `dashboardReadyVisible` | The driver's `dashboard-ready-visible` phase: DOM visibility seen by Playwright, not a painted frame |

  The phases are independent marks after one origin, not a sequence: `dashboardReadyVisible` is DOM visibility, not a painted frame, so it can come before or after the first contentful paint: before it locally, after it on hosted runners. The renderer's first application state is not logged anywhere, so it is not recorded; `dashboardReadyVisible` stands in for it. The receipt check requires exactly these names, whole numbers from 0 to 60,000, and null only for `historyStorageOpened` (exactly in `refusal`) and the two paint phases, each with a fixed upper-case reason in `unavailable`.
- **Per-process peak working sets** (`result.json`, `processMemory`). Right before `journey-complete` the driver reads Electron's `app.getAppMetrics()` from the application open at that time: the restart run in `lifecycle`, `recording`, `journal` and `plugin`, which `run` names. For each kind (`main`, `renderer`, `telemetryService`, `gpu`, `otherUtility`, `other`) it records the process count and the largest peak working set in bytes. Processes that ended earlier are missing. The storage worker is a worker thread of the telemetry service, so its memory is inside `telemetryService`; `unavailable` names it. The receipt check requires one main process and at least one renderer and telemetry service process, each peaking at 1 MiB or more, at most 16 processes and 4 GiB per kind.

The wrapper copies these values to `wrapper-result.json` under `resourceFacts` and prints one line of numbers to the job log. They hold no path and no new host fact. `coldLaunch.observationMs` and `processMemory.observationMs` record what each read cost the smoke: locally 72–131 ms (mostly waiting for the first contentful paint) and 1–2 ms. The first local numbers are in [ET-019 validation](validation/et-019.md#pr-11-job-peak-memory-and-cold-launch-phases-october-19-2026); hosted numbers come from the first dispatch run.

### Recording dot animation in runtime smokes

The sidebar recording dot pulses endlessly while the dashboard window has focus ([application lifecycle](app-lifecycle.md#recording-on-the-dashboard-and-in-the-tray-et-015c-pr-4)). The window has focus in these runs, and every animated frame costs CPU under the Job's 25% cap. On PR #203 (run 40578063106) the pulse doubled the Hard Mode hint loops on a hosted runner (18–19 s instead of 8–9 s) and timed out the packaged Hard Mode journey at 60 s. Locally the same journey took 28.2 s with the pulse and 22.4 s without it.

Every runtime smoke scenario except `ui` therefore stops that one animation. On every document of every launch (Playwright's `addInitScript`, plus the windows already open), the driver adopts a constructed stylesheet that sets `animation: none` on `.yu-dot` and its ring. CSSOM stylesheets are not restricted by the renderer's CSP. The driver then waits up to 5 s until the dashboard's dot and ring compute `animation-name: none`, fails with `RECORDING_DOT_NOT_STILL` otherwise, and records the result as `recordingDotStill` in `result.json`. Nothing else in the UI changes.

Two broader approaches were tried and rejected on October 27, 2026:

- Chromium's `--force-prefers-reduced-motion` switch: Electron ignores it, and `matchMedia('(prefers-reduced-motion: reduce)')` did not match.
- Playwright's `emulateMedia({reducedMotion: 'reduce'})`: it changes the whole UI's motion through the global reduced-motion rule, more than the one animation that costs CPU, and on hosted runners it reached the overlay renderer late or not at all (PR #182).

While testing these variants locally, the Hard Mode journey's parameter-tooltip loop sometimes failed: a hint did not open on hover, or its rendered text did not match in time. It failed with the emulation, with the dot-only stylesheet, without the window focus hook and without the indicator's tooltip, about 1 run in 6 overall, but not in 6 runs of `main`'s application code. The cause is unknown and the evidence does not tie it to this change; hosted runs are the judge.

What this does and does not cover:

- The `ui` shards run with normal motion. They are the only runtime checks of animation: the indicator's `data-motion` and focus gating, and the Cluster speed arc's transition.
- The other scenarios check their journeys without the dot's animation cost. Their time and resource evidence is therefore no measure of the pulse.
- The session-end audit (`session-end-smoke.mjs`) launches the application itself without the switch. It does not interact with the dashboard.

If the renderer shares a process with the other window, the pause also freezes the other window and the gate fails; a controlled local experiment confirmed this. The overlay must then recover its current projection after port-credit expiry; the symmetric dashboard stall retains direct overlay-during-stall evidence. The two stalls occupy 12 seconds of the unchanged 60-second Job allowance; this arithmetic is not a measured overall run duration. Actual runtime and timeout outcomes remain part of each run's evidence.

The overlay receipt additionally requires every phase, security/window observation, source identity, both stall-start/order/timing proofs, recovery result, normal app/service exit and zero remaining probes; a successful Job or missing overlay result cannot pass it. Its pure validator, barrier orchestration, coherent observations and isolated pipe controls are tested in `tests/unit/overlay-smoke-source.test.ts`. Observations made only after a stall or after its resume request, absent barriers, malformed timing, a missing resume time, a CPU-spinning or non-`debugger` pause, stalls or holds shorter than six seconds and source reconnection cannot satisfy the receipt. Original scaffold/telemetry receipt rules are unchanged. The wrapper binds the scenario into the Job receipt as well as driver/wrapper receipts.

### Strip containment step (ET-012c)

Right after the `initial` observation the driver runs one more check, recorded as `stripLayout` (decision S10). `stripLayoutObservation` waits (10 s, 50 ms polling) until exactly one `overlay-root` has `data-layout="strip"` and `data-freshness="current"` and its `overlay-section-*` ids equal `STRIP_SMOKE_SECTIONS`: speed, gear, RPM, fuel, SDK consumption, cargo, destination, expected income and game time, hand-derived from `tests/fixtures/protocol-v0/checkpoint.json` (range stays hidden because its estimate is not observed). Hosted run [38878781715](https://github.com/senukartur/ets2telemetry/actions/runs/38878781715) failed an exact 1280 × 110 check that way with every section inside the window; that was a smoke-harness assumption, not a product defect. The recorded `viewport` is the actual one. The observation is stored in the result before it is verified, so a failed receipt keeps it. No phase is added to `observations` or `windows`, and `RuntimeReceipt.ps1` does not validate the field; a failed step fails the driver and therefore the receipt. On the unfixed code the step failed with `outside` = expected income and game time in a 1280 × 38 viewport ([ET-012c validation](validation/et-012c.md)).

### Layout containment step (ET-012d)

The telemetry scenario, with its v0 and v1 sources current, asserts the card, HUD and cluster right after its strip assertion (decisions K10 and K11; [minimal overlay](minimal-overlay.md#fixed-rows-et-012d)). The overlay scenario keeps only the strip assertion. The driver first saves, through the dashboard bridge, exactly the twelve sections the v0 and v1 pair shows (`SYNTHETIC_V1_STRIP_SECTIONS`: every section except range and distance driven), so no window reserves a row for a hidden section and the slack of two unused rows cannot hide space the row model does not count. Then, for each of `card`, `hud` and `cluster` in that order, it saves the layout and sets the hidden overlay window to `LAYOUT_SMOKE_WINDOWS` in `scripts/ci/overlay-observation.mjs`: 300 × 360, 320 × 320 and 440 × 225 DIP at zoom 1. That is the size the product creates for those sections at scale 1: the card and HUD at their nominal floor, the cluster at its exact reserve. Without a game window the controller never places the overlay, so the driver sizes it. A unit test ties these hand-written sizes to `overlayWindowSize(layout, 1, sections)`, and the reserved CSS heights `LAYOUT_SMOKE_RESERVED_CSS` (card 48 + 24 × 12 = 336, cluster 36 + 21 × 9 = 225, HUD 18 + 24 × 12 = 306) to `layoutReservedCss`. All three windows are smaller than the hosted runner's 1024 × 768 screen, so Windows does not narrow them. The driver waits (10 s) until the document reports that layout and a viewport within one DIP of the size. Then `layoutContainmentObservation` waits (10 s, 50 ms polling) until exactly one `overlay-root` has the layout's `data-layout` and `data-freshness="current"`, and its `overlay-section-*` ids equal `SYNTHETIC_V1_STRIP_SECTIONS`. For the cluster the DOM order (gauge, then panel) is also the canonical order.

The observation reads, in one pass:

- the viewport;
- `outside`: sections with an empty box, or not fully inside the root and every ancestor up to the root whose computed `overflow` is not `visible`, such as the card body, the HUD lines and the cluster's side panel;
- `clipped`: sections whose `.overlay-value` box is not vertically inside the section's fixed row;
- `bottom`: the lowest section bottom below the higher of two tops: the root's top and the top of the surface that holds the rows (the card body, the cluster's side panel or the HUD lines; the root alone for the cluster's gauge sections). The surface's top matters for the cluster. Its panel is bottom-aligned, so space the model does not count grows the panel upwards past the window's top while its lowest row keeps its place; measured from the root's top alone, the check could never fail for the cluster (review pass 2). The root's top matters for the top-aligned card and HUD: a margin on the card body or padding on the root pushes the surface and its rows down, and measured from the surface's top alone that would go unnoticed (review pass 3);
- `surfaces`: the box of each such surface relative to the root's top, and whether it lies inside the root;
- for review only, `truncated`: values that end in an ellipsis.

Every comparison allows 0.01 CSS px, because Chromium reports a box flush with its row's edge with float noise. A layout unit is 1/64 of a device pixel, so 0.01 CSS px is below one layout unit at display scaling up to 150 % and about 1/50 of a device pixel at 200 %; it never hides a visible overhang. The tolerance is not scaled by `devicePixelRatio`: the hosted runner and the local runs then apply the same rule, and no display scaling the overlay supports makes it visible.

`verifyLayoutContainment` fails the driver with:

- `Enabled overlay sections lie outside the overlay window` when `outside` is not empty;
- `Overlay section values are clipped by their rows` when `clipped` is not empty;
- `Exactly one overlay surface must hold the rows` unless the sections' rows sit in exactly one surface, and `The overlay surface lies outside the overlay window` when that surface is not inside the root;
- `Overlay sections extend below the height the row model reserves` when `bottom` exceeds the layout's reserved CSS height for the shown sections. In each layout, vertical space the model does not count above or between the rows, including space that pushes the surface down from the window's top, therefore fails even while every section stays inside the window, once it exceeds the reserve's trailing slack: the card's 10 px bottom padding and 1 px border, the cluster panel's 8 px and 1 px, and none for the HUD. For example, a 12 px taller card header, a 4 px taller HUD tag row, a 2 px top margin on every cluster panel row and a 20 px top margin on the card body all fail the smoke. Smaller additions within that slack, such as the description list's default margins (8 px after collapsing with the header's gap), are caught by the CSS contract in `overlay-rows.test.ts` instead. The contract requires `margin: 0` on the list and its values, no nonzero margin on any fixed row, tag row, the cluster panel, the HUD lines, the card body or the cluster body, and no padding on the overlay root or a layout root. Space below the lowest row, which pushes nothing out of the reserve, is not measured;
- `The overlay window must have the reserved size` unless each viewport dimension is the window's size or one DIP more (`getBounds` can round a window up by one DIP; the cluster's viewport is one DIP higher locally).

Each observation is stored in `result.telemetry.layoutContainment[layout]` before it is verified, so a failed receipt keeps it, together with the saved sections (`layoutContainment.sections`) and the window bounds the driver set (`layoutContainment.windows`). The strip and the original sections, all fourteen, are restored at the size the product created in every case, and the first error, a failed assertion or a failed restore, fails the run. The step writes the settings six times: the shown sections, the three layouts, the strip and the original sections. `RuntimeReceipt.ps1` does not validate the field; a failed step fails the driver and therefore the receipt. On the unfixed code the step failed with the cluster's `outside` = game time ([ET-012d validation](validation/et-012d.md)).

### Hidden overlay evidence capture

After the edit step the driver keeps review evidence of the hidden overlay document, recorded as `result.overlay.capture` (`captureHiddenOverlay` in `overlay-observation.mjs`). It asserts nothing about rendering:

1. `hidden-overlay-dom.html` is the serialized DOM (`page.content()`), read through the renderer's JavaScript without a rendered frame. `page.content()` has no Playwright timeout, so the driver bounds it to 10 s and fails with `HIDDEN_OVERLAY_DOM_NOT_READ_WITHIN_10000_MS` inside the Job's 60 s limit, keeping `result.json`. The DOM is written before it is checked, and the run fails when it cannot be read or does not hold exactly one `overlay-root`. `capture.dom` records the file and its size.
2. `hidden-overlay-dom.png` is best effort, bounded to 5 s. `capture.screenshot` records `captured`, the time taken and, after a Playwright `TimeoutError`, `captured: false` with the error; that timeout does not fail the run, and the wrapper prints one `Hidden overlay PNG skipped (review evidence only)` line in the job log. Any other screenshot error still fails the run.

The PNG is optional because `page.screenshot` sends `Page.captureScreenshot`, which makes the page produce a new frame and returns only after that frame arrives from the window's compositor. The overlay window is never shown in this harness, and once Chromium stops presenting frames for it, later captures do not complete within the observed bounds (8 s for `page.screenshot`, 5 s for `webContents.capturePage()`). Before this change the step waited for Playwright's default 30 s timeout and then failed the run after every assertion had passed ([ET-010 validation](validation/et-010.md#hidden-overlay-screenshot-timeout-october-16-2026)). `RuntimeReceipt.ps1` validates neither file nor `capture`.

These are hidden-renderer projection and isolation checks. `hidden-overlay-dom.html` and, when captured, `hidden-overlay-dom.png` record that DOM; they do not establish an OS-visible overlay, game-following placement, click-through, foreground/focus behavior, mixed DPI, monitor removal, real game compatibility, display latency or frame-time performance. Those checks remain pending against the real-game candidate. Adding this harness/workflow is not an executed or passed UI/hosted check; actual runs and their candidate identities must be recorded separately before acceptance.

It runs in one Windows Job with the unchanged 60-second, 16-process, 2-GiB, 25%-CPU and kill-on-close limits and zero retries, and, like the lifecycle smoke, gets a separate `diagnostics-restart` directory for run B. The application runs with the isolated profile, TEMP, APPDATA and LOCALAPPDATA, the v0 synthetic source and gated live-smoke diagnostics of the other journeys, and with `ETS2TELEMETRY_RECORDING=synthetic:smoke`, so its telemetry service records into `<isolated LOCALAPPDATA>\ETS2Telemetry\synthetic\smoke.sqlite` instead of history ([recording gate](telemetry-service-v1.md#recording-gate-et-015a)). Its protocol v1 source is `ETS2TELEMETRY_SOURCE_PIPE_V1`:

- **Simulator.** The built simulator CLI (`tools/telemetry-simulator/dist/cli.cjs serve-v1`) serves the corpus scenario `normal-delivery` reactively, with its transport replaced in memory by three durable connections at 0, 360 and 2,010 ms. Since ET-015b PR-4 eight steps are appended:
  - on connection 2: frames at 1,100 ms (speed 0) and 1,600 ms (speed 2.5), then `simulation.paused` (eventSeq 10) at 1,700 ms;
  - on connection 3: `simulation.started` (11) at 2,050 ms, a frame at 2,100 ms (speed 12.25 m/s, odometer 1,000.53125 km), `simulation.paused` (12) at 2,900 ms, a frame at 3,100 ms and `simulation.started` (13) at 3,200 ms.

  Each connection's last appended event is the gate the journey waits for before it exits. Nothing follows a gate before the scripted disconnect, so an exit right after the gate's ACK cannot change what the simulator serves or its replay verdict. The derived scenario is written to `recording-scenario.json` in the run directory.

  The simulator runs with `--await-scripted-acks` ([simulator v1](simulator-v1.md)). Connections 2 and 3 acknowledge every commit, so each promised ACK is awaited before the scenario advances, with a 30-second liveness guard. Connection 1 uses `dropAfter:4`: its first four ACKs use that same guard, while the intentionally dropped fifth ACK keeps the bounded 1-second wait before disconnect. A slow session open or commit therefore cannot make the source advance past its promised ACK prefix before the recording cursor becomes active.
- **Recording proxy** ([recording-proxy.mjs](../scripts/ci/recording-proxy.mjs), tested over actual pipes in `tests/unit/recording-proxy.test.ts`). The proxy sits between the service and the simulator on its own synthetic test pipe. It refuses a hello that does not request durable delivery, which happens while storage is still opening (R10), so the simulator serves only the durable clients its script expects. A durable hello waits for its admission, one connection open at a time. Nothing is admitted until the journey asks, and connection 1 only after the dashboard shows current data, so connection 1's bounded 1-second ACK waits do not overlap application startup.

  A hold is limited to 2 seconds, about half the service's 5-second handshake deadline (the time from opening a connection to its checkpoint). An older hold is destroyed by its timer, or refused when an admission reaches it late, and the admission is kept. The service reconnects on its backoff, and its fresh hello is admitted with about 3 seconds left for its checkpoint, less the time from the service's `open()` to its hello: the deadline starts at `open()`, the hold at the hello's arrival. Without the limit, an admission that landed just before the service's deadline would be consumed by a connection the service then closes, and the journey would fail.

  Like the scenario's `dropAfter:4`, the proxy delivers the first four ACKs of connection 1 and drops the fifth. Every ACK the proxy sees was written by the service only after its storage commit (E8), so ACKs are the in-run evidence of commits. The proxy records each event's time to the first ACK that covers it.

Run A, in order:

1. Wait for current v0 data, then admit connection 1. It must deliver eventSeq 1–5, the proxy must see ACKs 1–5 (forwarding 1–4), and the simulator must end the connection at its scripted disconnect (350 ms). The service log must contain a `V1_SOURCE_STATUS` row with `durable: active`.
2. Emit the gated `ets2telemetry:diagnostic-service-exit`. Main's supervisor must start a new service process, and the dashboard must show current data again.
3. Close the main window to the tray, then admit connection 2. The restarted service must receive a checkpoint at ACK 4, eventSeq 5 again with `redelivered: true` and then 6–10, and acknowledge 5–10, with no dashboard and the same service PID. This is the cold start from seeds (R4) and a duplicate redelivery. The service writes the ACK of eventSeq 10 only after its commit, and so after it observed the two frames before it in its FIFO. A `durable: active` row of the new process must follow.
4. Stop tracing and emit the gated tray action `exit`. The launcher must exit 0 within 8 seconds with one `APP_EXIT_REQUESTED` (`tray`).

Run B starts the application again with the same profile and LOCALAPPDATA. After current data, connection 3 is admitted: it must start at ACK 10, deliver only eventSeq 11–13, acknowledge each and log `durable: active`. Run B then closes through Playwright's `close()`.

After both runs the driver checks:

- **Diagnostics.** Run A logs `RECORDING_TARGET {purpose: synthetic}` and `HISTORY_STORAGE_OPENED` twice (`created` true, then false, for the terminated service and its replacement), two `SERVICE_EXIT` rows and one `DIAGNOSTIC_SERVICE_EXIT_REQUEST`. Run B logs one of each with `created: false`. Each run's final stop has `ok` `recording-flush` and `history-storage` steps, one `HISTORY_STORAGE_CLOSED` and a clean `stopped` report. Neither run logs a `V1_DURABLE_RETRY`, `V1_DURABLE_UNAVAILABLE`, `V1_DURABLE_ACK_AHEAD`, `V1_DURABLE_RESTORE_LOSS`, `V1_EVENT_CONFLICT`, `RECORDING_TARGET_REJECTED`, `HISTORY_STORAGE_UNAVAILABLE` or failure event. Since ET-015b PR-4 they log no `V1_SAMPLES_RETRY`, `V1_SAMPLES_DROPPED`, `V1_SAMPLES_DISCARDED` or `V1_SAMPLES_SKIPPED` either. Only the terminated service's storage probe remains.
- **Exit flushes (ET-015b PR-4).** Run A's replacement service and run B's service each stop with one sample row pending. The 5 s sample flush cannot write it earlier than 5 s after the service's first connection. So when a service's `recording-flush` step is logged less than 4.5 s after its first `V1_SOURCE_STATUS` `connected` row, both times from its own log, it must log exactly one `V1_SAMPLES_EXIT {rows: 1, losses: 0, code: WRITTEN}`. The 0.5 s below 5 s absorb timer and clock granularity. Later, the 5 s flush may have written the row first, and the exit logs nothing or that row. The terminated service logs none. Each service's decision, its interval and its rows are recorded in `sampleExits`.
- **Simulator.** The simulator process exits 0 with a report of three durable connections, connection 1 closed by its script and the others by the client or the script, and `matchesReplay: true`: the events, checkpoints and snapshots it served equal its deterministic replay of the same scenario.
- **Files.** `smoke.sqlite` is a closed schema version 2 database (version 1 before ET-016 PR-1) of this application with no `-wal`, `-shm` or `-journal` file and no `synthetic\backups` directory, and `data\telemetry.sqlite` does not exist.

### Recording status (ET-015c PR-4)

The journey also follows the [recording status](telemetry-service-v1.md#recording-status-et-015c) that main keeps in `AppState.health.recording`, through three views: the dashboard's texts, the gated lifecycle state and main's opt-in `RECORDING_STATUS` timeline rows ([isolated smoke diagnostics](app-lifecycle.md#isolated-smoke-diagnostics)). The expected statuses and texts are written by hand in `recording-observation.mjs`; the scenario, the proxy policy and the hand-written rows are unchanged.

States such as `recording` last only while the scenario's frames stay fresh, about 0.5–0.7 s per connection, and `unknown` lasts only from a service exit to its replacement's first report. The journey therefore never polls for them. Main's timeline row exists once main received the status, and a MutationObserver installed in the dashboard (`startRecordingTextLog`) records every distinct text it rendered. Polls (`until`, `waitForRecordingText`, 5–10 s) only wait for those records or for states that stay until the journey's next step; they are hang guards. In order:

1. Before connection 1 is admitted, main reports `{state: 'waiting', target: 'synthetic', code: null}` with no losses and no trip, and the dashboard shows `Waiting for the recorded source to connect`, the detail `Synthetic test database (never game history)`, no loss or alert element and the notice `Prototype live display. Only a test database is recorded, never game history.` (`statusWaitingShown`).
2. After connection 1 ended: the dashboard's text log has `Recording` with the synthetic note, and main's timeline a `recording` row of the synthetic target with `lostEvents` 0 (`statusRecordingShown`). The status then reads `interrupted` with the trip `{phase: 'active', completeness: 'partial'}`, and the dashboard shows `Connection lost; …` with `Current trip is partial`.
3. After the diagnostic service exit, main's rows from the exit request on contain `{state: 'unknown'}` followed by the restarted service's `waiting`, and the dashboard's text log shows `Not known: the telemetry service is not running or has not reported a valid status` (`statusUnknownAfterServiceExit`). The restarted service then reads `waiting` with no trip and no losses: connection 1's totals were none.
4. The dashboard is reloaded; once its data is current again it shows the same texts, and the lifecycle state the same status (`statusReloadKept`).
5. While the dashboard is closed, main's rows after the admission of connection 2 contain `recording` of the synthetic target (`statusRecordedWhileClosed`). After the gate, main's totals are `notConnected` 1, the trip's consumer-restart interval, and every other counter 0: the redelivered eventSeq 5 is a duplicate, not a lost event, and no run A row counts one (`statusNoEventLoss`). The state at that moment may be `recording`, `paused` or `interrupted`.
6. The gated tray action `open` reopens the dashboard, which shows the totals `Gaps recorded since Yukon Union Telemetry started` and `Intervals without a connection: 1` with the synthetic note and no alert (`statusReopenedLosses`). It is closed again and must report `dashboard: false` with the same service (`dashboardClosedBeforeTrayExit`), so the tray exit follows with the main window closed, as before.
7. Run B waits again with no losses before its admission (new totals for a new application start), main's run B rows contain `recording` or `paused`, no run B row carries a loss, and the dashboard's text log shows `Recording` or `Game paused; recording continues when it resumes` without a loss line (`statusRunBFresh`). Run B's v1 data is often fresh only while the game is paused, so either state counts as recorded.

The additive `Test-RecordingStatusReceipt` rules require these nine flags and re-check the facts: the three `waiting` statuses and texts without losses, `interrupted` with the partial trip line, a `recording` row of connection 1, an `unknown` row between the services, the reload's unchanged texts, a `recording` row while closed, the closed status with `lostEvents` 0 and `notConnected` 1, the reopened dashboard's two loss lines and its closing, an entry of each dashboard text log (`Recording` in connection 1, the `unknown` headline between the services, a recorded state in run B), and run B's rows without losses with a `recording` or `paused` row. ### Application soak (ET-019 PR-12b)

The runtime smoke scenario `soak` records the soak source with the running application for `-SoakMinutes` minutes (1 to 90). It runs in the development and packaged modes only; the wrapper refuses `-Mode installed`, a soak without minutes and minutes without the soak. Its CPU series is summarized in 10 s buckets (`job-cpu-summary.mjs --bucket-ms 10000`, `cpu.perBucket` in `job-result.json`), so the file stays inside the receipt check's 256 KiB read bound; every other scenario keeps its per-second rows.

No proxy sits between them: the source itself refuses and counts the live-only hellos the service sends while storage opens (`refusedLiveOnly`, R10). The journey:

1. Waits for current v0 data, stops the trace of the start (a trace of the whole soak would grow without bound) and starts the series.
2. Every 30 s, a probe: Electron's `app.getAppMetrics()` summed per process kind (the kinds of the [resource evidence](#resource-evidence-et-019-pr-11)) as working set and private bytes, the round trip of a main-process and a dashboard evaluation, main's recording state, the size of the database and its WAL, and the source's latest progress line. 3. Once a progress line shows the source in its tail with the last eventSeq acknowledged, main's recording status must be exactly `recording`, target `synthetic`, no code, one `notConnected` loss per reconnect cycle and no other loss, and an idle trip (`{phase: 'idle', completeness: null, untrackedJob: false}`); each status read is bounded to 10 s like a probe's. Every page of the journal list, read through the bridge (`listJournalTrips`, 50 trips per page), must list the M trips newest first with their outcomes and completeness. A trip page carries a next cursor exactly when it is full ([journal contract](../packages/contracts/src/journal.ts)), so the pages are ⌊M / 50⌋ full ones and a last one of M % 50 trips, empty when M is a multiple of 50.
4. Once a progress line is 10 s or more into the tail, the driver writes `stop` and the application exits through the shared close path right away, so the exit's `recording-flush` writes the samples still pending. Progress lines come about every 10 s, so the stop lands 10 to 20 s into the tail. The driver gives the source up to M × 60 + 150 s from the soak's start to get there; drift moves scenario time ahead of wall time, never behind it, except while a scripted connect waits for the service.

After the exit the driver checks, before any check that reads the logs, that neither main's nor the service's `startup.jsonl` reached its budget of 256 KiB and 2,000 records (`LOG_BUDGET_REACHED`; a log within 8 KiB of its byte limit counts as reached, as in the log's rotation rule). Then:

- **Diagnostics.** One service process: `RECORDING_TARGET {purpose: synthetic}`, `HISTORY_STORAGE_OPENED` created, `ok` `recording-flush` and `history-storage` steps, one `HISTORY_STORAGE_CLOSED`, a clean stopped report, `APP_EXIT_REQUESTED` `app-quit`, and no durable, sample or failure event. - **Evidence, never gated** (ET-019 plan decision D3): per process kind, the first, minimum, maximum and last private bytes and working set, and the trend of private bytes after a warm-up of the larger of 5 minutes and 20% of the planned run: the least-squares slope in bytes per hour, r² and the means of four quarters, or `TOO_FEW_POINTS` with fewer than six points. **Budgets.** Each step budget is the local wall time on the implementer's machine x 3.0 x 1.5, rounded up to whole minutes, at least 3 minutes. 3.0 covers the measured hosted slowdowns: `protocol-fuzz.test.ts` took 16.46 s in the tests job of hosted `main` run [39214744965](https://github.com/senukartur/ets2telemetry/actions/runs/39214744965) against 7.42 s locally at the default size (2.2 times), and the slow hosted run [39174985694](https://github.com/senukartur/ets2telemetry/actions/runs/39174985694) slowed single storage files 2.8–3.0 times against the green run 39174886200 (`journal-scale` 98.2 against 34.4 s, `events-commit` 58.1 against 20.6 s, `producer-loss` 42.2 against 13.9 s; [storage suite headroom](validation/et-019.md#storage-suite-headroom-on-slow-hosted-runners-october-19-2026)). `trip-recorder-crash.test.ts` took 12.2 s locally in PR-1 and 25.7 s and 41.5 s on those two hosted runs, 2.1 and 3.4 times, also within 4.5. 1.5 is headroom. At the factor 3.0 the longest step, the frame decoders, would take about 12 minutes hosted. **Fuzz partition.** Vitest passes when a `-t` pattern matches nothing, so a renamed or added case would silently leave the campaign. Each JUnit file lists every case of the file, the unselected ones as skipped, and the step "Check the protocol fuzz partition" fails unless the three steps ran every case exactly once. Each case prints `fuzzMultiplier=` and its planned iteration counts before its first iteration, so a failing case's log names them. The seeds are unchanged. The extended job runs the executables directly, not through CTest: their CTest `TIMEOUT` properties (30 s for the snapshot transport, 60 s for the v1 cases) bound the x1 PR run, and the step budget bounds the x50 run. The CTest registrations and the AddressSanitizer job are unchanged and run at x1.

**Evidence.** `windows-extended-evidence-<run>-<attempt>`, kept 14 days and uploaded even after a failure, holds `.local/ci`: `extended-campaigns.json` (source commit, recovery seeds 1 to 200, 200,000 fuzz inputs per case with the default seed 20261019, multiplier 50, native seeds fixed in source), `vitest-recovery-extended.xml`, `vitest-fuzz-payloads.xml`, `vitest-fuzz-frames.xml`, `vitest-fuzz-brokers.xml`, `native-fuzz-v1-producer.log`, `native-fuzz-snapshot-transport.log`, `native-fuzz-v1-transport.log` and `versions.json`.

# Windows CI and regression infrastructure

ET-022 provides [Windows CI](../.github/workflows/windows-ci.yml) for pull requests, pushes to `main`, and manual dispatch. ET-024 limits automatic runs as described in [Triggers and draft checks](#triggers-and-draft-checks). Clean hosted execution and the deliberate failing-assertion/restoration sequence passed as recorded in [ET-022 validation](validation/et-022.md). The final current PR head still needs its own check/review association before owner merge. These runs do not establish branch protection or game compatibility.

The explicitly selected x64 `windows-2022` image uses Visual Studio 2022 with `Visual Studio 17 2022`, not the local Visual Studio 2026 generator. Image updates may change MSVC and SDK patch versions; each run records image identity and vendor versions. Node 24.19.0, npm 11.17.0, Electron 44.7.0 and Playwright 1.64.0 are pinned. CMake 4.3.1 is acquired explicitly before tool verification and configuration; the runner's CMake 3.31.6 does not satisfy the existing native minimum of 4.3. Action revisions are pinned to exact commits (checkout v5, setup-node v5, cache v4, upload-artifact v4). The [runner manifest](https://github.com/actions/runner-images/blob/main/images/windows/Windows2022-Readme.md) documents VS 2022 support.

`scripts/ci/Install-CMake.ps1` is restricted to GitHub Actions. It downloads the official [Kitware CMake 4.3.1 Windows x86_64 ZIP](https://github.com/Kitware/CMake/releases/download/v4.3.1/cmake-4.3.1-windows-x86_64.zip), verifies SHA256 `03a610be931546474e46a442d171ef10532f4fc847de9cf76b7a8065bbef6a23` before expansion, and checks `cmake version 4.3.1`. The [vendor checksum manifest](https://github.com/Kitware/CMake/releases/download/v4.3.1/cmake-4.3.1-SHA-256.txt) and GitHub release asset digest agree with that pin; the independently downloaded manifest SHA256 is `e101d7dacb65463f86fa1c04bf15181368f258f29a3dad4969de8f44ba6dcbd3`. Acquisition uses a fresh runner temporary directory and adds its `bin` to the current process PATH and `GITHUB_PATH`; no MSI/global installation or owner-host PATH change occurs. `.local/ci/cmake-toolchain.json` retains source, archive hash, observed version and executable path. The tool archive is not shared through dependency caches. The second hosted run passed all 122 tests, then exposed the runner's older CMake; that failed run remains part of the acceptance history rather than weakening the native requirement.

Every run installs the lockfile into a clean workspace, installs the separate lint lockfile and runs ESLint with zero allowed errors or warnings, runs PSScriptAnalyzer over tracked PowerShell files with zero allowed findings, runs typecheck and the full Node-safe Vitest corpus, builds desktop and native x64, runs CTest, executes a bounded development Electron smoke, makes the actual Forge/Squirrel artifact, inspects packaged bytes/native paths, and executes the packaged smoke from an unrelated working directory. A second job runs in parallel and builds and runs the native AddressSanitizer console tests; see [Job layout](#job-layout). Vitest never imports Electron or native SQLite. Lint (ET-023a) runs before the build for fast feedback; its toolchain, TypeScript 6 API rationale and rule exceptions are in [setup](setup.md#linting). The lint step measured 17-18 s on hosted runners; [ET-023a validation](validation/et-023a.md) records the controlled failure and restore runs. PowerShell script analysis (ET-023b) follows it; the hash-pinned module, Windows PowerShell 5.1 engine and rule exceptions are in [setup](setup.md#powershell-script-analysis). No test filtering or retries are enabled.

Caching is configured only for downloaded npm archives and Electron distributions. Before ET-024, every hosted run ended with `Path Validation Error: Path(s) specified in the action for caching do(es) not exist` and saved nothing: npm did not use `~\AppData\Local\npm-cache` on the runner, and Electron's installer ignores `ELECTRON_CACHE` (it reads `electron_config_cache`), so `.local/cache/electron` was never created. The job now sets `npm_config_cache` and `electron_config_cache` to `.local/cache/npm` and `.local/cache/electron` inside the workspace and caches exactly those paths. GitHub saves a cache only after a successful job, and a cache saved on `main` is visible to all PR branches, while a PR-branch cache is visible only to that PR. ET-024 measurements on dispatch runs [38167660898](https://github.com/senukartur/ets2telemetry/actions/runs/38167660898) (cold, saved ~212 MB in 4 s) and [38167962488](https://github.com/senukartur/ets2telemetry/actions/runs/38167962488) (cache hit, restored in 4 s) show `npm ci` taking 17 s cold and 14 s warm. The restore costs about what it saves, so the cache gives no measurable speedup; it is kept as protection against registry/CDN download failures, not as a time saving. The largest step is Forge make/inspection (68–108 s across these runs); whole-job time varied from 169 s to 236 s between runners for the same work. Keys include both lockfiles (root and `tools/lint`), Windows/x64, Node 24.19.0 ABI 137 and Electron 44.7.0 ABI 149. No `node_modules`, native build tree, SQLite binding compiled for another runtime, packaged artifact, profile or database is cached. This is deliberately stricter than [setup-node's default download caching](https://github.com/actions/setup-node/blob/main/docs/advanced-usage.md).

## Triggers and draft checks

| Event | Behavior |
| --- | --- |
| PR opened, updated or reopened while **draft** | Workflow run is created but both jobs are skipped (no runner minutes). A skipped job is not a passed check |
| PR marked **Ready for review**, or updated while ready | Both full jobs on the PR merge result |
| PR or `main` push changing only `**.md` or `docs/**` | No run at all; GitHub reports no check for that commit |
| Push to `main` touching anything else | Both full jobs; the scaffold job adds the extended regressions |
| Manual dispatch | Both full jobs on the selected branch head; the scaffold job adds the extended regressions unless `extended=false` |

Any change outside `**.md` and `docs/**` (code, tests, fixtures, scripts, workflow, `package*.json`, config) runs both full jobs. GitHub evaluates path filters against the whole PR diff, so a PR that later gains a code change runs normally. Documentation-only PRs rely on the focused document checks in [TESTING.md](../TESTING.md). If required status checks are ever enabled, a path-filtered workflow reports no check and would leave such PRs waiting.

To check a draft head without marking it ready, dispatch the workflow on the task branch:

```powershell
gh workflow run windows-ci.yml --ref <task-branch> -f extended=false
gh run list --workflow windows-ci.yml --branch <task-branch> --limit 1
```

A dispatch run checks the branch head itself, not the PR merge result with current `main`. GitHub attaches it to the head commit (visible in the commit's checks and the Actions list), but the PR check list keeps showing the skipped pull-request job for that commit, so record the dispatch run link in the PR or ledger. The final-head gate is therefore the pull-request run triggered by **Ready for review** (or a later push while ready). If that run fails, fix the branch or return the PR to draft (`gh pr ready <number> --undo`).

## Job layout

Since October 15, 2026 the workflow has two jobs. They start together on separate `windows-2022` runners with two logical processors each. Both use the same draft skip, triggers and path filter, and both belong to the workflow-level concurrency group, so a newer push to the same ref cancels both.

| Job ID and check name | Runs | Evidence artifact | Timeout |
| --- | --- | --- | --- |
| `windows`, **Windows x64 scaffold** | Pinned CMake, `npm ci`, ESLint, PSScriptAnalyzer, typecheck and the Node-safe Vitest corpus, the storage suite under Electron, `npm run build` with the Release client CTest, the Release plugin build and CTest, the CAP0 and protocol v1 chains, the v0 CLI smoke, the development and packaged runtime smokes, Forge make and package inspection, and the extended regressions on `main` pushes and on dispatch with `extended=true` | `windows-evidence-<run>-<attempt>`: `.local/ci`, package inspection, Release CTest diagnostics of both native trees | 20 min |
| `windows-asan`, **Windows x64 native AddressSanitizer** | Pinned CMake, then the unchanged steps "SDK-independent console AddressSanitizer checks" (plugin `build-asan` tree, `-R asan-contract`) and "Separate native client AddressSanitizer controls" (client `build-asan` tree, `-R '^native-pipe-client-asan-'`) | `windows-asan-evidence-<run>-<attempt>`: `.local/ci` of this job, ASan CTest diagnostics of both native trees | 20 min |

The AddressSanitizer job uses no output of the scaffold job. Both CMake trees build their targets from the checkout, including the uninstrumented `snapshot-transport-test-plugin` and `snapshot-transport-hooked-test-plugin` DLLs that the ASan DLL cases load, and the tests read their fixtures from `tests/fixtures`. The job installs no npm dependencies and restores no cache; pinned Node is set up only for `scripts/ci/versions.mjs`, which writes this job's own `versions.json`. The two ASan steps moved without changes: same commands, target lists, CTest selections and per-test deadlines, in the same order, with no filter or retry. Because the Release and ASan client suites now run on different machines, the endpoint-name collision described in [the ET-006a section](#et-006a-native-client-and-live-smoke-implementation-candidate) cannot occur between them.

A run passes only when both jobs pass. A cancelled or skipped job is not a passed check. If required status checks are enabled later, require both check names.

Before the split the single job ran out of time: hosted runs took 17.4 and 19.0 minutes, and the Ready run [38723874689](https://github.com/senukartur/ets2telemetry/actions/runs/38723874689) was cancelled at the 20-minute limit after every step had run. The two ASan steps took 399–476 s of those runs. Estimated from the measured step durations, the scaffold job now takes about 10.7–12.1 minutes and the AddressSanitizer job about 7.2–8.7 minutes (ASan steps plus about 30–45 s of checkout, Node, CMake and upload). These are estimates, not measured runs of the new layout; [the split record](validation/et-022-ci-split.md) holds the measurements.

Each job keeps the 20-minute timeout. For the scaffold job that leaves about 8 minutes (40%) above the slowest estimate for the steps that pending packages add, such as more storage and pipe smokes. For the AddressSanitizer job it leaves about 11 minutes; the plugin ASan selection grew from 114 s to about 150 s locally with ET-004b alone. When a job's measured duration passes about 15 minutes, split it again instead of raising its timeout. The next candidate is a third job for lint, PowerShell analysis, typecheck, the Node-safe suite and the storage suite, about 130 s of measured steps that need only `npm ci`. A separate packaged-smoke job would have to repeat `npm run build`, about 5 minutes with the native builds, and would save little. The split repeats about 35–45 s of setup per run, so a run uses roughly one more Windows runner minute in total, while wall-clock time falls to the longer of the two jobs.

## Bounded runtime checks

Run from the repository root on Windows with pinned Node on PATH, after `npm run build` / `npm run make` respectively:

```powershell
./scripts/ci/Invoke-RuntimeSmoke.ps1 -Mode development
./scripts/ci/Invoke-RuntimeSmoke.ps1 -Mode packaged
```

Each mode launches once under the existing Windows Job Object: 60 seconds maximum, 16 processes, 2 GiB committed memory, 25% system CPU and kill-on-close. The owner retains the Job until all descendants exit; a forced cleanup/timeout fails. Playwright launch keeps its 20-second deadline and normal close has 8 seconds. Release sandbox, context isolation, narrow frozen bridge and Node isolation remain enabled. [Playwright Electron support is experimental](https://playwright.dev/docs/api/class-electron); the prior ET-001 launch timeout remains unexplained and is not erased by later success.

Readiness proves Electron main → utilityProcess → storage worker → actual bundled better-sqlite3 N-API write, close, reopen, read. Successful close must report normal app/service exit, worker stop and removal of the temporary probe. This does not test production history, migrations or game telemetry. Paths for TEMP, profiles, APPDATA and LOCALAPPDATA are unique per mode/run; no real user history or game files are accepted. Development and packaged checks remain sequential inside the job to stay within desktop resource caps.

Evidence remains under `.local/ci/<mode>-<uuid>`: expected/actual assertions, candidate identity, Node/Electron/Playwright versions, bounded app/service/Job logs, screenshot and trace. Trace collection failure also fails the smoke. A launch failure can prevent trace creation; the Job stdout/stderr and failure metadata remain available. Abandoned synthetic files are retained for diagnosis rather than deleting evidence before upload. Hosted workspace disposal removes them; local users can remove their exact owned run directory after reviewing it. Test helper owners clean their own synthetic fixtures; `tests/unit/test-resources.test.ts` exercises parallel uniqueness and preservation of a second owner during cleanup.

Three diagnostics help explain a stalled launch. They are observations only: they change no deadline, retry, Job limit or pass condition.

- **Job CPU series.** The smoke wrapper calls `BoundedProcess.Run` with CPU sampling enabled, which writes `job/cpu.jsonl`. The first line records the wall-clock start, logical processor count and the 25% rate. Each following line, about every 100 ms, records cumulative Job CPU time, active Job processes and whole-system busy and idle time. `scripts/ci/job-cpu-summary.mjs` adds a per-second summary to `job-result.json` under `cpu`, in processors used (CPU ms per wall ms): `capProcessors` is the hard cap, 0.5 on a two-processor runner. A Job running at its cap during a stall points to starvation. A busy system with an idle Job points to outside load. Both idle points to a block inside the application. A missing or invalid series is recorded as `cpu.error` and does not fail the smoke. Other `BoundedProcess` callers are unchanged and write no series.
- **Main-process timeline.** Only when `ETS2TELEMETRY_DIAGNOSTIC_DIR` is set, which the smokes always do, main logs `DASHBOARD_WINDOW_CREATED`, `OVERLAY_WINDOW_CREATED`, `<DASHBOARD|OVERLAY>_LOAD_STARTED`, `<DASHBOARD|OVERLAY>_LOAD_FINISHED` with the renderer PID, and `CHILD_PROCESS_GONE` for any GPU or utility process. A 250 ms main-process timer logs `MAIN_EVENT_LOOP_LAG` with `gapMs` when it fires more than 1 s late. In Electron, main's event loop is also Chromium's browser UI thread, so the event is written only after a stall ends, at its end time, and `gapMs` gives its length. None of these names match the smoke's failure-event pattern. Default user logs contain none of them.
- **Driver phases.** `result.json` holds `phases`: wall and monotonic driver times for launch, tracing start, page discovery, dashboard readiness, journey completion or failure, tracing stop and close. If page discovery fails, `pagesAtRendererPagesFailure` lists the URLs Playwright had seen.

The wrapper also writes a distinct `wrapper-result.json`. A missing, malformed, failed or mismatched driver receipt fails even if the Job exits zero; a nonzero Job fails even when the driver reports success. The wrapper never overwrites driver evidence or invents worker/security/runtime observations after an early crash. Its receipt records actual Job exit, owned PID and log paths, observed Node version and pinned Playwright metadata; absent Electron runtime observations remain null. Inert `tests/unit/runtime-receipt.test.ts` protects these failure paths without launching Electron. ET-022's first local packaged launch timed out at the unchanged 20-second deadline with an unhandled Playwright promise rejection and no driver receipt; a separately recorded same-cap DEBUG diagnostic succeeded. That failure remains visible and is not a clean-pass claim or justification for retries.

Hosted smoke failures are compared in [the smoke failure record](validation/ci-smoke-window-stall.md). Dispatch run [38624116941](https://github.com/senukartur/ets2telemetry/actions/runs/38624116941) failed the development scaffold smoke because the Electron main process stopped dispatching for about 17.7 s right after creating its windows; Playwright saw no page within 10 s. Its cause is unknown: the Job records no CPU accounting and main records no event-loop timing, so CPU starvation under the 25% cap cannot be told apart from a native block. The Job CPU series, main-process timeline and driver phases described above were added afterwards to answer that on a recurrence; deadlines, retries and Job limits are unchanged.

CTest diagnostics from both build trees are uploaded. Since October 15, 2026 the ASan trees build and run in the separate `windows-asan` job and upload with its own artifact; see [Job layout](#job-layout). Local and current hosted outcomes belong in [ET-003 validation](validation/et-003.md); adding the workflow step alone is not a passed hosted check. Each job's timeout is 20 minutes; see [Job layout](#job-layout) for the per-job budget. The clean and restored hosted jobs of October 11, 2026, then a single job, measured 199 and 200 seconds respectively; feedback under 10 minutes remains a target for future runs. `versions.json` records elapsed time from toolchain verification through final collection. ## ET-006a native client and live smoke (implementation candidate)

The hosted AddressSanitizer job (`windows-asan` since October 15, 2026) also builds separate console AddressSanitizer client/fixture targets and runs the `native-pipe-client-asan-*` entries (`-R '^native-pipe-client-asan-'`) with the matching MSVC runtime on PATH. The client fixture is registered as one CTest entry per case: `native-pipe-client-<case>` in the ordinary build and `native-pipe-client-asan-<case>` in the ASan build. Each entry selects its case through `ETS2TELEMETRY_CLIENT_TEST_CASE`, and the entries share a resource lock because the fixture's endpoint names are fixed per user and session. The lock applies only within one `ctest` invocation, so do not run client suites concurrently: Release and ASan in parallel, or two worktrees at once, collide on the same endpoint names. Most cases finish well under a second. `quiet`, `quiet-exit`, `partial-prefix`, `partial-payload` and `v1-write-deadline` each wait out a fixed 5-5.5 s broker or fixture window. Each entry has its own hang backstop: 20 s, or 30 s for those five cases, doubled under ASan. The `*-case-list` entry fails if the registered names differ from the fixture's case list. Each case prints `case <name> ms=<n>` on stderr. The production broker remains uninstrumented. Local ASan controls failed during the recorded Avast scan interference investigation; a hosted result is a separate environment result and does not erase those failures. No antivirus exclusions are required or configured by this workflow.

The maintained client adds a fixed project-owned native broker for connected-pipe identity checks and bounded raw I/O. Ingestion, validation and subscriptions stay in the utilityProcess. The broker is built as part of npm run build using the documented CMake/MSVC toolchain. Its source-bound build receipt and executable are staged under ignored .local/package-native/telemetry-client and packaged as resources/telemetry-client; static inspection compares native bytes, x64 PE identity and source hashes. No generated binary is committed. See native-transport-boundary-v0.md and the feature validation record for final checks and pending real-game evidence.

Alongside the unchanged bounded scaffold probe, the candidate adds the following commands from the repository root:

```powershell
./scripts/ci/Invoke-RuntimeSmoke.ps1 -Mode development -Scenario telemetry
./scripts/ci/Invoke-RuntimeSmoke.ps1 -Mode packaged -Scenario telemetry
```

These use an explicitly isolated synthetic Windows pipe and the same 60-second/16-process/2-GiB/25%-CPU Windows Job Object limits with zero retries. The intended assertions exercise source-to-renderer speed/fuel, six-second renderer stall with changed values and subscription recovery, invalid source rejection, three renderer reloads, one deliberately terminated owned service followed by supervised reconnect/new ports, and stale readings after disconnect. The diagnostic main event is opt-in under isolated smoke configuration and is not a renderer command. The killed service's exact original temporary SQLite probe may remain as retained crash evidence; the replacement service must remove its normal-shutdown probe. Ordinary scaffold smokes still require zero remaining probes, unchanged SQLite 42/security assertions and normal shutdown. Actual outcomes must be recorded before acceptance; neither this planned harness nor synthetic telemetry establishes game support.

Since ET-010b the telemetry journey also checks the **Live telemetry** card. After the initial current observation, every element of the complete synthetic v0 field set (`SYNTHETIC_V0_LIVE_ROWS` in `scripts/ci/renderer-observation.mjs`) must exist once, be visible with a non-empty box and have its exact text, and no element of `SYNTHETIC_V0_HIDDEN_ROWS` may exist; card rows below the fold need no viewport intersection. Since ET-010c the telemetry scenario, and only it, also serves synthetic protocol v1 data from `scripts/ci/live-smoke-source-v1.mjs` through `ETS2TELEMETRY_SOURCE_PIPE_V1`: the shared `welcome-live`, `checkpoint-live` and `snapshot-live` fixtures with fresh identifiers, a new seq and SDK boundary every 50 ms on a monotonic capture clock, the v0 checkpoint's cargo and destination city ids set in memory, and the fixture's game window kept so the service must strip it. The card must show the combined rows `SYNTHETIC_V0V1_LIVE_ROWS` (v0 rows, v1's names for the same job, the v1 rows and the Protocol v1 source section) with `SYNTHETIC_V0V1_HIDDEN_ROWS` absent, and the hidden overlay document the v1 sections of `SYNTHETIC_V1_OVERLAY_CURRENT` (read from `overlay-origin`, `overlay-distance-remaining`, `overlay-deadline`, `overlay-cargo`, `overlay-cargo-detail`, `overlay-destination`, `overlay-speed` and `overlay-root`'s `data-freshness`, without a geometry predicate). While the v0 source is held, the v0 values must be not current while the v1 rows stay current (`v1CurrentWhileV0Stale`) and the overlay shows only dashes; while the v1 source is held, the v1 rows must read `unavailable` with `not current` beside a current speed line and the overlay's v1 sections must be dashes. Neither hold may reconnect its source. After the service restart both sources reconnect (two connections each), and after both final stops the v1 rows and overlay sections are not current. For review only, never asserted, `overlayOverflow` records which strip sections lie outside the overlay root and which values are cut off inside their box. Since the merge of ET-012c the journey **asserts**, with ET-012c's `stripLayoutObservation` and `verifyStripLayout`, that all twelve strip sections the v1 pair shows (`SYNTHETIC_V1_STRIP_SECTIONS`) lie inside the overlay window, before any resize. Since ET-012d it then **asserts**, with exactly those twelve sections saved, that they lie inside the card, HUD and cluster windows and within the height the row model reserves, recorded as `layoutContainment` ([layout containment step](#layout-containment-step-et-012d)). After that, for review only, `overlayLayoutOverflow` records the strip at scale 2 (`strip@2`, twice the window size the product created, `overlayWindowSize`, with a document zoom of 2): the journey saves the strip through the dashboard bridge, sets the hidden overlay window to that size (the controller never places it without a game window), measures it and restores the strip at the size the product created. Its wait is bounded at 3 s and the restore has its own 10 s bound. The scale-2 strip is twice the product's window width (2048 DIP or more), which a narrower screen cannot hold: Windows clamps the window, so on the hosted runner's 1024 px screen that review-only wait is expected to time out and is recorded as `error`. The measured results never fail the run, but every layout and sections save in these steps is a real settings write in the isolated profile: a failed write logs `SETTINGS_WRITE_FAILED`, which the diagnostic postcondition rejects, so a settings write failure fails the telemetry smoke as a product failure. Until ET-012d the card (300 × 360), HUD (320 × 320) and cluster (440 × 220) were also measured for review only, at their nominal sizes ([ET-010 validation](validation/et-010.md#merge-of-et-012c-and-remeasurement)). The `result.json` fields `v1Fields`, `overlayV1`, `overlayOverflow`, `overlayLayoutOverflow`, `layoutContainment`, `v1CurrentWhileV0Stale`, `v1Stale`, `v1StaleRecovered`, `sourceV1`, `v1DisconnectedHidden` and `sourceV1CloseFailure` are additive; `liveFields` now holds the combined rows. The overlay and lifecycle scenarios, the receipt rules, deadlines, retries and Job limits are unchanged.

The third reload, `renderer-reload-delayed-commit`, holds the replacement document's navigation request for 2 s through a Playwright route. The replaced document's 250 ms re-subscribe therefore always reaches main before the commit. The step requires current values and exactly one new `DASHBOARD_PRECOMMIT_SUBSCRIPTION_RETIRED` main event for that reload. Without it, a late commit on the CPU-capped hosted runner left the dashboard without a subscription and failed intermittently with `page.waitForFunction: Timeout 10000ms exceeded` after the second reload. ## ET-008 hidden overlay projection checks (implementation candidate)

The original development/packaged scaffold and telemetry recovery journeys remain separate. ET-008 adds two sequential bounded journeys, after the corresponding build/make:

```powershell
./scripts/ci/Invoke-RuntimeSmoke.ps1 -Mode development -Scenario overlay
./scripts/ci/Invoke-RuntimeSmoke.ps1 -Mode packaged -Scenario overlay
```

### Layout containment step (ET-012d)

The telemetry scenario, with its v0 and v1 sources current, asserts the card, HUD and cluster right after its strip assertion (decisions K10 and K11; [minimal overlay](minimal-overlay.md#fixed-rows-et-012d)). The overlay scenario keeps only the strip assertion. The driver first saves, through the dashboard bridge, exactly the twelve sections the v0 and v1 pair shows (`SYNTHETIC_V1_STRIP_SECTIONS`: every section except range and distance driven), so no window reserves a row for a hidden section and the slack of two unused rows cannot hide space the row model does not count. Then, for each of `card`, `hud` and `cluster` in that order, it saves the layout and sets the hidden overlay window to `LAYOUT_SMOKE_WINDOWS` in `scripts/ci/overlay-observation.mjs`: 300 × 360, 320 × 320 and 440 × 225 DIP at zoom 1. That is the size the product creates for those sections at scale 1: the card and HUD at their nominal floor, the cluster at its exact reserve. Without a game window the controller never places the overlay, so the driver sizes it. A unit test ties these hand-written sizes to `overlayWindowSize(layout, 1, sections)`, and the reserved CSS heights `LAYOUT_SMOKE_RESERVED_CSS` (card 48 + 24 × 12 = 336, cluster 36 + 21 × 9 = 225, HUD 18 + 24 × 12 = 306) to `layoutReservedCss`. All three windows are smaller than the hosted runner's 1024 × 768 screen, so Windows does not narrow them. The driver waits (10 s) until the document reports that layout and a viewport within one DIP of the size. Then `layoutContainmentObservation` waits (10 s, 50 ms polling) until exactly one `overlay-root` has the layout's `data-layout` and `data-freshness="current"`, and its `overlay-section-*` ids equal `SYNTHETIC_V1_STRIP_SECTIONS`. For the cluster the DOM order (gauge, then panel) is also the canonical order.

The observation reads, in one pass:

- the viewport;
- `outside`: sections with an empty box, or not fully inside the root and every ancestor up to the root whose computed `overflow` is not `visible`, such as the card body, the HUD lines and the cluster's side panel;
- `clipped`: sections whose `.overlay-value` box is not vertically inside the section's fixed row;
- `bottom`: the lowest section bottom below the higher of two tops: the root's top and the top of the surface that holds the rows (the card body, the cluster's side panel or the HUD lines; the root alone for the cluster's gauge sections). The surface's top matters for the cluster. Its panel is bottom-aligned, so space the model does not count grows the panel upwards past the window's top while its lowest row keeps its place; measured from the root's top alone, the check could never fail for the cluster (review pass 2). The root's top matters for the top-aligned card and HUD: a margin on the card body or padding on the root pushes the surface and its rows down, and measured from the surface's top alone that would go unnoticed (review pass 3);
- `surfaces`: the box of each such surface relative to the root's top, and whether it lies inside the root;
- for review only, `truncated`: values that end in an ellipsis.

Every comparison allows 0.01 CSS px, because Chromium reports a box flush with its row's edge with float noise. A layout unit is 1/64 of a device pixel, so 0.01 CSS px is below one layout unit at display scaling up to 150 % and about 1/50 of a device pixel at 200 %; it never hides a visible overhang. The tolerance is not scaled by `devicePixelRatio`: the hosted runner and the local runs then apply the same rule, and no display scaling the overlay supports makes it visible.

`verifyLayoutContainment` fails the driver with:

- `Enabled overlay sections lie outside the overlay window` when `outside` is not empty;
- `Overlay section values are clipped by their rows` when `clipped` is not empty;
- `Exactly one overlay surface must hold the rows` unless the sections' rows sit in exactly one surface, and `The overlay surface lies outside the overlay window` when that surface is not inside the root;
- `Overlay sections extend below the height the row model reserves` when `bottom` exceeds the layout's reserved CSS height for the shown sections. In each layout, vertical space the model does not count above or between the rows, including space that pushes the surface down from the window's top, therefore fails even while every section stays inside the window, once it exceeds the reserve's trailing slack: the card's 10 px bottom padding and 1 px border, the cluster panel's 8 px and 1 px, and none for the HUD. For example, a 12 px taller card header, a 4 px taller HUD tag row, a 2 px top margin on every cluster panel row and a 20 px top margin on the card body all fail the smoke. Smaller additions within that slack, such as the description list's default margins (8 px after collapsing with the header's gap), are caught by the CSS contract in `overlay-rows.test.ts` instead. The contract requires `margin: 0` on the list and its values, no nonzero margin on any fixed row, tag row, the cluster panel, the HUD lines, the card body or the cluster body, and no padding on the overlay root or a layout root. Space below the lowest row, which pushes nothing out of the reserve, is not measured;
- `The overlay window must have the reserved size` unless each viewport dimension is the window's size or one DIP more (`getBounds` can round a window up by one DIP; the cluster's viewport is one DIP higher locally).

Each observation is stored in `result.telemetry.layoutContainment[layout]` before it is verified, so a failed receipt keeps it, together with the saved sections (`layoutContainment.sections`) and the window bounds the driver set (`layoutContainment.windows`). The strip and the original sections, all fourteen, are restored at the size the product created in every case, and the first error, a failed assertion or a failed restore, fails the run. The step writes the settings six times: the shown sections, the three layouts, the strip and the original sections. `RuntimeReceipt.ps1` does not validate the field; a failed step fails the driver and therefore the receipt. On the unfixed code the step failed with the cluster's `outside` = game time ([ET-012d validation](validation/et-012d.md)).

- **Simulator.** The built simulator CLI (`tools/telemetry-simulator/dist/cli.cjs serve-v1`) serves the corpus scenario `normal-delivery` reactively, with its transport replaced in memory by three durable connections at 0, 360 and 2,010 ms and with a `simulation.paused` appended at 2,100 ms. The proxy sits between the service and the simulator on its own synthetic test pipe. It refuses a hello that does not request durable delivery, which happens while storage is still opening (R10), so the simulator serves only the durable clients its script expects. A durable hello waits for its admission, one connection open at a time. Nothing is admitted until the journey asks, and connection 1 only after the dashboard shows current data, so the simulator's 1-second ACK waits do not overlap application startup.

  A hold is limited to 2 seconds, about half the service's 5-second handshake deadline (the time from opening a connection to its checkpoint). An older hold is destroyed by its timer, or refused when an admission reaches it late, and the admission is kept. The service reconnects on its backoff, and its fresh hello is admitted with about 3 seconds left for its checkpoint, less the time from the service's `open()` to its hello: the deadline starts at `open()`, the hold at the hello's arrival. Without the limit, an admission that landed just before the service's deadline would be consumed by a connection the service then closes, and the journey would fail.

  Like the scenario's `dropAfter:4`, the proxy delivers the first four ACKs of connection 1 and drops the fifth. Every ACK the proxy sees was written by the service only after its storage commit (E8), so ACKs are the in-run evidence of commits. The proxy records each event's time to the first ACK that covers it.

The proxy's per-connection record also keeps each hold's age at admission (`heldMs`) and every latency (`ackLatencyMs`), so a hosted run shows its margins against the simulator's 1-second ACK waits. A failed run waits at most 1 second for the simulator before terminating it (5 seconds after a passing journey), so `result.json` is still written inside the Job.

The scripted disconnects of connections 2 and 3 (2,000 and 3,000 ms) are short because the reactive server waits out each paced interval in real time, even after its client has left. Either the script or the journey's own exit may end them, with the same stored rows.

What this journey does not show:

- **Flush timing.** It cannot tell whether `recording-flush` waits for a commit in flight. No commit is in flight at the tray exit, and `StorageClient.close()` lets the command in flight finish anyway. A `recording-flush` that started `flush()` without awaiting it passed this journey; the unit flush case in `telemetry-service-v0.test.ts` covers the wait.
- **The R10 upgrade.** It does not exercise `durableAvailabilityChanged()`. A live-only connection made while storage is still opening is refused by the proxy rather than upgraded, and the next connection is durable from its hello. With a real producer, the plugin counts every event it observes during such a live-only window at each service start as `noDurableConsumer` loss and later delivers a gap for it. The window is therefore not lossless, and its length is only made visible here (`refusedLiveOnly`). The upgrade itself is covered by the unit cases in `v1-ingestion.test.ts` and `telemetry-service-v0.test.ts`.
- **Scope.** The source is synthetic and the tray is reached through the gated diagnostic action. Real games, the production broker's v1 path, history recording (still gated off), the OS tray icon and real disks are not involved.

## ET-005b protocol v1 simulator pipe smoke

ET-005b PR-2 adds the step **Isolated synthetic v1 CLI pipe smoke** right after the v0 simulator smoke. It runs `npm run smoke:v1 --workspace @ets2telemetry/telemetry-simulator`, which serves `tests/fixtures/simulator-v1/pipe-reconnect.json` twice on private `\\.\pipe\ETS2Telemetry-SYNTHETIC-TEST-v1-{pid}-{uuid}` endpoints at real-time pace, each time with its client in the same process. In lockstep mode the scenario's scripted client must leave the served transcript, every client byte and applied message and its in-memory ledger equal to the deterministic replay; no paced message may be written before its schedule (checked on the server's clock, which also anchors the pacing); the first measurable message gap must arrive no more than one second after its 50 ms schedule (client clock); consecutive state messages must carry capture times at least 50 ms apart; and the clock probe must be answered. In reactive mode an independent consumer with its own client instance IDs, ACK delays and clock probes must leave the events, gaps, checkpoints and `end` equal to the replay except the message seq, the snapshots equal in state and continuity, and its ledger equal to the replay's. The two runs take about three seconds. They write no file, open no database and use no game; Node pipes are not DACL or peer-authentication evidence. Inside the Vitest suite, `simulator-v1-pipe.test.ts` serves every corpus scenario unpaced in lockstep mode, which checks equality with the replay but no timing, and `simulator-v1-reactive.test.ts` runs eight scenarios reactively, paced and unpaced. See [the simulator v1 guide](simulator-v1.md#named-pipe-serving).

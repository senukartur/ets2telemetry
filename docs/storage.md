# Durable history storage

ET-013 adds the local history database: a SQLite file written through [better-sqlite3](https://github.com/WiseLibs/better-sqlite3) by one connection that the telemetry service's storage worker owns. This document describes the schema, the durability rules, migrations, backups, the storage API and the worker that runs it.

Status (October 15, 2026): PR-1 added the in-process storage core in [packages/storage](../packages/storage) and its tests. PR-2 runs it in the storage worker of the telemetry utilityProcess, opens the production database at service start ([below](#history-database-in-the-telemetry-service)) and measured its size ([disk budgets](#disk-budgets)). The desktop application stays on protocol v0, records nothing and sends no ACK; recording starts with ET-015a. ET-006b PR-1 adds a [durable sink](#durable-sink-for-protocol-v1-ingestion-et-006b) for protocol v1 ingestion that only tests use with temporary synthetic databases; production durable delivery stays off. See [ET-013 validation](validation/et-013.md) for the checks performed.

ET-016 PR-1 (October 16, 2026): the current schema is [version 2](#schema-version-2-et-016). Migration `0002-journal` adds trip fuel used, the trip close carrier, checkpoint job configurations and trips that open from a checkpoint; a new database is created at version 2, and an existing version 1 database, including an existing history database, is migrated after a verified backup the first time a version 2 build opens it.

ET-016 PR-2 (October 16, 2026): the storage worker serves bounded [journal reads](#journal-reads-et-016) (`journalTrips`, `journalTrip`, `journalEvents`, `journalIntervals`) for the [trip journal](journal.md). Nothing in the application calls them yet; the schema is unchanged and no index was added.

ET-016b PR-7 (October 17, 2026): [`openAttachedTrip`](#late-attach-trips-et-016b-pr-7) writes a checkpoint job configuration and the late-attach trip it opens (J9), keyed per session and checkpoint `nextEventSeq`; it changes no coverage. `TripRecord` reports where a trip's opening and job came from. ET-015a PR-3 (October 16, 2026): the service's database is chosen by the [recording gate](telemetry-service-v1.md#recording-gate-et-015a). By default it is still the history database and nothing records. `ETS2TELEMETRY_RECORDING=synthetic:<name>` or `replay:<name>` opens a [synthetic or replay target](#history-database-in-the-telemetry-service) instead, and only that database receives trips and events from the trip recorder.

## Files and purposes

| Purpose | File | Accepted envelope origin |
| --- | --- | --- |
| `history` | `%LOCALAPPDATA%\ETS2Telemetry\data\telemetry.sqlite`, backups in `%LOCALAPPDATA%\ETS2Telemetry\backups\` | `game` only |
| `synthetic` | `%LOCALAPPDATA%\ETS2Telemetry\synthetic\<name>.sqlite`, name `[a-z0-9-]{1,64}`, backups in `synthetic\backups\` | `synthetic` only |
| `replay` | same directory rules as `synthetic` | `replay` only |

The paths are resolved at runtime from `LOCALAPPDATA` (`dataPaths` in [paths.ts](../apps/desktop/src/paths.ts), which also names the `synthetic` directory); the application never falls back to TEMP or the working directory. Each database stamps its purpose in `database_info` when it is created, and a schema trigger refuses a plugin session whose origin differs from the one its purpose accepts. Synthetic and replay data therefore never enter history. A synthetic or replay database may not use the production history path at all. Tests use only temporary directories from `tests/shared/resources.ts`.

The database path must be absolute and normalized; `:memory:`, relative, drive-relative and `file:` paths are refused with `DATA_PATH_INVALID`. A missing parent directory is created; a file in its place is refused.

## Durability

SQLite terms used here:

- **WAL (write-ahead log)** is a journal mode in which a commit appends pages to a separate `-wal` file instead of rewriting the database in place; a *checkpoint* later copies them back. A crash leaves a "live" WAL whose committed transactions SQLite replays on the next open.
- **`synchronous`** controls how often SQLite asks Windows to flush data to disk. `FULL` (2) flushes the WAL on every commit, so a commit that returned survives power loss. `NORMAL` (1) can lose the last commits on power loss in WAL mode.
- **Locking mode `EXCLUSIVE`** keeps the database lock after the first transaction instead of releasing it. Set before the first WAL access, SQLite also keeps the WAL index in memory, so no `-shm` shared-memory file exists.

Every writer open, including reopen, the open after a migration and the open after a restore, runs the same sequence:

1. Validate the path (above).
2. If the file exists, inspect it without writing. When no `-wal` or `-journal` file exists, the 100-byte file header is authoritative: a foreign `application_id` or a newer `user_version` is refused without opening SQLite at all. Otherwise a read-only connection reads `application_id`, `user_version`, the user tables and `database_info.purpose`. A read-only connection to a WAL file can create a `-shm` (and an empty `-wal`) beside it; the inspection removes exactly the files it created. It never changes the database or an existing WAL.
3. Refuse a file of another application, or one without this application's schema but with user tables (`DATABASE_UNRECOGNIZED`), a newer schema (`SCHEMA_NEWER`), another purpose (`PURPOSE_MISMATCH`) and a locked file (`DATABASE_LOCKED`). An existing file without write access is `PERMISSION_DENIED`; SQLite would otherwise fall back to a read-only handle and fail later with a misleading I/O code.
4. Open read-write with a 2,000 ms busy timeout.
5. `PRAGMA locking_mode = EXCLUSIVE`, read back `exclusive`.
6. Re-read `application_id`, `user_version` and the user tables on this connection. In exclusive mode this first read takes the file lock and keeps it. Another process could have changed the file since step 2: a schema that became newer is refused with `SCHEMA_NEWER`, and any other change (a different version or id, or tables in a file inspected as new) with `DATABASE_UNRECOGNIZED`, before any write.
7. `PRAGMA journal_mode = WAL`, read back `wal`.
8. `PRAGMA synchronous = FULL`, read back `2`. This comes after WAL on purpose: better-sqlite3 13.0.3 compiles `SQLITE_DEFAULT_WAL_SYNCHRONOUS=1` (`node_modules/better-sqlite3/deps/defines.gypi`), so a WAL database reopened without this setting runs at `NORMAL`. A test proves that a plain connection to the same file reads `1`.
9. `PRAGMA foreign_keys = ON`, read back `1`.
10. `BEGIN IMMEDIATE; COMMIT` to take the write lock now, so a second writer fails at open rather than at its first write.
11. Read integers as BigInt (`defaultSafeIntegers`), so no integer is silently rounded.

Any mismatch closes the connection with `DURABILITY_UNVERIFIED`. Only a connection that passed every step carries the durability record `{journalMode: 'wal', synchronous: 'full', lockingMode: 'exclusive', foreignKeys: true}`, and every write asserts it. A commit result exists only after `COMMIT` returned on that connection.

**One writer (OD-8).** Exclusive locking makes the running application the only connection: a second application instance or an external SQLite tool gets `DATABASE_LOCKED` while it runs. Read the database with external tools only while the application is closed. A second-instance policy belongs to ET-011.

Not established: behavior on real power loss or an operating-system crash, a genuinely full volume, real ACL denial on roaming, redirected or OneDrive folders, antivirus or indexer locks on `-wal` files and renames, and directory durability. Windows offers no directory `fsync`; renames rely on NTFS metadata journaling.

## Schema version 1

The schema text is frozen in [schema-v1.ts](../packages/storage/src/sqlite/schema-v1.ts) and in the committed fixture. `PRAGMA application_id` is `1163154226` (the ASCII bytes `ETS2`) and `PRAGMA user_version` is the schema version. Every table is `STRICT`: SQLite refuses a value that cannot become its column's type, such as text in an INTEGER column.

| Table | Contents |
| --- | --- |
| `database_info` | One immutable row: database UUID, purpose, accepted origin, creation time and application version |
| `schema_migrations` | One row per applied version, with the pre-migration backup file name and SHA-256 when one was taken |
| `plugin_sessions` | One row per plugin session from its welcome: identity, protocol and SDK versions, capabilities, the welcome's game-mode evidence, committed coverage and end marker. Identity columns are immutable |
| `clocks` | Source monotonic and game clock UUIDs per session |
| `events` | One immutable row per durable event, `UNIQUE(plugin_session_id, event_seq)`; occurrence columns plus the canonical payload |
| `event_gaps` | One immutable row per gap marker range, `UNIQUE(plugin_session_ref, first_event_seq, last_event_seq)`, with the six loss causes |
| `job_configurations`, `truck_configurations`, `trailer_configurations` | Normalized configuration events: stable ids and localized names side by side, never invented trailer names |
| `event_amounts`, `job_deliveries` | Money of revenue, penalty, fine, toll, ferry and train events, and delivery details |
| `trips` | Project-generated trip UUID, game, game-mode evidence, configuration references, outcome, close reason, recording completeness and times |
| `trip_trailers`, `event_attributions`, `completeness_intervals` | Trip trailers, per-event trip attribution, and known missing or discontinuous intervals |
| `samples` | One-second samples with numeric session, trip and clock references |

Conventions (OD-3, OD-6, OD-7):

- **Exact 64-bit identifiers.** Wire uint64 values in sessions, events and gaps (`eventSeq`, monotonic nanoseconds, UTC milliseconds, revisions, boundary order, loss counts) are stored as 20-digit zero-padded decimal TEXT. That is exact, and text order equals numeric order, so range queries and the UNIQUE key work. Sample `monotonic_ns` is an INTEGER; a value above 2^63-1 is refused with `VALUE_OUT_OF_RANGE`, never truncated.
- **Exact money.** Money is the raw canonical decimal TEXT with its SDK type (`s64` or `u64`) and currency status, never a REAL. A `GLOB` check enforces the shape and the codec checks the range with BigInt; `-0` and leading zeros are refused.
- **Availability.** Each SDK attribute has a value column and a `_state` column (`available`, `not-observed`, `not-supported`, `invalid`); the value is present exactly when the state is `available`. Zero is a value, and a provided empty string is an available `''`. Samples keep one NULL per unavailable reading plus `not_supported_mask` and `invalid_mask` bits; a NULL without a bit is not observed. Commands accept only exactly `{available: true, value}` with a present value or `{available: false, reason}` with a known reason; any other shape is `INVALID_INPUT`, never a silent not-observed.
- **Floats.** SDK float32 values are stored as float64 REAL copies, which is exact. One exception: SQLite keeps integral REAL values in integer form, so negative zero reads back as zero. The canonical event payload keeps `-0`.
- **Raw payload.** Each event row keeps `payload_json`, canonical JSON (sorted keys, no whitespace) of the validated `{occurred, record}`, beside its normalized columns. A redelivered event compares by this text.
- **Time.** Real time (source monotonic nanoseconds with their clock, UTC milliseconds as labels) and game time (minutes with their game clock) are separate columns and are never mixed.
- **Reserved values.** Enumerations match protocol minor 0 and include values reserved for later minors, such as game mode `convoy`, so adding them needs no table rebuild.

Indexes: samples by session and by trip, attributions and completeness intervals by trip, completeness by session, and the UNIQUE keys. Schema version 2 adds no index ([below](#schema-version-2-et-016)).

## Schema version 2 (ET-016)

Migration `0002-journal` (decision J6 in [concept.md](../concept.md#et-016-authorization--october-16-2026), amended after the PR-1 review to rebuild `trips`) is frozen in [schema-v2.ts](../packages/storage/src/sqlite/schema-v2.ts): a version 2 database is the version 1 text followed by exactly these statements, and the committed fixture `schema-v2-representative.sqlite` must keep matching it. The file repeats the column helpers of version 1 instead of importing them, so a later change elsewhere cannot change its text. It rebuilds two tables with the SQLite [12-step procedure](https://www.sqlite.org/lang_altertable.html#otheralter): create `new_<table>`, copy every row with its id, drop the old table, rename the new one.

**Foreign keys during the migration.** On the upgrade path the framework applies `foreignKeysOff`: it turns foreign keys off outside the transaction, runs every pending step in one transaction, and runs `foreign_key_check` and `quick_check` before the commit. A new database is different: `openConnection` applies every migration in one transaction with foreign keys still on (`connection.ts`, the `inspection.fresh` branch). That is harmless, because every table is still empty when 0002 drops and renames them.

| Table | Change |
| --- | --- |
| `job_configurations` | Rebuilt. New columns `plugin_session_ref INTEGER NOT NULL REFERENCES plugin_sessions (id)`, `source TEXT NOT NULL` (`event` or `checkpoint`) and `checkpoint_next_event_seq` (a 20-digit key above zero); `event_ref` becomes nullable and stays UNIQUE. CHECKs tie `event` to exactly an `event_ref` and `checkpoint` to exactly a `checkpoint_next_event_seq`, and `UNIQUE (plugin_session_ref, checkpoint_next_event_seq)` keys a checkpoint job per session (S-2). Every version 1 row gets `source = 'event'` and the session of its event; the copy uses a LEFT JOIN, so a row without its event would fail NOT NULL instead of being dropped (the verified backup's `foreign_key_check` already refuses such a database) |
| `trips` | Rebuilt. `opened_event_ref` becomes nullable, and the new `opened_by TEXT NOT NULL` (`event` or `checkpoint`, no default) is tied to it: `CHECK ((opened_by = 'event' AND opened_event_ref IS NOT NULL) OR (opened_by = 'checkpoint' AND opened_event_ref IS NULL))`. A late-attach trip can therefore open from a checkpoint, even in a plugin session without any event (J9). Every version 1 row is copied with its id and `opened_by = 'event'` |
| `trips` | `fuel_used_l REAL CHECK (fuel_used_l IS NULL OR fuel_used_l >= 0)` with `fuel_used_l_state TEXT NOT NULL DEFAULT 'not-observed'`, which has the same state CHECK and value/state rule as every other availability column (S-1). Every existing trip is `not-observed`; zero is a value |
| `trips` | The close carrier `closed_by_session_ref INTEGER REFERENCES plugin_sessions (id)` and `closed_by_event_seq` (a 20-digit eventSeq key, 1 to 18,446,744,073,709,551,614). Both are NULL together, and both are NULL while the trip is open (CHECKs). Trips closed under version 1 keep NULL: their carrier was not recorded |

Every other `trips` column keeps its version 1 text, constraints and default (`game_mode_ambiguous DEFAULT 0`), and the three version 1 table CHECKs are kept; the new columns follow `updated_utc_ms` and the new table CHECKs follow the version 1 ones. Because the copy keeps every row id, `trip_trailers`, `event_attributions`, `completeness_intervals` and `samples` keep their rows, and their `REFERENCES trips (id)` and `REFERENCES job_configurations (id)` text is unchanged: it names the table, which the rename restores. No trigger or view references `trips` or `job_configurations`, so the rename breaks nothing; the purpose, origin and immutability triggers and every version 1 index keep their text. After the renames SQLite stores the rebuilt tables as `CREATE TABLE "job_configurations" (...)` and `CREATE TABLE "trips" (...)` with quoted names and lists them last in `sqlite_schema`; a new database has exactly the same text, because it runs the same statements. The rebuilds also leave the old tables' pages on the freelist of a new database; later writes reuse them.

**Writes.** `normalize()` writes `plugin_session_ref` (the committing session) and `source = 'event'` for every `job.configured` row, and `trip.open` writes `opened_by = 'event'`. `trip.close` records the close carrier in the same transaction (J7), from the item being committed and never from the reducer: the committing session and the event's eventSeq, or for a gap the first eventSeq it newly covers, `max(firstEventSeq, previouslyCoveredThrough + 1)`. A restart close that a later plugin session commits records that later session. Since ET-016b PR-6, `trip.update` sets fuel used (see Trip effects below), and checkpoint job configurations and checkpoint-opened trips are written only by [`openAttachedTrip`](#late-attach-trips-et-016b-pr-7) (ET-016b PR-7). Since PR-7, `TripRecord.openedEventSeq` and `jobConfigurationEventSeq` are nullable, and `openedBy`, `jobSource` and `checkpointJob` say where a trip's opening and job came from.

**Indexes.** No index is added beyond the implicit indexes of the rebuilt tables' UNIQUE constraints: `trips` keeps its `trip_uuid` UNIQUE index under the same name (`sqlite_autoindex_trips_1`), and `job_configurations` gains `sqlite_autoindex_job_configurations_2` for `UNIQUE (plugin_session_ref, checkpoint_next_event_seq)`. The journal queries of J5 are expected to use the primary keys, `events` UNIQUE(session, eventSeq), `event_attributions_trip`, `completeness_intervals_trip` and `samples_trip`; ET-016 PR-2 proves each with `EXPLAIN QUERY PLAN` before any journal read ships. **H6 sample index decision:** no UNIQUE (session, clock, second) index on `samples`. The `uniqueSeconds` guard of `appendSamples` already keeps one row per source second; the index would cost about 5.7 MB per 100 hours (the size of `samples_session`) and could fail the migration of an older synthetic database that holds duplicate seconds. This closes the H6 deferral.

ET-016 PR-2 proves the plan of every journal query with `EXPLAIN QUERY PLAN` under [journal reads](#journal-reads-et-016): no index is needed.

**Upgrade.** The first launch of a version 2 build migrates an existing version 1 database, including the owner's history database at `%LOCALAPPDATA%\ETS2Telemetry\data\telemetry.sqlite`, through the normal [migration path](#migrations-od-4): a verified pre-migration backup first, then the migration in one transaction, and `HISTORY_STORAGE_OPENED {schemaVersion: 2, created: false, migratedFrom: 1}`. A version 1 build refuses a version 2 database with `SCHEMA_NEWER`.

## Storage API

[packages/storage/src/index.ts](../packages/storage/src/index.ts) is the in-process API; it loads native SQLite. [api.ts](../packages/storage/src/api.ts) holds the Node-safe types. Every method returns `{ok: true, value}` or `{ok: false, error: {code, retryable, message, sqliteCode?, cause?, backupFileName?}}`. The message is fixed text per code; an error never contains a filesystem path or a SQLite message. There is no delete command for history entities, and the MVP never deletes history automatically.

| Command | Behavior |
| --- | --- |
| `openStorage(options)` | The durability sequence, then creation or migration |
| `upsertSession({message})` | Stores the session from a validated welcome. Repeating it changes nothing; a changed identity, version or capability is `SESSION_CONFLICT`. Later game-mode changes arrive as `source.gameMode` events and are kept beside the welcome's evidence |
| `commitEvent({message, effects?})`, `commitGap({message, effects?})` | Validates the message again with the protocol v1 schema and requires a stored session with the same identity. One `BEGIN IMMEDIATE` transaction inserts the row keyed UNIQUE(session, eventSeq or range), its normalized rows and the effects, and advances coverage. Returns `committed`, `duplicate` (same canonical payload; effects not applied again), `conflict` (different payload; the stored row is kept, protocol v1 §9) or, for a gap only, `covered` (its whole range is already inside committed coverage; nothing is stored and effects are not applied), with `committedThroughEventSeq`. Every gap result also carries `previouslyCoveredThrough`, the coverage before the transaction |
| `committedThrough(pluginSessionId)` | The contiguous committed coverage: the `committedThroughEventSeq` input of `DurableAckCursor` |
| `appendSamples(pluginSessionId, rows, options?)` | Up to 3,600 samples in one transaction: all of them or none. Returns `{appended, skipped}`. With `{uniqueSeconds: true}` (ET-015b, H6) the transaction keeps at most one row per plugin session, source clock and source second, where the source second is floor(`monotonicNs` / 10^9): it reads the session's latest stored row through the `samples_session` index (`ORDER BY id DESC LIMIT 1`, joined to its source clock), then skips each row whose second is at or below the last accepted second of its own clock, from that stored row or an earlier row of the batch. A row on another clock is accepted. Across commands only the latest stored row is read, so a row that returns to a clock after a row on another clock is not compared with that clock's older rows; a plugin session's capture clock is constant, so the producer never does this. Every row is still validated, including the trip reference of a row that is skipped, so an invalid row stores none of the batch. A skipped row writes nothing, not even its clock rows. Without the option every valid row is appended and `skipped` is 0. A retry of a batch that a failure rolled back, or a redelivery after a restart, therefore stores each second once |
| `recordCompleteness(pluginSessionId, interval, options?)` | A known missing interval outside an event commit. With `{ifAbsent: true}` (ET-015a) the insert is skipped when the session already holds an interval with the same trip reference, kind, first and last eventSeq and canonical detail; labels and monotonic bounds are not compared. Because labels are not compared, `ifAbsent` requires both `firstEventSeq` and `lastEventSeq` and is `INVALID_INPUT` without them: two distinct outages that differ only in their labels would otherwise look equal. It is meant for eventSeq-bounded intervals such as the R9 restore-loss interval. Every value is still validated, a skipped interval writes nothing (not even its clock row), and the result is the same either way. A recorded loss can therefore be recorded again after a service restart without a second row |
| `openAttachedTrip({pluginSessionId, nextEventSeq, job, effects})` | ET-016b PR-7 (J9): opens a trip from a checkpoint job; see [late-attach trips](#late-attach-trips-et-016b-pr-7). Returns `committed` or `duplicate`; never changes coverage |
| `listTrips({cursor?, limit?, game?, outcome?})` | Trips in creation order, at most 100 per page. The optional `game` (`ets2`, `ats`) and `outcome` (`open`, `delivered`, `cancelled`, `none`) filter (ET-015a) is applied in SQL before the limit, so a full page has a `nextCursor` whenever more matches may follow; an unknown value is `INVALID_INPUT`. The trips table is small (about one trip per hour of play), so the filter needs no index |
| `getSession`, `getEvent`, `listEvents` (≤ 500), `getTrip`, `listSamples` (≤ 3,600 per trip or session), `storageInfo` | Bounded reads |
| `journalTrips(query?)`, `journalTrip(tripUuid)`, `journalEvents(tripUuid, page)`, `journalIntervals(tripUuid, page)` | The [journal reads](#journal-reads-et-016) of ET-016: 50 trips per page newest first, one trip's detail, and pages of 100 or 500 timeline events or completeness intervals. Arguments are checked strictly; every response carries the database purpose and schema version |
| `restoreBackup(manifest, options)` | Restore into a new file (below) |

**Coverage.** `committed_through_event_seq` is advanced in the same transaction as the commit. A range that starts at or before coverage + 1 extends it, and stored events and gaps that continue from there are absorbed, so commits {1, 2, 4} give 2 and committing 3 later gives 4. A gap range may overlap committed events; those keep their rows (protocol v1 §9). A gap that lies wholly inside coverage, such as a merged gap record redelivered after an ACK inside it (stream `ack-inside-gap-record`), is `covered`: storing it again would count the same losses twice and reapply its effects. An ACK may be built only from this value after the transaction returned (protocol v1 §10).

**Overlapping gap rows.** A gap row may overlap other gap rows. The producer extends a retained gap record in place, so after an ACK inside it the record can be redelivered with a larger range that contains ranges already stored as separate rows (protocol v1 §9). Example: event 1, gap [2, 2] (`queueCount` 1) and gap [3, 4] (`encodingFailed` 2) are committed; the producer holds them as one record [2, 4]; an ACK of 3 falls inside it; offline events 5 and 6 extend it to [2, 6], which the next connection redelivers. Storage keeps all three rows and nothing is dropped; coverage becomes 6 and the result reports `previouslyCoveredThrough` 4. Rules:

- Each gap row keeps the six cause counts of its own message. Counts are per message, not additive across overlapping rows: summing them counts the prefix [2, 4] twice.
- The set of lost eventSeqs is the union of the gap row ranges minus the eventSeqs that have an event row. Never sum the range lengths of overlapping rows.
- To total losses by cause without double counting, walk the gap rows in commit order (`id`) and keep only the eventSeqs above everything already counted. When a row overlaps earlier rows, it is a grown producer record whose counts include those of the earlier rows it contains, so its causes for the new suffix are its counts minus the counts of the earlier gap rows inside its range: [2, 6] minus [2, 2] and [3, 4] gives `offline` 2 for [5, 6]. A row's counts describe its whole range; they do not say which eventSeq had which cause.
- **Caller rule for effects.** Effects supplied with a gap are applied once, when its row is first stored, and must cover only (`previouslyCoveredThrough`, `lastEventSeq`]. Read `committedThrough()` right before committing; the single writer keeps it unchanged until the commit, and the result's `previouslyCoveredThrough` confirms the value the transaction used.

**Trip effects (OD-9).** The domain (ET-014) computes typed effects; storage applies them in the same transaction, in order, only when the event or gap is inserted for the first time. At most 16 per commit: `trip.open` (at a job configuration event), `trip.update` (whitelisted fields), `trip.close` (delivered or cancelled only with the matching gameplay outcome event), `event.attribute` and `completeness.add`. References to configuration events are resolved inside the transaction, within the current plugin session. Every trip reference (`trip.update`, `trip.close`, `event.attribute`, `completeness.add` and a sample's `tripUuid`) must name a trip of the current session's game: an ATS session can never bind data to an ETS2 trip, or the reverse. A trip of an earlier plugin session of the same game stays referable, because ET-014 closes it with close reason `restart` from the new session. A closed trip accepts only `trip.update` of recording completeness, observed distance and fuel used, since a late gap can still downgrade its completeness; its game-mode evidence and configuration are fixed once it is closed. Any failure rolls back the event as well and returns an explicit error, never a commit result. ET-013 tests effects only with synthetic examples. An in-process `testHooks.beforeCommit` exists for tests and is never part of a worker message.

Since schema version 2 (ET-016 PR-1), `trip.close` also records the trip's [close carrier](#schema-version-2-et-016) in the same transaction.

The ET-014 reducer that computes these effects, and its caller contract for ET-015a, are described in [trips](trips.md). Its readings accounting persists observed distance with `trip.update observedDistanceM` and, since ET-016b PR-6 (S-1, J8), fuel used with `trip.update fuelUsedL`.

**Fuel used (ET-016b PR-6).** `trip.update` accepts `fuelUsedL`, an availability object in litres, on open and closed trips, with the same validation as `observedDistanceM`: exactly `{available: true, value}` with a finite value of at least zero, or exactly `{available: false, reason}` with a known reason. Anything else, including a negative value, is `INVALID_INPUT` and rolls back the commit. It writes `fuel_used_l` and `fuel_used_l_state`. `TripRecord.fuelUsedL` reads the pair back as an availability object, `not-observed` until the trip's first fuel update; zero is a value. The reducer never sends a negative value: it sends `invalid` for a negative total ([trips](trips.md#readings-accounting-t16-t17)). Cold-start seeds pass an available stored value as `TripSeed.fuelUsedL`.

### Late-attach trips (ET-016b PR-7)

`openAttachedTrip({pluginSessionId, nextEventSeq, job, effects})` stores the trip that a checkpoint job opens when the recorder attached after the job started (J9, [trips](trips.md#late-attach-trips-j9)). In one `BEGIN IMMEDIATE` transaction it:

1. checks the session (`UNKNOWN_SESSION`), `nextEventSeq` (a canonical uint64 of at least 1 and at most the session's committed coverage + 1, else `INVALID_INPUT`) and `job`, strictly against the protocol v1 `JobConfiguration` shape: exactly its fields, each a strict availability object, the wire unit on the measure and game-minute fields and on no other, and a value of its column's kind and range;
2. answers `duplicate` and writes nothing when the session already holds a checkpoint job at `nextEventSeq` (`UNIQUE (plugin_session_ref, checkpoint_next_event_seq)`), whatever the effects; a retry or a later service attaching at the same checkpoint therefore never stores a second trip;
3. otherwise inserts the job as a `checkpoint` configuration (`checkpoint_next_event_seq`, no `event_ref`) with the same columns a `job.configured` event writes, and applies the effects in order: optional queued lifecycle effects of earlier trips of the game (`trip.update`, a `trip.close` without an outcome, `completeness.add`), exactly one `trip.open` whose `jobConfiguration` is `this-event` (the job this command stores) with no truck or trailer reference (J22, TD-007), then only `completeness.add` intervals of that trip. The trip is stored with `opened_by = 'checkpoint'` and no `opened_event_ref`. A queued close records this session and `nextEventSeq` as its close carrier (J7). Any other effect is `INVALID_INPUT` and rolls everything back. Since PR-7 review round 1 the command also refuses, with `INVALID_INPUT`: a close of a trip of the same plugin session, whose carrier at `nextEventSeq` the journal would read as the next live event; a `trip.open` whose UUID is not the late-attach derivation of the session and `nextEventSeq` (computed with `node:crypto`, since storage does not import the reducer); and a `trip.open` while another trip of the game is still open after the queued closes.

The command commits no event or gap: coverage, the ACK cursor and `committedThrough()` are unchanged, and it is never acknowledged. `TripRecord` reads such a trip with `openedBy: 'checkpoint'`, `openedEventSeq: null`, `jobSource: 'checkpoint'`, `jobConfigurationEventSeq: null` and `checkpointJob: {nextEventSeq, values}`, the stored job in the protocol v1 shape, which cold-start seeds read for its job key. The worker accepts exactly the four input fields and answers exactly `{status}`; `tests/storage/late-attach.test.ts` covers the command, its validation, the duplicate and the worker boundary, and the [journal window](#journal-reads-et-016) of such a trip starts at `nextEventSeq`.

## Storage worker

The database runs on a Node.js worker thread of the telemetry utilityProcess, never in Electron main or a renderer:

```text
Electron main -> telemetry utilityProcess -> storage worker thread (storage-worker.cjs) -> one better-sqlite3 connection
```

[apps/desktop/src/storage-worker.ts](../apps/desktop/src/storage-worker.ts) has two modes. Started with `workerData {kind: 'storage'}`, it runs the host in [worker/host.ts](../packages/storage/src/worker/host.ts) on the in-process storage core; every other start is the unchanged ET-001 readiness probe (`{kind: 'probe', filename}`). It is the only desktop module that loads better-sqlite3.

The service talks to the worker through [StorageClient](../packages/storage/src/client.ts), which is Node-safe: it never loads native SQLite. The messages are defined in [worker/protocol.ts](../packages/storage/src/worker/protocol.ts): `{type: 'storage.request', id, command}` and `{type: 'storage.response', id, result}`, where `command` names one storage method (`open`, `upsertSession`, `commitEvent`, `commitGap`, `appendSamples`, `recordCompleteness`, `committedThrough`, the bounded reads, `storageInfo`, the four journal reads and `close`) and `result` is the method's Result. Open options cross the boundary as exactly `{path, purpose, backupsDirectory, appVersion}`; the host copies them field by field and forwards only the message and effects of a commit, so injected migrations, clocks and `testHooks` never reach the worker. The `listTrips` page, the `recordCompleteness` options and the `appendSamples` options (ET-015b) are checked strictly: only their listed fields with values of the right type are accepted (an unknown key, a game or outcome that is not listed, or a `uniqueSeconds` that is not a boolean refuses the request), and the client copies only those fields. A page or options value that is not an object is forwarded unchanged, so the parser refuses it and the caller gets an `INVALID_INPUT` result rather than an exception. A journal command (ET-016) must carry exactly its listed fields, each checked as the storage core checks it ([journal reads](#journal-reads-et-016)); the client copies its query or page field by field. A malformed request with an id is answered with `INVALID_INPUT`.

`serveStorage(port, testOptions?)` has one in-process seam for test entries (ET-015a, R13): `testOptions.commitOptions(command)` may return the in-process commit options, such as a `testHooks.beforeCommit` fault, for one `commitEvent`, `commitGap` or, since ET-015b (H16), `appendSamples` command; the hook runs inside the command's transaction, after its rows are written. It is set by code on the worker thread and never read from a message; the production `storage-worker.ts` passes nothing.

| Rule | Value |
| --- | --- |
| Commands in flight | One at a time, in order; request ids are monotonic positive integers |
| Queue | At most 64 commands behind the one in flight; the next is refused at once with retryable `STORAGE_BUSY` |
| Deadline per command | 10 s after it was sent; `open` 120 s, because it can include a verified backup and a migration |
| Missed deadline | The command gets retryable `TIMEOUT`, the worker is terminated and every queued and later command gets `WORKER_FAILED` |
| Worker error or unexpected exit | The command in flight and every queued command get `WORKER_FAILED`; later commands too |
| Malformed answer | An answer for another id, an unknown error code, a commit result without a canonical decimal `committedThroughEventSeq` and a known status, or an `appendSamples` result whose `appended` and `skipped` are not both non-negative safe integers fails the client the same way. A journal answer is the one exception (ET-016 review pass 1): see the journal answer rule below |
| Close | Queued commands get `STORAGE_CLOSED`, the command in flight finishes with its real result, then the worker closes the database (SQLite checkpoints the WAL) and its thread exits with code 0. `StorageClient.close(graceMs?)` accepts an optional `graceMs` argument (ET-038) overriding the default `closeGraceMs`. When the close grace runs out, the client first lets one more event-loop turn deliver a close answer and exit that had already arrived (a stalled service thread runs its due timers before that I/O). Then the worker is terminated. A worker that had answered the close has closed its database, so the close is still clean; otherwise the command in flight gets `WORKER_FAILED` and the close is unclean. A termination cannot interrupt a running native SQLite call: the thread ends only when that call returns. Closing a client that had already failed (worker error or exit, missed deadline, malformed answer) only waits for the terminated thread and is never clean |

**Journal answer rule (ET-016 review pass 1).** Journal reads are off the commit and ACK path, so a journal answer that is well framed (a `storage.response` with the expected id and `{ok: true, value}`) but whose value breaks [the journal contract](../packages/contracts/src/journal.ts) or holds more rows than the request asked for does not fail the client. That one command resolves with the client-made error `{code: 'JOURNAL_ANSWER_INVALID', retryable: false}`, the `onJournalAnswerInvalid` option is called with the fixed fact `{command}` (the telemetry service logs it from ET-016 PR-3 on), and the client, the recorder and later commands keep running. `JOURNAL_ANSWER_INVALID` is not a storage error code: a worker cannot send it, and commits, the durable sink and the recording status never see it. Every other malformed frame, including a journal frame without a value, with an unknown error code or for another id, and every invalid answer to a non-journal command still fails the client closed.

**No success after a failure.** A worker failure, a missed deadline or a malformed answer fails the client closed. The command in flight may or may not have committed, so it is reported as `TIMEOUT` or `WORKER_FAILED`, never as a commit result, and an answer arriving later is ignored. A durable ACK may be built only from a commit result (protocol v1 §10), so a lost answer can delay an ACK but never advance one past stored coverage; after a restart the producer redelivers and storage answers `duplicate`. A storage error such as `DISK_FULL` is an ordinary result: the worker keeps serving and a retry can commit.

## History database in the telemetry service

OD-2: the telemetry service opens the production history database when it starts, without waiting for it ([history-storage.ts](../apps/desktop/src/history-storage.ts)). The ET-001 temporary probe stays the readiness gate, so live telemetry and the overlay never depend on the database.

- **Path.** `dataPaths(%LOCALAPPDATA%).database`, that is `%LOCALAPPDATA%\ETS2Telemetry\data\telemetry.sqlite`, with purpose `history` and backups in `%LOCALAPPDATA%\ETS2Telemetry\backups\`. A missing, empty, relative or drive-relative `LOCALAPPDATA` leaves history unavailable with `DATA_PATH_INVALID`; there is no TEMP or working-directory fallback.
- **Diagnostics.** The service log receives only fixed codes and numbers: `HISTORY_STORAGE_OPENED` with facts `{schemaVersion, created, migratedFrom}` (`migratedFrom` is `null` unless a migration ran), `HISTORY_STORAGE_UNAVAILABLE` with `{code}` at most once per service, `HISTORY_BACKUP_PARTIALS_REMOVED` with `{count}` after an open that removed stale partial backup files ([below](#backups-and-restore-od-5)), `HISTORY_STORAGE_REOPEN_EXHAUSTED` with `{attempts, code}` if retry attempts are exhausted, and `HISTORY_STORAGE_CLOSED` after an orderly close. A refused open ends the worker at once. When the open refusal is unrecoverable (for example `SCHEMA_NEWER`, `DATABASE_UNRECOGNIZED`, `PURPOSE_MISMATCH`, `DATA_PATH_INVALID`, `DATABASE_CORRUPT`, `DURABILITY_UNVERIFIED`, `MIGRATION_FAILED`, `PERMISSION_DENIED`, or `INTERNAL`), history stays unavailable until the service restarts. When the refusal is recoverable (ET-037: `DATABASE_LOCKED`, `DISK_FULL`, `IO_ERROR`, `STORAGE_BUSY`, `TIMEOUT`, or `BACKUP_FAILED` with a retryable cause), `HistoryStorage` automatically re-opens on bounded exponential backoff (`HISTORY_REOPEN_BACKOFF_MS = [250, 500, 1000, 2000, 4000]` ms, up to 60 attempts). Automatic re-open backoff applies specifically to open-time refusals (initial or re-open `client.open()` failure with a retryable error); runtime failures during active operation (worker crash, unhandled command timeout, or post-open worker failure via `onFailure`) transition directly to `unavailable` without automatic in-service re-open. While retrying, history remains `unavailable` and journal queries answer `DATABASE_UNAVAILABLE`. Once the recoverable cause is removed, the retry succeeds, logs `HISTORY_STORAGE_OPENED`, clears `failureCode`, and calls `onOpened` to resume durable delivery without an application restart. If retry attempts are exhausted without succeeding, `HISTORY_STORAGE_REOPEN_EXHAUSTED` is logged and history remains unavailable. Orderly shutdown cancels any pending retry timer and closes cleanly.
- **Recording target (ET-015a PR-3, R3).** With `ETS2TELEMETRY_RECORDING=synthetic:<name>` or `replay:<name>` (name `[a-z0-9-]{1,64}`), `HistoryStorage` opens `%LOCALAPPDATA%\ETS2Telemetry\synthetic\<name>.sqlite` with that purpose and backups in `%LOCALAPPDATA%\ETS2Telemetry\synthetic\backups\` **instead of** the history database, which it then neither opens nor creates. It logs `RECORDING_TARGET {purpose}` first and then the same codes and facts as above; history mode logs exactly what it logged before. The name is checked again before the path is built, so no value reaches the history file or leaves the synthetic directory (`DATA_PATH_INVALID`). An invalid variable is logged as `RECORDING_TARGET_REJECTED` and the history database opens as usual, with nothing recorded. The purpose trigger still refuses any foreign origin.
- **Client and readiness (ET-015a PR-3, R10).** `HistoryStorage.client` is the storage client only while the database is open (not while opening, after a refused open, after a worker failure or after close), and `onOpened` is called once after a successful open. The trip recorder reaches storage through `recorderClient`, which answers `STORAGE_CLOSED` while there is no client; the ingestion requests durable delivery only while the database is open and reconnects durable once it opens.
- **State for the recording status (ET-015c PR-3, G3, G7, G10).** `onStateChange` reports each change of `state`, and `failureCode` is the first code that made the database unavailable (the one `HISTORY_STORAGE_UNAVAILABLE` logs), null before any failure. An unavailable or closed database gives the [recording status](telemetry-service-v1.md#recording-status-et-015c) `stopped` with that code. For unrecoverable refusals, it remains stopped for the service lifetime. For retryable refusals (ET-037), `stopped <code>` is reported while waiting between retry attempts; once the database re-opens, `onOpened` notifies the ingestion, which reconnects with `durableEvents: true`, replaying unacknowledged events and transitioning recording status back to `recording`. **No `storage-unavailable` completeness interval is written** for such an outage, although the kind exists in the schema: while storage is unavailable nothing can be written, and once a later service records again the producer's gap causes (`noDurableConsumer`, `offline`, `retentionExpired`) carry the loss. The live status shows the outage while it happens.
- **Shutdown.** The step `history-storage` (nominal 1000 ms budget) runs in the `storage` phase of the [service shutdown sequence](app-lifecycle.md#service-shutdown), in parallel with `storage-probe`. It waits for a running open, closes the database and waits for the worker thread to end. 800 ms is the baseline grace when earlier phases consume their full budgets (within the nominal 1,000 ms step budget). In ET-038, adaptive stop grace cascades unused budget from earlier stop phases (prompt intake and flush phases, typically <50 ms) adaptively to history storage up to ~2,250 ms, expanding the step's effective budget up to ~2,450 ms (with a 200 ms termination reserve). After the grace, one event-loop turn delivers an answer that already arrived, and then the worker is terminated. The step fails, so the service reports `{type: 'stopped', clean: false}`, only when the worker had not answered the close; a worker that answered but whose thread was still ending is terminated and the step stays `ok` (October 18, 2026, [ET-013 validation](validation/et-013.md#history-close-grace-flake-october-18-2026)). The 200 ms reserve between the grace and the effective budget covers the termination of a thread that is not inside a native SQLite call; a close stalled inside SQLite ends as `timeout` at the budget, and every commit it reported is already durable in the WAL. The step budget's `timeout` verdict also waits one event-loop turn ([service shutdown](app-lifecycle.md#service-shutdown)), so after a service stall longer than the budget a close answer and exit that already arrived still make the step `ok`; if only the answer arrived, the step still times out while the thread is terminated. The step also fails when the worker had failed earlier in the session (a crash or a missed deadline), because the database was then not closed in order. Phase maxima were 1000 (intake) + 0 (flush) + 1000 (storage) = 2000 ms of the 2500 ms `SERVICE_STOP_BUDGET_MS`. ET-015a PR-3 adds the `recording-flush` step (500 ms) in the `flush` phase, which waits for the storage command in flight before the database closes: 1000 + 500 + 1000 = 2500 ms, the whole budget. ET-038 dynamically cascades the unused portion of this total 2500 ms budget to the storage phase while keeping the sequence inside main's 3000 ms kill deadline.
- **A failed probe** ends the service from its report, outside the orderly sequence (exit code 0 after the probe's own `stopped`, 1 after `SERVICE_STOP_FAILED`). The service first closes the history database, bounded by the same 1000 ms, and then exits with that code. After first readiness this close is best effort: the preceding `failed` report makes the supervisor kill the service at once, so the killed-service rule (WAL replay on the next open, no data loss) usually applies instead.
- **A killed service** does not close the database; SQLite replays committed WAL frames and discards the rest when the next service opens it. The exclusive lock ends with the process.
- **Second instance.** A second service process (which ET-011a's single-instance lock already prevents) would get `DATABASE_LOCKED`.

## Journal reads (ET-016)

ET-016 PR-2 adds four read commands for the [trip journal](journal.md) (J5). Each reads on the writer connection like every other read, through [sqlite/journal.ts](../packages/storage/src/sqlite/journal.ts); the shapes are [the journal contract](../packages/contracts/src/journal.ts). [Journal](journal.md#read-commands-and-bounds-j5) describes the fields, money totals and the timeline window in full.

| Command | Bound | Order and cursor |
| --- | --- | --- |
| `journalTrips({cursor?, game?, outcome?, completeness?})` | 50 trips; the page size is fixed and a `limit` is refused | Newest first: `id < cursor ORDER BY id DESC`; the cursor is the last row id, `^[1-9][0-9]{0,18}$`. The filters are in the `WHERE` clause, before the `LIMIT` |
| `journalTrip(tripUuid)` | One trip; its first 50 completeness intervals; its latest 10 trailer configurations with their total; at most 5,000 money amounts summed, beyond that `incomplete: true` | `UNKNOWN_TRIP` for an unknown trip |
| `journalEvents(tripUuid, {cursor?, limit})` | `limit` 100 or 500 | eventSeq order; the cursor is the last eventSeq, `^[1-9][0-9]{0,19}$` |
| `journalIntervals(tripUuid, {cursor?, limit})` | `limit` 100 or 500, with the trip's total | Insertion order; the cursor is the last interval id |

Samples reuse `listSamples` with `limit` 300 or 3,600, which its existing bound of 1 to 3,600 already allows.

**Window rule (J7).** The timeline lists events of the trip's own plugin session from the earlier of its opening event and its job configuration (event or checkpoint) up to its close carrier: through the closing event when an event of its own session closed it, before the first newly covered eventSeq when a gap closed it, to the end of its session when another plugin session closed it (restart), and without an end while it is open. A trip closed under schema version 1 has no carrier: `window.known` is `false`, and the timeline lists only the events of its session that are attributed to it or referenced by it. An event row at the carrier's eventSeq marks an event close; a gap that starts beyond coverage + 1 at an already stored event would be read as an event close, which the recorder's ordered FIFO never produces.

**No new index (J6).** Every statement is a constant of `JOURNAL_QUERIES`. `tests/storage/journal-scale.test.ts` writes 1,008 trips with 360,657 samples, then runs `EXPLAIN QUERY PLAN` on each statement through a read-only connection; each plan must contain the lines below and no `SCAN` of `events` or `samples` (by name or alias):

| --- | --- |
| Trip page | `SEARCH trips USING INTEGER PRIMARY KEY (rowid<?)` |
| Trip by UUID | `SEARCH trips USING INDEX sqlite_autoindex_trips_1 (trip_uuid=?)` |
| Job, session, event, truck, clock, sample label, database purpose | `SEARCH … USING INTEGER PRIMARY KEY (rowid=?)` |
| Event at the carrier | `SEARCH events USING COVERING INDEX sqlite_autoindex_events_1 (plugin_session_id=? AND event_seq=?)` |
| Trailers | `SEARCH x USING COVERING INDEX sqlite_autoindex_trip_trailers_1 (trip_ref=?)`, then the trailer configuration and event by primary key (the latest 10 in commit order, `ORDER BY e.id DESC`, because a trip can hold trailer configurations of a later plugin session whose eventSeqs start at 1 again); the total `SEARCH trip_trailers USING COVERING INDEX sqlite_autoindex_trip_trailers_1 (trip_ref=?)` |

## Durable sink for protocol v1 ingestion (ET-006b)

ET-006b PR-1 adds `StorageDurableSink` ([durable-sink.ts](../apps/desktop/src/durable-sink.ts)), the bridge from [protocol v1 ingestion](telemetry-service-v1.md) to this API: `openSession` is `upsertSession` with the validated welcome and returns `committedThroughEventSeq`, the `DurableAckCursor` input; `commit` is `commitEvent` or `commitGap`, without trip effects. ## Migrations (OD-4)

Migrations are forward-only and frozen once released: `MIGRATIONS = [{version: 1, name: '0001-initial'}, {version: 2, name: '0002-journal', foreignKeysOff: true}]` ([schema version 2](#schema-version-2-et-016)). Each step sets `user_version` and inserts its `schema_migrations` row. A table-rebuild step declares `foreignKeysOff`; on the upgrade path the framework turns foreign keys off outside the transaction and runs `foreign_key_check` before commit. A new database runs every step with foreign keys on, which is safe only because its tables are empty. Tests may inject migration lists only through the in-process API.

- A new or zero-length file (or an empty SQLite file: application id 0, no user tables and user version 0, as the inspection and the locked re-check both require) receives every migration in one transaction, without a backup, with foreign keys on.
- An existing database below the supported version is backed up and verified first (below), then every pending step runs in one `BEGIN IMMEDIATE` transaction that ends with `foreign_key_check` and `quick_check`. Any failure rolls back to the old version and content and returns `MIGRATION_FAILED` with the backup name. A backup failure migrates nothing. The file is not byte-identical afterwards, though: the writer open has already switched it to WAL (open sequence step 7), so header bytes, such as 18–19 (the WAL marker) and the change counter, can differ while every byte after the 100-byte header stays unchanged (ET-019 PR-6, `tests/storage/history-refusal.test.ts`).
- A newer database is refused with `SCHEMA_NEWER` at inspection, including a newer schema that exists only in a live WAL. There is no read-only fallback: an older application never reads or changes a newer schema.
- ET-001's isolated probe database lives in a temporary directory and is never migrated. An unrecognized file at the production path is refused with `DATABASE_UNRECOGNIZED` and never modified, moved or deleted.

## Backups and restore (OD-5)

The pre-migration backup is made with SQLite's online backup API (`db.backup()`), never a file copy: the writer connection copies pages under its exclusive lock, so the copy is consistent even with a live WAL. Steps:

1. Compute the source's logical digest: SHA-256 over the schema, the header versions and every row of every table in rowid order with type-tagged exact values, plus per-table row counts. A file in place of the backup directory is `BACKUP_FAILED` with cause `DATA_PATH_INVALID`.
2. Reuse an existing backup of exactly this content: a manifest with the same database UUID, source version, logical digest and row counts whose backup file still has the recorded size and SHA-256. A migration that fails the same way on every open therefore keeps one backup instead of a new full-size copy each time; a damaged backup is never reused. Otherwise require free space of at least (database + WAL) × 1.1, else `BACKUP_FAILED` with cause `DISK_FULL`.
3. Copy into `telemetry-<first 8 characters of the database UUID>-v<from version>-<UTC timestamp>.sqlite.partial`, then switch the copy to rollback-journal mode so it is one self-contained file.
4. Verify the copy read-only: `integrity_check`, `foreign_key_check`, `application_id`, `user_version`, database UUID, row counts and logical digest.
5. Flush it, write the manifest to `.json.partial` and flush it, rename the copy to `.sqlite`, then rename the manifest to `.json` last: `{format, databaseUuid, fromVersion, fileName, fileSha256, size, rowCounts, logicalDigest, createdUtcMs, appVersion, reason: 'pre-migration'}`.

Any failure removes the partial files. A writer that is terminated during the backup cannot do that, so every writer open of an existing database, once it holds the exclusive lock, removes that database's leftovers: regular files named `telemetry-<uuid8>-v<n>-<timestamp>.sqlite.partial` with `-journal`, `-wal` or `-shm`, `telemetry-<uuid8>-v<n>-<timestamp>.json.partial`, unmanifested orphan `.sqlite` backups of that database (with lingering sidecars) left when terminated between renames, and orphan manifests lacking a matching `.sqlite` backup. Existing backup pairs (where both `.sqlite` and `.json` exist), manifests of other databases, other databases' files and anything else are never touched; a removal that fails is retried at the next open. The open summary reports the number as `removedPartialBackups` (PR #60 review, ET-039). **Retention:** after the new backup is verified and its migration committed, the three newest verified pre-migration backups of that database are kept and older ones are deleted, the backup first and its manifest last. Files without a valid manifest of this application, backups of other databases and history rows are never touched. Budget backups at up to three times the database size.

**Kill points of an upgrade (ET-019 PR-2, October 18, 2026; ET-039).** `tests/storage/migration-crash.test.ts` terminates the opening process after the read-only inspection, after the backup copy and before its verification, after the backup rename to `.sqlite` and before its manifest is renamed (`afterBackupRename`, ET-039), inside the migration transaction after the 0002 statements ran, and after the open returned without a close ([tests](#tests)). A writer terminated at `afterBackupRename` leaves an unmanifested `.sqlite` backup and a `.json.partial` manifest; the next open's sweep removes both, preventing any disk leak, and the migration proceeds with a new verified backup.

**Restore** (`restoreBackup`) writes only to a new path. Before writing anything it checks the target path for the requested purpose (a synthetic or replay restore to the production history path is `DATA_PATH_INVALID`), refuses an existing target or any `-wal`, `-shm`, `-journal` or `.partial` file beside it, and checks the manifest, the file SHA-256, the logical digest and that the backup's `database_info.purpose` is the requested one (`PURPOSE_MISMATCH`). Only then does it create the target directory, copy through the backup API into `<target>.partial`, verify the copy, rename it and open it through the normal durability path, which migrates it when it is older. If that open fails, the restored file and its sidecars are removed again on a best-effort basis: a removal that fails (for example `EBUSY` from a scanner) is ignored, and the open's error is still returned as a result. In-place replacement of the live database is deferred: ET-018 did not take it on, and [TD-012](technical-debt.md#td-012-in-place-restore-of-the-history-database) records it. Open question for ET-015a: a restored database can hold less coverage than the producer has already acknowledged; ET-015a defines the `restore-loss` completeness marker.

## Tests

The storage suite loads native SQLite and runs only under the pinned Electron executable in Node mode, the runtime of the telemetry service: `npm run test:storage` first runs [build-storage-test-bundles.mjs](../scripts/build-storage-test-bundles.mjs), which bundles the storage worker entrypoint, the storage core and the client with Vite under plain Node into a new temporary directory, then starts [run-electron-node.mjs](../scripts/run-electron-node.mjs) with `ETS2TELEMETRY_STORAGE_TEST_BUNDLES` naming that directory; it runs Vitest inside `electron.exe` with `ELECTRON_RUN_AS_NODE=1` and removes the bundles afterwards. [vitest.storage.config.mts](../vitest.storage.config.mts) and `tests/storage/setup.ts` refuse any runtime other than Electron 44.7.0. The Node-safe suite (`npm test`) tests the codec, error mapping and retention policy without native SQLite. What enforces the split:

- **ESLint, statically.** Only `packages/storage/src/sqlite`, `apps/desktop/src/storage-worker.ts` and `tests/storage` may import `better-sqlite3`. The Node-safe set (`tests/unit`, `tests/shared`, every `apps/desktop/src` `.ts` module except the storage worker, and `packages/storage/src/{api,codec,errors,retention,client}.ts` and `worker/protocol.ts`) and the preloads and renderers may also not import the SQLite core, the in-process storage index that re-exports it, the storage worker host (`worker/host.ts`, which runs that index), or `tests/storage`. Relative names inside the package count too: `./index`, `../index`, `./sqlite/…`, `../sqlite/…`, `./host`, `./worker/host` and `../worker/host`, plus the bare directory specifiers `.`, `./`, `..` and `../`; only the storage worker entrypoint and the test-only fault storage worker in `tests/storage/fixtures` may import the host. In the Node-safe set, the preloads and the renderers, `no-restricted-syntax` also reports a dynamic `import()` or a `require()` of any of those modules or of `better-sqlite3` when the module name is a string literal or a template literal without expressions, any call whose first argument is the literal `'better-sqlite3'`, and any `createRequire` call. These selectors are built from the same regular expressions as the import restrictions, so the static and dynamic sets are identical. A computed module name, or a module outside these lists that loads SQLite and is then imported, is not detected statically.
- **Worker and process tests.** `tests/storage/worker.test.ts` drives the bundled worker in a real worker thread through `StorageClient`: open, commits with effects, reads, close with exit code 0 and no WAL left, reopen by a new worker, refused opens (`DATA_PATH_INVALID`, `SCHEMA_NEWER`, `DATABASE_UNRECOGNIZED`, `DATABASE_LOCKED`, `PERMISSION_DENIED`) and command errors as path-free results, and a terminated worker. Every real-worker `StorageClient` in the storage suite whose close is checked (in `worker.test.ts` and `v1-durable-ingestion.test.ts`) uses `TEST_CLOSE_GRACE_MS` (15 s) from `tests/storage/helpers.ts`. The longer grace bounds a hung close, and the suite asserts no close latency. The crash-test child processes keep the default grace, because they are killed and never close. `worker.test.ts` also runs a worker variant that holds the `close` request on the worker thread. With the test grace, a close held 500 ms past the 2 s production default ends clean with exit code 0. A client with the production grace reports that stall as `{clean: false}`. Grace expiry is covered by a close held past a 200 ms grace: the worker is terminated with exit code 1, the close is reported `{clean: false}`, and the reopened database keeps the committed event. A close that the worker finished while the client thread was blocked past a 200 ms grace, in a callback outside the worker's message port, is reported `{clean: true}`; the fake-timer cases in `tests/unit/storage-client.test.ts` and `tests/unit/history-storage.test.ts` cover the same verdict turn and a worker that answered the close but whose thread did not end. `tests/storage/crash-recovery.test.ts` runs [crash-child.cjs](../tests/storage/fixtures/crash-child.cjs) as a separate Electron process and ends it with `TerminateProcess`: inside a commit transaction (in-process `beforeCommit` hook), through the worker after `COMMIT` but before the ack line, and through the worker at five seeded acks. After each kill the database must pass `integrity_check` and `foreign_key_check`, coverage must equal the longest stored prefix and be at least every reported commit, every stored event must have exactly its attribution, every stored gap its completeness interval and every trip its open, close and completeness exactly when the causing rows are stored, and redelivering the whole stream must answer `duplicate` for stored items and complete the rest.
- **Killed open during backup and migration (ET-019 PR-2, ET-039).** `tests/storage/migration-crash.test.ts` runs the `migrate` mode of `crash-child.cjs` in process, because the worker never receives hooks or migration lists, on a copy of the version 1 fixture. The child reports a barrier and the test then ends it with `TerminateProcess`, never after a delay. The barriers are the `afterInspect` hook, the `afterCopy` hook (the `.sqlite.partial` copy exists), the `afterBackupRename` hook (the `.sqlite` copy was renamed, before the manifest is active), a wrapper around the real migration 0002 that blocks after its statements ran and before the runner records the step and commits, and the moment after the open returned, before any close. The 0002 case runs twice: once with the production page cache, where the small fixture's transaction left no WAL frame locally (observed, not asserted), and once with a one-page cache, so that uncommitted pages are on disk in the WAL when the process dies. Before any production open, a read-only connection must still see the unchanged version 1 database after the kill inside 0002. The next production open must reach version 2 with the hand-written version 1 to version 2 rows that `migrations.test.ts` checks (shared through `readVersion1` and `expectMigratedFromVersion1` in `helpers.ts`). The backups folder must hold exactly one verified backup with its manifest: the child's when it was complete, which is reused, otherwise a new one. No stale `.partial` or unmanifested orphan backup may remain, `removedPartialBackups` must count it, and `integrity_check` and `foreign_key_check` must pass.
- **Injected commit faults (ET-015a).** [fault-storage-worker.ts](../tests/storage/fixtures/fault-storage-worker.ts) is a test-only worker entry, bundled as `fault-storage-worker.cjs` beside the others; it is never part of the application. It runs the same host with the `commitOptions` seam above and a `testHooks.beforeCommit` hook inside the real `BEGIN IMMEDIATE` transaction of the commit whose event or gap range covers a configured eventSeq. Configured through `workerData`, it throws `SQLITE_FULL`, `SQLITE_READONLY` or `SQLITE_BUSY` for a configured number of attempts, so the core classifies the failure as `DISK_FULL`, `PERMISSION_DENIED` or `DATABASE_LOCKED` and the transaction rolls back the row with its trip effects. It can also hold that commit inside its transaction: it posts `{type: 'held', eventSeq}` on a control port and blocks the worker thread until `{type: 'release'}` arrives there. `worker.test.ts` checks that an injected `SQLITE_FULL` returns `DISK_FULL`, leaves neither the event row nor its trip close and attribution, keeps coverage, and that the retry commits once; that `SQLITE_READONLY` and `SQLITE_BUSY` are classified and store nothing; and that a held commit and the command queued behind it are answered only after the release. A real full volume is not used: it needs administrator rights, and a page-limited database makes the failing eventSeq depend on page fill (ET-013's `failures.test.ts` covers the real `SQLITE_FULL` mapping in-process). ET-015b adds `samplesFault`, the same hook for `appendSamples` commands: it throws one of the three codes inside the transaction of the first configured number of `appendSamples` commands that reach it, so the whole batch rolls back, or it holds the first `appendSamples` command inside its transaction, posting `{type: 'held', command: 'appendSamples'}` and waiting for `{type: 'release'}`. `worker.test.ts` checks that an injected `SQLITE_FULL` returns `DISK_FULL` and stores no row, that the retry appends the batch once and a second retry skips both seconds, and that a held batch and the read queued behind it are answered only after the release.
- **Cold-start reads (ET-015a).** `tests/storage/trip-recovery-reads.test.ts` checks through the real worker the `listTrips` filter (game, outcome, both, filtered paging, refused values), `recordCompleteness` with `ifAbsent` (repeats and a new worker add no row, each compared field makes a new one, an interval without both eventSeq bounds is refused, a skipped interval writes no clock row), and the seeds `readTripSeeds()` builds ([trip-seeds.ts](../apps/desktop/src/trip-seeds.ts)): the `jobKey` of every valid `job.configured` fixture of the protocol v1 manifest survives a commit and a seed read, and only open trips of the requested game are seeded, with the stored distance, the last usable label and a pending outcome after a clear.

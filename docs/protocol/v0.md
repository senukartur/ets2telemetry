# Prototype telemetry protocol 0.0

ET-002a defines an SDK-independent contract for current telemetry and optional copied diagnostics. The TypeScript implementation is [protocol-v0.ts](../../packages/contracts/src/protocol-v0.ts); the C++17 implementation is [protocol-v0.hpp](../../native/telemetry-plugin/src/protocol-v0.hpp) and [protocol-v0.cpp](../../native/telemetry-plugin/src/protocol-v0.cpp). Existing scaffold exports remain available. No SDK callbacks, actual pipe I/O, Electron ingestion, overlay, persistence, historical recording or game compatibility is implemented by this package. SP-01 remains unaccepted; the owner-authorized early start does not accept its failed ETS2 windowed appearance check or pending Convoy checks.

## Encoding and bounds

Every frame contains a four-byte **unsigned little-endian payload byte length**, followed by exactly that many bytes of UTF-8 JSON. Length must be 1–65,536 inclusive; the prefix is additional. There is no BOM, compression or trailing terminator. Whitespace permitted by JSON is allowed inside the payload, including after the JSON value. JSON object member order is immaterial. Duplicate member names, including duplicates spelled using escapes, are rejected at every nesting level. Arrays are ordered. Non-finite numbers, malformed numeric grammar, invalid UTF-8, overlong UTF-8, unpaired surrogate escapes, trailing non-whitespace bytes and nesting deeper than 16 are rejected. Root depth is zero; each child value increments depth. Decoders support arbitrary byte splits and multiple frames in one input chunk. They emit each complete message immediately; their callback must process or enqueue it within its own bounded policy.

A decoder retains at most one 65,536-byte payload plus a four-byte header and a bounded parsed representation. This is a bound on retained protocol state, not a claim that caller-supplied chunks or the parser's total allocation equal the payload size. Encoding validates the schema first, then enforces the payload byte limit. The native serializer checks its output budget before each append and validates caller-owned trees by reference before making a bounded valid copy. A callback exception closes the decoder. After malformed input, an invalid prefix, schema/version failure, or EOF with a partial header/payload, close the connection and discard the partial state. Do not scan for a new prefix or apply later frames in that stream. Clean EOF also closes the decoder; reconnection uses a new decoder and consumer. Already emitted valid earlier frames remain valid observations.

An emit callback may call `end()` after receiving its complete frame. This closes the decoder and stops processing the remaining bytes of that input chunk without emitting later frames or reporting an error for the intentional clean close. Recursive `push` calls from a callback are unsupported: they throw a protocol error and permanently close the decoder, even if the callback catches that error. Use each decoder on one ordered execution context; concurrent access is unsupported.

All object fields below are mandatory. Unknown JSON fields are rejected in 0.0. Optional information uses explicit availability, never omission or `null`. Text lengths are UTF-8 byte limits; text must contain valid Unicode scalars and no C0/DEL control characters. Identifiers/source labels are nonempty and at most 128 bytes; diagnostic unit labels are at most 32 bytes; copied diagnostic string values may be empty and are at most 1,024 bytes. UUIDs are lowercase canonical `8-4-4-4-12` hex strings; producers generate project-owned UUIDs rather than deriving them from game job identifiers. The validator checks UUID syntax, not entropy.

## Versions and handshake

`version` always equals `{"major":0,"minor":0}`. A client sends one `hello` before the server emits data:

```json
{"version":{"major":0,"minor":0},"kind":"hello","data":{"clientInstanceId":"00000000-0000-4000-8000-000000000001","minMinor":0,"maxMinor":0,"diagnostics":false}}
```

`maxMinor` is an integer 0–65,535; `minMinor` must be zero in this implementation. `negotiateV0` / native `negotiate` selects minor zero from this range; a wider offered range does not enable future fields. Other majors and other envelope minors fail closed. Future minor negotiation requires a revised implementation and compatible fixtures. `clientInstanceId` identifies one telemetry-service process lifetime. `diagnostics` is explicit opt-in; a server may decline it. The server sends `welcome` with `data: {diagnostics: boolean, durableRecording: false}`, then exactly one coherent `checkpoint` before any live snapshot or diagnostic. The welcome's diagnostics flag must not exceed the request. Source identity, clock identity and ordering are fixed for this connection. After an ordering error the consumer stays closed. A new connection requires a fresh hello/welcome/checkpoint cycle.

The pure helper and consumer implement schema selection and handshake ordering; transport owners must implement hello-once, handshake timeouts, client direction checks and welcome creation. Default intended handshake timeout is five real monotonic seconds, with one in-progress handshake and one active service client per endpoint; these transport limits are requirements for ET-004a, not tested pipe behavior here. A second service client is refused rather than displacing the active client. Lack of a handshake must never block a game callback.

## Source, ordering and time

Every server message (`welcome`, `checkpoint`, `snapshot`, `diagnostic`) contains:

| Field | Contract |
| --- | --- |
| `source.game` | `ets2` or `ats` |
| `source.pluginSessionId` | UUID for one plugin initialization lifetime; changes after plugin reinitialization |
| `source.processInstanceId` | UUID for the hosting game process lifetime; distinct from reusable OS PID |
| `source.processId` | Integer 1–4,294,967,295; validate against the actual pipe peer |
| `source.windowsSessionId` | Integer 0–4,294,967,295; Windows session, not game time or plugin session |
| `source.origin` | `game`, `synthetic` or `replay`; fixtures are never real history |
| `seq` | Canonical decimal-string uint64; session-local increasing outbound server message sequence |
| `capture.clockId` | UUID identifying one source monotonic clock origin/domain |
| `capture.monotonicNs` | Decimal-string uint64 elapsed real nanoseconds in that domain |

Decimal uint64 values use `0` or an unpadded sequence of digits up to `18446744073709551615`. JSON numbers, signs, whitespace, leading zeros and exponential spellings are rejected. TypeScript retains strings and uses `BigInt` only for arithmetic; native code materializes exact `std::uint64_t`. Never round an identity through a JavaScript number. OS window handles are decimal strings for the same reason, and are informational rather than trusted operating-system authority.

Assign `seq` before an outbound current-state update becomes eligible for coalescing. Include welcome/checkpoint/diagnostics in the same ordering domain. Coalescing can leave sequence skips; a skip alone is **not proof of lost gameplay data**. The receiver rejects duplicate/regressing sequence numbers, any source-identity change and regressing source capture time in the same clock. Equal capture timestamps are valid. At sequence exhaustion, end the session and initialize a new session; never wrap. Multiple consumers/reconnections require the producer to continue its session sequence, not restart it in place.

`withReceiveTime` adds a **local-only** receive wrapper containing `clockId`, `monotonicNs` and explicitly available/unavailable `utcUnixMs`. It is not a wire field. Source capture and receiver monotonic values have independent origins, even on the same machine. Subtract values only within a known clock domain. A future measured clock mapping with uncertainty is required for cross-process latency; this protocol does not invent one. UTC is unsigned milliseconds since Unix epoch and may jump; use it for labels, not elapsed durations. `state.captureUtcUnixMs` is optional source UTC at capture. `state.gameTime` is unsigned in-game minutes since the first game day, with its own `clockId`; rotate that ID when a save load or game-timer discontinuity is recognized. Game time can pause, jump or reset and must not be used as real-time sampling cadence. Recognition belongs to the adapter, not this schema validator.

## Availability and current state

A measure is either `{"available":true,"value":0,"unit":"L"}` or `{"available":false,"reason":"not-observed","unit":"L"}`. The unit remains mandatory when unavailable. The generic availability form has the same fields without `unit`. Reasons are `not-supported` (source cannot expose this field), `not-observed` (no valid current observation yet) and `invalid` (value could not be represented safely). Unavailable objects cannot carry `value`; available objects cannot carry `reason`. Zero is a real reading. On disconnect, ingestion must mark readings stale; an old checkpoint is not evidence of currently active simulation.

`checkpoint.data` has `boundarySeq`, `state`, `continuity`. `boundarySeq` must equal the envelope's `seq`; all current configuration/telemetry/status/window fields must be copied at one coherent producer boundary. `snapshot.data` has `state` and `continuity`. Both carry a full `CurrentState`, with:

| State field | Unit/type and permitted available value |
| --- | --- |
| `simulation` | `running`, `paused`, `unavailable` |
| `speed` | `m/s`, finite −1,000–1,000; negative means reverse |
| `fuel`, `fuelCapacity` | `L`, finite 0–1,000,000 |
| `engineRpm` | `rpm`, finite 0–100,000 |
| `gear` | `index`, integer −100–100; reverse negative, neutral zero |
| `odometer`, `estimatedRange` | `m`, finite 0–1,000,000,000,000 |
| `averageConsumption` | `L/100km`, finite 0–1,000,000; SDK-provided mean, not a trip-specific average |
| `gameTime` | Availability of uint64 string plus `unit: "min"`, `clockId: UUID` |
| `captureUtcUnixMs` | Availability of uint64 string |
| `configuration` | `revision: uint64`, `truckId: Available<string>`, `job: Available<Job>` |
| `window` | Availability of the window object described below |

Ranges are defensive representation bounds, not assertions that the actual game reaches those values. The adapter marks nonfinite/out-of-range readings `invalid`. The SDK-independent `normalizeSdkMeasurement` / `normalize_sdk_measurement` helpers implement the scalar mapping and preserve unavailable reasons and valid zero readings. Truck/cargo/city identifiers are source configuration identifiers, not project record UUIDs. Empty source identifiers map to unavailable; diagnostics can preserve an empty copied string separately. Increment configuration revision for current configuration changes; never use it as a durable event sequence.

`Job` contains `cargoId`, `destinationCityId`, `plannedDistance` (`m` measure, 0–1e12) and `expectedIncome`. No globally unique job ID is assumed. Expected income is `{rawValue, currency}`. `rawValue` preserves a decimal string with optional minus sign, up to 20 integer digits and up to six fractional digits. Real SCS income is copied from its exact u64 decimal form; this wider representation also permits synthetic/replay test values without rounding. It is not actual delivered revenue. Currency is either `{status:"unknown"}` or `{status:"verified",code:"EUR",source:"..."}` with a three-letter uppercase code and a nonempty source reference. Do not infer currency from the game name, UI locale or a display setting. A verified source must establish the units for that raw field. Currency conversion and display profiles are outside v0.

Available `window.value` contains `handle` (nonzero uint64 string), `x`, `y` (integer physical screen pixels −1e6–1e6), `width`, `height` (integer client-area physical pixels 0–100,000), `dpi` (integer 1–1,000), `foreground`, `minimized` (booleans) and `displayMode` (`windowed`, `borderless`, `exclusive`, `unknown`). Zero size is legal during transitions. Coordinates describe the client-area origin, not the decorated outer window. ET-007 must establish which window is owned by the verified game process and report unavailable when it cannot; renderer code must never use the wire handle for arbitrary access. Presence of `exclusive` reports a mode; it does not advertise exclusive-fullscreen overlay support.

## SDK mapping baseline

The following mappings were checked against headers in the official [SCS SDK 1.15 archive](https://download.eurotrucksimulator2.com/scs_sdk_1_15.zip), linked by the [SCS SDK page](https://modding.scssoft.com/wiki/Documentation/Engine/SDK/Telemetry). Archive version, telemetry API version and game version are separate identifiers. This package neither vendors the SDK nor proves any channel is available in a running game; ET-003 must pin the archive/API and verify callback availability.

| Wire field | Official SDK channel/config attribute | Mapping |
| --- | --- | --- |
| `speed` | `truck.speed`, float m/s | Copy; preserve reverse sign |
| `fuel` | `truck.fuel.amount`, float liters | Copy |
| `fuelCapacity` | Truck config `fuel.capacity`, float liters | Copy |
| `engineRpm` | `truck.engine.rpm`, float | Copy |
| `gear` | `truck.displayed.gear`, s32 | Copy displayed dashboard gear |
| `odometer` | `truck.odometer`, float km | Multiply by 1,000 |
| `estimatedRange` | `truck.fuel.range`, float km | Multiply by 1,000 |
| `averageConsumption` | `truck.fuel.consumption.average`, float L/km | Multiply by 100; preserve its SDK mean meaning |
| `gameTime` | `game.time`, u32 in-game minutes | Exact decimal string; no conversion to UTC |
| `plannedDistance` | Job config `planned_distance.km`, u32 simulated km excluding ferry distance | Multiply by 1,000; do not label as observed/delivered distance |
| `expectedIncome.rawValue` | Job config `income`, u64 internal game-specific currency | Exact decimal string; currency remains unknown until its source is verified |

SDK identifiers and localized data are retained as given when copied into diagnostics. Coordinates, if explored in diagnostics, remain game-world coordinates; no latitude/longitude conversion is defined. Channel capability, gameplay observation names and value availability require CAP-01 evidence before v1 design.

## Coalescing, checkpoints and copied diagnostics

`continuity` always contains three monotonic session counters, each a uint64 string: `coalescedSnapshots` counts newer current snapshots replacing unsent older snapshots; `lostObservations` counts unavailable diagnostic observations, including disabled/offline/drop cases when a source can count them; `offlineTransitions` counts known simulation/configuration transitions while no client was connected. These counters are distinct and cannot decrease within a connection. They count known omissions, not a reconstruction of unknown intervals. Initial unknown coverage remains unknown; a zero counter does not prove complete historical coverage. Source semantics and exact counting boundaries must be fixed by ET-003/ET-004a and CAP-01 before durable recording.

With no client, retain **only** one current configuration/state/snapshot and continuity counters, not historical samples, event payloads or a disk spool. With a client, the intended outbound policy is one replaceable unsent snapshot; welcome/checkpoint cannot be replaced. Keep at most one copied diagnostic batch (32 observations, one frame) ready for transport; count discarded copied observations explicitly, and never stall callbacks. Snapshot coalescing counts omitted current-state messages rather than assigning gameplay effects. The transport implements those slots; this package implements the contract/validators and consumers, not a producer queue.

On reconnect, take a coherent current-state checkpoint after welcome with its sequence boundary and current counters. Hydration replaces current state and reports known omissions; it must **not** deliver, cancel, accept or otherwise reapply gameplay effects. No historical events can be recovered from this current-state object. `AppliedState.hydration` identifies that boundary. `skippedSequences` is an exact arithmetic difference; use continuity to interpret it instead of classifying every skip as a lost event.

`diagnostic.data` is `{copied:true, observations:[...], continuity}` and is accepted only when enabled in welcome. At most 32 distinct channel identifiers are allowed per batch. Each observation contains `channel`, `sdkType`, `value: Available<scalar>` and `unit`. Supported copied types are `bool`, `s32` (integer signed 32-bit), `u32` (integer unsigned 32-bit), `u64` (decimal string), `float` (finite within ±3.4028234663852886e38), `double` (finite binary64) and `string`. Unit `raw` may identify a currently unknown/uncanonicalized diagnostic unit. These observations are values copied out of SDK callback context, never pointers to SDK-owned memory or calls from a transport thread. No offline retention, durable delivery, trip effects, persistence ACK, production-history write or capability to record is implied. The exact diagnostic payload shape is provisional for CAP-01 and must be replaced/reviewed before durable recording ships.

## Named-pipe integration requirements (ET-004a)

The **C++ plugin is the pipe server**; the Electron telemetry utilityProcess owns the client connection, ingestion and validation. Its fixed project-owned native broker performs connected-pipe identity queries and raw I/O under service supervision, as specified in the [native boundary contract](../native-transport-boundary-v0.md). This clarifies the operating-system authority boundary without changing wire messages or durable semantics. The intended local endpoint is:

```text
\\.\pipe\ETS2Telemetry-{game}-v0-{userTag}-{windowsSessionId}-{processInstanceId}
```

`userTag` is a lowercase fixed-length hash of the canonical current-user SID; it is a discovery discriminator, not authentication or a secret. ET-004a must fix/pin the hash format, keep the complete pipe name within the Windows limit, and implement per-user local discovery records under an owner-only directory. A record includes game, protocol major, user tag, Windows session ID, PID, process creation identity and process-instance UUID. Treat records/names and all claimed source fields as untrusted hints. Separate ETS2/ATS, protocol majors, user logons and simultaneous process lifetimes; do not choose a peer by PID alone or a broad first-match prefix.

Create the endpoint with an explicit protected current-user DACL, no Everyone/anonymous/network grants, non-inheritable handles, `PIPE_REJECT_REMOTE_CLIENTS`, and `FILE_FLAG_FIRST_PIPE_INSTANCE` for initial creation. Do not silently adopt a preexisting endpoint. On collision fail closed, report it and retire the owned discovery record; create a fresh process-instance endpoint only after independently verifying that identity rather than overwriting someone else's pipe. Limit one connected service client. Other users and remote clients must fail connection tests when actual I/O is implemented. See [CreateNamedPipe](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createnamedpipea).

Before accepting telemetry, the client obtains the server PID from the connected pipe, opens a constrained process handle, verifies process creation identity, token user and Windows session against the selected game/discovery identity, and verifies envelope PID/session/instance against those expectations. Retain a process handle/creation time to resist PID reuse and recheck on reconnection. The server similarly obtains/verifies the client PID, token user/session and the allowed installed/development telemetry-service executable provenance. Failed checks close the connection without state application. Executable-path checks alone do not prove authenticity against a compromised same-user process; the same-user local model is the boundary. See [GetNamedPipeServerProcessId](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid) and [GetNamedPipeClientProcessId](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeclientprocessid). This document specifies the security contract; ET-002a does not claim actual DACL, peer-authentication or collision tests.

## Deferred durable v1

Major 1 is incompatible and currently rejected. ET-002b follows CAP-01. Its separate `event_seq`, bounded retention count/bytes/age, connected accepted-but-unsent event retention, bounded disconnect behavior, offline-event loss, exit loss, persistence-commit ACK scope, redelivery, transactional deduplication `(plugin_session_id,event_seq)`, gaps and timeouts are **deferred, not implemented here**. Receiving a v0 message never acknowledges durable acceptance. V0 cannot advertise durable recording and contains no ACK or gameplay-effect event message. Replace/review this protocol before production trip history is enabled; do not infer v1 semantics from `seq`, configuration revision or copied diagnostics.

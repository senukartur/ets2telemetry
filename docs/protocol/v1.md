# Durable telemetry protocol 1.0

ET-002b defines protocol major 1: one separately negotiated contract that carries live current state, which replaces [protocol 0.0](v0.md), and a durable gameplay event stream with its own sequence, explicit gaps, bounded retention, a storage-commit acknowledgement and redelivery. The owner authorized ET-002b on October 14, 2026 as a contract-only package and accepted design decisions D1–D17 ([concept.md](../../concept.md#protocol-v1-decisions--october-14-2026)).

This document is the normative wire format. PR-1 adds this document, the TypeScript schemas and delivery helpers ([protocol-v1.ts](../../packages/contracts/src/protocol-v1.ts), [protocol-v1-delivery.ts](../../packages/contracts/src/protocol-v1-delivery.ts)) and the shared fixtures in [tests/fixtures/protocol-v1](../../tests/fixtures/protocol-v1). PR-2 adds the matching C++17 representation, which reads the same fixtures. Neither PR changes a runtime path. The plugin, broker, simulator and desktop service still speak v0. ET-004b adds the plugin's v1 endpoint, ET-005b the v1 simulator and ET-006b v1 ingestion. Durable storage belongs to ET-013/ET-015a. Nothing here establishes game, TruckersMP, display or performance support.

On October 14, 2026 the owner approved the ET-004b wording clarifications OD-5 S1–S11, marked "(OD-5 S*n*)" where they apply. They state how the plugin fills existing fields and change no wire shape, field or fixture. The producer's store rules are in [the native v1 transport](../native-transport-v1.md).

## 1. Terms

- **Producer**: the game plugin, which serves the pipe. **Consumer**: the Electron telemetry service, through the fixed native broker, which is the pipe client.
- **Message `seq`**: the outbound message order of one plugin session. It may skip values (coalescing) and is never an event identity.
- **`eventSeq`**: the durable event identity within one plugin session. Every observed event receives one, including events that are later lost.
- **Gap**: a message that states that the producer no longer holds a range of `eventSeq` values, with counted causes.
- **Durable consumer**: a client whose hello requested `durableEvents` and whose welcome granted it.
- **Commit**: the consumer's storage transaction for an event or gap marker (§10).

## 2. Staging, versions and coexistence

Major 1 has its own endpoint and discovery state, so the deployed v0 broker, which rejects any record with `protocolMajor` other than 0, is unaffected:

```text
\\.\pipe\ETS2Telemetry-{game}-v1-{userTag}-{windowsSessionId}-{processInstanceId}
%LOCALAPPDATA%\ETS2Telemetry\transport\v1\{processInstanceId}.json
%LOCALAPPDATA%\ETS2Telemetry\transport\v1\service-policy.json
```

Discovery records and the service policy use the [v0 schemas](../native-transport-v0.md#authentication-and-discovery-abi) unchanged, except that records carry `protocolMajor: 1`. The other naming rules (`userTag`, length limits, owner-only directory) are those of v0.

- `version` is always `{"major":1,"minor":0}` in this revision, on every message in both directions.
- A hello with another major, or with another envelope minor, closes the connection without an error frame, as in v0. The application shows "version incompatible" when discovery finds only records of other majors; it never infers that from a failed handshake.
- The v1 decoder rejects every v0 and CAP0 frame, and the v0 and CAP0 decoders reject every v1 frame. Shared fixtures prove both directions (§13).
- Sequencing (D2): during ET-004b and ET-006b the plugin serves v0 and v1 side by side. A v0-retirement PR lands before ET-015a enables recording; recording never ships on v0.
- v1 carries everything the application currently takes from v0, except the provisional v0 `diagnostic` kind. CAP0 replaced it as the evidence channel (D3), and a v1 `diagnostic` message is rejected.

## 3. Encoding and framing

The framing is that of v0 (D1): a four-byte unsigned little-endian payload length, then exactly that many bytes of UTF-8 JSON. There is no BOM, compression or terminator.

| Direction | Payload bytes |
| --- | --- |
| Server to client | 1–65,536 |
| Client to server | 1–4,096 |
| Any `event` message | at most 16,384, in addition to the server limit |

- JSON whitespace is allowed inside the payload, including after the value. Member order is immaterial.
- Rejected: duplicate member names at any depth, including duplicates spelled with escapes; invalid or overlong UTF-8; unpaired surrogates; non-finite or malformed numbers; trailing non-whitespace; nesting deeper than 16 (the root is depth 0); unknown or missing fields; `null` in place of an availability object.
- Decoders accept arbitrary byte splits and several frames per chunk, emit each message immediately and retain at most one payload of their direction's limit.
- Fail closed: after any error (prefix, UTF-8, JSON, schema, version, size, ordering) the connection is dead. Decoders never scan for a later prefix; a partial header or payload at EOF is an error; a callback may end the decoder, and recursive pushes close it.
- Encoders validate the message first, serialize it, then enforce the byte limits. Producers write strings as raw UTF-8 and escape only `"` and `\` (control characters are never valid text). Under that rule the worst-case checkpoint is 51,994 bytes and the worst-case event 6,305 bytes ([`checkpoint-worst.json`](../../tests/fixtures/protocol-v1/checkpoint-worst.json), [`event-worst.json`](../../tests/fixtures/protocol-v1/event-worst.json)); every text field there is at its byte limit and doubles under escaping. Decoders accept any valid JSON escape.
- The C++ encoder (`ets2telemetry::v1::encode_frame`) sorts members and writes JSON numbers with up to 17 significant digits, so its bytes can differ from the TypeScript encoder's. Agreement between the two sides is semantic: they give the same accept/reject result on every shared payload and stream, and each side's encoder output decodes back to the same message on that side. The C++ test re-proves the bounds under its own encoder; there the worst-case checkpoint, event and gap encode to 51,994, 6,305 and 854 bytes.

## 4. Handshake and capabilities

The client sends exactly one `hello` within 5 s of connecting (D8):

```json
{"version":{"major":1,"minor":0},"kind":"hello","data":{"clientInstanceId":"50000000-0000-4000-8000-000000000001","minMinor":0,"maxMinor":0,"durableEvents":true}}
```

- `clientInstanceId` is a UUID for one telemetry-service process lifetime. `minMinor` must be 0; `maxMinor` is 0–65,535. The server selects minor 0 (`negotiateV1`). A wider range does not enable future fields.
- `durableEvents` is the durable-consumer opt-in. A live-only v1 client (`false`) is allowed and must never send `ack`.
- One client per endpoint. A second client is refused rather than displacing the first. Lack of a hello never blocks a game callback.
- After its hello the client sends nothing until it has received the checkpoint. Afterwards it sends only `ack` and `clock.probe` (§10, §11) (OD-5 S6).

The server answers with `welcome`, then exactly one `checkpoint` before any snapshot, event, gap or clock reply. `end` may replace the checkpoint at shutdown.

| `welcome.data` field | Contract |
| --- | --- |
| `minor` | `0` |
| `durableEvents` | Granted durable delivery; never `true` when the hello requested `false` |
| `limits` | Exactly the constants in §9: `serverFrameBytes`, `clientFrameBytes`, `eventBytes`, `retainedEntries`, `retainedBytes`, `disconnectRetentionMs`, `helloTimeoutMs`, `writeDeadlineMs`, `snapshotIntervalMs`, `trailerSlots`. Any other value or key set rejects the welcome |
| `capabilities.gameplayEvents` | `registered` or `not-supported`: whether the SDK gameplay-event callback was registered |
| `capabilities.eventTypes` | Distinct record types this session can emit (§8). With `not-supported` it excludes the six gameplay types. A consumer rejects an event whose type is not listed |
| `versions` | `telemetryApi` and `gameTelemetry` as `{major, minor}` integers 0–65,535, and `sdkArchive` text (for example `scs-sdk-1.15`). Archive, API and game versions are distinct identifiers |
| `gameMode` | The session's game-mode evidence (§8) |

"Connected" for retention purposes (§9) means a client whose welcome granted `durableEvents`.

## 5. Envelopes, identity, sequences and time

Server message: `{version, kind, source, seq, capture, data}`. Client message: `{version, kind, data}`.

| Field | Contract |
| --- | --- |
| `kind` (server) | `welcome`, `checkpoint`, `snapshot`, `event`, `gap`, `clock.reply`, `end` |
| `kind` (client) | `hello`, `ack`, `clock.probe` |
| `source` | The v0 identity: `game` (`ets2`/`ats`), `pluginSessionId`, `processInstanceId` (UUIDs), `processId` (1–4,294,967,295), `windowsSessionId` (0–4,294,967,295), `origin` (`game`, `synthetic`, `replay`) |
| `seq` | uint64; strictly increasing per plugin session, continuing across connections; may skip; never wraps |
| `capture.clockId` | UUID of the source monotonic clock domain (QPC in the plugin) |
| `capture.monotonicNs` | uint64 nanoseconds in that domain; never decreases within a connection. The plugin stamps the time it encodes the message, unlike v0, whose capture time is the SDK observation. State freshness is `state.boundaryOrder`, not this field (OD-5 S7) |

Every uint64 on the wire is a canonical decimal string: `0` or digits without a leading zero, at most `18446744073709551615`. This covers `seq`, `eventSeq`, monotonic nanoseconds, game minutes, window handles, configuration revisions, boundary order, u64 money and loss counters. JSON numbers, signs, leading zeros and exponents are rejected. TypeScript keeps the strings and uses `BigInt` only for arithmetic; C++ materializes exact `std::uint64_t`.

Time domains are never mixed:

- **Real monotonic time** (`capture.monotonicNs`, `occurred.monotonicNs`, gap and retention times, clock replies) is the source clock named by `capture.clockId`. The consumer's clock has an independent origin; subtract across them only through a measured mapping (§11).
- **Game time** is u32 in-game minutes since the first game day, carried as `{minutes: Available<uint64 ≤ 4,294,967,295>, clockId}` with its own game clock UUID, which rotates when the adapter recognizes a game-time discontinuity. Game time can pause, jump and regress, and is never a real-time cadence.
- **UTC** (`captureUtcUnixMs`, `occurred.utcUnixMs`) is unsigned Unix milliseconds for labels only. It may jump. The plugin reads it with `GetSystemTimePreciseAsFileTime` (OD-5 S8).

A consumer rejects, within one connection: a source identity change, a capture clock change, a non-increasing `seq`, a decreasing `capture.monotonicNs`, and anything after `end`. Equal capture times are valid. A new connection needs a new hello, welcome and checkpoint.

## 7. Current state: checkpoint and snapshot

`checkpoint.data` is `{boundarySeq, state, status, continuity}`; `boundarySeq` equals the envelope `seq`. `snapshot.data` is `{state, status, continuity}`.

`state` keeps the v0 `CurrentState` fields in their v0 units (`simulation`, `speed`, `fuel`, `fuelCapacity`, `engineRpm`, `gear`, `odometer`, `averageConsumption`, `estimatedRange`, `gameTime`, `captureUtcUnixMs`, `window`) and adds (D17):

| Field | Contract |
| --- | --- |
| `navigationDistance` | `m` measure |
| `boundaryOrder` | uint64: the adapter's shared callback order, used to correlate state with events; never decreases within a connection |
| `worldPlacement` | `Available<{position: {x, y, z}, orientation: {heading, pitch, roll}}>` (§6) |
| `configuration` | `{revision: uint64, job: Available<Job>, truck: Available<Truck>, trailers: Available<Trailer>[]}`. The record shapes are those of the `*.configured` events without `type`. `trailers` has at most 10 entries; entry *i* describes slot *i* and an available trailer's `index` equals *i* |

`window` keeps the v0 structure: nonzero handle, physical client-area origin and size, `dpi`, `foreground`, `minimized` and `displayMode`.

`status` is `{gameMode, delivery, eventLoss}`:

| Field | Contract |
| --- | --- |
| `delivery.durable` | Equals the welcome's grant |
| `delivery.ackedThroughEventSeq` | uint64 *A*: the producer's release point in this plugin session. It equals the last cumulative ACK *T* the producer accepted, unless *T* falls inside a retained gap record, in which case it equals that record's `firstEventSeq` − 1 (§9). It never decreases and persists across connections |
| `delivery.nextEventSeq` | uint64 *N* ≥ 1, *A* < *N*: the next `eventSeq` the producer would assign. In the plugin this is the end of the coverage its event store holds; an event the SDK thread has observed but the transport worker has not yet stored is at or above *N* (OD-5 S11) |
| `delivery.retainedEvents`, `retainedBytes` | Retained entries (events and gap records) and their accounted bytes (§9): at most 256 and 1,048,576, both including the entry and bytes reserved for one trailing gap record; zero together; entries ≤ *N* − 1 − *A*. With 256 entries at least one is a gap record, so `retainedBytes` is at least 1,024 |
| `delivery.oldestRetainedMonotonicNs` | Available exactly when entries are retained; not after `capture`. The earliest retention time of a retained entry: the time the entry was admitted, or, for the gap record that retention expiry creates, the expiry time (OD-5 S2) |
| `eventLoss` | Cumulative per plugin session: `offline`, `noDurableConsumer`, `queueCount`, `queueBytes`, `retentionExpired`, `encodingFailed` (uint64 counts of lost `eventSeq` values) |

`continuity` is `{coalescedSnapshots, offlineTransitions}`. `offlineTransitions` counts the producer boundaries that occur while no v1 client is connected (OD-5 S10). The v0 `lostObservations` counter is dropped with diagnostics. Status counters, `nextEventSeq`, `ackedThroughEventSeq` and continuity counters never decrease within a connection, and a snapshot's `nextEventSeq` is never below the next `eventSeq` the connection's coverage requires (§9).

Rules:

- The checkpoint is copied at one coherent producer boundary, after the welcome and before any other data.
- **Hydration replaces current state only.** A consumer never derives a job start, delivery, cancellation or any other gameplay effect from checkpoint configuration (REG-003/REG-004). The TypeScript consumer reports it with `hydration: true` and no event coverage.
- Snapshot coalescing keeps one replaceable unsent snapshot and sends at most one per 50 ms (20 Hz). A `seq` skip alone is not lost gameplay data.
- With no client, the producer keeps only the current configuration and state, the continuity and loss counters and the delivery cursor. It keeps no samples, no offline event contents and no disk spool.

## 8. Durable events

One event per `event` frame (D15):

```json
{"eventSeq":"1","redelivered":false,
 "occurred":{"monotonicNs":{"available":true,"value":"1000149000000"},"gameTime":{"minutes":{"available":true,"value":"12345"},"clockId":"40000000-0000-4000-8000-000000000001"},
   "utcUnixMs":{"available":true,"value":"1791676800000"},"simulation":"running","configurationRevision":"8","boundaryOrder":"101"},
 "record":{"type":"job.cleared"}}
```

- `eventSeq` is 1 to 18,446,744,073,709,551,614. The upper bound keeps `nextEventSeq` representable as a uint64.
- `redelivered` is `true` when this event was already written to an earlier connection. It is never `true` at or after the checkpoint's `nextEventSeq`. An event or gap counts as written once the producer has issued its write, whether or not the client read it (OD-5 S9).
- `occurred.monotonicNs` is in the `capture.clockId` domain and not after `capture`. `occurred.gameTime`, `utcUnixMs` and `simulation` describe the callback moment; `configurationRevision` and `boundaryOrder` never decrease between events of one connection.
- `occurred.simulation` is the simulation state after the callback has been applied, so a `simulation.paused` event carries `paused` and a `simulation.started` event carries `running` (owner decision, October 15, 2026). This clarifies wording only. The occurrence values in the shared fixtures illustrate the shape, not this rule: `event-simulation-paused.json`, for example, carries `running`.

Record types in minor 0 (D4):

| `type` | Fields |
| --- | --- |
| `job.configured` | Each individually available: `sourceCityId`, `sourceCity`, `sourceCompanyId`, `sourceCompany`, `destinationCityId`, `destinationCity`, `destinationCompanyId`, `destinationCompany`, `cargoId`, `cargo`, `cargoMass` kg, `cargoUnitMass` kg, `cargoUnitCount`, `market`, `isSpecialJob`, `cargoLoaded`, `plannedDistance` m, `expectedIncome` money u64, `deliveryDeadline` absolute minutes |
| `job.cleared` | — |
| `truck.configured` | `brandId`, `brand`, `id`, `name`, `fuelCapacity` L, `licensePlate`, `plateCountryId`, `plateCountry` |
| `truck.cleared` | — |
| `trailer.configured` | `index` 0–9, `id`, `bodyType`, `chainType`, `cargoAccessoryId`, `brandId`, `brand`, `name`, `licensePlate`, `plateCountryId`, `plateCountry` |
| `trailer.cleared` | `index` 0–9 |
| `simulation.paused`, `simulation.started`, `timers.restart` | — |
| `gameTime.regression` | `from` and `to`, each `{minutes, clockId}`: the old and new game time and clock. The clocks differ, `to` precedes `from` when both are available, and the event's `occurred.gameTime` equals `to` |
| `job.delivered` | `revenue` money s64, `earnedXp` s32, `cargoDamage` fraction, `distance` m, `deliveryDuration` minutes, `autoParkUsed`, `autoLoadUsed` |
| `job.cancelled` | `penalty` money s64 |
| `player.fined` | `offence` (id text), `amount` money s64 |
| `player.tollgate.paid` | `amount` money s64 |
| `player.use.ferry`, `player.use.train` | `amount` money s64, `sourceId`, `sourceName`, `targetId`, `targetName` |
| `source.gameMode` | The game-mode fields below; emitted when the mode is first determined and on every change |

Every field other than `type` and `index` is an availability object; measures also carry their unit.

- **Bus and car jobs** (TD-002) have no v1 type. Producers do not emit them, and consumers reject unknown types such as `bus_job` or `car_job.delivered` rather than ignoring them.
- **Configuration granularity** (D13): one event per job or truck configuration callback, including identical re-sends. Trailer slots produce events only when non-empty, or on a clear that follows a non-empty slot.
- **Text** (D12): ids at most 128 UTF-8 bytes; localized display names (city, company, cargo, brand, model, plate, plate country, ferry/train endpoints) at most 256 bytes; no C0 or DEL characters; valid Unicode scalars. A value that violates a rule becomes `{"available":false,"reason":"invalid"}`; it is never truncated. A provided empty string is `{"available":true,"value":""}`, distinct from a value the game did not send (`not-observed`). This deliberately differs from v0, where an empty id became unavailable.
- **Money**: `{raw, sdkType, currency}`. `raw` is an exact decimal string, never a JSON number and never converted: `s64` within −9,223,372,036,854,775,808..9,223,372,036,854,775,807 (no `-0`), `u64` within 0..18,446,744,073,709,551,615. `sdkType` must match the field. `currency` is `{"status":"unknown"}` or `{"status":"sdk-documented","code":"EUR","source":"…"}` with an uppercase three-letter code and a nonempty `source` that names the pinned header reference (D11). SDK 1.15 documents Euro in `scssdk_telemetry_eut2.h` and US dollars in `scssdk_telemetry_ats.h`; runtime currency remains unobserved. Expected income is not revenue.
- **Game mode** (D9): `{mode: single-player | truckersmp | unknown, method: module-scan | process-scan | none, confidence: strong | weak | none, module: Available<id text>}`. Invariants: `unknown` pairs with method `none` and confidence `none`, and the other modes never use `none`; `single-player` is never `strong`, because a missing module is only weak evidence; `truckersmp` from `module-scan` carries the observed module name; `module` is available only with method `module-scan`, because no other method can name a module. `convoy` is reserved for a later minor and rejected in minor 0. The same object is in `welcome.gameMode` and `status.gameMode`.

## 9. Event sequencing, gaps, retention and bounds

`eventSeq` starts at 1 for each `pluginSessionId` and is assigned to every observed event, including events that are later lost (D5). It never wraps: after 18,446,744,073,709,551,614 the producer sends `end` with `sequence-exhausted` and retires the session.

**Coverage invariant.** For a plugin session with next sequence *N*, every `eventSeq` in [1, *N*) is exactly one `event` or lies inside exactly one `gap`. After a checkpoint with `ackedThroughEventSeq` *A* and `nextEventSeq` *N*, the first event or gap starts at *A* + 1, coverage is contiguous through *N* − 1 (retained entries, then live entries) and then continues live. Within one connection a duplicate or skipped `eventSeq` is a protocol error. Because nothing at or above *N* is assigned, a snapshot or `end` whose `nextEventSeq` is below one past the highest `eventSeq` already covered on the connection is also a protocol error. Across connections a duplicate is legal redelivery.

`gap.data` is `{firstEventSeq, lastEventSeq, causes, firstLostMonotonicNs, lastLostMonotonicNs, redelivered}`:

- `firstEventSeq` ≤ `lastEventSeq`, both within the `eventSeq` range;
- `causes` has the six `eventLoss` keys, and they sum to `lastEventSeq − firstEventSeq + 1`;
- `firstLostMonotonicNs` and `lastLostMonotonicNs` are availability objects in the source clock; neither is after `capture`, and when both are available the first is not after the last. They are the observation times of the first and last lost event (for a stored event, its `occurred.monotonicNs`); merging ranges keeps the earliest first and the latest last time (OD-5 S1);
- `redelivered` is `true` when any `eventSeq` in the range was already written to an earlier connection, as an event or as a gap;
- a gap is sent at its position in the stream and means "the producer no longer holds these". A storage row already committed for one of these `eventSeq` values keeps its committed event.

`end.data` is `{reason: plugin-shutdown | sequence-exhausted | source-retired, nextEventSeq, ackedThroughEventSeq, retainedUnacked}`, where `ackedThroughEventSeq` is the release point defined for status (§7), with `ackedThroughEventSeq` < `nextEventSeq` and `retainedUnacked` ≤ `nextEventSeq − 1 − ackedThroughEventSeq`. `retainedUnacked` counts retained events, not gap records (OD-5 S5). It is best effort at shutdown and the producer never waits for an ACK (D14). `end` is terminal for the connection; plugin exit loses retained unacknowledged events, and a new `pluginSessionId` restarts `eventSeq` at 1. A loss run that the plugin has not yet recorded in its store when it exits is part of that plugin-exit loss and gets no gap (OD-5 S11).

Bounds (D7):

| Limit | Value | Behavior |
| --- | --- | --- |
| Server frame | 65,536 bytes | Decoder rejects larger prefixes before allocating |
| Client frame | 4,096 bytes | Same |
| Encoded event | 16,384 bytes | An event that cannot be encoded within it becomes a gap with cause `encodingFailed` |
| Retained entries | 256 events and gap records, including one entry reserved for a trailing gap record | Newest-drop: a new event that does not fit becomes gap coverage (`queueCount`) |
| Retained bytes | 1,048,576, including 1,024 reserved for a trailing gap record; events count their encoded payload, measured once at admission with the worst-case envelope (OD-5 S3); a gap record always counts 1,024 | Newest-drop (`queueBytes`) |
| Disconnect retention | 300,000 ms of real monotonic time | Afterwards retained events become `retentionExpired` gap coverage; no age eviction while connected |
| Offline events | not retained | Become `offline` gaps (no client) or `noDurableConsumer` gaps (live-only client) |
| Hello timeout | 5,000 ms | Close |
| Write deadline | 1,000 ms per write | Close |
| Snapshot interval | 50 ms | At most 20 Hz; one replaceable unsent snapshot |
| Trailer slots | 10 | Indices 0–9 |
| JSON depth | 16 | Reject |
| Clock probes | one outstanding, at most one per second, 1 s reply deadline | §11 |

**Full store.** The retained store holds the unacknowledged entries that cover [*A* + 1, *N*) in order. Its last entry is "trailing". The producer keeps the store representable with these rules:

- A new event is retained only if, after adding it, the store still has one free entry and 1,024 free bytes (`GAP_RECORD_BYTES`), so events use at most 255 entries. Otherwise the event is lost with cause `queueCount` (no entry) or `queueBytes` (no bytes); when both apply, `queueCount` is counted.
- An event lost because the plugin's bounded handoff from the SDK thread to the transport worker is full also counts as `queueCount`. An event copied while a durable consumer was connected and stored after it disconnected is retained under the disconnect retention below (OD-5 S4).
- A lost `eventSeq` extends the trailing entry in place when that entry is a gap record, whatever the causes; the record keeps its 1,024 accounted bytes and its causes add up. Otherwise it creates a new gap record, which always fits in the reserved entry and bytes.
- While connected, the producer still writes a `gap` message for each newly lost range at its stream position. Extending a retained record does not rewrite messages already sent; a reconnection redelivers the merged record once.
- Gap records are never evicted by age. Only an ACK releases entries, events and gap records alike.
- An ACK never splits a retained entry. An ACK for *T* releases exactly the entries whose last `eventSeq` is ≤ *T*. A gap record with `firstEventSeq` ≤ *T* < `lastEventSeq` stays whole, with its causes and its 1,024 accounted bytes, so the release point is that record's `firstEventSeq` − 1 (§7, §10).
- When disconnect retention expires, every retained event is released and its `eventSeq` becomes `retentionExpired` coverage. Adjacent coverage merges into gap records in place, so expiry never adds entries; when every retained event expires, one gap record covers [*A* + 1, *N*).

The worst-case encoded gap message is 854 bytes ([`gap-worst.json`](../../tests/fixtures/protocol-v1/gap-worst.json)), within the 1,024 bytes accounted per gap record.

Redelivery happens only on a new connection; there is no in-connection retransmission or selective ACK. The welcome repeats these constants exactly, so a producer built with different bounds is rejected rather than half-trusted. Enforcement inside the producer (queue, newest-drop, retention clock, `end`) belongs to ET-004b; this package fixes the contract and its validators.

## 10. Acknowledgement and deduplication

The client sends `ack` with `{pluginSessionId, throughEventSeq}`. ACKs are cumulative only (D6).

**Normative ACK scope.** An ACK for *T* asserts that the consumer's durable storage committed every event with `eventSeq` ≤ *T*, and a gap marker for every lost `eventSeq` ≤ *T*, in the plugin session named by the ACK. The commit is a storage transaction that inserts rows keyed `UNIQUE(plugin_session_id, event_seq)` together with the event's effects. Receiving, parsing or validating an event is never grounds for an ACK.

- **Consumer rule.** On a connection whose checkpoint carried `ackedThroughEventSeq` *A*, the consumer sends *T* = min(*C*, *R*), where *C* is the highest contiguous committed `eventSeq` of the plugin session and *R* is the highest `eventSeq` covered by an event or gap received on this connection (*R* starts at *A*). It sends `ack` only when *T* exceeds the last ACK it sent on this connection, which also starts at *A* (`DurableAckCursor`). For example, commits {1, 2, 4} give *C* = 2. After a reconnection, a commit whose ACK was lost is acknowledged again once its range has been redelivered.
- **Producer rule.** The producer accepts *T* only when *A*′ ≤ *T* ≤ *S*, where *A*′ is the last ACK it accepted (initially *A*) and *S* is the highest `eventSeq` it sent on this connection (initially *A*). Because *R* ≤ *S* and the consumer never sends less than *A*, an ACK built by the consumer rule always satisfies the producer rule.
- A redelivered event whose `eventSeq` is already committed is a duplicate; the UNIQUE key makes its insert a no-op, and the cursor reports it as `duplicate`.
- The producer (`AckValidator`) rejects and closes the connection on any ACK from a live-only client, on an ACK before the checkpoint, on an ACK for another `pluginSessionId`, on *T* > *S* and on *T* < *A*′. An equal *T* is a no-op.
- After an ACK the producer releases the acknowledged retained entries. `ackedThroughEventSeq` persists across connections within the plugin session.
- **ACK inside a gap record.** The producer accepts any *T* that satisfies its rule, even inside a retained gap record, and *A*′ becomes *T*. The record is not released or trimmed: the six cause counters cannot attribute part of a range. Status and `end` then report the release point, the record's `firstEventSeq` − 1, and the next connection's checkpoint carries it as *A*. That connection redelivers the record whole with `redelivered: true`; the `eventSeq` values already committed are legal duplicates under the UNIQUE key, and the cursor reports them as `duplicate`. Stream `ack-inside-gap-record` covers this case. Enforcement belongs to ET-004b.
- A live-only client never sends `ack`; the producer rejects even `ack` with *T* = *A*.

## 11. Clock probes and mapping

- Client: `clock.probe` `{probeId}`, a uint64 ≥ 1 that increases within a connection. At most one probe is outstanding and at most one is sent per second.
- Deadline: a reply received more than 1 s after its probe was sent is late. The client discards that measurement, but the probe stays outstanding until its reply arrives: a late reply is accepted and ignored for mapping, and no new probe is sent or registered before it. If no reply ever arrives, the client sends no further probes on that connection.
- Server: `clock.reply` `{probeId, receivedMonotonicNs, sentMonotonicNs}` in the source clock, with received ≤ sent ≤ `capture`. It never precedes the checkpoint. An unsolicited or mismatched reply is a protocol error.
- The server closes the connection on a probe whose `probeId` does not exceed the previous one on the connection, or that arrives while its reply to the previous probe is still unsent (OD-5 S6).
- The consumer computes a local-only `ClockMapping {sourceClockId, clientClockId, offsetNs, uncertaintyNs, measuredAtClientNs}` with exact BigInt arithmetic (`computeClockMapping`). With client send *t0*, source receipt *t1*, source send *t2* and client receipt *t3*: round trip *δ* = (*t3* − *t0*) − (*t2* − *t1*) ≥ 0, offset = floor(((*t1* − *t0*) + (*t2* − *t3*)) / 2) as a signed decimal string, and uncertainty = ceil(*δ* / 2), so source ≈ client + offset ± uncertainty. A negative round trip is rejected, and that check runs before the lateness check, so a late reply cannot hide an impossible one. A late reply with a valid round trip yields no mapping.
- A change of either clock identity invalidates the mapping. The mapping is never a wire field. Never assume equal origins, for example Node `process.hrtime` and QPC.

## 12. Security and transport

v1 keeps the v0 local security model by reference to [the v0 pipe requirements](v0.md#named-pipe-integration-requirements-et-004a), [the native transport](../native-transport-v0.md) and [the native boundary](../native-transport-boundary-v0.md):

- the plugin is the pipe server; the Electron telemetry service, through the fixed project-owned broker, is the client;
- the endpoint has an explicit protected current-user DACL, no Everyone, anonymous or network grants, `PIPE_REJECT_REMOTE_CLIENTS`, `FILE_FLAG_FIRST_PIPE_INSTANCE` and non-inheritable handles;
- on a collision it fails closed: no adoption and no overwriting of foreign records;
- both peers verify the connected peer's PID, creation time, token user, Windows session and image provenance, and the envelope identity against them.

The only deltas from v0 are the `v1` path segment in the pipe name and discovery directory, `protocolMajor: 1` in records, and a separate service-policy file. No renderer receives pipe, handle, filesystem or source-selection authority.

# Protocol v1 simulator and CAP-01 replay

ET-005b adds a deterministic [protocol v1](protocol/v1.md) producer model beside the unchanged [v0 simulator](simulator-v0.md). It is a Node test tool, independent of Electron and the SCS SDK. It opens no database, writes no history, discovery or service-policy file, calls no SDK function and emits only synthetic or replay origins. The desktop application consumes v1 through the separately implemented [v1 ingestion](telemetry-service-v1.md). Nothing here establishes game, TruckersMP, display or performance behavior.

PR-1 provides deterministic replay. PR-2 serves the same model on a real named pipe, reactively for any contract consumer or in lockstep with client and wire fault injection ([below](#named-pipe-serving)). PR-3 imports minimized CAP-01 callback sequences with provenance; see [CAP-01 replay](#cap-01-replay-october-21-2026).

From the repository root, using the [pinned toolchain](setup.md):

```powershell
npm run build --workspace @ets2telemetry/telemetry-simulator
node tools/telemetry-simulator/dist/cli.cjs replay-v1 tests/fixtures/simulator-v1/save-load.json
npm run smoke:v1 --workspace @ets2telemetry/telemetry-simulator
node tools/telemetry-simulator/dist/cli.cjs smoke-v1 tests/fixtures/simulator-v1/wire-faults.json --scale 0
node tools/telemetry-simulator/dist/cli.cjs serve-v1 tests/fixtures/simulator-v1/normal-delivery.json
npm test -- tests/unit/simulator-v1-store.test.ts tests/unit/simulator-v1-source.test.ts tests/unit/simulator-v1-scenario.test.ts tests/unit/simulator-v1-replay.test.ts tests/unit/simulator-v1-pipe.test.ts tests/unit/simulator-v1-reactive.test.ts tests/unit/simulator-v1-faults.test.ts
```

`replay-v1` writes one JSON line per wire message to stdout: `{scenario, origin, connection, atMs, direction, message}`, where `direction` is `server` or `client`. Injected fault bytes appear at their place as `{scenario, origin, connection, atMs, direction, fault, bytesHex}` instead of `message`. Two runs of one scenario are byte-identical. `smoke-v1` and `serve-v1` are described under [named-pipe serving](#named-pipe-serving).

## Components

| Module (`tools/telemetry-simulator/src/v1/`) | Role |
| --- | --- |
| `store.ts` | `EventStore`, a TypeScript mirror of the native ET-004b store and its invariants I1–I8 ([native v1 transport](native-transport-v1.md#store-rules)) |
| `source.ts` | `AdapterModel`: SDK callbacks in, v1 records, occurrences and the published state slot out, following the [records table](native-transport-v1.md#records-from-the-callbacks) and the [§6 mapping](protocol/v1.md#6-units-and-sdk-mapping). `EventChannel` models the SDK-thread gate, `eventSeq` assignment, open loss runs and a full handoff ring. `ScenarioClock` holds the clocks |
| `producer.ts` | `V1Producer`: the transport worker without I/O. It drains the channel in the [caller sequence](native-transport-v1.md#caller-sequence) (loss parts in the order offline, noDurableConsumer, queueCount; then the copied record), measures each event once with the worst-case envelope, stamps `capture = max(now, last capture, carried times)`, passes every ACK through `AckValidator` and coalesces snapshots |
| `client.ts` | `ScriptedClient` built from the ET-002b `FrameDecoder`, `V1Consumer`, `DurableAckCursor` and `computeClockMapping`, plus `CommitLedger`, an in-memory stand-in for rows keyed `UNIQUE(plugin_session_id, event_seq)` (CD-6). It is not storage |
| `scenario.ts` | The strict scenario schema and the ordered timeline |
| `replay.ts` | `V1Driver`, the virtual-clock driver: a generator of transport effects (accept, expected client bytes, server writes, flushes, closes) that `replayV1` answers at once. Also the transcript and fault lines |
| `faults.ts` | The fault vocabulary and the bytes of each client and wire fault, built outside the producer |
| `pipe-host.ts` | The synthetic endpoint, `TEST_PIPE_PATTERN_V1`, accepted connections and bounded waits shared by both servers |
| `pipe.ts` | `serveV1`, the lockstep server, and `runV1PipeClient`, the scripted pipe client |
| `reactive.ts` | `serveV1Reactive`, the reactive server for any contract consumer, `reactiveDifferences` and `runIndependentClient` |
| `cadence.ts` | Real-time cadence checks of a paced lockstep run and the state-rate check on capture times |

The ET-002b contract modules are reused unchanged. Every server message is built through `encodeFrame`, and every client message through the same encoder; each side decodes the other's frames with `FrameDecoder`.

## Scenario format

A scenario file is strict JSON of at most 2 MiB, read once through the v0 simulator's bounded reader, which rejects duplicate keys. Unknown or missing fields are rejected at every level, and the result is rebuilt from validated fields only.

```json
{"format": "ets2telemetry-simulator-v1", "schemaVersion": 1, "id": "...", "purpose": "...", "reg": ["REG-001"],
 "origin": "synthetic", "game": "ets2", "seed": "...", "provenance": null,
 "source": {"versions": {...}, "gameplayEvents": "registered", "currency": "unknown", "gameMode": "unknown", "startEventSeq": "1"},
 "steps": [...], "transport": [...]}
```

- `origin` is `synthetic` with `provenance: null` for authored scenarios. CAP0-derived scenarios carry strict provenance and have `replay` origin for game captures or `synthetic` for synthetic captures. `game` is always rejected (CD-4).
- `source.gameplayEvents`: `registered` or `not-supported` (no gameplay steps, no gameplay types in welcome). `source.currency`: `unknown` or `sdk-documented`, which uses EUR from `scssdk_telemetry_eut2.h` for ETS2 and USD from `scssdk_telemetry_ats.h` for ATS (CD-9, D11). `source.gameMode`: `unknown` (OD-3: mode unknown, no `source.gameMode` type) or `synthetic-detection`, which allows `gameMode` steps (CD-8, D9 only). `startEventSeq` above 1 is a synthetic affordance for exhaustion: [1, start) counts as acknowledged and committed.
- At most 1,000 steps in total, `atMs` from 0 to 86,400,000 and ordered within each array, `repeat` and `count` at most 1,000, at most 255 attributes per callback, and at most 20,000 transcript messages per replay.

Source steps use the SDK-callback vocabulary (CD-3):

| `action` | Fields | Model |
| --- | --- | --- |
| `configuration` | `id`, `attributes`, `list?`, `repeat?` | `job`, `truck` and `trailer.0`–`trailer.9` emit records (D13); `bus_job`, `car_job`, `controls`, `hshifter`, `substances` and the legacy `trailer` only advance the boundary order (TD-002). An empty terminated list is a clear. `list: "null"` (no attributes) and `"unterminated"` (a shorthand for a list cut at the native 255-entry scan bound, with at least one attribute) make every unseen field invalid |
| `gameplay` | `id`, `attributes`, `list?`, `repeat?` | The six v1 gameplay types; `car_job.*` and unknown ids yield nothing |
| `lifecycle` | `event` | `simulation.started` or `simulation.paused`; `occurred.simulation` is the state after the callback |
| `frame` | `timerRestart?`, `channels?` | frame_start (a timer restart rotates the game clock and emits `timers.restart`), each listed channel in registration order, then frame_end: the loss-run flush and the state publication |
| `gameMode` | `mode`, `method`, `confidence`, `module?` | Synthetic detection; emits `source.gameMode` on the first result and on every change. Not an SDK callback |
| `encodingFailure` | `count` | Injects records the contract rejects (an out-of-range trailer index), so measurement fails |
| `handoff` | `full` | A full ring loses every event the durable gate would copy as `queueCount`; the run stays open until the ring drains |
| `utcJump` | `deltaMs` | Moves UTC labels only |
| `suspend` | `durationMs`, `sourceClockAdvances` | CD-12: the source clock either stops or advances across the suspend; nothing runs until it ends |
| `shutdown` | `reason` | `plugin-shutdown` or `source-retired`: a best-effort `end`, then nothing may follow; an open loss run gets no gap (OD-5 S11) |

Attributes are `{name, sdkType, value}` with the SDK names and types. `float` values must be float32-exact, `u64`/`s64` are exact decimal strings, and a `string` value of `null` is a null pointer (invalid). A wrong `sdkType` for the field is invalid. Channel values are numbers in SDK units (speed m/s, `fuel.amount` L, `odometer` and `fuel.range` km, `fuel.consumption.average` L/km, `navigation.distance` m, `game.time` u32 minutes, `displayed.gear`, `engine.rpm`), `null` for a callback without a value, or `"invalid"` for a wrong-typed value; `world.placement` is `{x, y, z, heading, pitch, roll}`.

Transport steps: `connect` with `client: {durable, commit?, ack?, probes?}` and `disconnect`. `commit` is `each` (default), `none`, `failAt:<eventSeq>` (crash before committing the item that covers it) or `crashAfterCommit:<eventSeq>` (commit it, then crash before its ACK). `ack` is `each` (default), `withhold` or `dropAfter:<n>` (later ACKs are lost after leaving the client). A live-only client (`durable: false`) has neither. `probes` are scenario times at least 1,000 ms apart within the connection. A crash closes the connection; a scripted `disconnect` after it is a no-op, and the next connection uses a new client instance whose cursor starts from the ledger.

Fault and endpoint steps (PR-2):

| `action` | Fields | Model |
| --- | --- | --- |
| `clientFault` | `fault` | A hello fault is a connection attempt of its own, made while no client is connected; the producer opens no v1 connection for it. A live fault acts on the open connection after its checkpoint |
| `wireFault` | `fault` | Server-to-client bytes injected on the open connection, built outside the producer and the encoder. Requires the top-level `faultInjection: true`, which a scenario without wire faults may not set |
| `secondClient` | | Another client connects while the open one continues; it is refused |
| `writeDeadline` | | Ends a connection whose client stalled (`clientFault: stallRead`) at the server write deadline. Another connection must follow it, because a stalled client learns of the closure only from the next accepted connection |

| Fault | Bytes | Outcome |
| --- | --- | --- |
| `helloOversized` | A prefix of 4,097 | Closed at the prefix (§3) |
| `helloMalformed`, `helloV0`, `helloCap0`, `helloOtherMajor`, `helloOtherMinor`, `helloUnknownKind`, `ackBeforeHello` | Malformed JSON, a v0 or CAP0 hello, version 2.0 or 1.1, kind `subscribe`, an `ack` first | Closed without a byte (§2, §4) |
| `helloExtraBytes`, `ackBeforeCheckpoint` | A valid hello and one more byte or an `ack` in the same write | Closed without a byte (OD-5 S6) |
| `helloPartialEof` | Half a hello, then the client ends its side | Closed at EOF |
| `helloTimeout` | Nothing | Closed at the 5 s hello deadline (§4) |
| `secondHello`, `unknownKind`, `oversizedFrame`, `malformedFrame` | A hello, kind `subscribe`, a prefix of 4,097, malformed JSON | Closed without an error frame (§4, OD-5 S6) |
| `ackLiveOnly`, `ackForeignSession`, `ackBeyondSent`, `ackRegressing` | An `ack` from a live-only client, for another plugin session, for the next uncovered `eventSeq`, or one below the accepted point | Closed by `AckValidator` (§10) |
| `ackDuplicate` | An `ack` equal to the accepted point | No-op; the connection continues (§10) |
| `probeRepeat`, `probeWhileReplyUnsent` | The previous probe ID again; two probes in one write | Closed (§11, OD-5 S6). A rejected read consumes no message `seq` |
| `partialFrameEof` | Half an `ack`, then the client ends its side | Closed at EOF |
| `stallRead` | Nothing; the client stops reading | Ends at the scripted `writeDeadline` |
| `duplicateEventSeq`, `skippedEventSeq` | The last event again, or one `eventSeq` beyond the next | `V1Consumer`: eventSeq coverage violation (§9) |
| `seqRegression`, `captureRegression`, `foreignSource` | A snapshot with the last `seq`, an earlier capture, or another plugin session | `V1Consumer`: identity, clock or order violation (§5) |
| `malformedJson`, `oversizedPrefix`, `partialEof`, `v0Frame` | Malformed JSON, a prefix of 65,537, half a frame and then EOF, a v0 `welcome` | `FrameDecoder`: rejected (§3) |
| `frameAfterEnd` | A consistent `end`, then a snapshot | `V1Consumer`: nothing may follow `end` |
| `seqSkip` | Nothing; the producer skips one message `seq` | Accepted: the next message reports one skipped sequence (§5) |

A rejected client fault, and a wire fault the client rejects, end only their connection. The producer then behaves as after a disconnect at that time: the gate closes, a durable connection starts its retention window, and nothing else changes. Each fault on a connection is recorded in the result (`faults`, `rejection`, `refusedClients`).

## Clocks, identities and ordering

- Source monotonic clock: 1,000,000,000,000 ns + `atMs` × 1,000,000, less any time a non-advancing suspend stopped it. UTC labels: 1,800,000,000,000 ms + `atMs` + UTC jumps. Client clock: 5,000,000,000,000 ns + `atMs` × 1,000,000, so a zero-latency probe maps with offset −4,000,000,000,000 ns and uncertainty 0. Game time comes only from frames.
- Identities are SHA-256-derived UUIDs over `simulator-v1:<seed>:<label>`: `plugin-session`, `process-instance`, `capture-clock`, `game-clock-<epoch>`, `client-instance-<n>`, `client-clock-<n>`. The process ID is 1 and the Windows session 0; neither is an authenticated identity.
- At one `atMs`, due timers fire first (a retention expiry before a snapshot), then source steps, then probes, then transport steps. A timer fires at its own time, or when a suspend ends if it fell due during it. Timers after the last step do not fire.
- The client applies each server message synchronously and the producer processes each reply before its next action. Every SDK callback, including frame_start, each channel and frame_end, advances `boundaryOrder`. Message `seq` counts written messages. The 50 ms snapshot interval starts at the checkpoint; a publication inside it replaces the one unsent snapshot and increments `coalescedSnapshots`. State is the slot published at the last frame_end (OD-5 S7), so a configuration change after it reaches the client only with the next frame.
- Store retention runs in source time (CD-11). Store misuse would be an invariant violation; the model throws instead of retiring the session, so a defect cannot pass silently.

## Named-pipe serving

Both servers serve one scenario on a new endpoint `\\.\pipe\ETS2Telemetry-SYNTHETIC-TEST-v1-{pid}-{uuid}`; `TEST_PIPE_PATTERN_V1` matches exactly these names, and both simulator clients refuse any other endpoint. Nothing else is published: no discovery record and no `service-policy.json`. The servers are Node, so they have no protected DACL and no peer authentication; they are not security evidence for the native endpoint.

```powershell
node tools/telemetry-simulator/dist/cli.cjs serve-v1 <scenario.json> [--scale <0-10>] [--lockstep] [--await-scripted-acks]
node tools/telemetry-simulator/dist/cli.cjs smoke-v1 <scenario.json> [--scale <0-10>] [--reactive]
```

`serve-v1` serves in **reactive** mode by default and prints `{origin, mode, endpoint, history: false}`, then a summary when the scenario ends; `--lockstep` selects lockstep mode. `smoke-v1` runs a lockstep server with the scenario's scripted client in the same process, or with `--reactive` a reactive server with an independent consumer, and exits with an error unless the run meets that mode's guarantee below. `--scale` is real milliseconds per scenario millisecond while a client is connected (default 1; 0 does not pace); offline segments are always fast-forwarded. `serve-v1 --await-scripted-acks` sets the reactive server's `awaitScriptedAcks` option described below; it is refused together with `--lockstep` and by `smoke-v1`. The recording runtime journey uses it ([CI](ci.md#et-015a-recording-journey-smoke)). `npm run smoke:v1` runs `pipe-reconnect` in both modes.

| | Reactive (`serveV1Reactive`, `reactive.ts`) | Lockstep (`serveV1`, `pipe.ts`) |
| --- | --- | --- |
| Client | Any consumer of the production transport contract: any client instance, its own ACK timing and clock probes. **ET-006b's desktop ingestion uses this mode** | Only the scenario's scripted client (`runV1PipeClient`); a client that deviates fails the run |
| Client bytes | Fed to the producer read by read as they arrive | Compared with the script's bytes, then fed as one read |
| Scenarios | `connect`, `disconnect` and `secondClient` steps; scripted probes are ignored. Client faults, wire faults and stalls script a client and are rejected | All steps, including every fault |
| Guarantee (checked by) | Plan item 7: per connection, events, gaps, checkpoints and `end` byte-identical to `replay-v1` except the message `seq` (and the checkpoint's `boundarySeq`, which equals it), because the client's own probes add replies; snapshots equal in number, state and continuity. Clock replies and client messages are not compared (`reactiveDifferences`) | The whole transcript, fault lines, every client byte and applied message and the client ledger byte-identical to `replay-v1` (`pipeDifferences`) |
| Conditions | The scenario passes `reactiveConflicts` (no client reaction inside one action changes the outcome); the consumer follows each scripted connection's durability, commit and ACK policy, and acknowledges what it will acknowledge, or leaves, within the 1,000 ms quiesce bound after each action. Where the server waits, the result depends on the client meeting that bound: it is not deterministic by construction. With `awaitScriptedAcks`, a connection scripted to commit and acknowledge each item is awaited until it did or left, so that dependence is gone for it | None beyond the script |

**Reactive mode.** Source steps and timers run in scenario time, paced from the hello of a connection. A scripted connect accepts the next client whose hello is valid, from any client instance; a missing, late or rejected hello ends only that attempt, and the connection waits for the next client within 30 s (`connectTimeoutMs`). A valid hello whose durability differs from the scripted connection fails the run. ACKs pass `AckValidator` and release entries as they arrive; a clock probe is answered at the scenario time the paced segment has reached, which is never later than the next action. A client that leaves is disconnected, at the scenario time of the last action; after `end` the server reads nothing more from the connection. After each action that wrote an event or a gap (a step, a timer snapshot or a connect), before writing an `end` (at shutdown or once the eventSeq space is exhausted) and at a scripted disconnect, the server waits up to 1,000 ms (`quiesceMs`) until a durable client has acknowledged everything written to it or has left, before it paces on; a disconnect then closes gracefully. A client that withholds ACKs therefore costs that bound at each such point. With the `awaitScriptedAcks` option (default off; the ET-006b storage tests and, through `serve-v1 --await-scripted-acks`, the recording runtime journey use it), a connection whose scripted client commits and acknowledges each item (`ack: each`, any commit policy but `none`) is instead awaited without that bound until it has acknowledged everything written to it or has left, so a consumer whose real commits are slow, or whose process is terminated late, still reacts at the same action boundary; if it does neither within `settleTimeoutMs` (default 30 s, a liveness bound) the run fails. Connections that withhold or drop ACKs keep the bounded wait. Within one action nothing is awaited, so the client's reactions (ACK releases, a crash) take effect only between actions. The replay applies each reaction right after the message that caused it, so the two can differ only inside one action. Reactive mode therefore rejects, before serving, any scenario where that matters (`reactiveConflicts`, found by stepping the replay driver): (A) an ACK the replay processes inside an action releases entries that a later admission of the same action needs at the 256-entry or 1 MiB store bound, for example a connected client that acknowledges each of 300 events of one step; (B) a client crash (`failAt`, `crashAfterCommit`) on an item while the store already holds later eventSeqs, or while the same action assigns more, for example a crash on the first of two events of one step or on the first of several redelivered items. For every other scenario the comparison holds under the conditions in the table: events, gaps, snapshots and their captures depend only on scenario time, not on when ACKs arrive; a gap record that is extended before its ACK arrives is written as the same delta gap that a released record would produce; ACKs and client crashes take effect at the same action boundaries as in the replay, so checkpoints, `end` and the eventSeqs a crashed client misses equal the replay's. A sweep of all 24 scenarios this mode accepts, at scale 0 and 1, matched the replay; before quiescing after actions, a crash racing the next step (`crash-before-commit`, because Windows timers have a 15.6 ms resolution), ACKs racing the `end` at exhaustion (`sequence-exhausted`) and a timer snapshot written to a crashed client did not. A consumer that acknowledges differently from the scripted policy (for example every ACK where the scenario loses some) produces other checkpoints, and `reactiveDifferences` reports them; a test checks this, and `serve-v1` prints the verdict (`matchesReplay`, `differences`) and exits non-zero on a difference. `runIndependentClient` is such a consumer for tests and the smoke: built only from `ScriptedClient` (the ET-002b helpers and the in-memory ledger), it uses its own client instance IDs, a fresh one after a crash, writes in order each after a seeded random delay, sends one clock probe per connection and retries a refused attempt.

**Lockstep mode.** The server runs the same `V1Driver` as `replay-v1` and answers its transport effects with pipe I/O. After each server frame it waits for exactly the bytes the scenario's client sends in reply, compares them and only then lets the producer process them, as one read. The producer's source clock is scenario time, and retention runs in it (CD-11), so the served transcript is byte-identical to `replay-v1` by construction. `runV1PipeClient` uses the PR-1 `ScriptedClient` with the in-memory `CommitLedger` and per-instance ACK cursors. Its script (`clientPlan`) comes from the replay, because a probe or a fault belongs to a point of the server stream that only the scenario timeline defines: each action is taken after the server message with a given `seq`. A probe is sent at its own scenario time on the connection's paced schedule, so its round trip does not include the server's wait. The client clock is `process.hrtime`, so mappings differ from the replay's zero-latency values: a reply within 1 s gives an offset and an uncertainty of half the measured round trip; a later reply gives no mapping (§11). Every arrival is queued in order; the script decides whether it is the next connection or a second client to refuse at its `secondClient` step, so pacing cannot turn a stalled client's next connection into a refused second client.

**Endpoint behavior.** The rules are those of the specification, §2–§4, §9–§11 and OD-5 S6, as the native ET-004b endpoint implements them in PR C (PR #54, merged as `ceba919`), in `native/telemetry-plugin/src/v1-server.cpp` at that commit. One client at a time: in reactive mode a client arriving while another is connected is closed at once without a byte and does not displace it; in lockstep mode the same happens at the scripted `secondClient` step. The hello is read with the 4,096-byte bound at the prefix, a byte beyond the hello in the same read rejected, and any other first message, major, envelope minor or kind rejected, all without an error frame. After the checkpoint only `ack` (through `AckValidator`) and `clock.probe` are accepted; probe IDs increase and no probe may arrive while a reply is unsent. One replaceable unsent snapshot at most every 50 ms. `end` at shutdown, at sequence exhaustion, and on cancellation (`stop` or an aborted signal): a live connection receives `plugin-shutdown` stamped at the scenario time its paced segment had reached, written within the write deadline, then the endpoint closes. Writes must complete within the 1,000 ms write deadline; a hello is due within 5,000 ms of the connect point. Only the scenario with a client that never sends a hello (`helloTimeout`) is run in tests with a shorter, 200 ms deadline. Deadlines are measured on `performance.now()`, the clock tests measure with, and judged only after one more I/O poll, so a completion already queued when a starved process wakes still counts.

**Deliberate differences from the native endpoint.** Lockstep mode checks the client against its script instead of reacting to arbitrary timing, and feeds the producer one scripted reply at a time, so the native window between the welcome and the checkpoint, in which a client byte resets the connection, does not exist there; such bytes are the `helloExtraBytes` and `ackBeforeCheckpoint` faults in the hello's own read. Reactive mode feeds real reads, but writes the welcome and the checkpoint in the same turn, so that window does not exist there either. The hello deadline counts from the scenario's connect point (lockstep) or from accepting the connection (reactive), not from the OS connection. A scripted `disconnect` is performed by the server (the client sees EOF without `end`); a graceful close returns only after the client has read every byte (libuv's `FlushFileBuffers`). After `end` at sequence exhaustion the endpoint keeps serving `welcome` then `end`, as PR-1 models it, while the native endpoint closes. Reactive mode waits, bounded, for the client's ACKs after actions, before `end` and at a disconnect; the native endpoint (`v1-server.cpp` at `ceba919`) never waits for an ACK and writes `end` at once (D14), so an ACK lost or still in flight at `end` or at a disconnect is outside what the simulator shows. ET-006b needs its own coverage of that case. Node keeps several pipe instances, so a second client connects at the OS level and is then closed; the native endpoint has one instance and refuses it at connect.

**Determinism by construction.** Lockstep comparisons depend on no timing. The stalled-reader scenario writes about 600 KB after the client stops reading, far beyond the 64 KiB pipe buffer, while the steps before it write a few hundred bytes, so the write deadline fires at the scripted step on any host; if the writes complete anyway the run fails visibly. Reactive comparisons are not deterministic by construction wherever the server waits: they depend on the consumer acknowledging, or leaving, within the 1,000 ms quiesce bound, which a cooperative consumer meets by a wide margin; a consumer that misses it produces a reported difference or, when the late reaction is only an ACK that no later message reflects, a missing ACK in the transcript. On October 15, 2026 most likely a storage commit on a stalled shared host missed the bound (inferred, not observed; see the ET-006b record) and the restarted service's ACKs were not recorded ([ET-006b validation](validation/et-006b.md#flaky-storage-ack-race--october-15-2026)); on October 18, 2026 the recording runtime journey, then served without the option, failed the same way on a hosted runner ([ET-015a validation](validation/et-015a.md#flaky-third-connection-ack-race-october-18-2026)); `awaitScriptedAcks` removes the bound for connections scripted to acknowledge each commit, leaving only a liveness bound that fails the run. Scenarios whose outcome depends on a reaction inside one action are rejected up front. Waits for a cooperative client are liveness bounds (5,000 ms). Real time is used only for pacing, the cadence smoke bounds and clock mappings. Cadence: no paced message is written before its schedule, checked on the server's own clock against the same hello receipt that anchors the pacing (a pacing defect fails it, scheduling delay cannot); the first measurable gap of at least 20 ms arrives no more than 1,000 ms after its schedule on the client's clock. `checkStateRate` checks that consecutive state messages carry capture times at least 50 ms apart, so the producer emits state at no more than 20 Hz of source time; this holds by construction of the model and is not a measurement of real delivery spacing.

## Soak source (ET-019 PR-12a)

A scenario holds at most 1,000 steps (`MAX_STEPS`), a run at most 20,000 transcript messages (`MAX_TRANSCRIPT_MESSAGES`) and a scenario file at most 2 MiB, while 30 minutes of frames at 20 Hz are 36,000 steps. The soak source ([`soak.ts`](../tools/telemetry-simulator/src/v1/soak.ts)) therefore generates its timeline instead of reading a file, and serves it in the reactive server's soak mode (`ReactiveSoakOptions` in `reactive.ts`):

```powershell
node tools/telemetry-simulator/dist/cli.cjs serve-v1-soak --minutes <1-90>
node tools/telemetry-simulator/dist/cli.cjs smoke-soak-v1 --minutes <1-90>
```

- **Generated timeline.** `soakEntries(minutes)` yields one entry at a time. Each step is built as scenario JSON and checked by the same per-step validators as a scenario file (`sourceStep`, `transportStep`). Nothing keeps the steps.
- **No transcript.** In soak mode the server counts messages by kind and direction and keeps the latest eventSeq written, the highest ACK received, the snapshot count, the connections and the refused live-only attempts (`SoakStatus`). It records each connection's client instance from the latest hello, not from a transcript. The report's `transcript` stays empty. Three lists still grow, each bounded: the connection records (one per scripted connect, at most 10 in 90 minutes), the client's commit ledger (one row per event, 3 + 6 per minute) and `PipeHost`'s accepted links, one small object per accepted connection attempt, kept until the run ends. A refused live-only attempt gets no checkpoint, so the desktop service's E9 reconnect backoff (250, 500, 1,000, 2,000, then 4,000 ms) does not reset, and a scripted connect gives up after `connectTimeoutMs` (60 s): about 20 refused attempts per scripted connect at most (at 0, 0.25, 0.75, 1.75 and 3.75 s, then every 4 s), so fewer than about 200 links in 90 minutes.
- **Live-only hellos.** A live-only hello for the soak's durable connection ends only that attempt, before anything is written, and is counted as `refusedLiveOnly`; the connection waits for the next client. The desktop service sends such a hello while its storage opens (R10). Outside soak mode such a hello still fails the run.
- **ACKs as a hang detector.** The soak runs with `awaitScriptedAcks`, so a missing ACK fails the run within the 30 s settle bound. A scripted connect waits up to 60 s for its client (`connectTimeoutMs`).
- **No conflict check over the whole run.** `reactiveConflicts` steps the replay driver, which would keep a transcript, so soak mode skips it. A unit test runs it on reduced-frame variants of one and two cycles, with the same events, connects and ACK policy and one frame per second, and expects no conflict.
- **`serve-v1-soak`** prints `{type: 'serving', origin, mode: 'soak', minutes, endpoint, history: false}`, then a progress line about every 10 s: `{type: 'progress', scenarioMs, lastEventSeq, maxAckThroughEventSeq, ackCount, snapshots, connections, refusedLiveOnly, heapUsedBytes}`. It ends at the end of the timeline, on SIGINT, or on a line `stop` on stdin, and prints one summary line. On Windows a kill is `TerminateProcess`, which runs no signal handler, so a driver that wants the summary writes `stop`. `BoundedProcess.Run` and `RunExtended` give the Job's root process a NUL stdin, so `serve-v1-soak` started as the Job root cannot receive `stop`; a driver inside the Job must spawn it with a stdin pipe (ET-019 PR-12b).
- **`smoke-soak-v1`** serves the timeline to an in-process soak client (`runSoakClient`: `ScriptedClient` with commit and ACK each, one client instance, reconnecting 250 ms after each close, emptying `received` after each read). It stops the source 5 s into the tail and exits non-zero unless the totals below hold. Its heap figures cover the server and the client together.

**Schedule.** One plugin session, ETS2, seed `soak-v1`, origin `synthetic`, gameplay events registered, unknown currency and game mode. A frame every 50 ms from 0 until M × 60 s + 300 s, M = `--minutes`. Scenario time runs 1:1 with real time while a client is connected; offline segments are fast-forwarded, as in every reactive run.

**Drift against wall time.** The client reconnects 250 ms after a scripted disconnect, and the server accepts it as soon as the schedule reaches the reconnect, so the 3 s disconnect window passes at once: scenario time gains about 3 s on wall time per reconnect cycle, at most about 27 s in 90 minutes (nine reconnect cycles). Scenario time stands still while a scripted connect waits for a client, before its hello. Event and sample-second expectations follow the source clock, which is scenario time, so drift does not change them; only wall-clock expectations move, and the source reaches its tail earlier by the drift. Every lifecycle, gameplay, configuration and transport step except the first connect sits on a 25 ms offset between two frames, so none shares a millisecond with a frame or a second boundary.

| Time (ms) | Step |
| --- | --- |
| 0 | Frame, then connect: durable, commit each, ACK each |
| 25 | `simulation.started`, then truck configuration, then `trailer.0` configuration |
| b + 25 | Job configuration (cycle k, b = 60,000 × k, k = 0 … M − 1) |
| b + 5,025 | `player.tollgate.paid` |
| b + 20,025 | `simulation.paused` |
| b + 30,025 | `simulation.started` |
| b + 35,025 | Only when k % 10 = 1: scripted disconnect |
| b + 38,025 | Only when k % 10 = 1: connect, as at 0 |
| b + 45,025 | `job.cancelled` when k % 4 = 2, otherwise `job.delivered` |
| b + 45,525 | Job configuration cleared (empty attribute list) |
| M × 60,000 to M × 60,000 + 299,950 | Trip-free tail: frames only. A driver stops the source during it |

The connect at 0 precedes the start steps so that they reach the client as events; at the same millisecond a source step would otherwise precede the connect and be lost as `offline`. Frame n (at n × 50 ms) carries float32-exact values derived from n only: speed 19.53125 m/s, `fuel.amount` 400 − n / 4,096 L, `odometer` 1,000 + n / 1,024 km and `game.time` 480 + ⌊n / 60⌋ min; frames keep running while the simulation is paused. The attributes are those of `normal-delivery`, with a toll of 150 and a cancellation penalty of 1,000. A run of M minutes therefore assigns 3 + 6M eventSeqs, all events and no gap when the client acknowledges everything, M jobs, ⌊(M + 1) / 4⌋ cancellations and 1 + ⌊(M + 8) / 10⌋ connections, without redelivery, because the server awaits the ACKs of everything written before each disconnect. `smoke-soak-v1` requires exactly these totals, and also that every connection but the last ended at its scripted disconnect and the last at the stop's single `end`, because a connection lost earlier in a reconnect cycle (a write deadline, a client close) would leave every total unchanged; `tests/unit/simulator-v1-soak.test.ts` writes the table by hand for one and three minutes.

The source soak runs under `BoundedProcess.RunExtended` through `scripts/ci/Invoke-SoakSource.ps1` and the dispatch-only workflow ([CI](ci.md#et-019-recording-soak-workflow-dispatch-only)). It measures the simulator, not the application; nothing about the desktop application's memory or recording follows from it. The packaged application soak of ET-019 PR-12b ([CI](ci.md#application-soak-et-019-pr-12b)) is the driver inside the Job: it spawns `serve-v1-soak` with a stdin pipe, lets the running application record it and writes `stop` in the tail.

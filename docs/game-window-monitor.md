# Native game-window monitor

ET-007 adds an SDK-independent `ets2telemetry::window::Monitor` and binds its latest fixed-size copy to the production transport serializer. The monitor does not serialize messages, retain window history, render an overlay, or call the SCS API. The accepted protocol v0 and SDK adapter remain unchanged. The serializer publishes eligible metadata in the existing `state.window`; ET-008 must consume the physical-coordinate contract and must not treat a numeric HWND as renderer authority.

## Identity and lifecycle

`start(sdk_game_id, plugin_session_id)` verifies the actual current process using a retained `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE)` handle, `QueryFullProcessImageNameW`, `GetProcessId`, `GetProcessTimes`, and `ProcessIdToSessionId`. `eut2` requires basename `eurotrucks2.exe`; `ats` requires `amtrucks.exe`. An SDK claim alone is rejected. The retained creation token and Windows session are checked on each poll. This verifies the loaded host's executable name and lifetime, not its publisher signature or the authenticity of arbitrary renamed executables. The monitor does not scan/open another game's process or read game memory.

The SDK export creates the monitor only after successful adapter initialization, then starts transport with a stable borrowed monitor pointer. Official shutdown and initialization failure first stop/join transport, then stop/join and delete the monitor, then unregister SDK callbacks. An exception follows the same retirement order. No monitor object or thread survives a completed SDK shutdown. There is no DllMain or static-destructor monitor join. The SDK must call its official shutdown before unloading the plugin; forced DLL removal while its worker runs is unsupported. Lifecycle methods have a single SDK-thread owner; `latest()` may be called concurrently and returns an owned fixed-size copy. A failed identity check leaves telemetry initialization available but window metadata `identity_rejected`; this avoids inventing a window in a foreign SDK test host. Transport startup failures retain their fixed reason and are logged only by the direct SDK caller.

The worker owns a 50 ms polling/message loop and an out-of-context destruction WinEvent hook. Hook callbacks only invalidate the tracked window identity; they never call SCS, serialize, allocate an application event queue, or send messages to the game window. Each iteration drains at most 256 messages and enumerates at most 4096 top-level windows, checking cancellation. A saturated drain, failed DPI/hook/query operation, or incomplete enumeration produces unavailable metadata. There is one latest slot, no spool, and no durable event semantics. The 50 ms cadence is independent of 1 Hz history sampling.

`stop()` signals an owned event and joins the worker; waits are cancellation-aware. The worker unhooks and restores its previous thread DPI context before exiting. Controlled tests assert a measured stop under 500 ms; Windows scheduling and synchronous system queries prevent interpreting that measurement as a universal hard real-time guarantee. No process is terminated by this component.

## Selection and invalidation

Candidates must be actual current-process top-level root windows, have no owner window, lack `WS_EX_TOOLWINDOW`, and be visible. More than one eligible candidate fails closed with `ambiguous` and zero public HWND. An already tracked valid hidden/minimized window is retained and reported with visibility/minimized flags. A different newly visible candidate while the tracked identity survives also remains ambiguous across polls, rather than silently choosing a different window. Destroying/invalidation of the tracked window clears it; a subsequent unique selection advances `window_generation` even when an observed destruction is followed by reuse of the numeric HWND. Repeated observations of the same identity do not advance its generation. `revision` advances on publication and across restart; these counters are local to a Monitor object, with SDK session identity retained separately.

Ownership is checked before and after geometry queries, and a destruction hook is required for availability. Windows observations are asynchronous: consumers must use the captured state as transient metadata, not as authorization to operate on an HWND. The controlled fixture observed recreation with a different numeric handle; numeric reuse and game-specific recreation remain pending actual observations.

## Coordinate and availability contract

The worker sets and verifies `DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2` using `SetThreadDpiAwarenessContext`, and restores it on exit. It never changes process-wide or game-thread DPI awareness. `GetClientRect` plus `ClientToScreen` acquire the client area in desktop physical pixel coordinates in this explicit querying context. Signed `x/y` preserve negative monitor origins; unsigned width/height describe extents. `MonitorFromWindow`/`GetMonitorInfoW` report the nearest monitor's physical desktop bounds. `GetDpiForWindow` is the window's effective DPI, which depends on that window's awareness; it is not a substitute for Electron's monitor conversion. ET-008 uses `screenToDipRect` for Electron placement. Actual game/DPI behavior still needs the REG-016 matrix.

`Status::available` means a validated window identity and visibility/minimize/foreground/monitor metadata are available. `client_bounds_available` separately states whether the current positive-size client rectangle was acquired. Actual minimized Windows fixtures returned 0x0 client geometry: the monitor keeps their minimized identity with `client_bounds_available=false` and empty bounds; it never repeats cached geometry as current. The serializer emits unavailable metadata for minimized, hidden, ambiguous, stopped, rejected, stale or zero-size observations. No old geometry is retained.

Foreground means exact equality with `GetForegroundWindow()`. The monitor never requests foreground, changes focus/z-order, injects input, modifies game window styles, or installs rendering hooks. `display_mode` is always `unknown`: client/monitor geometry and window styles cannot prove windowed/borderless/exclusive rendering. Exclusive fullscreen injection is outside scope.

## Transport and local freshness

`current_window` is a pure mapper. It requires an active SDK source, PMv2 observation, visible non-minimized positive client geometry, nonzero HWND/DPI, exact PID/Windows-session/plugin-session identity and the current process creation FILETIME captured by transport startup. The monitor observation must be no more than 250 ms old in `GetTickCount64` time, without a future timestamp. Signed physical origins and an exact uint64 decimal HWND are retained; display mode stays `unknown`. An absent optional provider preserves the ET-004a `not-supported` result, while an ineligible provider maps to `not-observed`.

Transport polls the monitor independently of `Adapter::read_latest`, including while SDK frames are paused or quiet. Changed revisions or expiry can produce window-only snapshots at the existing maximum 20 Hz display cadence. They keep the original SDK clock/capture, increasing transport sequence and continuity rules. One pending latest slot is retained; replacing it with a window update keeps its copied diagnostic observations and reserves their new sequence after the replacement snapshot. Only genuinely discarded SDK observations contribute to loss. Hydration and reconnect use the same mapper.

Protocol v0 has no independent window timestamp, window generation, visibility flag or monitor-bounds fields. The provider checks those fields locally; this package adds no wire fields. Consequently the receiver cannot reconstruct source window age or prove handle lifetime from a frame. Ingestion records separate local SDK and window receipts: the first valid checkpoint establishes the SDK receipt, and only a strictly greater SDK capture advances it. Equal-capture window updates cannot refresh speed/fuel. The existing 500 ms SDK expiry remains in both ingestion and preload; window availability has a separate conservative 250 ms receive TTL. Preload also retains its original SDK deadline across equal-capture deliveries and does not renew window expiry for a repeated local receipt. This receive TTL bounds how long delivered metadata is displayed, not the age of a delayed wire frame before receipt.

`currentGameClientBounds` exposes placement input only for the currently selected game source with fresh positive window geometry, foreground true and minimized false. It can return geometry while SDK metrics are stale; synthetic/replay, a mismatched game, background or unavailable/expired windows return no placement. It performs no HWND operations and creates no overlay. ET-008 still owns Electron `screenToDipRect` conversion and actual placement behavior.

## Verification

The controlled console test uses real owned Windows windows and a separately owned process fixture, shown with no activation. It checks rejection of false SDK claims, actual PID separation, physical negative bounds, DPI context isolation, move/resize, all available monitor moves, tool/owned-window exclusion, stable ambiguity, hidden/minimized/restore state, destruction/recreation, concurrent readers, cancellation and restart. A separate finite `eurotrucks2.exe` fake-SDK host uses the production identity rules and tests monitor-to-serializer-to-pipe movement/hide/minimize/restore/recreation with no new SDK frames. Named-host DLL lifecycle tests also exercise successful monitor startup and transport failure cleanup. These are controlled renamed fixtures, not games or evidence of publisher authenticity. CTest bounds the parent; the peer has its own finite exit deadline, readiness/stop events and normal owned cleanup. The `ETS2TELEMETRY_WINDOW_TEST_HOST` override is compiled only into separate console-test libraries, absent from the production monitor/DLL target. ASan copies instrument those console libraries only; new combined ASan execution is a separate pending hosted check.

See [the validation record](validation/et-007.md) for measured outcomes and missing acceptance evidence. No controlled window test establishes real-game focus/input safety, TruckersMP compatibility, exclusive/borderless detection, mixed-DPI behavior on absent displays, or overlay acceptance.

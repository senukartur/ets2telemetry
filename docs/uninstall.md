# Uninstall cleanup engine

ET-018 PR-2 (October 18, 2026) adds the engine that removes this application's own plugin files and local data on uninstall, in `apps/desktop/src/uninstall/`. It implements the owner's [uninstall rule of October 16, 2026](../DESIGN-DECISIONS.md#uninstall-removes-local-data--october-16-2026) and the ET-017 [contract with ET-018](plugin-setup.md#install-registry). Since ET-018 PR-3 the Squirrel uninstall hook runs it ([below](#squirrel-uninstall-hook)); PR-4 adds the [in-app uninstall](#in-app-uninstall), and PR-5 the [deferred cleanup at the next sign-in](#deferred-cleanup-at-the-next-sign-in). The [user guide](user-guide.md#uninstalling) explains both paths to users. Unit tests run it only on fake installs under guarded temporary folders.

| Module | Role |
| --- | --- |
| `roots.ts` | Derives the folders an uninstall may touch from the running executable (U3) |
| `pending-record.ts` | The atomic intent `<data root>\uninstall\pending.json` (U5 step 2) |
| `plugin-cleanup.ts` | Removes this application's plugin from the recorded game folders (U5 step 3) |
| `data-wipe.ts` | Removes the allowlisted data entries without following links (U4) |
| `engine.ts` | The order, the budget and the outcome (U5) |
| `deferral.ts` | PR-3: the README.txt a deferred run leaves, and cancelling a deferral on install, update or start (U7) |
| `executor.ts` | PR-5: copying the deferred-cleanup executor into `uninstall\` and its HKCU RunOnce registration (U7, O3) |
| `resources/uninstall/Complete-ETS2TelemetryUninstall.ps1` | PR-5: the executor itself, a Windows PowerShell 5.1 script that Forge ships as an extra resource |
| `../squirrel-events.ts` | PR-3: the Squirrel event handler that runs the engine on a Windows-initiated uninstall (U2, U6) |
| `app-uninstall.ts` | PR-4: the in-app uninstall's order: confirmation, preflight, plugin removal, the wipe after the exit and the handover (U8) |

## Roots

The central safety rule: an uninstall derives its folders from the running executable's install location, never from `%LOCALAPPDATA%` alone. `resolveUninstallRoots` reads the layout `<base>\ETS2TelemetryDesktop\app-<semver>\<executable>`:

- `app-<semver>` must be a folder named like Squirrel's version folders, and `ETS2TelemetryDesktop` must be a folder holding a regular `Update.exe`. Anything else, such as the portable package, an unpackaged or a development launch, is `NOT_INSTALLED`, and nothing is deleted.
- The base must be an absolute drive path, not a bare drive (checked before anything is read) and not a link: `LAYOUT_INVALID`. A relocated profile whose `AppData\Local` is itself a junction is therefore refused, and nothing is wiped. That is the safe direction; such a user removes the folders by hand, with the [manual steps](user-guide.md#removing-everything-by-hand) of the user guide.
- The data root is `<base>\ETS2Telemetry`; a link there is `DATA_ROOT_LINKED`.
- **Test-root mode.** When the base is named `LocalAppData` and its parent holds the ET-017 marker `ets2telemetry-plugin-test-root.marker` and a valid `ets2telemetry-install-test.json` (format `ets2telemetry.install-test`, version 1, a profile folder inside that parent, a RunOnce key `null` or `HKCU\Software\ETS2Telemetry-Test-<32 hex>\RunOnce`, and a `shortcuts` flag), the mode is `test-root`. The `LOCALAPPDATA` variable is ignored, and plugin cleanup is confined to that parent through the ET-017 confinement (`confineToRoot`). A marker or test file alone, or an invalid test file, is `TEST_ROOT_INVALID`, never production. A test install, even one uninstalled from Windows Settings, can therefore only wipe its own test root.
- **Production mode.** Otherwise the real location of the `LOCALAPPDATA` variable must equal the base's; a missing, relative or different value is `ROOT_MISMATCH`, and nothing is deleted.

The refusal codes carry no path. Only a successful result holds paths, and only main uses it.

## Intent

Before the first deletion the engine writes `<data root>\uninstall\pending.json` atomically (a synced temporary file renamed over it):

```json
{"format": "ets2telemetry.uninstall-pending", "version": 1, "phase": "plugins", "startedUtc": "...", "attempts": 1,
 "known": ["<sha256>", ...], "folders": [{"game": "ets2", "root": "...", "hashes": ["<sha256>"], "temps": ["..."], "createdPluginsDirectory": false}]}
```

- `known` holds the bundle's own and earlier released hashes; a later run adds the intent's `known` to its own, so a run from a different build keeps the older released hashes (this build's hashes first, the intent's only up to the bound of 257, so the intent always stays writable); `hashes` the hashes recorded for that folder or named by a pending install or update; `temps` the exact temporary files of pending intents, each validated as the installer's name inside that folder's `plugins` folder.
- A later run merges the intent's folders with the registry's, so it can finish even after the registry is gone or unusable (see [registry states](#plugin-cleanup)). `attempts` counts the runs.
- When the run defers, the intent keeps only the folders still blocked, with `phase: "deferred"`.
- Parsing is strict (at most 128 KiB, 32 folders, 17 hashes and 16 temporary files per folder, 257 known hashes); an invalid or linked file is ignored, never trusted.
- **Bounds of the merge** (advisory review of PR-2, October 18, 2026). The registry's own bounds do not keep the merge inside the intent's: 16 install records and 16 pending intents can name 32 folders, and one folder up to 17 hashes and 16 temporary files, while the previous intent adds its own 32 folders, 17 hashes and 16 temporary files. Writing such a merge would fail, and every run would be refused with `INTENT_FAILED`. Raising the intent's bounds would not help, because each run would merge the larger intent again. So the run **cleans every merged folder with the full merged hashes and temporary files**, and the intent **records what fits**:
  - the intent's own folders first, each with its own hashes and temporary files first, because once the registry is gone or unusable only the intent knows them; then the registry's folders, in registry order; each list cut at its bound;
  - if the record still exceeds 128 KiB (roots near the registry's 4096-character bound), folders drop from the end, the registry's first.

  Nothing is lost: whatever the intent cannot hold comes from the registry alone, and stays there, because a folder leaves the registry only after it was cleaned with the full list, and `setup.json` is wiped only after a clean run. The engine logs `UNINSTALL_INTENT` with the merged and the recorded folder counts. The one remaining limit is pathological: if the registry later turns unusable, a folder only it named is not cleaned, by the same rule as any other folder of a bad registry; and only when the intent's own folders plus a longer `known` list from a new build no longer fit in 128 KiB can one of the intent's own folders drop out. Before that happens, the known hashes that only an earlier intent carried are trimmed from the end, while this build's own stay. A folder that still drops out is attempted in that run; if it is blocked there and no usable registry names it, it is forgotten (only the `UNINSTALL_INTENT` log shows `folders` and `recorded` differing).

## Plugin cleanup

The ET-017 contract, step by step:

- **Registry states.** Only a registry that loads as `loaded` or `empty` is acted on. An `invalid-file`, `newer-version` or `unreadable` registry names no folder: no game folder is derived from it, and it is neither read for hashes nor updated. The run defers with `REGISTRY_INVALID`, `REGISTRY_NEWER` or `REGISTRY_UNREADABLE`, and `plugins\` stays with `setup.json` and any `setup.rejected-*.json`, even when every folder is clean. An `empty` registry names no folder.
- **The intent's folders with a bad registry** (advisory review of PR-2, October 18, 2026). The folders an earlier run recorded in its intent are still cleaned, by the same per-folder rules and only with the hashes and temporary files the intent itself records (plus the `known` hashes). They were written by this application before the registry turned bad, the intent is parsed strictly and independently of the registry, and a run already cleans them the same way when the registry is gone (`empty`); a bad registry must not make the cleanup weaker than a missing one. A blocked folder stays in the rewritten intent, and a cleaned one leaves it. Earlier, such a run rewrote the intent with no folders, so a folder blocked by a running game was forgotten the first time the registry turned bad. This replaces the PR-2 decision that a bad registry touches "not even the folders of an earlier intent" ([ET-018 validation](validation/et-018.md#advisory-review-fixes-october-18-2026)).
- **Folders.** Every folder named by an install record or by a pending `install` or `update` intent, plus the intent's folders, each once. A pending removal adds no folder.
- **Running games.** One running-game check (`game-processes.ts`), at most 3 s, before any folder. A running game or TruckersMP client blocks that game's folders (`GAME_RUNNING`, `CLIENT_RUNNING`); a failed or slow check blocks all of them (`RUNNING_CHECK_FAILED`). When the budget expires, the check's AbortSignal is aborted, so `tasklist` (bounded to 10 s on its own) never outlives the 10 s uninstall hook.
- **Per folder.** The layout is checked again without following links: a linked `bin`, `bin\win_x64` or `plugins` is `LINKED_FOLDER`, a missing root whose parent still exists is `absent` (note `GAME_FOLDER_GONE`), and a missing parent, or a parent that is not a plain folder, such as on an unplugged drive, is `FOLDER_UNAVAILABLE`; a root that is a link to a missing target defers like an unplugged drive. Then the exact temporary files are removed when they are regular files, the DLL is removed only while its hash is a recorded, pending or known hash, and the `plugins` folder only when this application created it and it is empty.
- **A game Steam uninstalled.** Steam usually leaves the game root behind when it holds files Steam did not install, such as this plugin, and removes the executable. Such a root is no longer a game folder, but it is not left to block forever (review of PR-2, October 18, 2026):
  - when the root is a folder (followed like ET-017 follows it, so a junctioned root of a game moved to another drive is reached) and `bin`, `bin\win_x64` and `plugins` are plain folders, not links, the same steps run by hash ownership as for a game folder (exact temporary files, a recognized hash only, a read-only DLL skipped, the plugins folder removed only if this application created it and it is empty); the folder's note is `GAME_EXECUTABLE_MISSING`;
  - when the root is not a folder, or one of the three is a link or not a folder, the folder is **not inspected**: nothing is read or touched through it, and it counts as `absent` with the note `LAYOUT_NOT_PLAIN`, so a plugin may remain there;
  - when one of them does not exist, nothing is left to clean: `absent` with the note `PLUGINS_FOLDER_ABSENT`.

  The result lists each such folder's game and note under `plugins.notes`. These notes must reach the user, because `LAYOUT_NOT_PLAIN` means a plugin may remain that this application did not check: PR-3's [receipt](#receipt) carries them, and **PR-4's result dialog must show them** with the outcome.
- **Kept.** A file with the plugin's name and an unknown hash, and every other file, stays; that folder is reported as `unrecognized` and does not block. A read-only DLL is skipped and reported as `READ_ONLY_FILE`, because Node's unlink on Windows would clear the attribute.
- **Locks.** A sharing violation (`EBUSY`) on the unlink is retried after 20, 40, 60, 80 and 100 ms, then reported; `EPERM` (a mapped image or a denied delete) is reported at once. Both are `TARGET_LOCKED`. A DLL another process opened without read sharing fails the hash read with `EBUSY`, also `TARGET_LOCKED`.
- **Registry.** After each cleaned folder, its install record, pending intents and failure are removed from `setup.json`.

`plugin-installer.ts` now exports the shared `hashPluginFile` and `removeEmptyPluginsDirectory`; the installer calls them unchanged.

## What is removed

The data root's top-level allowlist is `data`, `backups`, `settings`, `logs`, `synthetic`, `plugins`, `captures`, `transport`, `uninstall` and, since ET-055 PR-6, `updates` (the in-app update's download, UP18), compared case-insensitively; the deferred-cleanup executor uses the same list. A unit test fails if `dataPaths()` names anything outside it.

- **The walker** lstats every entry and never follows a link: a symbolic link or junction is unlinked itself, so its target is never entered. It never clears a read-only attribute; a read-only file stays and is reported (`READ_ONLY_FILE`), as does a locked or denied entry (`TARGET_LOCKED`, `PERMISSION_DENIED`).
- **Unknown top-level entries** stay and are counted as `kept`; the data root is removed only when it is empty.
- **Never touched:** exports, other plugins and game files, `%LOCALAPPDATA%\SquirrelTemp`, Squirrel's own binaries and any server records.
- **Roaming userData (O7).** The engine calls an optional `removeRoamingUserData` hook only in production mode and only after a complete run; in test-root mode the result is `not-applicable`. PR-3's hook removes `%APPDATA%\ETS2Telemetry Desktop` only when userData is exactly that folder and no `ETS2TELEMETRY_PROFILE_DIR` is set, and never through a link. It removes everything but Chromium's `lockfile` while it still holds the single-instance lock, then releases the lock and removes the `lockfile` and the folder. In the window between that release and the last removal (one or two file operations) a new start could take the lock and recreate the folder and its own logs in the data root; a start in the middle of a Windows uninstall makes that unlikely, and the hook does not detect it. Chromium may also recreate an empty folder while the hook process exits, which stays recorded. The in-app path does not call the hook itself, because the running application holds that folder: it hands over to `Update.exe --uninstall`, whose hook finds the data root gone, completes and removes the folder then ([in-app uninstall](#in-app-uninstall)). A Windows-initiated uninstall that defers leaves the folder to the [deferred-cleanup script](#deferred-cleanup-at-the-next-sign-in), which removes it after its own complete run, in production only (review of PR #123).

## Order and outcome

1. Read-only preflight: roots, registry, previous intent, running games.
2. The intent, before anything is deleted. If it cannot be written, the run is `refused` with `INTENT_FAILED` and nothing changes. Then, still before anything is deleted, the Squirrel hook's run copies and registers the [deferred-cleanup executor](#deferred-cleanup-at-the-next-sign-in) (the `armExecutor` port; the in-app scopes never do).
3. Plugin cleanup, folder by folder, with the registry updated after each.
4. Every folder clean: the allowlisted data except `plugins` and `uninstall`, then `plugins`, then `uninstall`, then the empty data root, and last the executor's registration (the `disarmExecutor` port).
5. A folder blocked or a data entry left: everything except `plugins` and `uninstall` goes, the intent keeps what is left, and the executor stays registered.

`runUninstall` returns `complete`, `deferred` or `refused` with one primary code and counts: plugins `removed`, `absent`, `unrecognized` and the `blocked` games with their reasons, data entries `removed`, `kept` and `failed`, whether the data root is gone, the Roaming result and the executor's registration (`registered`, `removed`, `not-applicable`, `failed` or `not-run`). It never carries a path. `complete` means nothing of this application is left in a game folder or an allowlisted data entry; unknown entries may remain and are counted.

- **Budget.** The caller passes a monotonic clock and a deadline (PR-3 uses 8 s inside Squirrel's 10 s hook). Before each folder and each data entry the engine checks it; once spent, the run stops and defers with `BUDGET_EXPIRED`. It never reports `complete` with something left. Since the review of PR-4 a spent budget deletes nothing more but still lists every allowlisted entry it did not reach as `BUDGET_EXPIRED` in `data.failed`, `plugins` and `uninstall` included when the plugin folders were clean, so the receipt and the in-app result name everything that remains; before, the list stopped at the first entry. The check is latched within one wipe. A real failure still keeps `plugins` and `uninstall` for the deferral without listing them.
- **Interruption.** Every step can be cut off and run again: a run killed after any deletion leaves a state that the next run finishes, from the registry, the intent or what is on disk.

## Squirrel uninstall hook

ET-018 PR-3 (plan U2, U6). Windows Settings, Apps and Control Panel run the registered `"<install root>\Update.exe" --uninstall`. Squirrel first ends every process whose image lies under the install root (`KillAllExecutablesBelongingToPackage` at the pinned commit), then starts the installed executable with `--squirrel-uninstall <version>` and waits at most 10 s; whatever the hook reports, Squirrel then deletes the binaries and the registration. `apps/desktop/src/squirrel-events.ts` handles it before anything else in main (see [application lifecycle](app-lifecycle.md#squirrel-events)):

1. **Roots** (above). A refusal writes a `refused` receipt and changes nothing.
2. **A running instance.** In test-root mode userData is first set to the test file's `profileDir`, the folder a test launch locks. A running portable copy uses the same userData and the same data root as the install, so it also receives the request, quits, and its data is wiped: the owner's rule removes this application's local data, whichever copy wrote it. The hook requests the single-instance lock with `{ets2telemetry: 'uninstall-exit'}`; a running instance answers with its explicit exit, reason `uninstall`, and deletes nothing itself. The hook requests the lock again every 200 ms for up to 6 s; each refused request signals the instance again (`tests/unit/single-instance-relock.test.ts` proves this with the real Electron binary). An instance that is still running, or a profile that could not be set, defers everything with `INSTANCE_RUNNING`: the engine writes the intent and touches no game folder or data entry.
3. **The engine** with a global deadline. Squirrel's 10 s start when it spawns the process, so the deadline counts from the process time origin (`performance.now()` is 0 there): the engine stops at min(hook start + 8 s, 8 s − 0.5 s), the margin covering the time before that origin. The running-game check gets at most 3 s and never more than what is left. A game or TruckersMP that runs, a lock, a permission error, an unreadable registry or the deadline gives `deferred`. Right after the intent, before the first deletion, the hook copies the executor and registers it under RunOnce ([below](#deferred-cleanup-at-the-next-sign-in)); each `reg.exe` call gets 2 s, cut to what is left before the deadline but never below 0.5 s.
4. **Shortcuts.** Beside the engine, `Update.exe --removeShortcut=<executable>` runs for a production install, and for a test install only when its test file sets `shortcuts: true`, within 4 s; Squirrel does not remove the shortcuts of an application that handles its events. `--removeShortcut` removes only the current name, so the hook then deletes this install's old-name `ETS2Telemetry Desktop.lnk` on the Desktop and in the Start menu folder, within 1 s and never past the engine deadline, without requiring a current one; a foreign or unreadable file of that name stays, and an unreadable one, or one left at the deadline, makes the receipt's `shortcuts` `failed` (ET-045h, [shortcut migration](release.md#shortcut-migration-et-045h)).
5. **README.** A deferred run writes `uninstall\README.txt` ([Deferral](#deferral)); when the executor is registered, it says that the cleanup finishes at the next sign-in.
6. **No process left.** Squirrel deletes the install folder as soon as the hook's main process exits, so no process of this application may still hold a file then. Every Squirrel event process starts no child process (hardware acceleration off, the GPU and the network service in process; see [application lifecycle](app-lifecycle.md#squirrel-events)), and before the receipt the uninstall hook waits, polling every 200 ms until its engine deadline, until no other process of its executable runs in its own Windows session (by image name and tasklist's session number, without itself and its own children): an instance Squirrel ended or a portable copy that got the uninstall-exit request may still be ending. Processes in other sessions, such as another signed-in user's copy, are never counted or waited on. Nothing is counted once the deadline has passed, and a listing still running at the deadline is cut off, so the wait never runs into the hard stop. The receipt records the last count (`null` when nothing was counted) and the wait.
7. **Receipt and exit.** One receipt, then the exit code 0 (`complete`), 3 (`deferred`) or 4 (`refused`). A hook still running at the hard stop, min(hook start + 9 s, 9 s − 0.5 s) on the same clock (a file operation that never settles), writes a `deferred` receipt with `BUDGET_EXPIRED` and exits 3. If the engine reached its intent, a later run finishes; otherwise nothing was deleted. The run and the hard stop claim the result once: whichever claims first writes the only receipt and sets the exit code, and the process exits only after that receipt was written. If the engine itself throws, the receipt is `deferred` with `ENGINE_FAILED`; if a hook step before the engine throws, `deferred` with `HOOK_FAILED`, and nothing was deleted. A step after the engine (the README, the shortcuts, the process wait) never replaces the engine's result: the receipt keeps its outcome and counts and names the step in `failedStep`.

`complete` is impossible while anything remains: the hook downgrades an engine result of `complete` to `deferred` with `RESIDUE_REMAINS` when a folder is blocked, a data entry failed or the data root still exists.

**The Installed apps icon (ET-045g).** The install and updated hooks place `<install root>\app.ico` and set the uninstall entry's `DisplayIcon` ([releases](release.md#installed-apps-icon-et-045g)). Both belong to Squirrel's layout, not to the data root: Squirrel's uninstall deletes the install root's files, `app.ico` among them, and `RemoveUninstallerRegistryEntry` deletes the key with its `DisplayIcon`. The engine, its roots (U3) and its allowlist (U4) are unchanged and never touch either. The hosted [residue check](installer-testing.md#binary-root-residue) refuses an `app.ico` left in the binary root.

### Receipt

`%TEMP%\ETS2Telemetry-uninstall-<yyyymmddThhmmssmmmZ>.json`, created new (never overwritten), with fixed codes, counts and allowlisted entry names only, never a path:

```json
{"format": "ets2telemetry.uninstall-receipt", "version": 1, "createdUtc": "...", "appVersion": "0.1.0",
 "outcome": "complete | deferred | refused", "code": null, "mode": "production | test-root | null", "instance": "none | exited | running | not-checked",
 "plugins": {"removed": 1, "absent": 0, "unrecognized": 0, "notes": [{"game": "ets2", "note": "GAME_EXECUTABLE_MISSING"}], "blocked": []},
 "data": {"removed": 8, "kept": 0, "failed": [], "rootRemoved": true}, "roaming": "removed | failed | not-applicable | not-run",
 "executor": "registered | removed | not-applicable | failed | not-run", "readme": false, "shortcuts": "removed | skipped | failed", "startupOffsetMs": 180, "otherProcesses": 0, "processWaitMs": 0, "elapsedMs": 1234}
```

`code` is the engine's primary reason (a roots refusal, `INTENT_FAILED`, `RUNNING_CHECK_FAILED`, `BUDGET_EXPIRED`, a registry problem, a plugin block reason, `DATA_ENTRY_BLOCKED`, `INSTANCE_RUNNING`) or one of the hook's own: `RESIDUE_REMAINS` (the engine said complete, but something is left), `ENGINE_FAILED` (the engine itself threw; a later run finishes from the intent if the engine reached it) and `HOOK_FAILED` (a step before the engine threw, such as the instance lock; the engine did not run and nothing was deleted).

The texts for the two failures depend on the path (review of PR-3, settled in PR-4). After a Windows-initiated uninstall Windows has already removed the program, so "run the uninstall again" cannot be followed there:

| Code | In-app path (`UNINSTALL_FAILURE_TEXT`, shown on the card) | Windows-initiated path (the receipt; [user guide](user-guide.md#if-something-is-left-behind)) |
| --- | --- | --- |
| `ENGINE_FAILED` | "Yukon Union Telemetry was not uninstalled: an unexpected error stopped it. Nothing more was removed; run the uninstall again." | "The uninstall cleanup stopped because of an unexpected error. Windows removed the program; follow `%LOCALAPPDATA%\ETS2Telemetry\uninstall\README.txt` if it exists, or reinstall Yukon Union Telemetry and uninstall it from the application." |
| `HOOK_FAILED` | Not used: the in-app path runs no hook. | "The uninstall could not start its cleanup, and nothing of your data or plugin was removed. Reinstall Yukon Union Telemetry and uninstall it from the application, or remove the files by hand as the user guide describes." |

`executor` (PR-5) is the deferred-cleanup executor's registration when the receipt was written: `registered` after a deferred run, `removed` after a complete one, `not-applicable` for a test install without a RunOnce key, `failed` when the copy, the registration or its removal failed (the README stays the fallback), `not-run` when the engine never got there. `shortcuts` is `removed` only when `--removeShortcut` succeeded, no owned old-name shortcut failed to delete, and no old-name shortcut was left undecided (ET-045h; the field and its values are unchanged); `failed` otherwise, and `skipped` for a test install without shortcuts. Undecided means its ownership was never settled, so it may still be this install's: a candidate left at the step's deadline, a file that could not be inspected, or a shortcut Electron could not read. A shortcut proven foreign by the ownership rule, or a link, folder or oversize file at the old name, stays and does not make the receipt `failed`. When the Desktop and Start menu folders cannot be resolved at all, nothing is looked at and nothing counts. `failedStep` is `readme`, `shortcuts` or `process-wait` when a step after the engine threw, otherwise `null`; the outcome and counts are the engine's either way. `startupOffsetMs` is the time from the process time origin to the hook's start, so CI can measure how much of Squirrel's 10 s the startup takes; `otherProcesses` is the number of other processes of this executable in the hook's session still running when the receipt was written (`null` when they were not counted: the deadline had passed, or the listing failed or was cut off), and `processWaitMs` how long the hook waited for them; the outcome does not change with them, because they concern Squirrel's binaries, not the data or plugin cleanup. `elapsedMs` is the time from the hook's start to the receipt. The in-app path's result dialog explains the same `outcome`, `code`, `plugins.blocked`, `plugins.unrecognized` and `plugins.notes` ([in-app uninstall](#in-app-uninstall)); the receipt is the Windows-initiated path's only record, because nothing can show a window there.

### Deferral

A deferred run leaves `plugins\` (the install registry) and `uninstall\` with `pending.json`, `README.txt` and, since PR-5, the registered executor `Complete-ETS2TelemetryUninstall.ps1`. The README (CRLF, plain text) names the reason, says when the executor finishes the cleanup at the next sign-in (at most 10 attempts), and gives the manual fallback: the plugin file of each remaining game folder, the SHA-256 hashes of this application's plugin, how to check a file with `Get-FileHash`, then to delete the `plugins` and `uninstall` folders and to check anything else in the data root before deleting it (the engine keeps unknown entries on purpose), or that reinstalling cancels the cleanup.

A new install, an update (`--squirrel-install`, `--squirrel-updated`) or a start of the installed application cancels a pending deferral: it removes only `uninstall\pending.json`, `uninstall\README.txt` and the copied executor when they are regular files (never through a link), then the `uninstall` folder when it is empty, then (PR-5) the executor's RunOnce value, and silent plugin setup adopts the remaining plugin files from the registry. The registry is touched only when there was something to cancel. A start logs `UNINSTALL_DEFERRAL_CANCEL` with `cancelled` or `failed` and the executor state only when there was something to cancel. Unpackaged and development launches never cancel.

## Deferred cleanup at the next sign-in

ET-018 PR-5 (plan U7, owner decision O3, October 18, 2026). Squirrel deletes the program after its uninstall hook whatever the hook reports, so a hook that defers (a game or TruckersMP runs, a file is locked, the 8 s budget ran out) leaves no application that could finish later. The retained executor does it at the next sign-in.

**Registration** (`apps/desktop/src/uninstall/executor.ts`).

- Forge ships `resources/uninstall/Complete-ETS2TelemetryUninstall.ps1` as an extra resource; `inspect:package` checks that the packaged copy is the only file in its folder, equals the tracked script by SHA-256 and is plain ASCII (Windows PowerShell 5.1 reads a BOM-less file in the ANSI code page, so the script stays ASCII). ET-055: the script holds both build channels' names and one line `$Channel = 'production'`; `scripts/build.mjs` stamps the build's channel into that line of the copy it stages for Forge (`scripts/uninstall-executor.mjs`), and `inspect:package` compares the packaged copy with the tracked script stamped the same way. A production copy equals the tracked script.
- The hook's engine run copies it atomically into `<data root>\uninstall\`, reads the copy back and compares it, then registers `HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce` value `ETS2TelemetryUninstall` = `"<windows>\System32\WindowsPowerShell\v1.0\powershell.exe" -NoProfile -NonInteractive -ExecutionPolicy Bypass -WindowStyle Hidden -File "<data root>\uninstall\Complete-ETS2TelemetryUninstall.ps1"` through the fixed `%SystemRoot%\System32\reg.exe`. reg.exe exits 1 both for a missing value and for any failure, with localized error text, so the port trusts only exit 0 and the listing on stdout: a removal that fails is `absent` only when the key's listing lacks the value, or when the nearest readable ancestor (up to `HKCU\Software`) does not list the key; a key that exists but cannot be listed is `failed`. The delete and these queries share one timeout (review of PR #123); `<windows>` is `%SystemRoot%`, expanded when the command is built, so no folder on PATH can stand in for PowerShell (review of PR-5). A copy that fails registers nothing, so the value never names a missing or partial script. A failure is recorded as `executor: failed`, and the README is the fallback.
- **260 characters.** Windows runs a Run or RunOnce command of at most 260 characters ([Run and RunOnce registry keys](https://learn.microsoft.com/en-us/windows/win32/setupapi/run-and-runonce-registry-keys)). The absolute form takes 139 characters plus the script's path, and the usual path `C:\Users\<name>\AppData\Local\ETS2Telemetry\uninstall\Complete-ETS2TelemetryUninstall.ps1` is 83 characters plus the user name, so with `C:\Windows` the absolute form fits user names of up to 38 characters. A longer path falls back to the PATH form, `powershell.exe ...` (94 characters plus the path, up to a path of 166 characters), and a path longer than that is not registered at all: README.txt is then the fallback. The installer lifecycle's run root on a hosted runner makes the path 126 characters, so it registers the PATH form; `Test-DeferredCleanup.ps1` checks the absolute form in a short scene and the unit tests check both bounds.
- **When.** Registration happens after the intent and before the first deletion, on every hook run that has something to clean, and the registration is removed only after a complete run, once the data root and the copied script are gone. Registering only on a deferred outcome would leave a window in which a hook killed after its first deletion (Squirrel stops waiting after 10 s, and the hard stop is at 9 s) leaves plugin files and no way to finish; registering first costs one `reg.exe` call more on a complete run and closes that window. A crash between the last deletion and the removal leaves a value that names a missing script: Windows deletes the value before it runs it, and PowerShell exits on the missing file, so nothing else happens.
- **Test installs.** A test root's `ets2telemetry-install-test.json` names its own key `HKCU\Software\ETS2Telemetry-Test-<32 hex>\RunOnce`, and the registration goes there. A test file with `runOnceKey: null` copies nothing and writes no key at all. The production RunOnce key is used only in production mode (U3 is unchanged), and the `reg.exe` port refuses every other key and value without starting `reg.exe`.

**The executor at sign-in.** Windows deletes the RunOnce value, then starts the script hidden. The script:

1. Takes its folders from its own location, `<base>\ETS2Telemetry\uninstall`, with no link in the base, the data root or the `uninstall` folder. ET-055: a staging copy works only in `<base>\ETS2TelemetryStaging\uninstall`, with the staging RunOnce value, plugin file, install root and Roaming folder; an executor of one channel inside the other channel's data root refuses with `LAYOUT_INVALID` and changes nothing. A test root (the base named `LocalAppData`, its parent holding the ET-017 marker and a valid test file) uses only the test file's key; otherwise the base must be the known-folder LocalAppData (`Environment.GetFolderPath`, never the `LOCALAPPDATA` variable), or the run is refused with `ROOT_MISMATCH` and changes nothing.
2. Reads the intent. Without one it only removes its value (`not-needed`, `NO_INTENT`). An intent that does not parse strictly, as `pending-record.ts` parses it, or that cannot be read, is never trusted: `INTENT_INVALID`, nothing changes, nothing is registered again, and README.txt says that the cleanup stopped.
3. Right away, before anything else, rewrites the intent with `attempts + 1` and, while that is below 10, registers itself again with the same command. The uninstall hook's own run is attempt 1, so the script runs at most 9 times. From this point any unexpected error or kill is followed by another counted attempt at the next sign-in; an error before it stops the cleanup (below).
4. Does nothing but remove its value when the application is installed again (`<base>\ETS2TelemetryDesktop\app-*\ETS2TelemetryDesktop.exe` exists: `not-needed`, `APP_INSTALLED`). The check sees only an installed copy: a portable copy that shares the data root does not stop the deferred wipe, in line with the owner's rule that an uninstall removes this application's local data, whichever copy wrote it.
5. Runs the same contract as the engine on the intent's folders, merged with the install registry's when `plugins\setup.json` is a valid version 1 document (an invalid, newer or unreadable registry adds no folder and keeps `plugins\`, as in the engine): no change while that game or a TruckersMP client runs (image names, `Get-Process`; a failed listing blocks every folder); the layout checked without following `bin`, `bin\win_x64` or `plugins`; the exact temporary files of pending installs; the DLL only while its SHA-256 is a hash this application installed and it is not read-only; the plugins folder only when this application created it and it is empty; in a test root, no folder outside it. Then the allowlisted data entries without following links and without clearing a read-only attribute, `plugins\` and `uninstall\` (with the script and the intent) only when every folder is clean, then the empty data root.
6. Complete: removes Electron's Roaming userData best effort (owner decision O7; review of PR #123), then its value, last. In production the folder is `%APPDATA%\ETS2Telemetry Desktop`, taken from the known folder ApplicationData (never the `APPDATA` variable), with exactly that name. A link or junction there is removed itself and never entered, and a read-only or locked file stays (`failed`). A test root never touches a Roaming folder (`not-applicable`), unless a test names a stand-in inside the test root. Unlike the hook, the script has no single-instance lock and no userData of its own to compare: the application is gone when it runs, except a portable copy, whose files may then stay. A portable copy that shares the Roaming userData and runs while the script completes keeps the files it holds open (`roaming: failed`); the rest of its Chromium profile is removed. The stand-in that tests name with `-TestRoamingFolder` must lie inside the test root through every link on the way down to it (`Test-Confined`, as for game folders), so a junction inside the test root that leads out of it is refused (delta review of PR #123). Still blocked: rewrites the intent with only the blocked folders and README.txt with the attempt (`deferred`, registered for the next sign-in); after the 10th attempt it stops, removes its value and says so in README.txt (`stopped`). The rewritten intent keeps the intent's own folders first and stays within 32 folders and 128 KiB, dropping the folders only the install registry names from the end, as `recordable` does in the engine (review of PR-5): an oversized intent would be refused by the next attempt. The script's JSON escapes only control characters, as `JSON.stringify` does, so a rewrite of the same content is never longer than the application's document.
7. Writes `%TEMP%\ETS2Telemetry-deferred-cleanup-<yyyymmddThhmmssmmmZ>.json` (a staging copy: `ETS2TelemetryStaging-deferred-cleanup-…`, ET-055) (format `ets2telemetry.deferred-cleanup-receipt`, version 1) with the mode, the outcome (`complete`, `deferred`, `stopped`, `refused`, `not-needed`), the code, the attempt, the plugin and data counts in the engine's shape, `roaming` (`removed`, `absent`, `failed`, `not-applicable` in a test root, `not-run` unless complete; the hook reports a missing folder as `removed`), `runOnce`, `readme` and `messageBox`, never a path; and, in production only, shows one message box with the outcome. A test run never shows a window. Exit code 0 (complete or not needed), 3 (deferred or stopped) or 4 (refused).

**An unexpected error** ends the run as `refused` with `EXECUTOR_FAILED` (review of PR-5). Windows removed the value before it started the script, so what happens next depends on where the error came: after step 3 the attempt was counted and the script registered again, so the next sign-in tries again, and README.txt says so (with the attempt); before step 3 nothing is registered, the cleanup stops, and README.txt says that it does not run again and how to finish by hand. The README lists the folders and hashes when the intent can be read; otherwise the notice goes above the README an earlier run wrote. When the roots themselves fail, the README goes into the script's own folder only if that is a plain folder named `uninstall`; a roots refusal (`ROOT_MISMATCH`, `LAYOUT_INVALID`, `DATA_ROOT_LINKED`, `TEST_ROOT_INVALID`) writes nothing, because that location is not trusted. Every path stays bounded by the 10 attempts. The `!` prefix, which makes Windows remove a RunOnce value only after its command ran, is not used: a run that fails before it counts its attempt (for example while it resolves its roots) would then be started again at every sign-in, without bound.

**Registering again during the run.** The Run and RunOnce documentation says that a program started from these keys should not write to the key while it runs, because that interferes with the other programs registered there, and that an application must not continually recreate RunOnce entries. The script writes its own value once per sign-in, at most 9 times in all, and only while the cleanup is still blocked. If Windows starts a value that is added while it still processes the key, a blocked script could run several times in one sign-in; each run counts an attempt, so this stays bounded by the 10 attempts. Whether that happens on a real sign-in is a pending manual check.

**What can stop the executor.** Antivirus or EDR products may flag or block a hidden PowerShell command started from RunOnce with `-ExecutionPolicy Bypass`, or the deletes it makes. A Group Policy execution policy (for example `AllSigned` for the machine or the user) overrides `-ExecutionPolicy Bypass`, and this script is not signed, so PowerShell refuses to run it. In each case nothing is removed at sign-in, and the cleanup degrades to README.txt and its manual steps, or to reinstalling and uninstalling from the application. Both stay manual checks.

The script takes no argument in production. Its four test parameters work in a test root only, and a production run that receives any of them is refused:

- `-TestRunningImages` replaces the process list;
- `-TestFailAt start|registered` raises an unexpected error before or right after the attempt is counted and registered;
- `-TestLateEntry <allowlisted entry>` creates that entry after the registry step, as a writer that kept running would leave it;
- `-TestRoamingFolder <folder>` names a stand-in for the Roaming userData, which must lie inside the test root (otherwise `TEST_PARAMETER_REFUSED`), so the production removal can be tested without a real Roaming folder.

**The last step, in both implementations** (merge with main, October 18, 2026). After clean earlier steps, the last step of the wipe removes every allowlisted entry still present, then `uninstall`, then the empty root: `wipeEverything` in `engine.ts` keeps nothing there, and neither does the script's `Clear-Everything`. Only after an unfinished earlier step (a failure or the budget) does the engine's last step become report-only. It then keeps every allowlisted entry except `uninstall` and only lists `uninstall` as not reached. The script has no budget, so it never reaches that mode. The shared case `allowlisted-entry-at-the-last-step` checks the clean path in both.

**One contract, two implementations.** `tests/fixtures/uninstall/deferred-cases.json` lists scenes (owned, released and unrecognized plugin files, a read-only file, a linked plugins folder, running games and clients, temporary files, a created plugins folder, a game folder that is gone or lost its executable, unknown, read-only and linked data entries) with the outcome, the code and what is kept or removed. `tests/unit/uninstall-deferred-cases.test.ts` runs them through the engine and `tests/windows/Test-DeferredCleanup.ps1` through the script. Known differences outside the table: the script maps an unexpected error on a game root to `IO_ERROR` where the engine may report `PERMISSION_DENIED`, it refuses a read-only temporary file of an interrupted install where Node's unlink would clear the attribute and remove it, and in a test root it resolves a link on a folder's way only one level, through its target.

## In-app uninstall

ET-018 PR-4 (plan U8, O8). The dashboard's Live tab ends with an **Uninstall Yukon Union Telemetry** card: a warning that the local trip history, which is not synchronized anywhere, is deleted for good with its backups, that settings, logs, captures and synthetic recordings are deleted as well, that trip exports saved elsewhere stay, and that the game plugin is removed from the game folders while the games are closed; then the button **Uninstall Yukon Union Telemetry…**. One bridge method, `uninstallApplication()`, reaches main ([application lifecycle](app-lifecycle.md#in-app-uninstall-et-018-pr-4) for the channel and the exit). `apps/desktop/src/uninstall/app-uninstall.ts` runs the steps:

1. **Roots** (above). A portable, unpackaged or development copy answers `not-installed` before any dialog, and the card says that uninstalling is available only in an installed copy. Another refusal answers `failed` with its code.
2. **Confirmation.** A native warning dialog owned by the dashboard window repeats the warning, with **Cancel** as the default and the Escape answer. Declining answers `cancelled`; nothing changes.
3. **Preflight, read-only.** The engine runs with scope `preflight`: roots, registry, previous intent, the running-game check and every folder's layout and DLL, with the plugin cleanup in a dry run that deletes nothing. A running game or TruckersMP, a read-only plugin file, a linked folder, a lock, a failed listing or a registry problem answers `blocked` with the primary code and one `{targetId, reason}` per blocked folder, and nothing changes. `targetId` is the plugin card's id (`ets2:steam:0`, `ats:manual:0`), or `<game>:other` for a recorded folder the card no longer lists. A file with the plugin's name that this application did not install does not block; it stays.
4. **Plugin setup suspended.** Silent setup stops its timers, aborts its run in flight and waits until that run and its registry write have settled. While suspended it starts nothing and refuses exclusion changes and folder choices.
5. **Plugin removal.** The engine runs with scope `plugins`: it writes the intent, removes the plugins and updates the registry, and stops there; no data entry is touched yet. A removal that fails now, because a game started since the preflight or a file was locked, removes the intent (this path writes no README), resumes setup and keeps the data. If no plugin file was removed yet, it answers `blocked`, and nothing changed that matters in use: `blocked` means that no plugin file was removed, although the removal may already have cleaned the stale install record of a game that was uninstalled or the leftover temporary file of an interrupted plugin install. If some were (another game's folder came first), it answers `interrupted` with the number removed: the card says that the plugin was removed from some game folders, that the data was kept, and that ETS2Telemetry puts the plugin back automatically in every game folder it manages while that game is closed, which the resumed setup run does. An engine that throws answers `failed` with `ENGINE_FAILED` after the same cleanup.
6. **`started`.** Main runs the explicit exit with reason `uninstall`, wipes the data after the service and every writer stopped (`wipeEverything`, within what is left before the 12 s failsafe less 1 s, at most 5 s), shows the result dialog with every note and remaining entry, and hands over to `Update.exe --uninstall` ([application lifecycle](app-lifecycle.md#in-app-uninstall-et-018-pr-4)).

Only one run at a time: a second request while one runs, or after `started`, answers `failed` with `BUSY`. Since ET-055 PR-6 the in-app update excludes it: while an update downloads, installs or restarts, main and the orchestrator answer `failed` with `UPDATE_IN_PROGRESS`, checked before the confirmation and again after it closes, and nothing changes ([application lifecycle](app-lifecycle.md#in-app-updates-et-055)). Main logs `APP_UNINSTALL` with the outcome, code, number of blocked folders and, for `interrupted`, the number of plugin files removed, and the engine its `UNINSTALL_PREFLIGHT` and `UNINSTALL_PLUGINS` counts; none carries a path. The card shows each outcome and reason as a fixed text from `apps/desktop/src/strings.ts` (`UNINSTALL_STRINGS`, `UNINSTALL_REASON_TEXT`, `UNINSTALL_FAILURE_TEXT`, `UNINSTALL_TARGET_TEXT`), and the result dialog the `UNINSTALL_NOTE_TEXT` and `UNINSTALL_DATA_ENTRY_TEXT` texts.

**Why the wipe waits for the exit.** The service holds the history database open, and the log writer and plugin setup write into the data root. Wiping before they stop would fail on the locked database and could let a late write recreate a folder. The order is therefore: plugins while the application runs (so a running game still blocks with nothing deleted), then the exit, the final log rows, and the wipe.

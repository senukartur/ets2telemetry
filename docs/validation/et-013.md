## Test runner spike

Vitest 5.0.3 runs unchanged inside the pinned Electron executable in Node mode. `scripts/run-electron-node.mjs` starts `node_modules/electron/dist/electron.exe` with `ELECTRON_RUN_AS_NODE=1`, inherited standard streams and the child's exit code; Vitest's `forks` pool starts its workers from the same executable, so every test file runs on Electron 44.7.0 (Node 24.21.0, module ABI 149). The configuration prints that runtime and, like `tests/storage/setup.ts`, fails under any other runtime; plain `node` running the storage configuration failed as intended. The `node:test` fallback in the plan was not needed.

The spike also observed facts the design relies on, with better-sqlite3 13.0.3 and SQLite 3.53.4:

- A reopened WAL database reads `synchronous = 1` before any explicit setting, which confirms the compiled `SQLITE_DEFAULT_WAL_SYNCHRONOUS=1`.
- With `locking_mode = EXCLUSIVE` set before WAL, no `-shm` file is created; a second connection, read-only or read-write, gets `SQLITE_BUSY`.
- A read-only connection to a WAL-format file creates `-wal` and `-shm` and leaves them behind; backups are therefore switched to rollback-journal mode before verification, and the open-time inspection removes the files it created.
- A read-only connection with exclusive locking on a live WAL fails with `SQLITE_IOERR_LOCK`, so the inspection uses an ordinary read-only connection.
- A Windows read-only file opens "read-write" without an error and fails at the first lock with `SQLITE_IOERR_LOCK` or at the first write with `SQLITE_READONLY`; the open now checks write access first and reports `PERMISSION_DENIED`.
- `max_page_count` below the needed size fails a transaction with `SQLITE_FULL` and rolls it back.
- SQLite returns an integral REAL as an integer internally, so `-0.0` reads back as `0`. The samples test records this as expected behavior; canonical event payloads keep `-0`.

## Fixture provenance

`schema-v1-representative.sqlite`, `schema-newer-999.sqlite` and `foreign-application.sqlite` were created once on October 15, 2026 by executing their `.sql` files with better-sqlite3 13.0.3 into new files in rollback-journal mode, with a throwaway builder that is not committed. The representative SQL contains the exact `sqlite_schema` text that migration `0001-initial` produced and hand-chosen synthetic values: one ETS2 synthetic session, a job configuration with u64 maximum expected income, a truck, a trailer with a provided empty accessory id and unobserved names, a gap [4, 5], a cancellation with the s64 minimum penalty, an event at eventSeq 9007199254740993, a cancelled trip, attributions, a completeness interval and three samples with every availability state and monotonic time 2^63-1. Only the `payload_json` texts were produced by the canonical JSON encoder, because a redelivery must compare equal to them. `schema-v1-representative.expected.json` was written by hand from the SQL. `manifest.txt` lists the SHA-256 of every fixture file; `.gitattributes` keeps the databases binary and the text files LF.

## Post-review fix (PR #51 advisory review)

The advisory Claude review of PR #51 found that trip references were resolved by `trip_uuid` alone. An ATS session's samples, attributions, completeness intervals, updates and closes could bind to an ETS2 trip and still commit, and `trip.update` wrote configurations of the current session onto that foreign trip. Coordinator decision, implemented in `346365f`:

- Every trip reference must name a trip of the current session's game, otherwise `INVALID_INPUT`, and the whole transaction, including the event, rolls back.
- A trip of an earlier plugin session of the same game stays referable, because ET-014 closes it with close reason `restart` from the new session.
- A closed trip accepts only `trip.update` of recording completeness and observed distance.

The new tests in `events-commit.test.ts` check four cases. An ATS session's attribution, completeness interval, update, close and sample against an ETS2 trip are each refused, with the event and the sample rolled back. A same-game later session closes the trip with `restart`. A closed trip refuses game-mode and truck updates but accepts completeness and distance.

RED: without the game guard, the cross-game test failed; without the closed-trip restriction, the closed-trip test failed. Both files were restored byte for byte.

## Close flake in `worker.test.ts` (October 15, 2026)

The owner directed on October 15, 2026 that flaky tests be fixed by subagents. This section records one such fix on branch `fix/storage-worker-close-flake`, based on `origin/main` `4076d0d`.

### Failure

`npm run test:storage` failed once on the shared development host. The host was at about 20% CPU, with other agents running. In `tests/storage/worker.test.ts`, the case "reports a second writer and a read-only file through the worker" received `{clean: false}` from `holder.client.close()` after 5,370 ms. Reruns passed, with the case taking 3.3–3.9 s.

### Cause

The test clients used the production close grace, `CLOSE_GRACE_MS` = 2,000 ms. `StorageClient` reports a close as clean only after the worker answers the close and exits with code 0. If that does not happen within the grace, the client terminates the worker and reports `{clean: false}`. The test therefore depended on a real close finishing within 2 s of wall-clock time on a shared host, although it checks the close protocol, not close latency.

Evidence:

- **Phase timing.** A temporary, uncommitted instrumented copy of the case measured the phases. The holder open took 45–49 ms. The refused second open took 3.2 s, because it waits out SQLite's busy handler. The holder's close answer and thread exit took 6–16 ms. The failed run was about 2.1 s longer than a normal run: the 2,000 ms grace plus termination. The other unclean paths (a worker error, an exit before the answer or with a non-zero code, a refused close) end the close within milliseconds of the event, so they cannot account for that duration.
- **Reproduction.** Holding the holder's close request on the worker thread for 2.5 s reproduced the reported failure: the same assertion line, `{clean: false}`, after 5,304 ms.
- **Load does not reach 2 s.** The load generator ran 24 CPU-bound threads and 4 threads that wrote 1 MiB with `fsync` in a loop, on this 24-logical-processor host. Under it, 15 isolated closes took 9–31 ms. With the whole storage suite running in parallel under the same load, 10 closes took 10–51 ms with one outlier of 629 ms, and a further 80 closes had a median of 14 ms, a 95th percentile of 35 ms and a maximum of 295 ms. Without the load generator, 10 closes inside the suite took 6–18 ms.
- **A busy main thread does not cause it.** Blocking the client's main thread for 800 ms right after `close()`, in a microtask and in a timer callback, with a 500 ms grace, still produced `{clean: true}` and exit code 0. libuv delivers the worker's answer and exit, which are already pending, before it runs the expired grace timer.

So the holder's worker thread did not finish closing the database and exiting within 2 s of real time. The stall was in the worker or the operating system, for example a slow file flush or a file-system filter driver on the WAL checkpoint (ESET Security and Avast Antivirus are registered on this host; Microsoft Defender real-time protection is off). The specific source was not identified and could not be reproduced with CPU or disk load.

### Decision

This is a test-only race, not a product bug. The client behaved as specified. A close that a stall holds past the grace is reported unclean, which is the documented outcome. The new test below shows that committed data stays intact when the worker is terminated. The service uses an 800 ms grace inside its 1,000 ms `history-storage` step. A stall like this one would make it report `stopped {clean: false}`, as [storage](../storage.md#history-database-in-the-telemetry-service) documents. The measured closes stayed below 800 ms. However, the 629 ms outlier, recorded under deliberate oversubscription, leaves about 1.3 times headroom at that load. No product code or budget changed.

### Fix

Commit `ff19225`, test-only:

- The real-worker clients in `worker.test.ts` use `TEST_CLOSE_GRACE_MS` = 15 s. The constant bounds a hung close inside the 30 s case timeout and is documented as not being a latency check. A hung close still fails, as `{clean: false}`.
- A worker variant, `DELAYED_CLOSE_WORKER`, wraps the unchanged bundled worker. It holds each `close` request on the worker thread with `Atomics.wait` before the host receives it. Two new cases use it. In the first, a close held 500 ms past the 2 s default still ends `{clean: true}` with exit code 0; this is the regression test. In the second, a close held past a 200 ms grace is terminated: exit code 1, `{clean: false}`. A new worker then reopens the database with coverage `1` and the open trip intact. This checks grace expiry against the real worker, in addition to the fake-timer cases in `storage-client.test.ts`.
- The second-writer case also asserts exit code 0 for the holder's and the second worker's closes.

No assertion was removed and no retry was added. The production `CLOSE_GRACE_MS` and `HISTORY_CLOSE_GRACE_MS` are unchanged.

### RED

Before the fix, the test clients used the default grace. The new regression case failed with `{clean: false}` after 2,082–2,093 ms. The second-writer case, with its holder's close held for 2.5 s, failed with `{clean: false}` after 5,304 ms. With the fix and the same 2.5 s hold, the second-writer case passed in 5,840 ms. The temporary hold was then removed.

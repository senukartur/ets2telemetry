## Test runner spike

Vitest 5.0.3 runs unchanged inside the pinned Electron executable in Node mode. `scripts/run-electron-node.mjs` starts `node_modules/electron/dist/electron.exe` with `ELECTRON_RUN_AS_NODE=1`, inherited standard streams and the child's exit code; Vitest's `forks` pool starts its workers from the same executable, so every test file runs on Electron 44.7.0 (Node 24.21.0, module ABI 149). The configuration prints that runtime and, like `tests/storage/setup.ts`, fails under any other runtime; plain `node` running the storage configuration failed as intended. The `node:test` fallback in the plan was not needed.

The spike also observed facts the design relies on, with better-sqlite3 13.0.3 and SQLite 3.53.4:

- A reopened WAL database reads `synchronous = 1` before any explicit setting, which confirms the compiled `SQLITE_DEFAULT_WAL_SYNCHRONOUS=1`.
- With `locking_mode = EXCLUSIVE` set before WAL, no `-shm` file is created; a second connection, read-only or read-write, gets `SQLITE_BUSY`.
- A read-only connection to a WAL-format file creates `-wal` and `-shm` and leaves them behind; backups are therefore switched to rollback-journal mode before verification, and the open-time inspection removes the files it created.
- A read-only connection with exclusive locking on a live WAL fails with `SQLITE_IOERR_LOCK`, so the inspection uses an ordinary read-only connection.
- A Windows read-only file opens "read-write" without an error and fails at the first lock with `SQLITE_IOERR_LOCK` or at the first write with `SQLITE_READONLY`; the open now checks write access first and reports `PERMISSION_DENIED`.
- `max_page_count` below the needed size fails a transaction with `SQLITE_FULL` and rolls it back.
- SQLite returns an integral REAL as an integer internally, so `-0.0` reads back as `0`. The samples test records this as expected behavior; canonical event payloads keep `-0`.

## Fixture provenance

`schema-v1-representative.sqlite`, `schema-newer-999.sqlite` and `foreign-application.sqlite` were created once on October 15, 2026 by executing their `.sql` files with better-sqlite3 13.0.3 into new files in rollback-journal mode, with a throwaway builder that is not committed. The representative SQL contains the exact `sqlite_schema` text that migration `0001-initial` produced and hand-chosen synthetic values: one ETS2 synthetic session, a job configuration with u64 maximum expected income, a truck, a trailer with a provided empty accessory id and unobserved names, a gap [4, 5], a cancellation with the s64 minimum penalty, an event at eventSeq 9007199254740993, a cancelled trip, attributions, a completeness interval and three samples with every availability state and monotonic time 2^63-1. Only the `payload_json` texts were produced by the canonical JSON encoder, because a redelivery must compare equal to them. `schema-v1-representative.expected.json` was written by hand from the SQL. `manifest.txt` lists the SHA-256 of every fixture file; `.gitattributes` keeps the databases binary and the text files LF.

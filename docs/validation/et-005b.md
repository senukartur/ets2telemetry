### queueBytes reconciliation

The plan expected 166 retained events and the first `queueBytes` at eventSeq 167, from the documented 6,306-byte measure of `event-worst`. That measure holds only for a record with maximum process and session IDs, eventSeq, occurrence times, revision, boundary order and a 256-byte escaped currency source. The simulator's identity (process 1, session 0), 13-digit clocks and the 76-byte ETS2 header source make its worst achievable `job.configured` 6,001–6,007 bytes. The expectation derives this by hand, as m(k) = 5,998 + 2 digits(k) + digits(k + 3), so 174 events fit (1,044,900 bytes plus the reserved 1,024) and 175 is the first `queueBytes` loss. The scenario repeats 180 callbacks, because 170 would not overflow. The replay matched the derivation on its first run. The store test keeps the 166/167 split for records that measure exactly 6,306 bytes.

### Deviations from the plan

- **Lockstep instead of quiescing only at disconnect.** The server waits for every scripted client reply before the producer acts again, so the whole served transcript, including snapshots and clock replies, is byte-identical to the replay. The plan claimed less (snapshots equal in state and continuity only). The wait is a 5,000 ms liveness bound for a cooperative client, not the plan's 1 s: the 1,000 ms write deadline still applies to every server write, but a client's reply time includes its own scheduling, which a two-processor runner does not bound.
- **Client script from the replay.** Probes, live faults and second clients are taken after a given server message (`afterSeq`), which `clientPlan` reads from the replay; a probe is sent at its own paced time, so its round trip excludes the server's wait. The server performs scripted disconnects; the client sees EOF without `end`.
- **Endpoint differences**, listed in [the guide](../simulator-v1.md#named-pipe-serving): the hello deadline counts from the scenario's connect point; the native window between welcome and checkpoint does not exist (S6 bytes are modeled in the hello's own read); after `end` at sequence exhaustion the endpoint keeps serving `welcome` and `end` as PR-1 models it, while the native endpoint closes; Node accepts a second client at the OS level and closes it, where the native endpoint has one instance.
- **New steps.** `stallRead` and `writeDeadline` script the stalled reader; a stalled connection must be followed by another, through which the stalled client learns of its closure. The plan's fault list maps to hello faults (`helloOversized` at 4,097, `helloMalformed`, `helloV0`, `helloCap0`, other major and minor, unknown kind, `ackBeforeHello`, `ackBeforeCheckpoint`, extra bytes, partial EOF, timeout), live faults (second hello; live-only, foreign, beyond-sent, regressing and equal ACKs; repeated and early probes; unknown kind; oversized, malformed and partial frames) and the listed wire faults; lost, withheld and crash cases remain the PR-1 commit and ACK policies.
- **Fault lines** are kept beside the transcript (`ReplayResult.faults`, placed by `beforeLine`), so the PR-1 `TranscriptLine` type and every PR-1 `replay-v1` output are unchanged.

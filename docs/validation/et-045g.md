Task: item 14 of [ET-045](https://trello.com/c/OmNYTBsp), under the owner's decision D3 of October 24, 2026 (an install/update hook writes `app.ico` and `DisplayIcon`). ## Owner observation

During the installed checks of ET-044 on main `cca3e16`, Windows Settings → Installed apps showed the Electron atom for ETS2Telemetry, while the window, tray, taskbar, Start menu and Desktop icons showed the approved road-merge icon. The screenshot is local evidence only and is not committed: `.local/validation/et044-installed-20261023-cca3e16/installed-app-icon/installed-app-entry.png`. The owner's real `DisplayIcon` value was not observed: the tool scans of HKCU recorded at the time saw no uninstall key, so the value on the owner's machine is inferred below, not read.

## Cause

Read from configuration and the primary sources, as recorded in the architect's plan:

- `forge.config.cjs` sets `setupIcon` (Setup.exe's own icon), `skipUpdateIcon: true`, `packagerConfig.icon` (embedded in the executable) and no `iconUrl`.
- electron-winstaller 5.4.4 (`lib/index.js`) then sets `metadata.iconUrl` to `https://raw.githubusercontent.com/electron/electron/main/shell/browser/resources/win/electron.ico`; its nuspec template writes it, and its options accept HTTP(S) URLs only.
- Squirrel at the pinned commit `eef37460ae`: `src/Update/Program.cs` calls `CreateUninstallerRegistryEntry()` after `FullInstall` and after `ApplyReleases` (`--update`); an install over an existing root deletes the root first. `UpdateManager.InstallHelpers.cs` opens the uninstall key with `CreateSubKey`, which keeps existing values, and only `if (zp.IconUrl != null && !File.Exists(targetIco))` with `targetIco = <root>\app.ico` does it download the icon and set `DisplayIcon` to that file; failures are swallowed. `ApplyReleases.invokePostInstall` runs `--squirrel-install` or `--squirrel-updated`, with a 15 s limit, before that call.

So the first online install downloaded the atom into `<root>\app.ico` and registered it; an update never refreshed it, and a Setup over the install downloaded it again. The icon cache is not the cause.

## Change

- `apps/desktop/src/installed-app-icon.ts`: `placeInstalledIcon` writes the bundled icon to `<install root>\app.ico` atomically (`wx` temporary file, synced, read back and compared by SHA-256, renamed with bounded retries on EPERM, EACCES or EBUSY, hashed again); an identical file is left unwritten, a link, junction or folder is never touched, and a failure keeps the previous file and leaves no temporary file. `regExeUninstallEntry` runs `%SystemRoot%\System32\reg.exe add HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\ETS2TelemetryDesktop /v DisplayIcon /t REG_SZ /d <data> /f` with no shell, a hidden window and a deadline; data that is not an absolute drive path ending in `.exe,0`, or holds a quote or a control character, or is longer than 1,024 characters, fails without starting reg.exe. `registerInstalledIcon` places the icon, then sets `DisplayIcon = <install root>\app-<version>\ETS2TelemetryDesktop.exe,0` with one retry of at most 2 s per attempt, whatever the placement did.
- `apps/desktop/src/squirrel-events.ts`: `--squirrel-install` and `--squirrel-updated` run that step beside `Update.exe --createShortcut`, then cancel a pending deferral as before. The production ports read `resources\icon\app.ico` (a regular file, not a link, at most 1 MiB) and use the reg.exe port. Obsolete and uninstall never call either port; a portable or development layout does nothing. The hooks still exit 0, and a failure of the icon or the shortcuts changes neither the other step nor the deferral cancel. Worst case: max(10 s shortcuts, 2 × 2 s registry) + 2 s disarm = 12 s, inside Squirrel's 15 s.
- `forge.config.cjs` ships `resources/icon` as an extra resource; `scripts/inspect-package.mjs` requires exactly `app.ico` with the tracked bytes there, and `--installer` already checks that the NuGet package carries the portable package's files. `iconUrl` stays the default.
- The hosted installer lifecycle: `classifyRegistrationIcon` and `checkRegistrationIcon` (`scripts/installer/installer-guard.mjs`) after every install, repair, update and reinstall; a `legacy-icon` step before the update; and an `ExtractIconEx` pixel comparison after the install and the update ([installer testing](../installer-testing.md#what-is-asserted)).

The displayed value changes from Squirrel's `<root>\app.ico` to a versioned executable path, and with every version, so Windows is not expected to reuse an icon it cached for the old value; the owner check confirms it. Nothing clears the cache or calls `SHChangeNotify`. No settings, schema, IPC, preload, wire, native, plugin, uninstall-engine or data-root change; `GAME_HISTORY_RECORDING` is unchanged.

The owner's pre-fix `DisplayIcon` stays inferred, not observed. The residual risks depend on which part of the hook fails:

- A failed icon placement on a fresh online install brings back the atom, because Squirrel downloads it.
- A failed `DisplayIcon` write after a successful placement leaves no `DisplayIcon`, because Squirrel skips its icon branch while `app.ico` exists. Windows shows a generic icon until the next install or update.
- An update whose registry write fails keeps the old value. A Squirrel `<install root>\app.ico` value now points to the product bytes. Two such failures in a row leave a generic icon.

A failed Squirrel install after the hook can leave a key with only `DisplayIcon`, which Installed apps does not list ([releases](../release.md#installed-apps-icon-et-045g)). No release is authorized.

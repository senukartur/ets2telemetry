# ET-012c validation: wrapped overlay strip

ET-012c, a package of the Trello card ET-012, makes every enabled section of the overlay strip visible. The strip window was one 38 px row high while its items wrapped onto a second line that the window clipped, so trailing enabled sections disappeared. On October 16, 2026 the owner decided to fix the strip first, in its own package, before ET-010c (PR #73) merges; under that decision and the standing delegation of October 15, 2026 the coordinator adopted the architect's decisions S1–S12 ([concept.md](../../concept.md#et-012c-strip-overflow-fix--october-16-2026)). The behaviour is described in [the minimal overlay](../minimal-overlay.md#geometry-and-placements-et-012b).

## Scope

- `apps/desktop/src/overlay-strip.ts` (new, pure and renderer-safe): the strip constants (36 px rows, 1 px border, 12 px padding, 14 px column gap, two 96 px tag slots), a fixed maximum width per section, `stripRowCount(sections, cssWidth)` and `stripCssHeight(rows)`.
- Geometry: the strip is `ceil((36 × rows + 2) × scale)` DIP high, where `rows` is what its enabled sections need at its CSS width `floor(width / scale)`; it fits only when the client height is at least that plus 16. `overlaySize`, `overlayBounds` and `placementFromBounds` take the sections (default: every section), and `overlayWindowSize` gives the size the window is created with. The width rule, margins, fractions and anchors are unchanged.
- Controller: it holds the saved sections; a sections-only change re-places a driving strip and moves and raises it only when its rectangle changed, never shows or raises a hidden one, and while editing re-sizes the draft from its unchanged fractions, which may report `too-large`.
- Main: the overlay window is created for the saved sections, the controller receives them at construction, and every settings change passes them after the durable write.
- Renderer and CSS: each strip item carries its maximum width inline, a longer value ends in an ellipsis, the strip surface takes its content height (no fixed 38 px) at the top of the reserved window.
- Overlay smoke: a strip containment step that fails when a shown strip section lies outside the overlay window ([CI](../ci.md#strip-containment-step-et-012c)).

Unchanged (S11, S12): the card, cluster and HUD; settings format v3, preload and IPC, `OverlayPresentation`, `overlay-view.ts`, `overlay-presentation.ts`, the protocol, fixtures, service and native code; the CI workflow and `RuntimeReceipt.ps1`. The 20 Hz subscriptions, click-through, no focus, `showInactive()`, the topmost re-assertion and the REG-016 invariant keep their code paths.

## Decisions S1–S12

S1 one PR, strip only, with the smoke assertion as the reproducing regression case. S2 the height model: greedy in-order packing of maximum widths, `ceil` height with an epsilon. S3 the per-item maximum widths and two tag slots. S4 the shared pure module. S5 the geometry API. S6 a strip that does not fit hides as a whole; edit mode reports `too-large`. S7 the controller's sections handling. S8 the main changes, applied only after the durable write. S9 the renderer and CSS rules. S10 the smoke step. S11 card, cluster and HUD unchanged. S12 no settings, IPC, presentation, protocol, service or native change. The full table is in [concept.md](../../concept.md#et-012c-strip-overflow-fix--october-16-2026).

## Decisions recorded during implementation

- The smoke step stores the observation in the result before verifying it (`verifyStripLayout(result.stripLayout = await waitForStripLayout(…))` instead of S10's `result.stripLayout = verifyStripLayout(…)`), so a failed receipt keeps the observation. The RED run below relies on that.
- `stripRowCount` also returns undefined for a non-finite CSS width; `overlayWindowSize` keeps the previous creation width `round(1280 × scale)` and counts rows at the full 1280 CSS px.
- Besides the architect's table, the implementer worked out these expected values by hand: job-focus at 928 CSS px needs three rows (tags, speed, gear and fuel = 668, cargo would reach 982; cargo, destination and distance remaining = 778, deadline would reach 1012; deadline), so 110; speed only at 325 CSS px needs two rows; the strip at scale 1.5 is created 1920 × 165; a strip dropped at y 500 in 1920 × 1080 converts to 0.5157 with every section and 0.4795 with driving-only; an edit strip dropped at y 100 in the 960 × 540 client (fraction 0.269) re-sizes for driving-only to {−944, 129, 928, 74}. The first job-focus expectation written in `overlay.test.ts` (74) had not been worked out and failed; the hand derivation above gives 110, which the test now expects with its arithmetic in a comment.

### Test changes because the requirement changed

The strip's height requirement changed from one 38 px row to as many 36 px rows as the enabled sections need, so tests that place the strip with every section (the default) expect the reserved height:

- `overlay-geometry.test.ts`: the strip in the four anchor cases (110, 110, 218, 182), the 512 × 378 fit threshold, the fractional case (110), the scaled sizes (55, 165, 292), the scaled thresholds (992 × 740, 272 × 197) and `{x: 0, y: 1}` ({16, 962, 1280, 110}). The previous one-row values are kept as speed-only cases.
- `overlay.test.ts`: the three strip expectations at 928 DIP wide (height 182 instead of 38); the edit-mode helper gains an optional `sections` argument.
- `main-boundaries.test.ts`: the created window (1280 × 110), the strip bounds {−1600, 8, 1280, 110}, and the edit flow at scale 1.23 (height 136 instead of 47, drop fraction 0.5302 instead of 0.4838); the test that creates the default window is renamed accordingly.

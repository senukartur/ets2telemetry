# ET-012c validation: wrapped overlay strip

ET-012c, a package of the Trello card ET-012, makes every enabled section of the overlay strip visible. The strip window was one 38 px row high while its items wrapped onto a second line that the window clipped, so trailing enabled sections disappeared. On October 16, 2026 the owner decided to fix the strip first, in its own package, before ET-010c (PR #73) merges; under that decision and the standing delegation of October 15, 2026 the coordinator adopted the architect's decisions S1–S12 ([concept.md](../../concept.md#et-012c-strip-overflow-fix--october-16-2026)). The behaviour is described in [the minimal overlay](../minimal-overlay.md#geometry-and-placements-et-012b).

## Scope

- `apps/desktop/src/overlay-strip.ts` (new, pure and renderer-safe): the strip constants (36 px rows, 1 px border, 12 px padding, 14 px column gap, two 96 px tag slots), a fixed maximum width per section, `stripRowCount(sections, cssWidth)` and `stripCssHeight(rows)`.
- Geometry: the strip is `ceil(36 × rows × scale + 2 × max(1, scale))` DIP high, where `rows` is what its enabled sections need at its CSS width `floor(width / scale)` and zoom, with the surface border modelled as `max(1, 1 / scale)` CSS px (fix round 1, below); it fits only when the client height is at least that plus 16. `overlaySize`, `overlayBounds` and `placementFromBounds` take the sections (default: every section), and `overlayWindowSize` gives the size the window is created with. The width rule, margins, fractions and anchors are unchanged.
- Controller: it holds the saved sections; a sections-only change re-places a driving strip and moves and raises it only when its rectangle changed, never shows or raises a hidden one, and while editing re-sizes the draft from its unchanged fractions, which may report `too-large`.
- Main: the overlay window is created for the saved sections, the controller receives them at construction, and every settings change passes them after the durable write.
- Renderer and CSS: each strip item carries its maximum width inline, a longer value ends in an ellipsis, the strip surface takes its content height (no fixed 38 px) at the top of the reserved window.
- Overlay smoke: a strip containment step that fails when a shown strip section lies outside the overlay window ([CI](../ci.md#strip-containment-step-et-012c)).

Unchanged (S11, S12): the card, cluster and HUD; settings format v3, preload and IPC, `OverlayPresentation`, `overlay-view.ts`, `overlay-presentation.ts`, the protocol, fixtures, service and native code; the CI workflow and `RuntimeReceipt.ps1`. The 20 Hz subscriptions, click-through, no focus, `showInactive()`, the topmost re-assertion and the REG-016 invariant keep their code paths.

## Decisions S1–S12

S1 one PR, strip only, with the smoke assertion as the reproducing regression case. S2 the height model: greedy in-order packing of maximum widths, `ceil` height with an epsilon. S3 the per-item maximum widths and two tag slots. S4 the shared pure module. S5 the geometry API. S6 a strip that does not fit hides as a whole; edit mode reports `too-large`. S7 the controller's sections handling. S8 the main changes, applied only after the durable write. S9 the renderer and CSS rules. S10 the smoke step. S11 card, cluster and HUD unchanged. S12 no settings, IPC, presentation, protocol, service or native change. The full table is in [concept.md](../../concept.md#et-012c-strip-overflow-fix--october-16-2026).

## Fix round 1: border snapping below zoom 1

The independent review of `8086805` found that the model assumed the 1 px surface border stays 1 CSS px at every zoom. Below zoom 1 Chromium snaps a nonzero border thinner than one device pixel up to one device pixel (CSS Values 4 "snap as a border width"), so the real inner width is `2 × (1 − s) / s` CSS px narrower and each border one device pixel high. The coordinator decided to model the border as `max(1, 1 / s)` CSS px with the inner width rounded down, and the height as `ceil(36 × rows × s + 2 × max(1, s) − 1e-6)` DIP; both are unchanged for `s ≥ 1`. At a device scale factor above 1 the snapped border is thinner than this, so the model stays conservative.

Hand-worked cases (also in the test comments):

- Reviewer's case: an 800 × 600 client at 0.75 gives a 768 DIP strip, CSS width floor(768 / 0.75) = 1024. Two 96 px tags, cargo 300, origin 300 and distance driven 150 with four 14 px gaps take 998. The old inner width 1024 − 26 = 998 holds them in one row; the new one, floor(1024 − 2 × 1.3333 − 24) = 997, needs two: ceil(36 × 2 × 0.75 + 2) = 56 DIP high, not ceil(38 × 0.75) = 29.
- Scale 0.5 in 1920 × 1080 with every section: CSS width 1280, inner 1280 − 4 − 24 = 1252, still three rows (distance remaining would reach 1256), ceil(54 + 2) = 56 high (was 55).
- Scale 0.5 at the minimum: CSS width 480, inner 452, still ten rows, ceil(180 + 2) + 16 = 198 (was 197); speed only one row, ceil(18 + 2) + 16 = 36 (was 35).
- Driving-only at CSS width 992 still fits one row at scale 2 and needs two at 0.99 (inner floor(992 − 2.0202 − 24) = 965 < 966).

RED before the fix: the new and changed cases in `overlay-strip.test.ts` and `overlay-geometry.test.ts` failed on `8086805` (5 failed: the 0.5 size `{640, 55}`, the 0.5 one-row height `{640, 19}`, both 0.5 fit thresholds, and the reviewer's case with one row instead of two); the all-scale sweep passed there and is a guard, not the regression case. After the fix all passed. The CSS contract's new assertions each failed when their declaration was removed from `renderer.css` (`box-sizing: border-box` on `.overlay *, .overlay *::before, .overlay *::after`, `flex-wrap: wrap` and `max-width: 100%` on `.overlay-strip-row`).

No overlay smoke at zoom 0.5 was added. The synthetic fixture fills two of the three reserved rows and no row lies near its width boundary, so a zoom 0.5 pass could not tell the old model from the new one. Without a game window main never re-sizes the hidden overlay window, so the pass would also need the driver to resize the window through main, which checks the harness rather than the product. Border snapping on real displays stays pending.

## Hosted CI failure: a screen-narrowed overlay window (run 38878781715)

The first hosted Windows CI run on PR #76 (head `1f51f56`, run [38878781715](https://github.com/senukartur/ets2telemetry/actions/runs/38878781715)) failed the development overlay smoke `-ForceRendererReuse` in `verifyStripLayout` with `The strip overlay window must have its reserved size`: the viewport was 1024 × 110 instead of 1280 × 110. The containment check ran first and passed, and the retained `stripLayout` observation (the step stores it before verifying) shows every section inside the window: `outside` and `uncapped` empty, `truncated` = expected income, two rows. The run's trace shows overlay frames of 1024 × 110 and dashboard frames of 784 × 435, the dashboard's normal 800 × 500 outer size. Windows limits a window to the screen size, and without a game window main never places the hidden overlay, so on the runner's 1024-wide screen the window created 1280 × 110 stayed 1024 wide. The exact width was a smoke-harness assumption about the screen, not a product defect: with a game window, placement sizes the strip for the client area and its width.

The step now requires the reserved height of 110 (the creation height for every section at scale 1, which the screen does not limit) and a width between the strip's limits of 480 and 1280, besides `outside` and `uncapped` empty; the recorded viewport is the actual one. Checking the height against the rows every section would need at the actual width was rejected: at 1024 CSS px every section needs four rows (146), more than the 110 the unplaced window was created with, so that check would fail on a window the product never sized for that width.

The new `overlay-smoke-source.test.ts` case (a 1024 × 110 window passes; heights 74, 111 and 146 and widths 479 and 1281 fail; containment still applies) failed before the change with the CI message. Checks at `1d3a42c`: `npm run lint` 0 findings, `npm run typecheck` passed, `npm test` 77 files and 2,083 tests passed. The development overlay smoke `-ForceRendererReuse` passed (`development-2e65e08a715849d7b27af5b18017aeaa`, viewport 1280 × 110). A local run with the overlay temporarily created 1024 wide in an uncommitted copy of `main.ts`, which reproduces the runner's narrowed window, also passed (`development-98e73b66051643c087081b95ef050523`, viewport 1024 × 110, `outside` and `uncapped` empty, two rows); `main.ts` was restored and rebuilt before the real run.

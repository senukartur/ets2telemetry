## PR-1 one stored sample per source second (October 16, 2026)

Branch `feat/one-second-samples`, from `main` at `00bd88b` plus the coordinator's authorization commit `e155d40`.

It changes (H6, H16):

- the storage API: `appendSamples(pluginSessionId, rows, options?)` with `SampleAppendOptions {uniqueSeconds?}` returns `SampleAppendResult {appended, skipped}`, in `api.ts`, `sqlite/writes.ts`, `index.ts` and `client.ts`. With `uniqueSeconds` the transaction reads the session's latest stored row through the `samples_session` index, joined to its source clock, and skips each row whose source second, floor(`monotonicNs` / 10^9), is at or below the last accepted second of its own clock; a row on another clock is accepted. Without the option nothing changes except the new `skipped: 0`;
- the worker protocol: the request parser checks the `appendSamples` options strictly, like the `recordCompleteness` options, and the response check requires `appended` and `skipped` to be non-negative safe integers; the client copies only `uniqueSeconds`;
- the storage worker host: the in-process `commitOptions(command)` seam also covers `appendSamples`, so a test entry can run `testHooks.beforeCommit` inside its transaction; nothing of it crosses a message, and the production storage worker passes nothing;
- the test-only `tests/storage/fixtures/fault-storage-worker.ts`: `samplesFault` throws `SQLITE_FULL`, `SQLITE_READONLY` or `SQLITE_BUSY` inside the first configured number of `appendSamples` transactions, or holds the first one until a release message;
- the tests below and the documentation ([storage](../storage.md), the [registry](../regression-registry.md) rows REG-005, REG-007 and REG-009).

No schema, migration, wire, preload/IPC, renderer, main-process, service or native changes, no frozen fixture changes (only the test-only fault worker above changes), and no dependency or lockfile changes. Production behaviour is unchanged: nothing calls `appendSamples` outside tests yet.

### Interpretations and deviations from the plan

- **Per-clock comparison within a batch.** H6 compares a row with "the last stored or an earlier batch row second on the same clock". The implementation keeps the last accepted second per source clock, seeded with the session's latest stored row, so within one batch a row that returns to a clock is compared with that clock's earlier rows. Across commands only the latest stored row is read, as planned; a row that returns to a clock after a row on another clock is therefore not compared with that clock's older stored rows. A plugin session's capture clock is constant, so the producer never does this; the limit is documented in `api.ts` and [storage](../storage.md#storage-api) and not asserted by a test.
- **A skipped row is still validated.** Its trip reference is resolved like a kept row's, so an unknown or foreign trip refuses the batch whether or not the row would be skipped (all-or-none, like `ifAbsent`, which validates every value before skipping).
- **In-process options.** The storage core refuses options that are not an object or a `uniqueSeconds` that is not a boolean with `INVALID_INPUT`. Like `recordCompleteness`, it does not refuse unknown keys in-process; the worker parser does.
- **Commit options parameter.** `Storage.appendSamples` takes the in-process `CommitOptions` as a separate fourth parameter, as `commitEvent` and `commitGap` take theirs, so `SampleAppendOptions` holds only what may cross the worker boundary.
- **Fault attempts.** A `samplesFault` failure is used up only when an `appendSamples` command reaches the hook inside its transaction, like the event faults, so a batch the core refused earlier does not consume it.
- **Changed expected values.** `tests/storage/events-commit.test.ts` (not in the plan's owned files) and one existing `samples.test.ts` case compared the `appendSamples` result with `{appended: n}`. The requirement behind them changed: H6 adds `skipped` to every result. Both now expect `skipped: 0`; the appended counts are unchanged.
- **More fault-worker coverage.** Besides the planned `SQLITE_FULL` case, `worker.test.ts` checks the `samplesFault` hold, which PR-3's priority tests rely on.
- **Documentation.** TESTING.md is not changed in PR-1; it gains its ET-015b paragraph with PR-3, as planned.

### Interpretations and deviations from the plan

- **`observe` context.** `DurableSink.observe(message, context)` takes the context as a required parameter, because DurableDelivery always passes it; a sink that ignores it still satisfies the type.
- **`SampleSink.dropped()`.** The interface gains `dropped()`, the lifetime count of rows the bound dropped, so the pipeline can log `V1_SAMPLES_DROPPED` without a logger in the recorder.
- **`pending()` reports loss intervals.** A loss run of a plugin session with no pending row (a new session meeting a full buffer) is then still written, by a batch without rows, and the final write does not end before it. Since review pass 1, `pending()` returns `{rows, losses}`, the batch trigger counts rows only, and `V1_SAMPLES_EXIT` reports `{rows, losses, code}`.
- **Diagnostic codes.** H12 names `V1_SAMPLES_RETRY`, `V1_SAMPLES_DISCARDED`, `V1_SAMPLES_SKIPPED` and `V1_SAMPLES_DROPPED`. Every storage code is retryable or unavailable under E7, so SKIPPED and DROPPED are read as the running totals of rows storage skipped (H6) and of rows the bound dropped (H9), logged when they reach or pass 1, 2, 4, …. `V1_SAMPLES_EXIT` reports `WRITTEN`, the failure code, or `INTERNAL` for a malformed result or a write that stored nothing.
- **Discard on any lifetime failure.** Pending rows are discarded, with `V1_SAMPLES_DISCARDED`, whenever durable delivery fails for the service lifetime, also when an event commit fails, because `stop()` writes nothing afterwards.
- **Loss interval stored before a failed row write.** A batch stores its loss intervals first, and a stored interval leaves the buffer at once, so a retry does not write it again. Since review pass 1, only ended runs are written (and every run by the final write), so the first batch after an outage writes rows, and the interval follows in the next batch, before that batch's rows.
- **`stop()` twice.** The second call returns the first call's promise, so the final write runs once when the service and a test both stop the ingestion.
- **Owned-file scope.** Besides the one-line `appendSamples` forward, `tests/storage/recording-helpers.ts` gained two plan options and the shared `storedSamples` helper, appended at the end of the file to keep the merge with the open PR #84 simple. The crash child gained `sampleFlushMs` and `stopAfterDisconnect`, so a cold-started process writes its rows deterministically before it is terminated.
- **Journey files of PR-4.** As the coordinator instructed for the named risk, `recording-database.cjs`, `recording-observation.mjs`, the journey expectation and [CI](../ci.md) changed minimally; the asserted sample rows remain PR-4.
- **The held-batch fault case.** It shows that no event is acknowledged while a sample batch is held inside its transaction, and that items continue after the release. That exactly one batch precedes the waiting item is shown by the unit case (H10), not at the storage boundary.
- **Timing-dependent counts.** In faults (f) the discarded count is accepted between 7 and 10: rows 1000–1005 and 1009, plus 1010–1012 when they were observed before the batch ran. In crash (e) the killed process's rows are accepted as any prefix of 1000–1005; three local runs stored all six.
- **Tooling note.** `npx tsx` fetched `tsx` 4.23.15 into the npm exec cache once, to validate the new scenario with the simulator's `validateScenario`; nothing was added to `package.json` or a lockfile.

### PR-3 review pass 1 (October 16, 2026)

The independent review of `98a6a26..265448d` requested changes:

1. **Major: loss runs grew without bound.** `nextBatch` froze every loss run, so during an outage longer than the bound, each failed 5 s retry started a new run. The reviewer's scratch run of one hour gave 720 loss intervals for one outage. One op would then have written them one after another, holding events far longer than one batch, the final write could exceed the 500 ms step, and H9's one interval per contiguous run was broken. Fixed in `f5a1b5e`:
   - A run stays open while the buffer is full. It ends when a row of its session is accepted, when stored rows free room, or when a dropped row is on another clock.
   - Only ended runs are written, except by the final write at `stop()` (`write(maxRows, final)`).
   - A batch keeps a snapshot of each run, and storing the interval removes exactly that part, so rows dropped meanwhile remain.
   - At most `MAX_LOSS_RUNS` = 16 runs are kept per plugin session and source clock; a further one is merged into the latest.
   - New tests: buffer cases for one run with the full count across failed batches, the remainder after a stored snapshot and the 16-run merge, and recorder S6, which stores one interval for one outage across three failed row writes and two failed interval writes. S4's expected write order changed with the requirement: the first batch after the outage writes rows, and the interval follows in the next batch, before its rows.
2. **Minor: fault cases (f) and (g) kept the 5 s flush.** On a slow runner a smaller timer batch could have taken the injected fault or hold. Fixed in `37639f6` with a 600 s flush delay. The discarded count of (f) stays a bound of 7 to 10: snapshots decoded in the same read as the seventh row can still be observed before the batch runs. Five local runs discarded exactly 7.
3. **Nit: `V1_SAMPLES_EXIT {rows}` also counted loss intervals.** Fixed in `f5a1b5e`: `SampleSink.pending()` returns `{rows, losses}`, and the log reports `{rows, losses, code}`. The unit and service expectations gained `losses: 0`, and a delivery case writes a pending loss interval at the stop.
4. **Nit: the REG-007 text overstated fault case (e).** The registry now says that the case asserts the final rows and acknowledgements, and that the unit retry case shows the interleaving.

## PR-1 one stored sample per source second (October 16, 2026)

Branch `feat/one-second-samples`, from `main` at `00bd88b` plus the coordinator's authorization commit `e155d40`.

It changes (H6, H16):

- the storage API: `appendSamples(pluginSessionId, rows, options?)` with `SampleAppendOptions {uniqueSeconds?}` returns `SampleAppendResult {appended, skipped}`, in `api.ts`, `sqlite/writes.ts`, `index.ts` and `client.ts`. With `uniqueSeconds` the transaction reads the session's latest stored row through the `samples_session` index, joined to its source clock, and skips each row whose source second, floor(`monotonicNs` / 10^9), is at or below the last accepted second of its own clock; a row on another clock is accepted. Without the option nothing changes except the new `skipped: 0`;
- the worker protocol: the request parser checks the `appendSamples` options strictly, like the `recordCompleteness` options, and the response check requires `appended` and `skipped` to be non-negative safe integers; the client copies only `uniqueSeconds`;
- the storage worker host: the in-process `commitOptions(command)` seam also covers `appendSamples`, so a test entry can run `testHooks.beforeCommit` inside its transaction; nothing of it crosses a message, and the production storage worker passes nothing;
- the test-only `tests/storage/fixtures/fault-storage-worker.ts`: `samplesFault` throws `SQLITE_FULL`, `SQLITE_READONLY` or `SQLITE_BUSY` inside the first configured number of `appendSamples` transactions, or holds the first one until a release message;
- the tests below and the documentation ([storage](../storage.md), the [registry](../regression-registry.md) rows REG-005, REG-007 and REG-009).

No schema, migration, wire, preload/IPC, renderer, main-process, service or native changes, no frozen fixture changes (only the test-only fault worker above changes), and no dependency or lockfile changes. Production behaviour is unchanged: nothing calls `appendSamples` outside tests yet.

### Interpretations and deviations from the plan

- **Per-clock comparison within a batch.** H6 compares a row with "the last stored or an earlier batch row second on the same clock". The implementation keeps the last accepted second per source clock, seeded with the session's latest stored row, so within one batch a row that returns to a clock is compared with that clock's earlier rows. Across commands only the latest stored row is read, as planned; a row that returns to a clock after a row on another clock is therefore not compared with that clock's older stored rows. A plugin session's capture clock is constant, so the producer never does this; the limit is documented in `api.ts` and [storage](../storage.md#storage-api) and not asserted by a test.
- **A skipped row is still validated.** Its trip reference is resolved like a kept row's, so an unknown or foreign trip refuses the batch whether or not the row would be skipped (all-or-none, like `ifAbsent`, which validates every value before skipping).
- **In-process options.** The storage core refuses options that are not an object or a `uniqueSeconds` that is not a boolean with `INVALID_INPUT`. Like `recordCompleteness`, it does not refuse unknown keys in-process; the worker parser does.
- **Commit options parameter.** `Storage.appendSamples` takes the in-process `CommitOptions` as a separate fourth parameter, as `commitEvent` and `commitGap` take theirs, so `SampleAppendOptions` holds only what may cross the worker boundary.
- **Fault attempts.** A `samplesFault` failure is used up only when an `appendSamples` command reaches the hook inside its transaction, like the event faults, so a batch the core refused earlier does not consume it.
- **Changed expected values.** `tests/storage/events-commit.test.ts` (not in the plan's owned files) and one existing `samples.test.ts` case compared the `appendSamples` result with `{appended: n}`. The requirement behind them changed: H6 adds `skipped` to every result. Both now expect `skipped: 0`; the appended counts are unchanged.
- **More fault-worker coverage.** Besides the planned `SQLITE_FULL` case, `worker.test.ts` checks the `samplesFault` hold, which PR-3's priority tests rely on.
- **Documentation.** TESTING.md is not changed in PR-1; it gains its ET-015b paragraph with PR-3, as planned.

## PR-2 the one-second sampler (October 16, 2026)

Branch `feat/one-second-sampler`, from main `00bd88b`. The review fixes are in `b9a5329` and `9b3f11d`.

### Changes

- `packages/telemetry-core/src/history-samples.ts` (new): the pure `sampleReading(state, {message, receivedUtcMs, view})` and `initialSamplerState()`.
  - The tick is the absolute source second `floor(capture.monotonicNs / 1e9)` per plugin session and capture clock (H3).
  - A reading qualifies only when its `boundaryOrder` is strictly above the session's previous reading, across connections, the simulation is running, its second is new on its clock and its capture is at most 2^63−1 ns. The first reading of a plugin session is a baseline (H4).
  - Paused and unavailable readings advance the boundary and add no row, and no catch-up happens (H5).
  - Rows copy the wire's canonical units without unit keys, with position from `worldPlacement.position` and game time on its own clock (H14).
  - `utcMs` is the capture label when it is available and a safe integer, otherwise the receipt label (H13). `tripUuid` is set only while the trip view is `active` with no untracked job and the view belongs to the reading's game (H7).
  - `SampleInput` is a type-only import of `packages/storage/src/api.ts` (T2).
- `packages/telemetry-core/src/index.ts` exports it.
- `tests/unit/telemetry-core-boundaries.test.ts` lists the new module and allows the same storage-API type import from the telemetry-core root.
- `docs/trips.md`: the R17 trip-view consumer rule (H7) and a "One-second sampler (ET-015b)" section.
- Nothing calls the sampler yet. No storage, wire, preload/IPC, renderer or native change.

### The invariants and their sources

| Invariant | Rules | Source |
| --- | --- | --- |
| I1 no duplicate delivered trips | A delivered or cancelled trip names its outcome event, which is stored, has the matching type and is attributed to that trip (`trip`, or `trip-before-loaded` for an active cargo_market job before pickup, T14); its close reason is `outcome`; a trip without an outcome names none; no outcome event closes two trips; each gameplay event has exactly one attribution and every other event none; at most one open trip per game | trips.md, transitions (`attribute trip; close {outcome, this-event}`), "Each game has one slot with at most one open trip", Attribution (T14) |
| I2 no acknowledged-but-lost events | Every ACK is at or below the session's committed coverage; every eventSeq from 1 to coverage is a stored event or inside a stored gap row | storage.md, Coverage ("an ACK may be built only from this value"), Overlapping gap rows; protocol v1 §10 |
| I3 no falsely complete trip | A `complete` trip is closed by its outcome, opened at an event, opens and closes in one plugin session, has no completeness interval except annotations, every eventSeq between its opening and its outcome is a stored event, and none of those events was first stored from a redelivery | trips.md, What "complete" means (T13); protocol v1 §5 (`redelivered`); storage.md, the lost-set rule of overlapping gap rows |
| I4 a sound file | `integrity_check` is `ok`, `foreign_key_check` is empty | storage.md, durability and backups |
| I5 one sample per second | At most one sample per plugin session, source clock and source second | trips.md, one-second sampler (H3); storage.md, `uniqueSeconds` (H6) |

Interpretations of the plan's I3 wording, checked against docs/trips.md:

- "No completeness interval" is "no interval other than annotations": trips.md says annotations (`detail.annotation: true`) never downgrade, so a complete trip may carry a `truck-change` or `refuel` annotation.
- "No gap overlap" is read through storage.md's rule that the lost eventSeqs are the gap ranges minus the eventSeqs that have an event row: a window in which every eventSeq is a stored event has no loss, even if a merged gap row's range touches it.
- "No restart close" follows from requiring the `outcome` close reason.
- The redelivery rule is added: an event first stored from a redelivery was written to an earlier connection, so the trip's window spans a reconnection, a consumer restart or a replayed configuration, each of which makes the trip partial (T13).

### Kill rows

The first connection withholds its ACKs, and the first process commits only after that connection ended, so the server retains everything and the second process receives all of it again. Final trips are `[job eventSeq, outcome, close reason, recording completeness]`, reasoned in the test from docs/trips.md:

| Scenario | Kill | Final trips |
| --- | --- | --- |
| normal-delivery | before 3, after 5, after 8 | `[3, delivered, outcome, partial]` |
| save-load | before 2 / after 7 / before 12 | `[3, open, –, partial]` / `[3, none, configuration-cleared, partial]`, `[9, open, –, partial]` / `[3, none, discontinuity, partial]` |
| timers-truck-refuel | before 3, after 3 | none |
| quick-job-profile-change | after 5 (the clear) | `[2, none, discontinuity, partial]` |
| ferry-train | after 2 | none |
| retention-expired | before 1 / after 1 / after 2 | `[–, open, –, partial]` (late attach) / `[1, none, gap, partial]` / `[1, open, –, partial]` |
| app-absent-hydration | after the attach op | `[–, none, gap, partial]` (the late-attach trip) |
| two-jobs | before 10 / after 10 / after 11 | `[3, delivered, outcome, partial]` with `[10, delivered, outcome, partial]` / the same / `[10, delivered, outcome, complete]` |

Two-jobs is normal-delivery followed by a second job configured while the simulation runs, its delivery, its clear and a frame, appended in the test (`withTransport`). The frame after the clear is deliberate: without it the reconnection's checkpoint would still show job 10 (finding F1). It is the only kill scenario with a complete trip: no simulator scenario or recording fixture has one (every trip there opens at load).

### Review fixes (October 18, 2026)

- **I1 and `trip-before-loaded`.** I1 required the closing outcome event to be attributed `trip`. docs/trips.md, Attribution (T14), attributes an event of an active cargo_market job before pickup, its outcome included, as `trip-before-loaded`; such a job cancelled before pickup closes its trip {cancelled, outcome}, complete after a clean window. I1 now accepts `trip` or `trip-before-loaded` and still requires the trip it closes. Unit cases: that cancellation holds every invariant, and the same attribution naming another trip breaks I1. RED: restoring the `trip`-only rule fails the passing case.
- **No game history in case (e).** The `GAME_HISTORY_RECORDING` check and the absent `data\telemetry.sqlite` check moved into `expectNoGameHistory()`, which `crash()` and case (e) call before they start processes and after the processes ended; (e) spawns its own children and had neither.

### Findings

- **F1: a stale checkpoint opens a late-attach trip for a finished job.** With the late-attach op running in the child, normal-delivery killed before commit 3 or after commit 8 ends with an extra open late-attach trip. The reconnection's checkpoint carries the state of the last frame (simulator v1, OD-5 S7: "State is the slot published at the last frame_end"), which still shows job 3 at configuration revision 3, while its `nextEventSeq` (10) is past the delivery (8) and the clear (9). trips.md says a checkpoint "describes the state at its `status.delivery.nextEventSeq`" and that a replayed clear or outcome does not end the checkpoint job, so J9 opens a trip for a job that was delivered and cleared. The two documents disagree about what a checkpoint's state describes. In a real game frames keep publishing the state, so the window is likely short, but a reconnection right after a clear with no frame between could produce it. The invariants still hold (one open trip, partial). The existing normal-delivery and save-load rows therefore keep running without the late-attach op, as before ET-019; the seeded campaign runs it everywhere and asserts only the invariants. Not fixed here. The independent review of PR-1 confirmed it, also with the real plugin (a window of about one frame at connect), and a separate product fix tracks it on branch `fix/late-attach-stale-checkpoint`. The two-jobs suffix ends with a frame after the clear to avoid it.
- **F2: no complete trip in the recording corpus.** Every simulator and recording expectation is partial, because every job opens at load. Without the two-jobs variant, I3 and the cold-start downgrade had no executable protection at the process boundary.
- **F3: the (d) design cannot see early ACKs.** The first process commits only after its connection ended, so it writes no ACK; ACK-before-commit faults are visible only in (a)–(c) and (e).
- **Docs and code.** No difference between docs/trips.md or docs/storage.md and the code was found for I1–I5: every hand-written final and every invariant held on the unchanged code.

## PR-2: killed storage open during backup and migration

Recorded October 18, 2026 on branch `test/et019-migration-crash`, base `main` `ad18279`. The PR changes tests and documentation only. No product source, wire, schema, IPC or native code changed, `GAME_HISTORY_RECORDING` stays `false`, and no game was launched; no claim about games, TruckersMP, display or performance follows.

### PR-2: what it adds

- `tests/storage/fixtures/crash-child.cjs` gains a `migrate` mode. It opens a database in process through the storage core, because the storage worker copies open options field by field and never receives test hooks or migration lists ([storage worker](../storage.md#storage-worker)). At its configured barrier it writes `barrier <name> <facts>` synchronously to stdout and blocks the main thread. The test then ends it with `process.kill(pid, 'SIGKILL')`, which is `TerminateProcess` on Windows. If no test ends it, the child stops itself after 60 s with an error on stderr, which fails the case; a child still running after a failed case is terminated in `afterEach` (checked once with the kill removed: the case timed out and no child process remained).
- `tests/storage/migration-crash.test.ts` (REG-013, REG-006) runs it on a copy of the immutable `schema-v1-representative.sqlite`. It has five cases:
  1. **`afterInspect`.** Before the writer opens: nothing is written and no backups folder exists. The next open migrates and takes its own backup.
  2. **`afterCopy`.** The backup copy exists only as `<name>.sqlite.partial` and the database is unchanged. The next open reports `removedPartialBackups: 1`, backs up again under its own name and leaves exactly that backup and its manifest.
  3. **Inside the real 0002 transaction, with the production page cache.** The child's migration list is `[MIGRATIONS[0], MIGRATIONS[1] wrapped]`. The wrapper runs the real 0002 statements, reads the uncommitted state on the migrating connection, then blocks before the runner records the step and commits. The barrier facts show that the kill lands there: `trips` already has `opened_by`, and the connection still reports user version 1 and only the version 1 row of `schema_migrations`.
  4. **Inside 0002 with a one-page cache.** The same case with `cache_size = 1` set on the migrating connection before the 0002 statements, so SQLite writes uncommitted pages to the WAL before the kill. The `-wal` file holds them afterwards. In both 0002 cases a separate read-only connection, before any production open, must see the unchanged version 1 database: the same logical digest, user version 1, the version 1 `trips` and `schema_migrations` rows, a clean `integrity_check` and an empty `foreign_key_check`. The child's complete backup and manifest are reused by the next open, as docs/storage.md step 2 says.
  5. **After the open returned, without a close.** The committed migration is in the WAL, and the next open reports no migration.
- After every kill, the next production open must match the hand-written version 1 to version 2 rows of `migrations.test.ts`. These are now `readVersion1` and `expectMigratedFromVersion1` in `tests/storage/helpers.ts`, moved without changing an expected value. The backups folder must hold exactly one backup and its manifest, `integrity_check` must be `ok` and `foreign_key_check` empty. The child receives the workspace as `LOCALAPPDATA`, and no `ETS2Telemetry` folder may appear there. Every path is inside the per-test temporary directory. The real profile is not read, not even with a stat. After the file runs, the fixture's SHA-256 must still match `manifest.txt`.
- The expected states come from [docs/storage.md](../storage.md#migrations-od-4) (one `BEGIN IMMEDIATE` transaction that rolls back to the old version and content; backup steps 1-5; the stale-partial sweep; backup reuse) and from SQLite's atomic commit. A transaction that never committed is rolled back on the next open ([atomic commit](https://www.sqlite.org/atomiccommit.html), [WAL](https://www.sqlite.org/wal.html)). A reader uses only WAL frames that are a commit frame or are followed by one ([file format, 4.5 Reader Algorithm](https://www.sqlite.org/fileformat2.html#the_write_ahead_log)).

### PR-2: uncovered kill point

A kill between the rename of the verified backup to `.sqlite` and the rename of its manifest has no hook and is not tested. Such a crash leaves a finished backup without a manifest. By design that file is never trusted, reused or deleted, so the next open takes a new backup, and each crash there leaks one database-sized file (recorded in [storage](../storage.md#backups-and-restore-od-5)).

### PR-3: determinism

- (a) and (b) keep the commit backlog below the 512 bound on any host: the second connection's stream after its redelivered eventSeq 1 is held (ClientSocket gate) until storage reports coverage 260 or 262, polled every 25 ms. Without the gate, a slow host could hold the first connection's 260 items and the redelivery of 256 at once.
- (b) releases the held commit inside the same gate, after the redelivered eventSeq 1 arrived, so all 262 items of the first connection are queued behind it at the release.
- The overflow cases' liveness bounds are 120 s per wait and 240 s per case (`OVERFLOW_GUARD_MS`, `OVERFLOW_CASE_MS`). Unloaded each case takes 3–6 s, but with a busy-loop process on every logical processor of a host that other agents' builds already kept near 100% CPU, single cases took up to 89 s.

### PR-3: findings

- **Docs and code.** No difference between docs/trips.md, docs/storage.md, protocol v1 §9 or G6 and the code was found for these cases: every hand-written row, count and journal value held on the unchanged code.
- **A source without frames reads `waiting`.** In (c) and (d) the published state never has an available simulation, so v1 reads `waiting` (docs/telemetry-service-v1.md, Freshness) and the recording status stays `waiting` by G3 rule 8 while events, gaps and losses are committed and counted. This is the documented rule; a first draft of the test expected `recording`. A real plugin publishes frames.
- **One gap message per lost event while connected.** A connected consumer that cannot acknowledge receives one gap message per newly lost event (protocol v1 §9), so its commit backlog keeps growing with the source's event rate after the producer's store is full. (b) stays below 512 items with seven losses; a longer stall reaches `BACKLOG_FULL`, which is bounded and retryable (ET-015c G11). Not a defect; noted for the soak (PR-12).
- **Run time under load.** The overflow cases cross several hundred thread and pipe hops per connection; under an artificial full-processor load they slow down by more than an order of magnitude, which the liveness bounds above allow for.

# ET-018: installer, upgrade and uninstall

ET-018 packages the application for distribution: installed upgrades that keep local data, and an uninstall that removes the application's own data and plugin ([concept](../../concept.md#uninstall-removes-local-data--october-16-2026)). The architect's plan of October 18, 2026 splits it into six PRs; its decisions U1–U17 and the owner decisions O1–O8 are recorded with the coordinator's authorization. This record collects each PR's local checks and the checks that stay pending. Hosted CI runs, independent review and acceptance are recorded by the coordinator. No game was launched, no installer ran on a personal machine, and no claim about real games, TruckersMP, display or performance follows.

### Decisions and deviations

- **Synthetic target instead of `data\telemetry.sqlite`.** The plan seeds `schema-v1-representative.sqlite` as `data\telemetry.sqlite`. That fixture's `database_info.purpose` is `synthetic`, and the history path refuses any other purpose (`checkPath`, `PURPOSE_MISMATCH`), so the copy would never migrate. A history-purpose copy would mean editing the fixture's contents. The harness therefore seeds the copy as `synthetic\upgrade.sqlite` and launches with `ETS2TELEMETRY_RECORDING=synthetic:upgrade`, which opens it through the same `openConnection` migration and backup path, with backups in `synthetic\backups`. It also requires that no `data\telemetry.sqlite` is created. The fixture itself is checked against `manifest.txt` before and after the copy. This proves the shared migration and backup path (`openConnection` with its verified pre-migration backup and manifest) in the installed runtime with its installed better-sqlite3. It does not prove the history-target wiring end to end: the default selection of `data\telemetry.sqlite`, the `history` purpose and the history backups folder `backups`. That wiring is unit-tested only: `tests/unit/history-storage.test.ts` ("opens the production history database under LOCALAPPDATA without waiting for it", "keeps history mode unchanged with an explicit history target"), `tests/unit/recording-policy.test.ts` ("opens history with no durable selection when the variable is unset or empty") and `tests/storage/migrations.test.ts`, which refuses the synthetic fixture under the history purpose with `PURPOSE_MISMATCH`; the runtime smokes also create a new history database at `data\telemetry.sqlite`, without a migration. The owner's first real upgrade of version 1 history remains the end-to-end check.
- **Step Jobs.** `BoundedProcess.Run` allows at most 60 s per Job, so the whole lifecycle cannot run in one Job. Every installer program and driver command runs as the root of its own Job, and the installed smokes keep their own 60 s Jobs. The `step` command waits until no process image under R is left, because Squirrel's `--updateSelf` helper outlives its parent while `BoundedProcess` gives descendants only one second after the root exits. The fixture build runs outside a Job, like `npm run make`, bounded by the step's 8 minutes.
- **Run root and evidence.** R is `$env:RUNNER_TEMP\installer-<id>`, so the installed binaries are never uploaded; the evidence is `.local/ci/installer-<id>-evidence`, already inside the uploaded `.local/ci`, so the upload paths need no new entry.
- **Copies for the read.** A read-only connection to a WAL database leaves `-wal` and `-shm` files, which would change the data root the next installer step is compared against. The reader opens copies in `R\temp`; the original is checked for sidecars before.
- **Native binding name.** The module cache names the binding by its ASAR path, `resources\app.asar\node_modules\better-sqlite3\prebuilds\win32-x64.node`, which Electron loads from `app.asar.unpacked`; the driver requires that name and the unpacked file.
- **Default scenarios.** Installed `scaffold` on 0.1.0, and `scaffold`, `plugin` and `telemetry` on 0.1.1 (`-ScenariosA`, `-ScenariosB`). The first dispatch run measures the step; trim them if the scaffold job nears 15 minutes.

### Decisions

- **Unrecognized file.** A file with the plugin's name and an unknown hash stays and does not block the uninstall; nothing of this application is left there, and a deferral could never remove it.
- **Read-only DLL.** It stays and blocks (`READ_ONLY_FILE`), so the run defers and the intent keeps the folder; the user can clear the attribute and run again.
- **Removed game folder.** A root that is gone while its parent remains counts as cleaned, as the installer's recovery decides; a missing parent (an unplugged drive) defers as `FOLDER_UNAVAILABLE`.
- **Registry states.** An invalid, newer or unreadable registry touches no game folder, not even the folders of an earlier intent, and defers with a fixed code; `plugins\` stays whole. (Replaced for the intent's folders by the [advisory review fixes](#advisory-review-fixes-october-18-2026).)
- **Unknown data entries.** They stay and are counted, and the run still reports `complete`: nothing of this application is left. The data root then stays.
- **A data entry that cannot be removed** (read-only, locked or denied) defers with `DATA_ENTRY_BLOCKED` and keeps `plugins\` and `uninstall\`.
- **Running-game check budget.** 3 s by default; tests shorten it through the `runningCheckBudgetMs` port.
- **Roaming userData (O7).** Only an optional hook in production mode after a complete run; PR-3 and PR-4 wire it.
- **Real denied delete.** A real `EPERM` comes from an ACL deny of DELETE on the DLL and of delete-child on its folder; a handle without delete sharing makes the unlink a sharing violation (`EBUSY`), measured on October 18, 2026, which the cleanup retries five times and then reports.

### Advisory review fixes (October 18, 2026)

Two findings of the advisory review of PR #118 at `1af0172`:

- **The intent's folders with a bad registry.** An invalid, newer or unreadable registry made the run rewrite its intent with no folders, so a folder an earlier run left in `pending.json`, for example one blocked by a running game, was forgotten the first time the registry turned bad. Now the run still cleans the folders of its own earlier intent, by the same per-folder rules with only the intent's own hashes (and the `known` ones); no folder is derived from the bad registry, the registry is neither updated nor removed, and the run stays deferred with the registry's code. Of the two options (carry the folders through untouched, or clean them), cleaning was chosen: the intent is written by this application before the registry turned bad and parsed strictly on its own, and a run already cleans these folders when the registry is missing, so a bad registry should not make the cleanup weaker than a missing one. See [uninstall](../uninstall.md#plugin-cleanup).
- **Bounds of the merge.** The registry's bounds (16 installs, 16 pending intents) do not keep the merged list inside the intent's (32 folders, 17 hashes and 16 temporary files per folder, 128 KiB): 32 registry folders plus the intent's 32, up to 34 hashes and 32 temporary files in one folder, and long roots, made `writePendingRecord` throw, so every run was refused with `INTENT_FAILED`. Raising the intent's bounds cannot converge, because each run merges the larger intent again. Now the run cleans every merged folder with the full lists, and the intent records what fits, the intent's own folders, hashes and temporary files first, then the registry's; past 128 KiB, folders drop from the end. What it cannot hold is the registry's alone and stays in `setup.json`, which a folder leaves only after it was cleaned with the full list and which is wiped only after a clean run. See [uninstall](../uninstall.md#intent).
- **Tests** (`uninstall-engine.test.ts`): "a registry that turned invalid" and "turned newer keeps and then cleans the folder of an earlier intent by its own hash, and stays deferred" (a DLL whose hash only the registry and then the intent know); "cleans the maximum registry merged with the maximum intent, and records what fits with the intent's own entries first" (16 installs and 16 pending updates of one folder, an intent of 32 folders with 17 hashes and 16 temporary files in that folder: the deferred intent holds the intent's 32 folders with their own lists, the registry keeps its 16 records, and a second run removes the DLL whose hash only a pending update names, dropped from the intent); "keeps the intent within its byte bound for a registry of long game roots" (16 roots near 4096 characters, whose unbounded record exceeds 128 KiB, a precondition the test asserts). No existing test changed.
- **RED**, each alone and reverted: a bad registry ignoring the intent's folders fails both registry cases; no bounding fails both bound cases with `INTENT_FAILED`; the count bounds without the byte fit fail the long-root case with `INTENT_FAILED`; cleaning only the recorded list instead of the full merge fails both bound cases.

### Decisions and deviations

- **Squirrel ends the running instance before the hook.** The plan's risk G1 assumed that Squirrel does not end a running application. At the pinned commit `eef37460ae`, `UpdateManager.FullUninstall` calls `KillAllExecutablesBelongingToPackage`, which ends every process whose image lies under the install root (except Update.exe and squirrel.exe), before `--squirrel-uninstall` runs. The hook's lock request (U6) is still implemented and tested; for a Windows-initiated uninstall it mostly finds the lock free (`instance: none`). The CI scenarios accept `none` and `exited` and record which. The plan's RED "the instance is not signalled, so (1) is deferred" therefore cannot fail on CI; it is shown at the unit level (RED (d) below).
- **Lock re-request.** Proved with the real Electron binary (`single-instance-relock.test.ts`); no CIM fallback was needed.
- **Hard stop at 9 s.** Besides the engine's 8 s deadline, a hook still running 9 s after its start writes a `deferred` receipt with `BUDGET_EXPIRED` and exits 3, inside Squirrel's 10 s.
- **Shortcut removal on uninstall.** Squirrel removes no shortcut for an application that handles its events, so the uninstall hook runs `Update.exe --removeShortcut=<exe>` beside the engine, under the same production and test-file rule as the creation.
- **Shortcuts in the lifecycle.** The harness writes `shortcuts: true` only on a GitHub-hosted runner (plan U12), so a local run creates none; on CI the scenarios assert that each install created at least one and each uninstall removed them.
- **Residue predicate.** The harness checks the binary root after each uninstall with the rule of `tests/windows/Assert-UninstallResidue.ps1` (only `Update.exe`, `app-<version>\squirrel.exe` with the installed helper's bytes and the one-byte `.dead`), written inline because a reinstall can leave more than one `app-` folder and that script accepts one fixed version.
- **Job bound.** Each driver command runs in a BoundedProcess Job of at most 60 s, so the uninstall program and its drain get 35 s after the launch that precedes them.
- `tools/lint/config.mjs` still names `electron-squirrel-startup` among the modules renderer and preload code may not import; the restriction is harmless and the lint configuration was not among the plan's files.

### Review fix round (October 18, 2026)

- **The hard stop and the run claim one result.** Before, the hard stop could set its flag while its receipt was still being written and the run then returned 0 (the process exiting with a cut receipt), or the hard stop could return 3 while the run wrote a `complete` receipt. Now the side that claims first writes the only receipt and sets the exit code; the result resolves only after that write, and the other side never resolves the race. Two cases cover the run settling just after the hard stop and the hard stop firing during the run's write.
- **Deadlines from the process time origin.** Squirrel's 10 s start at spawn, so the engine deadline is min(hook start + 8 s, 8 s − 0.5 s) and the hard stop min(hook start + 9 s, 9 s − 0.5 s) on `performance.now()`; the receipt records `startupOffsetMs`.
- **Wording.** The hard stop no longer claims that the intent is on disk: if the engine reached it, a later run finishes; otherwise nothing was deleted.
- **Roaming userData.** Everything but Chromium's `lockfile` goes while the hook holds the lock; the remaining window between the release and the last removal is documented.
- **`ENGINE_FAILED`.** An engine or hook step that throws is reported as `ENGINE_FAILED` instead of `DATA_ENTRY_BLOCKED`; its text for PR-4 is in [uninstall](../uninstall.md#receipt).
- **README.** It asks to delete the `plugins` and `uninstall` folders and to check anything else in the data root first, because the engine keeps unknown entries on purpose.
- **Portable copy.** [uninstall](../uninstall.md#squirrel-uninstall-hook) states that a running portable copy shares the userData and the data root, receives the request, quits and has its data wiped.

RED, each applied alone and reverted: the losing side resolving the race fails both race cases; a claim that resolves before its receipt is written fails both race cases; deadlines counted from the hook start fail the anchoring and late-start cases; an engine throw reported as `DATA_ENTRY_BLOCKED` fails the `ENGINE_FAILED` case; the old README sentence fails the README case.

### Decisions and deviations

- **Exit order.** The service and every writer stop first (the explicit exit), then `log.finalize` lands the final rows (`SERVICE_EXIT`, `APP_EXIT`), then the wipe runs. After `finalize` every row is written synchronously, so none can be in flight during the wipe; while the log folder lies inside the data root (a production install), main writes no row after the wipe, because one would recreate the folder. `APP_UNINSTALL_FINISHED`, the failsafe's and the handover's rows are written only when the log folder lies outside the data root.
- **Failsafe.** The 12 s failsafe is armed when the uninstall exit begins and disarmed just before the result dialog, which waits for the user. The supervisor's 3,000 ms kill and 5,000 ms bounds stay as they are for every reason; the failsafe adds the wipe's 5 s and a margin on top of them.
- **Dialog before the handover.** Squirrel ends every process under the install root before its hook runs, so the result dialog comes before Update.exe starts; a failed start gets a second, error dialog.
- **Preflight through the engine.** The preflight is the engine with scope `preflight` and a dry-run cleanup, not a separate code path, so it applies the same registry, intent, running-game and per-folder rules as the removal.
- **Blocked targets.** A blocked folder is named by the plugin card's target id; a recorded folder the card no longer lists is `<game>:other`.
- **Roaming userData (O7).** The running application holds `%APPDATA%\ETS2Telemetry Desktop`, so the in-app path does not remove it itself: Squirrel's uninstall hook, started by the handover after the application exited, finds the data root gone, completes and removes the folder in a production install. If Update.exe cannot start, the folder stays until the user uninstalls from Windows Settings.
- **Race.** When a removal races, plugin setup resumes and installs the plugin again where it was removed; the card says that nothing was changed, which holds for the end state.
- **Installed scaffold smoke.** An installed copy's `scaffold` smoke (the installer lifecycle's) would open the confirmation, so it reads the warning but does not press the button; its receipt records `notInstalledShown: null`, and `RuntimeReceipt.ps1` refuses `true` for mode `installed`. The plan named only the portable answer; this keeps the installed smokes valid.
- **Main-boundaries race case.** `main-boundaries.test.ts` replaces the orchestrator and checks that main passes every answer through unchanged and wires suspend, resume and the target ids to plugin setup; the removal race itself, with the resumed setup, is tested on fake installs in `app-uninstall.test.ts`.
- **(4) exit code.** Squirrel may end the application between the handover and `app.exit(0)`, so scenario (4) records the exit code without asserting it; the dialog and finished rows prove the order.
- **Path-specific failure texts.** `ENGINE_FAILED` on the card says "run the uninstall again", which fits only the in-app path. - **The plugin is installed first.** A `plugin-launch for-app` step (60 s Job, PR-3's command) installs it, so each in-app run only starts the application and finds the plugin recorded.

### Decisions and deviations

- **When to register.** The hook registers on every run that has something to clean, right after the intent and before the first deletion, and removes the registration only after a complete run, once the data root and the copied script are gone. Registering only when the outcome is deferred would leave a window: a hook killed after its first deletion (the hard stop is at 9 s and Squirrel stops waiting at 10 s) would leave plugin files with nothing registered to finish them. The cost of registering first is one `reg.exe` call more on a complete run. A crash between the last deletion and the removal leaves a value whose script is gone; Windows deletes the value before it runs it, and PowerShell exits on the missing file.
- **A failed registration does not stop the uninstall.** The copy or `reg.exe` may fail (`executor: failed`); the run continues, and the README, without the sign-in promise, stays the fallback. A failed copy registers nothing, so the value never names a missing or partial script.
- **260 characters.** Windows runs a Run or RunOnce command of at most 260 characters; a longer command is never registered and the README is the fallback. A typical profile path gives about 185 characters.
- **The executor also reads the install registry.** The plan says the script runs the contract "read from pending.json". The engine merges the registry's folders with the intent's, and the hook's intent can hold fewer folders than the registry (its bounds); the script therefore merges the folders of a `plugins\setup.json` that is a valid version 1 document, and treats an invalid, newer or unreadable registry as the engine does (no folder from it, `plugins\` kept, deferred). The script never writes the registry; a cleaned folder that stays in it is absent on the next attempt.
- **Production check.** The script requires its base to be the known-folder LocalAppData (`Environment.GetFolderPath`), not the `LOCALAPPDATA` variable, which a sign-in does not let anyone redirect for it; a test root needs the marker and a valid test file, as U3 does.
- **Nothing to do.** The script removes its value and changes nothing when the application is installed again or when there is no intent (`not-needed`), and when the intent is invalid (`refused`); it then never registers again.
- **Attempts.** The hook's run is attempt 1; the script rewrites the intent with attempt + 1 and registers itself again before it deletes anything, so a killed run is still retried and counted. After the 10th attempt it stops, removes its value and writes README.txt.
- **Message box.** One box in production only. A test root never shows one, with no switch needed, so a test or a CI run can never block on it. Its appearance at a real sign-in stays a manual check.
- **Test parameter.** `-TestRunningImages` replaces the process list only in a test root, so the case table runs without depending on the machine's processes; a production run that receives it is refused. The registered command passes no argument.
- **Lifecycle scenarios.** The brief asked to extend scenario (2) with the registered command after the fake host stops. Scenario (3) needs (2)'s deferral to prove that a reinstall cancels it, now including the RunOnce value, so (2) is followed by an executor run while the host still runs (blocked: attempt 2, registered again), and the final uninstall of (3), which used to complete while the application ran, now defers while the host runs and is completed by the executor once the host stopped. Scenario (1) still covers a complete uninstall while the application runs, and every complete hook run asserts that no value is left. This adds two driver commands of 60 s Jobs; each stays within the cap (`installer-guard.test.ts` "harness Job bounds").
- **Simulating a sign-in.** The PowerShell test and the driver delete the value before they start the command, as Windows does for a RunOnce value, so "registers itself again" is observable; one PowerShell case leaves the value in place to show that a complete run removes it.
- **Extended CI.** The plan did not name a CI entry for `Test-DeferredCleanup.ps1`; it is added to `scripts/ci/Invoke-Extended.ps1` (main pushes and extended dispatches), next to `Test-UninstallResidue.ps1`. No job or check is added or renamed.
- **Known differences between the implementations** (outside the table, all on the side of keeping files): an unexpected error on a game root is `IO_ERROR` in the script where the engine may say `PERMISSION_DENIED`; a read-only temporary file of an interrupted install blocks in the script, while Node's unlink clears the attribute and removes it; in a test root the script checks the target of each link on a folder's way into the root, where the engine resolves real locations.

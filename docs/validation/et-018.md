# ET-018: installer, upgrade and uninstall

ET-018 packages the application for distribution: installed upgrades that keep local data, and an uninstall that removes the application's own data and plugin ([concept](../../concept.md#uninstall-removes-local-data--october-16-2026)). The architect's plan of October 18, 2026 splits it into six PRs; its decisions U1–U17 and the owner decisions O1–O8 are recorded with the coordinator's authorization. This record collects each PR's local checks and the checks that stay pending. Hosted CI runs, independent review and acceptance are recorded by the coordinator. No game was launched, no installer ran on a personal machine, and no claim about real games, TruckersMP, display or performance follows.

### Decisions and deviations

- **Synthetic target instead of `data\telemetry.sqlite`.** The plan seeds `schema-v1-representative.sqlite` as `data\telemetry.sqlite`. That fixture's `database_info.purpose` is `synthetic`, and the history path refuses any other purpose (`checkPath`, `PURPOSE_MISMATCH`), so the copy would never migrate. A history-purpose copy would mean editing the fixture's contents. The harness therefore seeds the copy as `synthetic\upgrade.sqlite` and launches with `ETS2TELEMETRY_RECORDING=synthetic:upgrade`, which opens it through the same `openConnection` migration and backup path, with backups in `synthetic\backups`. It also requires that no `data\telemetry.sqlite` is created. The fixture itself is checked against `manifest.txt` before and after the copy.
- **Step Jobs.** `BoundedProcess.Run` allows at most 60 s per Job, so the whole lifecycle cannot run in one Job. Every installer program and driver command runs as the root of its own Job, and the installed smokes keep their own 60 s Jobs. The `step` command waits until no process image under R is left, because Squirrel's `--updateSelf` helper outlives its parent while `BoundedProcess` gives descendants only one second after the root exits. The fixture build runs outside a Job, like `npm run make`, bounded by the step's 8 minutes.
- **Run root and evidence.** R is `$env:RUNNER_TEMP\installer-<id>`, so the installed binaries are never uploaded; the evidence is `.local/ci/installer-<id>-evidence`, already inside the uploaded `.local/ci`, so the upload paths need no new entry.
- **Copies for the read.** A read-only connection to a WAL database leaves `-wal` and `-shm` files, which would change the data root the next installer step is compared against. The reader opens copies in `R\temp`; the original is checked for sidecars before.
- **Native binding name.** The module cache names the binding by its ASAR path, `resources\app.asar\node_modules\better-sqlite3\prebuilds\win32-x64.node`, which Electron loads from `app.asar.unpacked`; the driver requires that name and the unpacked file.
- **Default scenarios.** Installed `scaffold` on 0.1.0, and `scaffold`, `plugin` and `telemetry` on 0.1.1 (`-ScenariosA`, `-ScenariosB`). The first dispatch run measures the step; trim them if the scaffold job nears 15 minutes.

### Local driver check without an installer

To check the driver before CI, a fake installed layout was built under `.local\ci\installer-<id>`: a copy of the portable package as `LocalAppData\ETS2TelemetryDesktop\app-0.1.0` and a placeholder `Update.exe` text file that was never executed. No Setup.exe, Update.exe or `--squirrel-*` command ran. The facts held the known-folder paths, the process list and `false` for the real install and registration (not probed). `tasklist` showed no ETS2, ATS, TruckersMP or ETS2TelemetryDesktop process before each launch, and every launch went through Playwright with `ETS2TELEMETRY_PROFILE_DIR` inside the root and never with `ETS2TELEMETRY_PLUGIN_SETUP=real`.

- Under `BoundedProcess` Jobs: `guard plan` and `guard ready`, `seed`, `snapshot`, `launch` (HISTORY_STORAGE_OPENED `{schemaVersion: 2, created: false, migratedFrom: 1}`, SETTINGS_LOADED `migratedFrom: 2`, `test-root` plugin mode, no action, exit 0), `verify` (the hand-written content, one backup and manifest, the binding), a second `launch` (`migratedFrom: null`) and `verify`: all exit 0. The second launch left the data root byte-identical to the snapshot after the first verify.
- `Invoke-RuntimeSmoke.ps1 -Mode installed` against that layout: `scaffold`, `plugin` and `telemetry` passed, each receipt with `executableMatches`, `cwdOutsideInstall`, `minimalPath`, `developmentVariablesAbsent` and `packaged` true.
- `Invoke-InstallerLifecycle.ps1` locally: `-Plan` printed the steps; without it the harness refused with `LOCAL_RUN_REFUSED` before it created or read anything, also with `GITHUB_ACTIONS=true` and `RUNNER_ENVIRONMENT=self-hosted`; `-AllowLocal` refused with `LOCAL_RUN_UNAVAILABLE_UNTIL_PR3`. The retired harnesses printed their plans and refused `-Run` with `RETIRED_ET018_REAL_ROOTS`.
- The fake layout was then deleted with the driver's `cleanup`.

This is not an installed run: Squirrel's file layout, hooks, registration and update are observed only on CI.

## Geometry and pixel measurement

At scale 0.5 the 2560 × 1440 client is 1706.67 × 960 DIP. The strip is 640 DIP wide (CSS 1280). Job focus needs two rows, 40 DIP; Driving only one row, `ceil(19 + 2) = 21` DIP. With y = 1 the window's bottom is 8 DIP above the client's bottom, so a rectangle applied as requested cannot overflow. The architect's plan computed these values; `tests/unit/overlay-bounds.test.ts` restates them from the rules, and the implementer checked them against `overlayBounds`: Job focus `{2601, 1152, 640, 40}` and Driving only `{2601, 1171, 640, 21}` in a client at (1706.67, 240) DIP.

The architect measured the screenshot pixel by pixel (1:1 physical):

- The dashed edit outline is exactly 960 px wide (x 2784–3743), which is 640 DIP.
- The outline's top is at y 1091. Its right edge runs down to y 1146, with no bottom outline visible.
- The game window's bottom frame is at y 1132–1133, and the overlay tint extends 13–15 px below it.
- The requested one-row rectangle would have its top at about client bottom − 29 DIP, about 1088.5 px, and a height of 31.5 px.

The observed top matches within about 2 px, but the painted window is at least 56 px (at least 37 DIP) high, not 31.5 px. The Driving only content sits at the window's bottom (`contentAnchorY` 1).

## Established

1. Main's requested rectangle was correct and inside the client. The actual window took the new top but kept a larger height than 21 DIP.
2. The `.overlay` root spans 100vw × 100vh with the edit outline, so the renderer viewport, and therefore the window, was at least about 37 DIP high.
3. Code defect: `OverlayController` stored the requested rectangle, called `setBounds` only when the next computed rectangle differed, and never read the actual bounds; `OverlayWindow` had no `getBounds`. Sections 5, 4, 3, 2 and 1 are all one row at scale 0.5, so they produce the same rectangle and no `setBounds` call. A scale change produces a new rectangle and a new `setBounds`, which matches the owner's workaround. The workaround is not the fix.
4. Main's ordering is not the cause. Main publishes the projection, then calls `setLayout` with layout, placement and sections together; the bounds are computed once, the zoom is applied first, and the window size comes only from `overlayBounds`.
5. The renderer's CSS row wrapping is not the cause.

## Hypotheses (none established)

- **H-stale.** Windows or Electron applied the move but kept the previous two-row height of 40 DIP (60 px). On the base first show the interactive toggles come first, then `setBounds` on a hidden window, then `showInactive`.
- **H-min.** An effective minimum height of about 37–40 DIP, from `WM_GETMINMAXINFO` or the minimum track size, or from DIP-to-pixel rounding of Electron's minimum and maximum size for a non-resizable window.
- **H-expand.** Chromium's old 64 × 64 minimum for translucent windows. It is not in the current source, so it is unlikely.

A drag in progress was rejected as a cause.

## Change

The controller now verifies the window's actual bounds after every requested rectangle and on every later placement, with 1 DIP of tolerance per edge. A mismatch is applied again at most twice, after an inactive show if the window was still hidden (H-stale). A window that keeps another size is placed once at that size by the same fractions when it fits inside the client (H-min). Otherwise the overlay hides fail-closed, and edit mode reports `too-large`. The same rectangle is not set again until something it depends on changes. The saved placement, the edit draft, Cancel, Escape and minimize, the fit refusal, focus, click-through and the topmost re-assertion keep their behaviour. `OVERLAY_BOUNDS_MISMATCH` goes to the default log; `OVERLAY_BOUNDS_SET` goes only to the opt-in diagnostic timeline. Settings, IPC, preload, the overlay payload, wire, storage and native code are unchanged. See [the minimal overlay](../minimal-overlay.md#geometry-and-placements-et-012b).

The manual probe `scripts/diagnostics/Run-OverlayBoundsProbe.ps1 -OutputRoot <new directory>` records what Windows applies for the hypotheses' raw `setBounds` sequences on a window with the production overlay options. It records immediate bounds, bounds after 250 ms, the renderer viewport and the scale factor. It then replays the owner's sequence through the real controller. It runs in a 30 s Job with an isolated profile and opens no game, settings or user data. It is local evidence, not a CI check, and it cannot show what the game window does.

## Geometry and pixel measurement

At scale 0.5 the 2560 × 1440 client is 1706.67 × 960 DIP. The strip is 640 DIP wide (CSS 1280). Job focus needs two rows, 40 DIP; Driving only one row, `ceil(19 + 2) = 21` DIP. With y = 1 the window's bottom is 8 DIP above the client's bottom, so a rectangle applied as requested cannot overflow. The architect's plan computed these values; `tests/unit/overlay-bounds.test.ts` restates them from the rules, and the implementer checked them against `overlayBounds`: Job focus `{2601, 1152, 640, 40}` and Driving only `{2601, 1171, 640, 21}` in a client at (1706.67, 240) DIP.

The architect measured the screenshot pixel by pixel (1:1 physical):

- The dashed edit outline is exactly 960 px wide (x 2784–3743), which is 640 DIP.
- The outline's top is at y 1091. Its right edge runs down to y 1146, with no bottom outline visible.
- The game window's bottom frame is at y 1132–1133, and the overlay tint extends 13–15 px below it.
- The requested one-row rectangle would have its top at about client bottom − 29 DIP, about 1088.5 px, and a height of 31.5 px.

The observed top matches within about 2 px, but the painted window is at least 56 px (at least 37 DIP) high, not 31.5 px. The Driving only content sits at the window's bottom (`contentAnchorY` 1).

## Established

1. Main's requested rectangle was correct and inside the client. The actual window took the new top but kept a larger height than 21 DIP.
2. The `.overlay` root spans 100vw × 100vh with the edit outline, so the renderer viewport, and therefore the window, was at least about 37 DIP high.
3. Code defect: `OverlayController` stored the requested rectangle, called `setBounds` only when the next computed rectangle differed, and never read the actual bounds; `OverlayWindow` had no `getBounds`. Sections 5, 4, 3, 2 and 1 are all one row at scale 0.5, so they produce the same rectangle and no `setBounds` call. A scale change produces a new rectangle and a new `setBounds`, which matches the owner's workaround. The workaround is not the fix.
4. Main's ordering is not the cause. Main publishes the projection, then calls `setLayout` with layout, placement and sections together; the bounds are computed once, the zoom is applied first, and the window size comes only from `overlayBounds`.
5. The renderer's CSS row wrapping is not the cause.

## Hypotheses (before the probe)

- **H-stale.** Windows or Electron applied the move but kept the previous two-row height of 40 DIP (60 px). On the base first show the interactive toggles come first, then `setBounds` on a hidden window, then `showInactive`.
- **H-min.** An effective minimum height of about 37–40 DIP, from `WM_GETMINMAXINFO` or the minimum track size, or from DIP-to-pixel rounding of Electron's minimum and maximum size for a non-resizable window.
- **H-expand.** Chromium's old 64 × 64 minimum for translucent windows. It is not in the current source, so it is unlikely.

A drag in progress was rejected as a cause.

What the probe shows on this machine only:

- **H-min is supported.** Windows or Electron enforces a minimum height of 38 DIP for this overlay window. Which mechanism enforces it (the minimum track size, `WM_GETMINMAXINFO` or Electron's size limits) is not established, and neither is the owner's machine. On the owner's 150% display the painted window was at least about 37 DIP high, which is consistent with this minimum but does not prove it.
- **H-stale is not supported.** A shrink applied while hidden, after a show or in the base edit order was not kept at the previous height. The height went to 38 DIP, not to 40.
- **H-expand** was not tested separately; the measured minimum is 38 DIP, not 64.

The base controller never read the actual bounds. That defect is why the 38 DIP window lay outside the client. The fix places the window by its actual height inside the client.

## Change

The controller now verifies the window's actual bounds after every requested rectangle and on every later placement, with 1 DIP of tolerance per edge. A mismatch is applied again at most twice. A window that keeps another size is placed once at that size by the same fractions when it fits inside the client, which addresses H-min. Otherwise the overlay hides fail-closed, and edit mode reports `too-large`. Since review round 2, a hidden window stays hidden while it is re-applied and fitted and is shown only once a rectangle is accepted; the first round showed it first, as a remedy for H-stale, which the probe did not support. A refused request is not set again while nothing changes, and since round 2 the next distinct game client observation gives it one more bounded verification. The saved placement, the edit draft, Cancel, Escape and minimize, the fit refusal, focus, click-through and the topmost re-assertion keep their behaviour. `OVERLAY_BOUNDS_MISMATCH` goes to the default log; `OVERLAY_BOUNDS_SET` goes only to the opt-in diagnostic timeline. Settings, IPC, preload, the overlay payload, wire, storage and native code are unchanged. See [the minimal overlay](../minimal-overlay.md#geometry-and-placements-et-012b).

Review round 1 refined the change:

- **Drops.** A drop of a fitted window converts against the size Windows kept on each axis it changed, using the optional window size of `placementFromBounds`. A horizontal drop of the 38 DIP window therefore keeps y = 1. Before, it converted against the 21 DIP layout and gave y = (1154 − 248) / 923 = 0.9816, so the content rose about 17 DIP on every drop, and Done saved that fraction.
- **Fit by changed axes.** The fit keeps the requested dimension where the actual one differs only by rounding (at most 2 DIP). A strip as wide as the client allows is therefore not refused for one inflated DIP of width.
- **Log bound.** `OVERLAY_BOUNDS_MISMATCH` logs one line per mode, outcome and size difference, and at most 16 lines per launch (`BOUNDS_MISMATCH_REPORT_LIMIT`). A deterministic minimum height therefore logs once, not once per lower request. `OVERLAY_BOUNDS_SET` stays in the timeline only.

Review round 2, from the advisory review of PR #174, refined it again:

- **Recovery.** A fail-closed hide no longer waits for a layout, placement or sections change. The next distinct game client observation re-arms the refused request for one more bounded verification, with at most two re-applies and one fit. Such an observation is a changed client rectangle, a driving gate that opens again (the game back in front or restored, a fresh window report after an expired one), the overlay enabled or loaded again, or the edit overlay allowed to show again. Renewed window reports with the same rectangle set nothing, and no timer retries.
- **No show before acceptance.** A hidden window is re-applied and fitted while hidden. It is shown with `showInactive()` and the topmost re-assertion only once a rectangle is accepted, so a refused one never appears over the game at a wrong size.
- **Hide logging.** A `hidden` outcome is logged once per refused request, still within the per-launch limit, so the size-difference de-duplication cannot hide a refusal of another request.

The manual probe `scripts/diagnostics/Run-OverlayBoundsProbe.ps1 -OutputRoot <new directory>` records what Windows applies for the hypotheses' raw `setBounds` sequences on a window with the production overlay options. It records immediate bounds, bounds after 250 ms, the renderer viewport and the scale factor. It then replays the owner's sequence through the real controller. It runs in a 30 s Job with an isolated profile and opens no game, settings or user data. It is local evidence, not a CI check, and it cannot show what the game window does.

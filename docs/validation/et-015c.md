### Interpretations and deviations from the plan

- **Runtime interface.** It follows the plan, with three additions: `plan` is exposed; `historyOverrides` (`appVersion`, `closeGraceMs`) lets the storage suite use its `TEST_CLOSE_GRACE_MS`, as every real-worker client of the suite does; and `ingestionOverrides` is typed to exclude the wiring keys (sources, sink, selections, readiness, diagnostics, state), so a test can change bounds and timers but not the wiring under test. The step budgets are the exported constants `V1_INTAKE_BUDGET_MS` and `RECORDING_FLUSH_BUDGET_MS`, with the same values. Options that are functions are function-typed properties, which the lint's `unbound-method` rule requires.
- **Release point in (a) and (d).** The plan says to release after the intake phase logs. The release comes one macrotask after the flush step started, which is after the intake phase logged. Releasing at the intake log itself would let a flush step that does not wait still end after the release, which the first RED mutation would then not catch.
- **`history-storage` outcome.** (a) and (d) assert that the step ran in the `storage` phase and that `HISTORY_STORAGE_CLOSED`, which is logged only for a clean close, follows the flush, but not that the step ended `ok`. A real-worker close took longer than 2 s once on a loaded shared host (`TEST_CLOSE_GRACE_MS`, [ET-013 validation](et-013.md)), above the step's 1,000 ms budget; the budget itself is covered by the unit tests. (c) asserts both recording steps `ok` and the whole stop within 2,500 ms.
- **R10 scenario (G14).** The reactive server cannot wait for a client to close a live-only connection: it paces in real time while a client is connected and only a scripted `disconnect` ends a connection. The derived scenario therefore paces at scale 1 with a frame every 100 ms, so the server stays at most one frame behind the client's close and fast-forwards after it. The scripted disconnect at 10,050 ms is the hang guard of the upgrade; the `closedBy: client` check rejects a run in which it fired. `reactiveConflicts` is empty for the scenario, so the plan's fallback (lockstep scenario or plain test server) was not needed. The connection-1 snapshots depend on when the client closes, so the run is not compared with the replay (`reactiveDifferences`); rows, gaps, ACKs and the order are.
- **Gap rows.** `r10-upgrade.rows.expected.json` adds `gaps` to the usual shape, read from `event_gaps` by `storedGaps`, so the committed `noDurableConsumer` gap itself is compared, not only its interval.
- **Selecting after the open.** (a), (c) and (d) select the simulator only once the database is open; otherwise R10 makes the first hello live-only.
- **(c) failure setup.** Both event commits and sample writes fail, as on a full volume, so `V1_SAMPLES_EXIT` reports `DISK_FULL`. The flush timer is set far beyond the run, so the only sample write is the one at the stop. The stop is started one macrotask after the `disconnected` state, so the retry timer is armed; the case checks that only one socket existed at the stop and at the end of the run. The end of the run can come before a full backoff step, so this case does not prove that the stop cancels an armed retry timer. `V1Ingestion` clears that timer when the source stops; no test yet holds the stop past one backoff step with the timer armed.
- **(d) feasibility.** The optional stop while `restoreLoss` is in flight was feasible with two runtimes on one simulator run and the request held by `tracedHandle`; no fault-worker change was needed.
- **Live state while a commit is held (G20).** Not asserted in PR-1. In (a) the simulator, which waits for each ACK, writes nothing while eventSeq 4 is held, so there is no later live state to observe. PR-3's planned storage case covers it.

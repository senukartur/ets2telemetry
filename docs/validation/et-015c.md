### Interpretations and deviations from the plan

- **Runtime interface.** It follows the plan, with three additions: `plan` is exposed; `historyOverrides` (`appVersion`, `closeGraceMs`) lets the storage suite use its `TEST_CLOSE_GRACE_MS`, as every real-worker client of the suite does; and `ingestionOverrides` is typed to exclude the wiring keys (sources, sink, selections, readiness, diagnostics, state), so a test can change bounds and timers but not the wiring under test. The step budgets are the exported constants `V1_INTAKE_BUDGET_MS` and `RECORDING_FLUSH_BUDGET_MS`, with the same values. Options that are functions are function-typed properties, which the lint's `unbound-method` rule requires.
- **Release point in (a) and (d).** The plan says to release after the intake phase logs. The release comes one macrotask after the flush step started, which is after the intake phase logged. Releasing at the intake log itself would let a flush step that does not wait still end after the release, which the first RED mutation would then not catch.
- **`history-storage` outcome.** (a) and (d) assert that the step ran in the `storage` phase and that `HISTORY_STORAGE_CLOSED`, which is logged only for a clean close, follows the flush, but not that the step ended `ok`. A real-worker close took longer than 2 s once on a loaded shared host (`TEST_CLOSE_GRACE_MS`, [ET-013 validation](et-013.md)), above the step's 1,000 ms budget; the budget itself is covered by the unit tests. (c) asserts both recording steps `ok` and the whole stop within 2,500 ms.
- **R10 scenario (G14).** The reactive server cannot wait for a client to close a live-only connection: it paces in real time while a client is connected and only a scripted `disconnect` ends a connection. The derived scenario therefore paces at scale 1 with a frame every 100 ms, so the server stays at most one frame behind the client's close and fast-forwards after it. The scripted disconnect at 10,050 ms is the hang guard of the upgrade; the `closedBy: client` check rejects a run in which it fired. `reactiveConflicts` is empty for the scenario, so the plan's fallback (lockstep scenario or plain test server) was not needed. The connection-1 snapshots depend on when the client closes, so the run is not compared with the replay (`reactiveDifferences`); rows, gaps, ACKs and the order are.
- **Gap rows.** `r10-upgrade.rows.expected.json` adds `gaps` to the usual shape, read from `event_gaps` by `storedGaps`, so the committed `noDurableConsumer` gap itself is compared, not only its interval.
- **Selecting after the open.** (a), (c) and (d) select the simulator only once the database is open; otherwise R10 makes the first hello live-only.
- **(c) failure setup.** Both event commits and sample writes fail, as on a full volume, so `V1_SAMPLES_EXIT` reports `DISK_FULL`. The flush timer is set far beyond the run, so the only sample write is the one at the stop. The stop is started one macrotask after the `disconnected` state, so the retry timer is armed; the case checks that only one socket existed at the stop and at the end of the run. The end of the run can come before a full backoff step, so this case does not prove that the stop cancels an armed retry timer. `V1Ingestion` clears that timer when the source stops; no test yet holds the stop past one backoff step with the timer armed.
- **(d) feasibility.** The optional stop while `restoreLoss` is in flight was feasible with two runtimes on one simulator run and the request held by `tracedHandle`; no fault-worker change was needed.
- **Live state while a commit is held (G20).** Not asserted in PR-1. In (a) the simulator, which waits for each ACK, writes nothing while eventSeq 4 is held, so there is no later live state to observe. PR-3's planned storage case covers it.

## PR-2 commit backlog bound (October 16, 2026)

Branch `fix/commit-backlog-redelivery-bound`, from `main` at `b99e120`, in parallel with PR-1.

### Defect

`DurableDelivery` counted every coverage item queued or in flight across all connections against `MAX_PENDING_COMMITS` = 256. A connection that ends without its items being dropped (a plain disconnection) leaves them queued, and they keep counting until they leave the FIFO. The producer retains up to 256 entries ([native v1 transport](../native-transport-v1.md#store-rules), I2) and redelivers all unacknowledged ones on the next connection. Leftovers plus that redelivery could exceed 256, so the reconnection was closed with a retryable `BACKLOG_FULL` while the earlier work drained, and the events the plugin observed while it reconnected became `offline` loss. The new tests below reproduce it against the old bound.

### Changes

- `apps/desktop/src/v1-durable-delivery.ts`: `MAX_PENDING_COMMITS` = 512, twice the producer's 256 retained entries (G11), with a comment stating the rule. An ended connection's leftover items were never acknowledged, so they cover retained entries (at most 256). The redelivery is at most the 256 retained entries, and live events are admitted into the same entries until an ACK releases some, which follows commits that already left the queue. The guarantee covers the leftovers of one ended connection plus one full redelivery plus live events; a live delta gap item fits only while the leftovers and the redelivery stay below 512. Leftovers stacked from several connections that ended before the queue drained, or the delta gaps of a gap record growing during a true storage stall, can still fill the queue and close the connection as retryable `BACKLOG_FULL`: bounded and draining, never a livelock. `MAX_PENDING_READINGS` stays 512. The `>=` check, the overflow handling and the sample op are unchanged.
- `tests/unit/v1-durable-delivery.test.ts`: the backlog case now fills 512 items and closes on the 513th, instead of 256 and the 257th. The requirement behind it changed (G11); the test's structure and its other expectations are unchanged. A new case covers an ended connection: 200 items wait behind a held commit, and the next connection then redelivers its full 256 entries (255 events and the reserved gap record) plus one live delta gap. 457 items are pending without `BACKLOG_FULL`, every item commits once (1–200 first for the ended connection without an ACK, then as duplicates), and the new connection acknowledges each in order.
- `tests/storage/backlog-redelivery.test.ts` (new) with `tests/fixtures/recording/backlog-redelivery.rows.expected.json` (new, hand-written before the first run). The scenario is `normal-delivery.json` with 194 identical truck re-sends at 250 ms, so that the first connection carries eventSeq 1–200. The test-only fault worker holds the commit of eventSeq 1 inside its transaction. The first connection's client does not wait for ACKs and is disconnected at 450 ms. At 460 ms the same service's second connection receives 1–200 as redeliveries and then the live 201–203. The commit is released only once the redelivered eventSeq 200 has reached the ingestion, so 400 items are pending. The test asserts:
  - no `V1_DURABLE_*` log;
  - one service;
  - the live state reached the second connection's checkpoint while the commit was held;
  - the second connection's events are `1r`–`200r` and then 201–203, and its ACKs are 1–203;
  - every ACK is at or below the reported coverage;
  - 203 first commits and 200 duplicates;
  - the stored trips, attributions and intervals equal the hand-written rows;
  - a synthetic-purpose database, and no `ETS2Telemetry\data\telemetry.sqlite` or `data\telemetry.sqlite` under the workspace used as LOCALAPPDATA.
- `tests/storage/recording-helpers.ts`: the harness gate takes an optional `redelivered: true`. The gated stream is then the first one that carries the gate's event as a redelivery, instead of the first connection's stream. The gate is passed to each connection until it fires. `tests/storage/client-socket.test.ts` gains one case for it. The `maxPendingCommits` comment no longer names 256.
- `tests/storage/trip-recorder-faults.test.ts`: the S4 (c) comment states the new production bound and points to the new test; the test is unchanged.
- Documentation: [telemetry service v1](../telemetry-service-v1.md) (queue bound, the "Transient refusal" paragraph replaced by the 512 rule and its reasoning, the samples note, the tests table and Pending, where the backlog decision is removed) and the [registry](../regression-registry.md) row REG-011.

No change to `v1-ingestion.ts`: none of its comments names the bound. There is no wire, fixture, native, broker, storage, schema, preload/IPC or renderer change, and no dependency or lockfile change. Production behaviour is unchanged: the service passes no sink for game sources.

### Interpretations and deviations from the plan

- **Unit redelivery shape.** The plan names "256 items plus one live gap". The producer admits at most 255 events and keeps the 256th entry for a gap record (I2). The redelivery is therefore 255 events and the reserved gap record (256 entries), and the live item is a delta gap that extends that record (I3, I6).
- **Harness gate.** The release must follow the arrival of the whole redelivery. The reactive server awaits the second connection's ACKs before it writes anything later, so no later server message can mark that point. The existing harness gate could hold only the first connection's stream. It gained the `redelivered` option instead of a sleep or a poll of private state. `recording-helpers.ts` is also edited by PR-1, which may need a merge.
- **Scenario source.** The scenario is derived in the test from `normal-delivery.json` (one inserted step and a new transport), as the S4 cases derive theirs with `withTransport`. It is not a new fixture file.
- **Release in the old-bound run.** Besides the gate, a `BACKLOG_FULL` status also releases the held commit, so the old-bound run fails with its assertion instead of hanging. With the fix that status never occurs.

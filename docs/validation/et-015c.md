### Interpretations and deviations from the plan

- **Runtime interface.** It follows the plan, with three additions: `plan` is exposed; `historyOverrides` (`appVersion`, `closeGraceMs`) lets the storage suite use its `TEST_CLOSE_GRACE_MS`, as every real-worker client of the suite does; and `ingestionOverrides` is typed to exclude the wiring keys (sources, sink, selections, readiness, diagnostics, state), so a test can change bounds and timers but not the wiring under test. The step budgets are the exported constants `V1_INTAKE_BUDGET_MS` and `RECORDING_FLUSH_BUDGET_MS`, with the same values. Options that are functions are function-typed properties, which the lint's `unbound-method` rule requires.
- **Release point in (a) and (d).** The plan says to release after the intake phase logs. The release comes one macrotask after the flush step started, which is after the intake phase logged. Releasing at the intake log itself would let a flush step that does not wait still end after the release, which the first RED mutation would then not catch.
- **`history-storage` outcome.** (a) and (d) assert that the step ran in the `storage` phase and that `HISTORY_STORAGE_CLOSED`, which is logged only for a clean close, follows the flush, but not that the step ended `ok`. A real-worker close took longer than 2 s once on a loaded shared host (`TEST_CLOSE_GRACE_MS`, [ET-013 validation](et-013.md)), above the step's 1,000 ms budget; the budget itself is covered by the unit tests. (c) asserts both recording steps `ok` and the whole stop within 2,500 ms.
- **R10 scenario (G14).** The reactive server cannot wait for a client to close a live-only connection: it paces in real time while a client is connected and only a scripted `disconnect` ends a connection. The derived scenario therefore paces at scale 1 with a frame every 100 ms, so the server stays at most one frame behind the client's close and fast-forwards after it. The scripted disconnect at 10,050 ms is the hang guard of the upgrade; the `closedBy: client` check rejects a run in which it fired. `reactiveConflicts` is empty for the scenario, so the plan's fallback (lockstep scenario or plain test server) was not needed. The connection-1 snapshots depend on when the client closes, so the run is not compared with the replay (`reactiveDifferences`); rows, gaps, ACKs and the order are.
- **Gap rows.** `r10-upgrade.rows.expected.json` adds `gaps` to the usual shape, read from `event_gaps` by `storedGaps`, so the committed `noDurableConsumer` gap itself is compared, not only its interval.
- **Selecting after the open.** (a), (c) and (d) select the simulator only once the database is open; otherwise R10 makes the first hello live-only.
- **(c) failure setup.** Both event commits and sample writes fail, as on a full volume, so `V1_SAMPLES_EXIT` reports `DISK_FULL`. The flush timer is set far beyond the run, so the only sample write is the one at the stop. The stop is started one macrotask after the `disconnected` state, so the retry timer is armed; the case checks that only one socket existed at the stop and at the end of the run. The end of the run can come before a full backoff step, so this case does not prove that the stop cancels an armed retry timer. `V1Ingestion` clears that timer when the source stops; no test yet holds the stop past one backoff step with the timer armed.
- **(d) feasibility.** The optional stop while `restoreLoss` is in flight was feasible with two runtimes on one simulator run and the request held by `tracedHandle`; no fault-worker change was needed.
- **Live state while a commit is held (G20).** Not asserted in PR-1. In (a) the simulator, which waits for each ACK, writes nothing while eventSeq 4 is held, so there is no later live state to observe. PR-3's planned storage case covers it.

## PR-2 commit backlog bound (October 16, 2026)

Branch `fix/commit-backlog-redelivery-bound`, from `main` at `b99e120`, in parallel with PR-1.

### Defect

`DurableDelivery` counted every coverage item queued or in flight across all connections against `MAX_PENDING_COMMITS` = 256. A connection that ends without its items being dropped (a plain disconnection) leaves them queued, and they keep counting until they leave the FIFO. The producer retains up to 256 entries ([native v1 transport](../native-transport-v1.md#store-rules), I2) and redelivers all unacknowledged ones on the next connection. Leftovers plus that redelivery could exceed 256, so the reconnection was closed with a retryable `BACKLOG_FULL` while the earlier work drained, and the events the plugin observed while it reconnected became `offline` loss. The new tests below reproduce it against the old bound.

### Changes

- `apps/desktop/src/v1-durable-delivery.ts`: `MAX_PENDING_COMMITS` = 512, twice the producer's 256 retained entries (G11), with a comment stating the rule. An ended connection's leftover items were never acknowledged, so they cover retained entries (at most 256). The redelivery is at most the 256 retained entries, and live events are admitted into the same entries until an ACK releases some, which follows commits that already left the queue. The guarantee covers the leftovers of one ended connection plus one full redelivery plus live events; a live delta gap item fits only while the leftovers and the redelivery stay below 512. Leftovers stacked from several connections that ended before the queue drained, or the delta gaps of a gap record growing during a true storage stall, can still fill the queue and close the connection as retryable `BACKLOG_FULL`: bounded and draining, never a livelock. `MAX_PENDING_READINGS` stays 512. The `>=` check, the overflow handling and the sample op are unchanged.
- `tests/unit/v1-durable-delivery.test.ts`: the backlog case now fills 512 items and closes on the 513th, instead of 256 and the 257th. The requirement behind it changed (G11); the test's structure and its other expectations are unchanged. A new case covers an ended connection: 200 items wait behind a held commit, and the next connection then redelivers its full 256 entries (255 events and the reserved gap record) plus one live delta gap. 457 items are pending without `BACKLOG_FULL`, every item commits once (1–200 first for the ended connection without an ACK, then as duplicates), and the new connection acknowledges each in order.
- `tests/storage/backlog-redelivery.test.ts` (new) with `tests/fixtures/recording/backlog-redelivery.rows.expected.json` (new, hand-written before the first run). The scenario is `normal-delivery.json` with 194 identical truck re-sends at 250 ms, so that the first connection carries eventSeq 1–200. The test-only fault worker holds the commit of eventSeq 1 inside its transaction. The first connection's client does not wait for ACKs and is disconnected at 450 ms. At 460 ms the same service's second connection receives 1–200 as redeliveries and then the live 201–203. The commit is released only once the redelivered eventSeq 200 has reached the ingestion, so 400 items are pending. The test asserts:
  - no `V1_DURABLE_*` log;
  - one service;
  - the live state reached the second connection's checkpoint while the commit was held;
  - the second connection's events are `1r`–`200r` and then 201–203, and its ACKs are 1–203;
  - every ACK is at or below the reported coverage;
  - 203 first commits and 200 duplicates;
  - the stored trips, attributions and intervals equal the hand-written rows;
  - a synthetic-purpose database, and no `ETS2Telemetry\data\telemetry.sqlite` or `data\telemetry.sqlite` under the workspace used as LOCALAPPDATA.
- `tests/storage/recording-helpers.ts`: the harness gate takes an optional `redelivered: true`. The gated stream is then the first one that carries the gate's event as a redelivery, instead of the first connection's stream. The gate is passed to each connection until it fires. `tests/storage/client-socket.test.ts` gains one case for it. The `maxPendingCommits` comment no longer names 256.
- `tests/storage/trip-recorder-faults.test.ts`: the S4 (c) comment states the new production bound and points to the new test; the test is unchanged.
- Documentation: [telemetry service v1](../telemetry-service-v1.md) (queue bound, the "Transient refusal" paragraph replaced by the 512 rule and its reasoning, the samples note, the tests table and Pending, where the backlog decision is removed) and the [registry](../regression-registry.md) row REG-011.

### Interpretations and deviations from the plan

- **Unit redelivery shape.** The plan names "256 items plus one live gap". The producer admits at most 255 events and keeps the 256th entry for a gap record (I2). The redelivery is therefore 255 events and the reserved gap record (256 entries), and the live item is a delta gap that extends that record (I3, I6).
- **Harness gate.** The release must follow the arrival of the whole redelivery. The reactive server awaits the second connection's ACKs before it writes anything later, so no later server message can mark that point. The existing harness gate could hold only the first connection's stream. It gained the `redelivered` option instead of a sleep or a poll of private state. `recording-helpers.ts` is also edited by PR-1, which may need a merge.
- **Scenario source.** The scenario is derived in the test from `normal-delivery.json` (one inserted step and a new transport), as the S4 cases derive theirs with `withTransport`. It is not a new fixture file.
- **Release in the old-bound run.** Besides the gate, a `BACKLOG_FULL` status also releases the held commit, so the old-bound run fails with its assertion instead of hanging. With the fix that status never occurs.

### Interpretations and deviations from the plan

- **Rule 8.** G3 says that active durable delivery with stale, disconnected or waiting v1 data reads `interrupted`, and that everything else reads `waiting`. The order of a connection's session open and its checkpoint is not fixed, so that literal rule gives a passing `interrupted` at some first connections and a passing `waiting` at some reconnections. The rule now reads `interrupted` when the selection was recording or paused (cursor active and v1 connected or paused; paused since review pass 1) since it was selected, and `waiting` otherwise. Stale data after recording still reads `interrupted`, and `recording` still needs all three conditions. Exception (PR-3 review pass 2, a nit recorded in documentation only): the latch is set from each synchronous `onState` call, so a cursor briefly `active` with fresh data before an `ACK_AHEAD_OF_STORAGE` failure latches it. After a later plugin session lifts the block, rule 8 can read `interrupted` instead of `waiting` until the new session's checkpoint, although that selection recorded nothing. It affects only the shown state, never the data.
- **Settling.** The publisher computes a noted change in a `setImmediate` callback. Changes made in one I/O callback and its promise jobs, such as a session opening and its checkpoint finding the database behind the plugin, then give one status and no passing `recording`. The 250 ms coalescing and the immediate loss changes follow G5. The storage cases set the interval to 0 (`statusOverrides`), so real time removes no step. They compare states and codes, since a trip or loss change alone can merge with a state change in one settled turn, and they compare the final status in full.
- **Closed database and unknown codes.** A `closed` database reads `stopped` with its failure code, `STORAGE_CLOSED` without one. A code outside the closed set reads `INTERNAL`. Main accepts `unknown` from a service as a valid status.
- **(a) "SQLITE_FULL twice".** One injected failure, so that the hand-written `normal-delivery-retry` rows apply unchanged; they describe exactly one reconnection. A second failure of the redelivery would need a third connection and other rows. The case shows both transitions, `recording` to `retrying DISK_FULL` and back.
- **(b) "then live-only".** Read as the reconnection being live-only (hello `durableEvents: false`, no ACK) while the status stays `stopped PERMISSION_DENIED` for the service lifetime (G10; rule 4 precedes `not-recorded-source` and `live-only` is reserved for `ACK_AHEAD_OF_STORAGE`).
- **(c) "then recording".** With a bound of four, the same service refuses the redelivery again, because every received item is redelivered, one more than the bound. As in S4 (c), a restarted service with the production bound records it. The case therefore shows `retrying BACKLOG_FULL` on the first service and `recording` on the second.
- **(g) A new plugin session.** Each reactive server serves one plugin session, so the new session is reached by selecting the same source again with the second server's endpoint, as a game restart reaches the same endpoint.
- **(i) G20.** Live state advancing while a commit is held is one dedicated case, not an assertion of every case: the other cases' clients wait for each ACK, so nothing more arrives while a commit is in flight.
- **Staleness in the storage cases.** A 600 s staleness bound (see the failed run above). Staleness stays covered by the unit rule table.
- **Restore loss across services.** A later service in the same plugin session counts a restore loss again, although storage keeps one row: `recordCompleteness(…, {ifAbsent: true})` does not report whether it inserted. Recorded as a known overcount in [TD-004](../technical-debt.md#td-004-restore-loss-counted-once-in-the-live-loss-totals); no storage API change.
- **Tray.** Main hands the status to the tray presenter with the rest of the health. The tray model ignores it until PR-4, so the test observes the presenter's input through a subclass.
- **Changed test expectations (the requirement changed, G2 superseding C9 for ET-015c).** `recording: 'unavailable'` became `{state: 'unknown'}` in `app-health.test.ts` (four expectations and a title) and `main-boundaries.test.ts` (eight), `{state: 'unknown'}` in the `dashboard-startup.test.ts` helper and `{state: 'disabled'}` in the `tray-model.test.ts` helper. `preload-recovery.test.ts` now forwards a full recording status unchanged. The stand-ins of `telemetry-service-v0.test.ts` gained `current`, `durableRetryCode` and `failureCode`, which the runtime reads; no expectation there changed.

### Interpretations and deviations from the plan

- **Main's timeline row.** The plan names the dashboard and the gated lifecycle state. `recording` lasts about 0.5–0.7 s per connection here, only while the scenario's frames are fresh, and `unknown` only from a service exit to the next service's first report, so a poll of either view could miss them on a slow runner. Main therefore logs `RECORDING_STATUS` in its opt-in smoke timeline, the mechanism that already logs `TRAY_OPEN` and the window events. It is fixed facts only and never in default logs (`main-boundaries.test.ts`). The journey proves the short states from these rows and from the dashboard's MutationObserver log, and uses the lifecycle state and plain waits for the states that last until its next step.
- **Run B "recording".** Run B's checkpoint often activates the durable cursor only after its frame at 2,100 ms went stale, and its later fresh data is paused. Run B therefore counts `recording` or `paused` (both mean an active cursor with fresh data, rule 7) as recorded. In the three development runs both `recording` and `paused` appeared.
- **Run A while closed.** Asserted from main's rows: a `recording` row after connection 2's admission. The state at the moment the journey reads the totals may be `recording`, `paused` or `interrupted`, so only its target, code and losses are exact.
- **Reopened dashboard.** To render `health-recording-losses` at runtime, run A reopens the dashboard from the tray after the closed-window checks, then closes it again (review pass 1), so the tray exit still runs with the main window closed. The scenario, the proxy policy and the rows are unchanged; the exit flush rules of ET-015b PR-4 accept the later exit, and in every run so far the exit flush was still required.
- **Texts not fixed by G8.** `opening`: `Opening the database`; `waiting`: `Waiting for the recorded source to connect`; `recording`: `Recording`; `paused`: `Game paused; recording continues when it resumes`; `not-recorded-source`: `Not recording the selected source`. A replay target reads `Replay test database (never game history)` instead of the synthetic note, so a replay is not called synthetic. Trip lines beyond G8's two examples: `Current trip is recorded completely so far`, `The current trip's completeness is not known yet`, the phase suffixes and `A trip is in progress` for an open trip without completeness. A missing code reads `an internal error occurred`.
- **Prototype notice.** Unchanged while disabled; while `unknown` it says the status is not known; for a test target it says only a test database is recorded; for the history target, which no build reaches yet, it says game history recording is new.
- **Alert variant.** `retrying` uses the default variant, since it recovers by itself; `stopped` and `live-only` use the destructive one.
- **Changed test expectation (the requirement changed, G8).** The disabled tray line in `tray-model.test.ts` changed from `Recording: not available in this version` to `Recording: off in this version`.

## Flaky recording-status case (c) (October 16, 2026)

**Failure.** [Attempt 1](https://github.com/senukartur/ets2telemetry/actions/runs/38949384603/attempts/1) of hosted Windows CI run 38949384603, on PR #91, whose changes do not touch this test, failed the step "Storage suite under the pinned Electron runtime" in `tests/storage/recording-status.test.ts` > (c) "a held commit and a bound of four: retrying BACKLOG_FULL, then the restarted service records the redelivery (REG-011)". The first service's status sequence was `opening`, `not-recorded-source`, `waiting`, `retrying BACKLOG_FULL`; the expected `recording` step before `retrying BACKLOG_FULL` was missing. The case had passed locally and in earlier CI runs.

**Root cause: a race in the test, not a product defect.** `recording` needs an open database, an active durable cursor and fresh v1 data. In `normal-delivery` the checkpoint reports the simulation as unavailable, so the source first becomes `connected` with the snapshot at 100 ms. That snapshot arrives after events 2-4 and before eventSeq 5, whose item exceeds the bound of four while eventSeq 1 is held. The publisher computes the status one macrotask after a change (`setImmediate`, G5). When that snapshot and eventSeq 5 are applied in the same macrotask, the status is computed only after the overflow and is correctly `retrying BACKLOG_FULL`, with no passing `recording`. That happens when both frames are already read when the ingestion applies them: on a slow host because both reads complete in the same event loop turn, or because the harness gate releases its held frames together. The old gate held everything after eventSeq 1 until the worker held its commit, so it decided which frames were held back but did not separate the snapshot from eventSeq 5. Locally the frames after the gate usually arrived in separate turns, which is why the case passed.

**Fix** (`d09729d`, test-only). `ClientSocket` in `tests/storage/recording-helpers.ts` gains a `beforeEventSeq` gate, which holds back the gate event's own frame and everything after it. Case (c) now holds its first connection before eventSeq 5 until both the fault worker has reported the commit of eventSeq 1 held and the publisher has sent `recording`. The first condition keeps the protection from the [S4 (c) fix](et-015a.md#flaky-s4-c-queue-pressure-case-october-16-2026): items 2-4 queue behind a commit in flight, so eventSeq 5 still exceeds the bound. The second is an observable event, not a delay, and is raced against the named hang guard. The expected status sequence, the final `retrying BACKLOG_FULL` status, the `V1_DURABLE_RETRY` log, the served ACKs, the restarted service's `recording` and `interrupted` sequence and the `normal-delivery-backlog` rows are unchanged. A new case in `tests/storage/client-socket.test.ts` checks the `beforeEventSeq` gate on a fake pipe socket. [Telemetry service v1](../telemetry-service-v1.md#recording-status-et-015c) now names this coalescing next to the existing session-open example. No product code changed.

**RED.** Two temporary changes, each removed before committing, forced the hosted ordering on the old case:

- the old gate opened 300 ms after the `held` message, so every later frame waited in the gate and was released in one macrotask;
- the first service's `upsertSession` was held for 300 ms through `tracedHandle`, so the frames after eventSeq 1 were already read when the slow session open let the commit of eventSeq 1 reach its hold.

Each failed with the same assertion as CI, at the `sequence(a.statuses)` line: `recording` was missing before `retrying BACKLOG_FULL`. The first failed in 4 of 4 runs and the second in 4 of 4 runs. With the new gate the same changes passed in 5 of 5 runs (the gate also opened 300 ms late, after both conditions) and 3 of 3 runs.

# ET-035 validation: Electron main process soak memory growth

Recorded October 19, 2026 on branch `fix/et035-main-process-soak-leak`, base `d81d24ec0baf8ade376a7c19197dfd1a9b61acfb`.

## Objective

Identify the cause of steady private memory growth in the Electron main process during sustained soak testing, and eliminate it if it is a leak.

## Problem & Soak Evidence

Sustained 90-minute soak testing in `windows-soak.yml` (ET-019 PR-12b) running the packaged app against a synthetic protocol v1 source revealed steady linear private-bytes growth isolated to the Electron main process:

| Run / Duration | Initial Private (MiB) | Final Private (MiB) | Slope | $r^2$ |
| --- | --- | --- | --- | --- |
| 30 min (run 39237647153) | 77.8 | 79.8 | +12.8 MiB/h | 0.93 |
| 90 min (run 39243151933) | 77.6 | 91.5 | +10.9 MiB/h | 0.99 |

Over the same 90 minutes, the other application processes remained completely flat or slightly negative:
- Telemetry service: -1.3 MiB/h
- Renderer: -0.5 MiB/h

The high linearity ($r^2 \ge 0.93$) and consistent ~11–13 MiB/h slope indicated monotonic native memory creep rather than garbage-collection buffering.

## Root Cause Analysis

In `apps/desktop/src/overlay-controller.ts`, `OverlayController.update()` calls `this.place()` on every live telemetry frame received by the Electron main process (20 Hz, or every 50 ms).

When game client bounds are absent or unready — which is true for synthetic soak runs, during headless runs, or whenever the game window is not in the foreground — `currentGameClientBounds(this.live)` evaluates to `undefined`, which led `place()` to invoke `this.hide()`.

In `OverlayController.hide()`:
```ts
private hide(): void {
  this.visible = false; this.moving = false; this.window.hide();
  ...
}
```
`this.window.hide()` was invoked unconditionally on every 20 Hz frame, even when `this.visible` was already `false`.

Calling Electron's native `BrowserWindow.hide()` 20 times per second invokes Chromium's `views::Widget::Hide()` and Win32 `ShowWindow(hwnd, SW_HIDE)` at 20 Hz (108,000 calls over a 90-minute soak). This continuous stream of native window visibility task dispatches without state transitions causes continuous task posting in Chromium's UI thread message loop. Eliminating these redundant calls ensures native visibility APIs are only invoked on actual state transitions; confirming whether this completely flattens the measured private-bytes slope is tracked under remaining verification.

### Rejected Alternatives

- **Throttling or debouncing `OverlayController.update()`**: Rejected because the overlay requires low-latency tracking (up to 20 Hz) to smoothly match moving game window client bounds and display timely telemetry.
- **Refactoring `LiveFreshness` timer rescheduling**: Rejected because Node.js timer allocations exist entirely within V8 JavaScript nursery space and are reclaimed by scavenge GC; the telemetry service process uses identical message rates and showed a negative memory slope (-1.3 MiB/h). Modifying `LiveFreshness` would risk altering protocol v0/v1 expiry mechanics without affecting Chromium's native private-bytes growth.
- **Querying `this.window.isVisible()`**: Rejected because calling `isVisible()` makes a synchronous native aura/views query across the Electron boundary, whereas checking internal boolean state properties `this.visible` and `this.interactive` is instantaneous, deterministic, and readily mocked in unit tests.

## Fix

Added an idempotency guard at the beginning of `OverlayController.hide()` in `apps/desktop/src/overlay-controller.ts`:
```ts
private hide(): void {
  if (!this.visible && !this.interactive) return;
  this.visible = false; this.moving = false; this.window.hide();
  if (!this.interactive) return;
  this.interactive = false;
  this.window.setMovable(false); this.window.setIgnoreMouseEvents(true); this.window.setFocusable(false);
  this.window.setSkipTaskbar(true);
}
```

### Invariant

`OverlayController` mutates native window visibility (`this.window.hide()`, `this.window.showInactive()`) only when the window's logical visibility or interactive edit state actually transitions.

## Verification

### Automated Unit Checks

1. **Overlay Controller Idempotency (`tests/unit/overlay.test.ts`)**:
   - Calling `update()` repeatedly with unavailable game metadata while hidden never calls `window.hide()`.
   - Transitioning from visible to hidden calls `window.hide()` exactly once.
   - Subsequent `update()` calls while remaining hidden do not re-invoke `window.hide()`.
   - Ending interactive edit mode transitions to hidden and resets interactivity flags once, ignoring subsequent redundant hide requests.
   - Updated existing layout and section change assertions: changing layout or sections on a hidden overlay does not dispatch redundant `window.hide()` calls.

2. **Main Boundaries Orderly Exit (`tests/unit/main-boundaries.test.ts`)**:
   - In synthetic mode where the overlay window was never shown, orderly application exit retires subscriptions without issuing redundant native `window.hide()` calls.

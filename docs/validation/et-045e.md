# ET-045e: rebased overlay scale and strip width

Date: October 24, 2026 (Europe/Warsaw). Task: items 9 and 6 of [ET-045](https://trello.com/c/OmNYTBsp), under the owner's decisions D1 (option b) and D5 of October 24, 2026 ([ET-045 validation](et-045.md)). Branch `fix/et-045e-rebase-overlay-scale-and-strip-width` from base `552b605a1a4086fb91045a87e882b915c2725156` (after ET-045c #174 and ET-045d #175).

This record makes no game, display, DPI, readability or performance claim, and it neither passes nor waives an ET-044 assertion.

## Owner requests

- **Item 9.** The current 100% overlay is too large: the new 100% must look about as large as the current 70%, without merely setting the control to 70%. Saved scales and placements must be handled explicitly; fit, width, bottom anchoring and persistence must be rechecked; an old/new visual reference is needed.
- **Item 6.** At 50% the strip becomes narrow and wraps densely while game width stays unused (`strip-width.png` in the ET-044 evidence). The width must come from the actual game client and DPI, not from the monitor.

## Root cause of item 6

`overlaySize('strip')` capped the width at `1280 × scale` DIP and laid the content out at the CSS width `floor(width / scale)`, which is at most 1280 CSS px whenever the client is wider than `1280 × scale + 32`. The CSS capacity was therefore the same at every scale: a lower scale only made the window smaller (640 DIP at 0.5), with the same rows as at 100%. In the owner's 1706.67 DIP client the strip with every section at 0.5 was 640 × 59 (three rows), leaving about 1035 DIP unused.

## Decisions

The architect's decisions Z1–Z9, adopted by the coordinator under the owner's delegation, are in [concept.md](../concept.md#et-045e-rebased-overlay-scale-and-strip-width--october-24-2026); the geometry is in [the minimal overlay](../minimal-overlay.md#rebased-scale-and-strip-width-et-045e-october-24-2026) and the format in [settings](../settings.md). In short:

- A saved `scale` is the user's setting in [0.5, 3] (50–300%); the overlay document's zoom is `overlayZoom(scale) = scale × 0.7`, rounded to three decimals. Saved numbers are kept and reinterpreted (D1 option b).
- The strip is `floor(min(1280 × max(1, scale), client width − 32))` wide with its rows at `floor(width / zoom)`, so it is never narrower than at 100% (D5); the client width is the game's client area from `screen.screenToDipRect`.
- Settings format v7 with an identity v6-to-v7 step; older builds read v7 as newer-version.
- No new IPC channel, bridge method, preload key, string, wire, storage, export or native change; `GAME_HISTORY_RECORDING` is unchanged.

## Verifier round 1 (October 24, 2026)

The verifier ran the checks on `6ef7b04`. Lint, PowerShell analysis, typecheck, `npm test` (4,844), `npm run test:storage`, `npm run package`, the packaged `overlay -ForceRendererReuse`, `lifecycle`, `ui` (`overlay` in 38.3 s of the 60 s Job bound with `stableNumbers`, `clusterRpmContained` and `scaleRange` true and 70 PNGs; `settings` with `scaleControl` true; `live`) and `scaffold` smokes, the development `ui` overlay shard (37.6 s of 60 s) and the bounds probe passed. The probe recorded these 50% product windows at zoom 0.35 and display scale 1.5: strip 1280 × 16 kept at 1280 × 38, card 105 × 136 at 106 × 136, cluster 154 × 95 at 154 × 96 and HUD 112 × 124 exactly; `controllerAt100` fitted 1280 × 29 to 1280 × 38 inside the client, and the 50% replay fitted 1280 × 16 to 1280 × 38.

**Failed, deterministically twice:** the packaged `telemetry` smoke, `page.waitForFunction: Timeout 10000ms exceeded` in `renderedLayout` from `assertLayouts` for the cluster. At display scale 1.5 the windows read back about one DIP larger than requested (card 211 × 252, HUD 225 × 224, cluster 309 × 160 for 210 × 252, 224 × 224 and 308 × 159; the product strip 1281 × 56), while the card's viewport stayed 300 × 360 CSS px. Windows applies whole physical pixels and the DIP readback rounds; the card and HUD heights are whole at zoom 0.7, the cluster's 159 / 0.7 = 227.14 is not, and the wait allowed only one CSS px around the requested size. This is a smoke tolerance defect; the product is unchanged.

A first fix (uncommitted) waited on the actual size with `1 + 1 / zoom` CSS px; the author's packaged rerun then passed the cluster (content 308 × 160 DIP, viewport 440 × 229 CSS) but failed the same way at the strip restore, which resized the window to the product's `getBounds` of 1281 DIP (a 1830 CSS px viewport) and waited for the recorded 1828.

Fix, with the independent review's tolerance: the layout step requires the applied content size (`getContentBounds`) within one DIP below and two above the request (`verifyAppliedWindow`, fail-closed), then waits for and verifies the CSS viewport as that actual content size / zoom within `1 / zoom + 0.5` CSS px (`zoomedViewportTolerance`, 1.93 at zoom 0.7), so the ET-045d cluster's 225 and 267 px viewports and a two-DIP error still fail. Every restore and the review-only measurement use the product window's content size. The strip height uses the same tolerance (80 ± 1.93), the UI overlay frames allow `max(1.5, 1 + zoom / 2)` DIP, and the 50% UI frames are the product windows (only the strip raised to the 38 DIP minimum height). `overlay-smoke-source.test.ts` pins the tolerance, the verifier's 308 × 160 content readback, the discriminating negatives and the applied-window bounds. The local display scale factor is 1.5. The verifier's reference PNGs were copied to `.local/et-045e/scale-reference/`. The rerun results are under [Fix round 1 checks](#fix-round-1-checks).

## Known risks and limits

- **Windows minimum window size.** Since verifier round 1 the UI shard's 50% frames are the product windows (`SCALE_RANGE_FRAMES`; the strip at the 38 DIP minimum height measured at 150%), which Windows accepted within one DIP locally at 150%; a hosted runner that refuses one fails the frame wait, and the refusal is recorded. The 50% Cluster probe frame stays 160 × 100. The card (105 DIP) and HUD (112 DIP) product windows at 50% may meet a minimum width over a real game; the probe records it, and a horizontal offset is a recorded limit, not handled.
- **Text at zoom 0.35.** Whether Chromium enlarges 11–34 px text at zoom 0.35 is recorded by the UI shard (`scaleRange` width ratios), not gated. Readability at 50% (text about 3.9–6 DIP high) is an owner check.
- **Floating point.** `floor(width / zoom)` can be one CSS px low through binary noise, which only reserves conservatively; every pinned literal was checked against the code.

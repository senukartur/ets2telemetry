### Native test-contract diagnosis

The real-collision reporting test unconditionally required `generic_error`, one error log and less than 1,000 ms.
That contradicts the [accepted pending-start policy](et-004-startup-budget.md): incomplete startup returns `ok` with one
pending warning after the fixed wait, then reports the actual stage once on an SDK callback. The former scenario-2
observation (`result: 0`, two logs, 1,000 ms) is consistent with that path and remains a failed historical test run.
The corrected test accepts only the exact caller-owned error or exact pending warning plus deferred stage error.
It drives `frame_end` before shutdown, so "ended by shutdown" cannot substitute for the foreign-object failure;
severity, SDK thread, foreign sentinel and no shutdown duplicate remain required.

The pending-startup stop test also imposed an unconditional sub-second stop/status expectation. The
[existing lifecycle contract](../native-transport-v0.md#lifecycle-and-bounds) requires mandatory join, including protected
endpoint/publication/deletion I/O, and records the 1,000 ms measured-target diagnostic after joining. The corrected test
requires joined ownership, retirement and status consistent with **internal** `shutdown_ms`, including
`shutdown_deadline_exceeded` above the unchanged target. The historical 1,078 ms stop remains a measured-target miss;
its kernel cause and improved performance are not claimed.

Controlled regressions force protected discovery publication held after stop's first cancellation (1,110 ms join),
and a foreign discovery record held past the startup wait (pending, then exact deferred publication error). The former
assumptions fail both (2/2 RED); the corrected contracts pass all five affected entries (16.12 s): startup-late,
stop-discovery, normal/window reporting and hooked late reporting. Logs stay in ignored
`.local/et011-local-contract-fix/`. Product code, startup wait, cancellation windows, mandatory join, 1,000 ms target
and existing 30-second CTest hang guards are unchanged. No early unload, forced termination or detached worker is used.

## Windows session-end diagnostic fix — October 21, 2026

The owner's real sign-out on main `856f46e` / PR #166 completed without reported problems. Its frozen portable
fingerprint is `9086546e34247f516abc0fc28fce3a12e1c55f5058aed2cc223225d24278d046`. The service closed storage and reported
all six stop steps successful; the contained process tree exited 0 and left no processes. Main's log nevertheless
contained no exit request, stop request or final supervisor observations. Raw evidence stays unchanged under ignored
`.local/validation/et011-signout-166-20261021` in the control checkout; this historical result remains partial.

The pinned [Electron 44.7.0 Windows source](https://github.com/electron/electron/blob/v44.7.0/shell/browser/native_window_views_win.cc#L383-L413)
explains the loss: after notifying confirmed `session-end` listeners it immediately terminates main unless Electron's
own quit is underway. This application redirects that quit to its asynchronous supervisor. The original callbacks
queued log writes and requested the stop, but could not await an append or service response before native termination.

The correction enters synchronous terminal logging before requesting the same lifecycle stop and removes the tray
before returning. It records `WINDOWS_SESSION_END_HANDOFF` with fixed `{completion: 'os-owned'}`. That marker does not
fabricate `APP_EXIT` or `SERVICE_EXIT`, nor prove a service flush. Queries remain cancellable and inert; no shutdown veto
or wider budget is introduced. Existing log capacity and stalled/unavailable disk limits still apply; an older append
already in flight can land later or be lost, and is never replayed. See [lifecycle](../app-lifecycle.md#windows-terminal-session-boundary--october-21-2026).

Unit regressions cover terminal writes before an unresolved earlier append, fixed-code fallback, inert cancelled
queries, one request across both windows and immediate tray removal. The separately bounded native-message regression
(`scripts/ci/Invoke-SessionEndSmoke.ps1`) verifies the exact HWND/PID/image before sending a cancelled query and then a
confirmed `WM_ENDSESSION` to the remaining overlay after dashboard close. It never broadcasts or logs off Windows.
An explicit frozen-baseline mode retains `passed: false` while identifying reproduced missing audit rows; only the
current-build mode can pass. Runtime results, full verification, independent review and hosted CI are recorded by the
coordinator on the final candidate. No actual sign-out/restart with the correction is claimed here.

## Fix round 2

## Settings late read fix — October 15, 2026

### Failure

Hosted CI run 38755116140 (attempt 1, a PR that changed only a native test) failed in the development `lifecycle` smoke. Run A expected the seeded corrupt `settings.json` to give `{state: 'invalid-file', writable: true}` and got `{state: 'unreadable', writable: false}`. The main diagnostics show `SETTINGS_FALLBACK` with `{state: 'unreadable', reason: 'load-budget'}` exactly 1.0 s after `APP_START`; `SERVICE_START_REQUESTED` followed only 4.4 s after `APP_START`, `SERVICE_READY` after 5.1 s and both windows had loaded after about 6.2 s. The runner has 2 logical processors and the smoke's Job caps CPU at 25 % (0.5 processors).

### Cause

Startup was CPU-starved. The single settings read (directory and file `lstat`, open, bounded read, close), started in parallel with the service, did not settle within its 1000 ms budget. The budget then made the whole session read-only `unreadable` defaults, although the file was readable, and nothing ever applied the read's eventual result. This was a product behavior, not a smoke defect: on a slow start a user would also have lost their saved units and the ability to save until the next launch.

### Fix (`41c0d86`)

Coordinator decision under the owner's standing delegation ("clean late read"):

- `SettingsStore.load()` still returns within 1000 ms, so the first windows still open after at most the same wait. If the read has not settled, it returns defaults in the new read-only `loading` state (contract `SettingsState`; text `Saved settings are still being read; defaults are in use and changes cannot be saved yet.`) and logs `SETTINGS_LOAD_PENDING` (`loading`, `load-budget`).
- The same read keeps running. When it settles, its own result is applied (state, writability and units) with the same log row as a read within the budget, and the new `changed` option reports it. Main then pushes `AppState` and republishes the overlay projection exactly as after a save (`settingsChanged()`, formerly `settingsSaved()`), accepting no observation and renewing neither SDK nor window freshness.
- A read error stays `unreadable`. A read still unsettled 30 s after the start (`SETTINGS_READ_LIMIT_MS`) is declared hung: `unreadable` with reason `load-limit`, reported once through `changed`, and its later result is ignored.
- While the read is pending, `loading` is read-only, so a save is refused at once (`SETTINGS_WRITE_FAILED`) and never queued. A late invalid or unsupported-older file is therefore quarantined only by a save after its state was applied. A save requested before `load()` returned (not reachable from a window) waits for the read's result or, at most, the read limit.
- Unchanged: nothing is written at startup, quarantine is byte-identical, newer-version files are never written, saves are serialized and bounded to four, values apply only after the durable rename, the exit waits at most 1000 ms for a save, and only fixed messages cross IPC.

Design choices:

- The state name `loading` describes what the user sees: defaults apply because the saved file is still being read. The units card keeps its existing mechanism: one state line and radio groups disabled while `writable` is false. No spinner is added, in line with the functional UI direction.
- The 30 s limit is far above the starved start that triggered this failure (about 6 s to both windows on a 0.5-processor Job) and below the 60 s smoke Job. A bounded read of at most 64 KiB that takes longer points to a stuck file system rather than starvation.
- The late result is applied rather than retried: the file is read once, and it was not changed in between because saves were refused, so the result is as current as a read within the budget.

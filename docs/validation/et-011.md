## Fix round 2

Hosted draft CI run [38666784946](https://github.com/senukartur/ets2telemetry/actions/runs/38666784946) on `ae78c78` failed the step "Bounded development tray lifecycle, single instance and explicit exit smoke" with `Runtime smoke failed: LIFECYCLE_RESULT_INCOMPLETE_OR_INVALID, Job exit 0`. The coordinator's downloaded driver receipt shows `passed: true`, every lifecycle flag true, zero exit codes for the second instance, the explicit exit and the restart, and only `ok` shutdown steps. The run remains failed evidence.

Root cause: the CI steps run under PowerShell 7 (`shell: pwsh`), whose `ConvertFrom-Json` parses JSON integers as Int64. The lifecycle branch of `RuntimeReceipt.ps1` required `[int]` for `secondInstance.exitCode`, `explicitExit.launcherExit` and `restartLauncherExit`, so it rejected an intact receipt. Local smokes and the batched validator tests use Windows PowerShell 5.1, which parses the same values as Int32, so they passed. The other integer checks in the file already accepted Int32, Int64, Double and Decimal.

Fix (`f7756f0`): those three fields now use `Test-ReceiptInteger` with an exact range of 0, like the other integer fields. An audit of the rest of the ET-011a receipt code found no other `[int]`-only checks. The remaining checks compare values (`-ne 0`), booleans, strings and array counts, which behave the same in both versions. The JSON depth of the receipt (about six levels) is far below either version's limit. PowerShell 7 converts ISO timestamp strings to `DateTime`, but the validator does not read any timestamp. PowerShell 7 itself is not installed on the owner workstation, so the hosted run on the new head is the only direct PowerShell 7 evidence.

Regression protection: `tests/shared/Read-RuntimeReceipt.ps1` gains an `int64` case mode. It retypes every integer of the parsed receipt to Int64, confirms the retyping, and calls `Test-LifecycleReceipt` inside the existing single PowerShell 5.1 batch. `runtime-receipt.test.ts` adds an intact Int64 lifecycle receipt, which must pass, and Int64 receipts with a second-instance exit 1 and a restart exit 1, which must fail. RED: before the fix, and again with only the `restartLauncherExit` check reverted, the intact Int64 case failed with `passed: false`, reproducing the hosted outcome.

Checks on `f7756f0`: `npm run lint:ps` (35 files, 0 findings), `npm run lint`, `npm run typecheck`, `npm test` (931 tests in 39 files; the receipt suite is one batched test) and `git diff --check` pass. The development lifecycle smoke passed in 2.4 s with the `21c1997` application build; this round changed no application code. The final code commit of ET-011a is `f7756f0`; later commits change documentation only.

### Deviations and notes

- Settings load in parallel with the service start instead of before it; the first windows still open only after the load settled, and nothing reads the units earlier. Loading first would delay the service by up to 1000 ms for no consumer.
- `unreadable` (a link, junction, read error or the 1000 ms load budget) is read-only for the session, like `unavailable`, so a file that could not be read safely is never replaced blindly.
- A failure after the quarantine rename leaves no `settings.json`; the next start reads defaults. The quarantined file is kept byte-identically.
- A refused settings save never touches the service's last problem; since fix round 1 the refusal lives in the settings view's `saveError`, which the next successful save clears.
- More than four outstanding saves are refused without a health change.
- The overlay's ATS conversion now uses telemetry-core's exact `3600 / 1609.344` instead of the earlier truncated literal `2.2369362920544`; the two differ by about 1e-15 relative, and every existing expectation is unchanged.
- The dashboard fuel row now shows a rounded negative zero as `0.0`, like speed.

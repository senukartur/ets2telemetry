# ET-009 frame-time session — October 13, 2026

The owner ran this real-game frame-time session on their own PC. It is a first, bounded measurement for the ET-009 performance criterion, not an acceptance result. It shows whether the desktop application, its overlay and CAP0 capture measurably change game frame times. It does not measure the plugin's own cost.

## Environment

- **Game:** Euro Truck Simulator 2 1.61.1.1 (`g_game_version`), single-player, SDK game-telemetry version 1.20.
- **Display:** one monitor at 5120 × 2160 and 120 Hz, NVIDIA GeForce RTX 4070 Ti, Windows 11 10.0.26200 at 150 % scaling. The game rendered at 5120 × 2160 (`r_mode_width`/`r_mode_height`, `r_mode_refresh 120`). Its window covered the whole monitor (3413 × 1440 logical), which matches borderless fullscreen. PresentMon reported `Composed: Flip` with VSync (`SyncInterval 1`), so Windows composed the frames and exclusive fullscreen was not in use. With VSync at 120 Hz, the measured 54–65 FPS is below the refresh ceiling.
- **Third-party mods present in the game process:**
  - OptiScaler v10.0.0-dev in "Dx11 with Dx12" mode. Its frame generation was off (FG input and output `None`), and the owner turned its DLSS Neural Rendering off for the session.
  - DLSS 5 bridge add-ons.
  - `SnowyMoon.dll`.
  - Other telemetry plugins in the `plugins` folder.
- **Project build:** plugin and desktop app from `main` `a7724de`. Plugin DLL SHA-256 `B03A6C79E9BE958E5F6F2BE67EABBE2C7506EF13B43B543B3DB131928FACF113`. The app was started with `npm run dev`.
- **Tool:** PresentMon 2.6.0 console (Intel, Authenticode-signed; SHA-256 `b2a706bc6ad475749e3b7e3409263aa1e6906d45bdcf993f6dbc0f660188f1af`). It captured `eurotrucks2.exe` with `--v2_metrics` into local CSV files. The CSV files stay on the owner's machine and are not committed.
- **Scene:** the truck parked at one city spot with one fixed camera, engine on, game not paused. Weather was set to clear and time to noon through the developer console. Nothing was touched during the recordings.

## Method

Four continuous 240 s recordings were made in one game session, in the order B1, C, D, B2:

| Config | Plugin | Desktop app | Overlay | CAP0 capture |
| --- | --- | --- | --- | --- |
| B1 | loaded | closed | — | — |
| C | loaded | running, live ETS2 data | visible | off |
| D | loaded | running, live ETS2 data | visible | on |
| B2 | loaded | closed | — | — |

Repeating the closed-app config (B2) after C and D measures how much the scene drifts on its own. Metrics are computed per 60 s window: mean FPS, median and 99th-percentile frame time, 1 % and 0.1 % lows, and mean CPU and GPU busy time per frame.

An earlier no-plugin recording (A) was made in a different weather state; rain and a thunderstorm started during it. It is kept only as a drift example and is not compared.

## Results

| Config | FPS (60 s windows) | Frame time p50 / p99 | CPU busy | GPU busy | 1 % low |
| --- | --- | --- | --- | --- | --- |
| B1 | 65.46 / 65.23 / 65.17 / 65.33 | 15.2 / 21.9 ms | 15.2–15.3 ms | 15.3 ms | 41–44 |
| C | 61.54 / 61.75 / 61.06 / 60.51 | 16.1 / 22.9–33.3 ms | 16.1–16.4 ms | 16.2 ms | 29–42 |
| D | 54.61 / 54.56 / 54.63 / 54.62 | 18.2 / 25.5 ms | 18.2 ms | 18.3 ms | 35–38 |
| B2 | 53.16 / 54.50 / 54.89 / 54.93 | 18.1–18.4 / 25.0–33.5 ms | 18.1–18.7 ms | 18.2–18.4 ms | 27–38 |

CPU busy and GPU busy are PresentMon v2 per-frame metrics. Both are about equal to the frame time in every config. With VSync and Windows composition, this does not show which side limits the scene.

## Findings

- Performance drifted strongly, with GPU busy rising from 15.3 to 18.3 ms per frame and FPS falling from about 65 to about 54. The drift persisted with the application closed (B1 → B2).
- The cause is most likely scene or thermal drift (time of day and lighting, GPU temperature). This is a hypothesis: B1 → B2 shows only that the drift outlived the application. It does not rule out lasting state changed during C and D, such as GPU clock or thermal state, the focus changes, or the topmost diagnostics. The order was not counterbalanced: the whole drift falls between B1 and D, and there was no closed-app run between C and D.
- The comparison that carries the result is the single adjacent pair D and B2. D (app, overlay and CAP0 capture) and B2 (app closed) have the same FPS (54.6 against 54.5–54.9 in B2's settled minutes), the same CPU busy (18.2 against 18.1–18.7 ms) and the same GPU busy (18.3 against 18.2–18.4 ms). **In this scene, no FPS or frame-time change from the desktop application, the overlay or CAP0 capture was detected; any such change is below about 1 %.** This does not show that the application has no CPU cost: extra CPU work in other processes can be absorbed without changing frame time when the game is not limited by the CPU.
- C on its own cannot be judged, because it falls in the middle of the drift. D includes everything C runs.

## Overlay defect found during the session

- **Symptom.** With live data connected, the overlay window was visible to Windows (`IsWindowVisible`) but hidden behind the game. Its extended style lacked `WS_EX_TOPMOST`, although it is created with `alwaysOnTop: true`. Its z-order placed it far below the game window.
- **Trigger.** This happened twice, each time after the owner focused the dashboard to select the source and then returned to the game.
- **Diagnosis.** Re-asserting topmost with `SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE | SWP_NOMOVE | SWP_NOSIZE)` made the overlay appear, and the game kept focus.
- **Effect on this session.** For C and D the overlay was made visible through that diagnostic, not by the application itself. In both configs the re-assert happened **before** the recording window. For C, the overlay was re-asserted and the owner confirmed it was visible; only then was PresentMon started, and recording began 30 s later. For D, the re-assert and the PresentMon start ran back to back, and recording began 30 s later. The re-assert was verified only programmatically: `WS_EX_TOPMOST` was set afterwards and the game stayed in the foreground. Nobody visually confirmed the overlay in D. No focus changes happened during either 240 s window. C therefore reflects an overlay observed to be visible. D assumes the overlay stayed visible, based on the successful re-assert and the unchanged foreground, but this was not observed. Neither config reflects the application's own (defective) topmost behaviour.
- **Fix.** Tracked as a separate ET-008 fix on the [ET-008 card](https://trello.com/c/37RpcL1u) (defect comment of October 13, 2026; branch `fix/overlay-topmost`, PR title prefix `[ET-008]`). The fix is [PR #39](https://github.com/senukartur/ets2telemetry/pull/39); its root cause and checks are in [ET-008 validation](et-008.md#topmost-loss-behind-a-borderless-game-october-13-2026). C and D measured the overlay only after the manual re-assert, so they remain valid for frame time, but they do not show the fix.

## Not established

- **The plugin's own cost** relative to no plugin: every recording here had the plugin loaded. A precise measurement needs in-plugin timing of the SDK callbacks.
- **The application's CPU cost and its effect in CPU-limited conditions:** process CPU usage, a CPU-heavy scene, or a system with less CPU headroom.
- **A counterbalanced repeat** (for example D before C, with closed-app runs between them) to separate drift from configuration.
- **Other conditions:** ATS, TruckersMP, driving rather than parked scenes, other display modes, other hardware, and a system without the third-party mods.
- **Long sessions:** sustained resource use and long-session stability.
- **Statistical certainty:** single recordings per config, so no statistical confidence intervals.

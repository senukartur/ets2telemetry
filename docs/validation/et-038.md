# ET-038 validation: Adaptive history close grace during service shutdown

Recorded October 20, 2026 on branch `fix/adaptive-history-close-grace`.

## Objective

Resolve product gap G18: a history close taking longer than the nominal 800 ms baseline grace (such as during a large WAL checkpoint on a slow disk) is terminated prematurely and reported unclean, causing the service to exit 1 even though nothing committed was lost and ample stop budget remained unused.

## Problem & G18 Context

The telemetry service stop sequence has a hard upper bound of 2,500 ms `SERVICE_STOP_BUDGET_MS`, designed to finish safely before Electron main's 3,000 ms process kill deadline (`apps/desktop/src/shutdown-sequence.ts`). The sequence is partitioned into three sequential phases:

1. `intake` (nominal budget: 1,000 ms, `v1-ingestion`)
2. `flush` (nominal budget: 500 ms, `recording-flush`)
3. `storage` (nominal budget: 1,000 ms, `history-storage` and `storage-probe`)

Under the prior fixed-budget model:
- `history-storage` operated with a fixed `HISTORY_CLOSE_GRACE_MS = 800` ms and a 200 ms termination reserve (`CLOSE_TERMINATE_RESERVE_MS = 200`).
- During normal shutdowns, `intake` and `flush` complete very quickly (<50 ms total).
- The remaining ~1,450 ms of the service's 2,500 ms budget was discarded.
- If SQLite needed >800 ms to flush/checkpoint WAL pages on a slow disk, `StorageClient` terminated the worker after 800 ms and reported the step `failed`/`timeout`, forcing the service to exit with code 1.

## Solution

Implemented adaptive stop budget cascading in `ShutdownSequence.execute()` (`apps/desktop/src/shutdown-sequence.ts`):

1. **Targeted cascading**: When the `storage` phase begins, `ShutdownSequence` measures elapsed time since shutdown sequence start and computes the remaining overall sequence budget:
   ```ts
   const elapsed = this.timers.now() - sequenceStarted;
   const remainingStopBudget = Math.max(0, SERVICE_STOP_BUDGET_MS - elapsed);
   ```
2. **Selective budget expansion**: Only the step matching `HISTORY_STORAGE_STEP_NAME` (`history-storage`) receives the expanded budget and dynamic grace:
   ```ts
   if (step.name === HISTORY_STORAGE_STEP_NAME) {
     const effectiveBudget = Math.max(step.budgetMs, remainingStopBudget);
     const graceMs = Math.max(HISTORY_CLOSE_GRACE_MS, effectiveBudget - CLOSE_TERMINATE_RESERVE_MS);
     return {budgetMs: effectiveBudget, graceMs};
   }
   return {budgetMs: step.budgetMs};
   ```
   Other storage steps (such as `storage-probe`) retain their registered nominal budget `step.budgetMs` (1,000 ms).
3. **Grace forwarding**: `recording-runtime.ts` passes `context?.graceMs` to `history.close(graceMs)`, which forwards it to `StorageClient`.
4. **Zero duplication**: The constants `HISTORY_STORAGE_STEP_NAME`, `HISTORY_CLOSE_GRACE_MS`, and `CLOSE_TERMINATE_RESERVE_MS` are defined authoritatively in `apps/desktop/src/history-storage.ts` and imported by `shutdown-sequence.ts` and `recording-runtime.ts`.

### Invariants Preserved

1. **Total Bound Invariant**: Total shutdown duration never exceeds 2,500 ms `SERVICE_STOP_BUDGET_MS` plus loop clock slack.
2. **Graceful Expansion**: When earlier phases take <50 ms, `history-storage` receives up to ~2,450 ms effective budget and up to ~2,250 ms close grace, with a 200 ms termination reserve.
3. **Safe Fallback**: If earlier phases consume their full budgets (1,500 ms), `history-storage` automatically scales down to its nominal 1,000 ms budget and 800 ms baseline grace.
4. **Data Durability**: Under both clean and terminated outcomes, all committed transactions remain durable in the SQLite WAL.

## Verification Evidence

### 1. Storage Integration Tests (`tests/storage/shutdown-stalls.test.ts`)

Executed via `npm run test:storage -- tests/storage/shutdown-stalls.test.ts`:

- **Case (b1)**: Slow close held for 1,200 ms (exceeding the baseline 800 ms grace).
  - **Result**: Completes cleanly under adaptive grace (~2,250 ms available), logs `HISTORY_STORAGE_CLOSED`, exits 0 clean, and elapsed stop duration stays well within 2,500 ms.
- **Case (b2)**: Stalled close held indefinitely (`closeHold`).
  - **Result**: Worker is terminated after the expanded adaptive grace (`terminatedAfterMs >= 2000`, `<= 2500`). The stop completes as unclean with exit code 1, bounded within 2,500 ms `SERVICE_STOP_BUDGET_MS` + loop clock slack, and all committed WAL events survive.
- **Cases (a) & (c)**: Bounded stop with armed reconnection and process kill during final `appendSamples` remain fully passing.

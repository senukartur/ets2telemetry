### Interpretations and deviations from the plan

- **`ifAbsent` trip reference.** The plan compares `trip_ref IS NULL`. The implementation compares the trip reference with `IS`, so a session-level interval (the R9 restore-loss use) matches only session-level rows, as planned, and a trip-level interval matches only rows of the same trip.
- **A skipped interval writes nothing.** Every value is validated first; a skipped interval then registers no clock row either.
- **Seed details.** `jobKey` is also null when the job row is not at the trip's job configuration eventSeq. A label counts only when it is a safe integer, the reducer's own label rule (T15); `TripStorageModel.seeds()` reads any available label, which differs only for labels above 2^53, such as the worst-case fixtures' uint64 maximum.
- **Worker boundary.** The client copies only the listed page and option fields, and the request parser refuses unknown keys and values, like the four copied open fields.
- **More fault-worker cases.** Besides the planned `SQLITE_FULL` smoke case, `worker.test.ts` checks the `SQLITE_READONLY` and `SQLITE_BUSY` classification and the hold-until-release mode, so every mode of the test entry that PR-2 relies on is exercised.
- **Documentation.** TESTING.md and the registry rows are updated in this PR, as the coordinator requested; `docs/trips.md` (the answered rebuild question and the seed rules) stays with PR-2 as planned.

### Advisory review (October 16, 2026)

The advisory review of PR #75 found that `readTripSeeds` paged every stored event of a plugin session from eventSeq 0 and kept all rows, with their payloads, in memory until every seed was built. Its cost grew with the session's history rather than with the open trips, on the path the recorder will wait on. Fixed in `b9801bd` on top of the coordinator's merge of `main` (`bb90702`):

- Each session is read forward from the earliest opening event S of its open trips (`afterEventSeq` = S - 1). Every job event that decides `awaitingOutcome` comes after an opening event, so nothing earlier is needed for it.
- Only running values are kept: the usable label with the highest eventSeq and, per trip, the last `job.configured` or `job.cleared` event after its opening event. No event rows are retained.
- **Label fallback and its cost.** `listEvents` pages only forward, so there is no backward read. When no event at or after S has a usable label, the range before S is read from the session's first event, for the label only, until a page reaches S - 1. That costs one page per 500 events before S, and it is needed only when the opening event and everything after it are unlabelled. The opening event normally carries its own label, so the fallback is rare.
- `seedFromStored(trip, jobRow, sessionEvents)` keeps its contract and now applies the same running-value rules as the reader, so the seeds are unchanged.

**Changed expectation.** The paging case's recorded calls changed because the requirement changed: each session's first `listEvents` call now carries `afterEventSeq` S - 1 (`'0'` for S1, `'6'` for S2). S2 has no usable label at or after eventSeq 7, so its fallback call `{afterEventSeq: '0'}` is new. The seeds themselves did not change, and the case now also checks them against `seedFromStored` over all session events.

**Tests before the fix.** `tests/unit/trip-seeds.test.ts` gained two cases and an equivalence check, and was run against the unfixed reader first: 3 of 12 failed. In each case the seeds already matched and the recorded `listEvents` calls differed:

- the paging case;
- a session read from its earliest opening event (the trips open at 900 and 700) that never reads the 699 events before it when a label follows: 501 events served, every eventSeq at least 700;
- the label fallback, where the last usable label (550) lies before the opening event (600).

### Interpretations and deviations from the plan

- **Recorder codes.** `RECORDER_FAILURE_CLASS` was first placed in `trip-recorder.ts`, as planned, with `durable-sink.ts` importing it for `failureClass`. Review pass 1 moved it, with `RecorderErrorCode`, into `durable-sink.ts` (below).
- **Interfaces.** `DurableConnection.checkpoint` takes the checkpoint message instead of its `ackedThroughEventSeq`, so the sink can observe it, and `enqueue` takes the receipt label. The existing delivery cases pass a fixture checkpoint with the same A and a fixed label; their expectations are unchanged. `DurableStorageClient` no longer includes `committedThrough`, which only the removed hook used, so its wrapper line was removed from `tests/storage/v1-durable-ingestion.test.ts`.
- **U2.** The plan expects the retried commit to carry the same `trip.open` and no extra effects. It carries the same `trip.open`, plus an `opened-before-attach` interval. The redelivered configuration lies before the new checkpoint's `nextEventSeq`, so the reducer treats it as replayed ([trips](../trips.md), "Replayed events").
- **U9** is in `tests/unit/v1-ingestion.test.ts`, because durable selections and readiness are ingestion behaviour; `trip-recorder.test.ts` has U1–U8 and U10.
- **Bundles.** Only the `trip-recorder` entry was added. The child never loads the pipeline on its own, and the `v1-ingestion` bundle already contains it, so a `v1-durable-delivery` entry would be unused.
- **S3 barriers** are counted in commits, not ACKs. In (d) the first process starts committing only after its first connection ended (`commitAfterFirstEnd`), and that connection's client is scripted not to wait for ACKs. The server has therefore written the whole stream and retains everything unacknowledged. A first version killed the process while the server was still writing; later events then became offline gaps and the invariants no longer applied. The kill points are a fixed list (three per scenario), not seeded.
- **S3 (d), `save-load` killed before commit 12.** The resumed trip loses its reload-check phase (documented in [trips](../trips.md)), so the save load's regression closes it as `discontinuity` and no trip stays open. The first version of the check expected an open trip; the per-kill-point expectations were then written from the cold-start rules.
- **S4 (b)** restarts the service in the same test process (a new worker on the same file and a new recorder), not as a new process. A frame step at 650 ms is appended to the derived scenario. The simulator publishes a loss run only at `frame_end`, so without it the job clear lost on the live-only connection never became a gap record.
- **S4 (c).** A connection closed by `BACKLOG_FULL` received one item more than the bound, and the producer redelivers all of them. The same service, with a bound of four, would refuse that burst again at every reconnection. The redelivery therefore goes to a restarted service with the production bound of 256, which starts with nothing queued. The bound of four applies to the first service only. Equality of the production bound with the producer's 256 retained entries is not enough on its own (review pass 1): items still queued or in flight from an ended connection also count, so a redelivery can be refused once or a few times ([telemetry service v1](../telemetry-service-v1.md#storage-commit-ack-pipeline-e5e8)).
- **Shared test code.** `tests/shared/trip-messages.ts` gains `Script.snapshot` and `Script.redeliver` and an optional state override for `Script.checkpoint`; existing callers are unaffected. `tests/storage/recording-helpers.ts` is a new shared harness for S2 and S4.

### Interpretations and deviations from the plan

- **Workflow file.** The plan names `.github/workflows/ci.yml`; the workflow is `.github/workflows/windows-ci.yml`.
- **Recording proxy (not in the plan).** The plan's setup is the reactive simulator behind `ETS2TELEMETRY_SOURCE_PIPE_V1`. Without a proxy, the journey would be timing-dependent:
  - R10 makes a hello live-only while storage is still opening, and the reactive server fails the run when a scripted durable connection gets a live-only client;
  - every ACK would reach the simulator, so a restart would have nothing to redeliver.

  The proxy refuses live-only hellos. It admits one durable connection at a time when the journey asks, so connection 2 starts only after the window is closed. Like the scenario's `dropAfter:4`, it loses connection 1's fifth ACK, which makes the redelivery deterministic and keeps the simulator's replay verdict exact. It never changes server bytes.
- **Simulator process.** The driver is plain Node ESM and cannot import the simulator's TypeScript, so it runs the built CLI (`serve-v1`, built by `npm run build`) as a child process. The driver reads the endpoint from the CLI's first output line and the report from its last.
- **Database reader.** The plan allowed the storage reader or a small script with the storage package under Electron's Node mode. The storage package opens read-write with exclusive locking and is TypeScript, so it would need a bundle. Instead `recording-database.cjs` opens a copy read-only with better-sqlite3 under the checkout's Electron in Node mode. Its trip, attribution and interval queries follow `tests/storage/recording-helpers.ts`, and the driver maps them to the shape of the other `tests/fixtures/recording` files. The copy keeps the original byte-identical, so the no-sidecar check applies to the application's own close.
- **Durable `active` diagnostics.** `V1_SOURCE_STATUS` is logged only when the status changes, with the durable state of that moment. So the journey waits, as a liveness bound, for a row with `durable: active` from each service process. In practice that is the first `connected` or `stale` row after the session opened.
- **Scripted waits.** The first committed transport ended connections 2 and 3 at 5,000 and 15,000 ms. The reactive server waits out each paced interval in real time even after its client left, so run B waited for the simulator and each run took about 17.6 s. `b26ec7b` shortened them to 2,000 and 3,000 ms (runs now about 5.7 s). Either the script or the journey's exit may end those connections; the stored rows and the replay verdict are the same.
- **Registry.** Besides REG-012 and REG-017, REG-006 gained one clause, because the journey kills a recording service after a commit whose ACK was lost.

**Failures during development** (harness defects; no product code and no expectation was changed for them):

- the first development run (`development-d4bce5f5…`) failed at the first connection: the proxy started with no admission, so it held every durable hello. The proxy now admits the first connection from the start;
- `npm run lint` reported an unused destructured variable in the files check, which was rewritten.

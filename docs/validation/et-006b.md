## Flaky storage ACK race — October 15, 2026

**Symptom.** The verifier's first `npm run test:storage` on the PR-3 head `5f2210e` (host CPU about 3%) failed one case, and the rerun passed. The case was `tests/storage/v1-durable-ingestion.test.ts`, "sends no ACK after the storage worker is terminated, so the next checkpoint keeps the last acknowledged point (REG-007)": `expected [ [ '1' ], '1', [] ] to deeply equal [ [ '1' ], '1', [ '2', '3' ] ]`. The restarted service's connection recorded no ACKs. The case took 4,454 ms. A normal run takes 170–200 ms, and 300–1,400 ms under 32 CPU burners. The owner's instruction of October 15, 2026 delegates flaky-test fixes to subagents; this one was fixed on `fix/v1-durable-terminate-flake` from `origin/main` `1a7afcb`.

**Cause: a test-only race; the product behaved correctly.** The reactive simulator (`serveV1Reactive`) waits after each action that wrote an event or gap. The wait ends when the client has acknowledged everything written, when it has left, or after at most 1,000 ms (`quiesceMs`). The server then paces on and closes at the scripted disconnect. In `crash-before-commit`, the restarted service receives eventSeq 2 and gap 3 at its connect, and the disconnect follows at once at scale 0. The service must therefore complete `upsertSession`, `commitEvent` and `commitGap` through a new storage worker within that real-time bound. An instrumented copy of the case shows ACK 2 about 8 ms and ACK 3 about 11 ms after the welcome on an idle host. If the worker takes longer, for example on synchronous `FULL` WAL syncs on a stalled shared disk, the server closes first. The ACKs are then built after the connection stopped being current, and E8 correctly withholds them. The 4,454 ms fits this cause: the 1,000 ms quiesce elapsed, then `stop()` waited for the stalled command in flight. The failing run recorded no per-command timings, so the source of the stall itself is not observed.

**Product causes examined and ruled out**, because ACK correctness is safety-critical:

- No older-generation ACK. `DurableDelivery` writes only while `link.current()` holds, and the ingestion's link adds the generation guard. Both are covered by the existing RED mutations above.
- `WORKER_FAILED` arrives before the next command is sent. The client's `exit` listener is registered before `terminate()`'s own listener, so the commit of eventSeq 2 fails at once and nothing is acknowledged (`acks(report, 1)` = `['1']` held in the failing run).
- No lock contention in the new worker. It holds the exclusive lock from `open`, which the harness awaits before it selects the source.
- No early connect. The server's scripted connect waits up to 30 s for a valid hello, so a slow restart cannot make the server skip the connection.
- The old service cannot reconnect first. Its 250 ms backoff timer is cancelled in the same event-loop iteration, by the socket's `close` callback, before any timer phase.
- The cursor and coverage were consistent. The failing run's checkpoint carried A = 1, and `reactiveDifferences` was empty.

**Reproduction (RED).** Each delay was injected into a scratch copy of the test harness, not into product code:

**Fix (`5a09be1`).**

- `serveV1Reactive` has a new opt-in `awaitScriptedAcks` option. It applies to a connection whose scripted client commits and acknowledges each item (`ack: each`, any commit policy but `none`). Such a connection is awaited without the quiesce bound until it has acknowledged everything written to it or has left. If it does neither within `settleTimeoutMs` (default 30 s, a liveness bound), the run fails instead of pacing on. Connections that withhold or drop ACKs keep the bounded wait. The default stays off, so `serve-v1`, the smoke and the other reactive tests are unchanged ([simulator v1](../simulator-v1.md)).
- `v1-durable-ingestion.test.ts` and `v1-ingestion-crash.test.ts` use the option. With it, how long the real worker's commits take, or how late a service is terminated, no longer changes what the server writes or records.
- At a restart, the storage harness first selects no source on the old service. This cancels its reconnection, while its durable pipeline keeps committing what the connection delivered.

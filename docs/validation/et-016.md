### Interpretations and deviations from the plan

- **Gap carrier.** The plan says `previouslyCoveredThrough + 1`. Storage uses `max(firstEventSeq, previouslyCoveredThrough + 1)`, the first eventSeq the gap newly covers: the two differ only for a gap that starts beyond coverage + 1, which the recorder's ordered FIFO does not produce. A dedicated case covers both shapes.
- **Carrier on an open trip.** Beyond "both NULL together", a CHECK keeps the carrier NULL while `outcome` is `open`, as J6 states it.
- **Checkpoint key range.** `checkpoint_next_event_seq` is a 20-digit key above zero, up to 2^64 − 1, because protocol v1 allows `nextEventSeq` up to that value.
- **`trip.close` without a carrier context** fails with `INVALID_INPUT` instead of writing NULL; no caller can reach it.
- **The orphan case.** The plan expected a failure inside 0002 to prove the rollback. A version 1 database with a broken foreign key never reaches 0002, because the verified backup refuses it; that case now asserts the refusal, and the rollback of 0002 is proven with an injected failing version 3 after it.
- **Existing tests changed because the requirement changed** (version 2 is current). `migrations.test.ts`, `backup-restore.test.ts` and `fixtures.test.ts` used a test-only version 2 step on top of `MIGRATIONS`; injected steps now start at version 3, and the cases that must read version 1 unchanged pass `MIGRATIONS.slice(0, 1)`. `worker.test.ts`, `open-durability.test.ts` and `recording-target.test.ts` expect a new database at version 2.
- **`tests/storage/failures.test.ts`** (not in the plan's owned list). Its `SQLITE_FULL` case caps `max_page_count` at the current page count. The 0002 rebuild leaves the old `job_configurations` pages on the freelist of a new database, so the event fitted into free pages and storage run 1 failed that case. The case now asserts a non-empty freelist, runs `VACUUM`, asserts an empty one, and then caps; the assertion on `DISK_FULL` is unchanged.
- **`RuntimeReceipt.ps1` and `tests/unit/runtime-receipt.test.ts`** (not in the plan's owned list, named in the task): the recording receipt rule accepted only `userVersion` 1; it now accepts only 2, and a negative case refuses a version 1 receipt.

## PR-2 journal reads in the storage worker (October 16, 2026)

Branch `feat/journal-storage-reads`, stacked on PR-1 at `0ae2362` (`feat/trip-journal`).

### Changes

- `packages/contracts/src/journal.ts` (new, exported from `packages/contracts/src/index.ts`): the journal read contract. It holds the query and page types and the fixed bounds: 50 trips per page, events and intervals 100 or 500, samples 300 or 3,600, 50 intervals in a detail and 5,000 money amounts. The list row, detail, event, interval and money total shapes keep the protocol v1 availability and money shapes, every response carries `database: {purpose, schemaVersion}`, and cursors have a fixed format. - `packages/storage/src/worker/protocol.ts`, `host.ts`, `client.ts`: four worker commands. The parser accepts a journal command only with exactly its listed fields and checked values; the host forwards only the parsed fields; the client copies queries and pages field by field and validates every answer, failing closed on a malformed one.

### Interpretations and deviations from the plan

- **The database UUID.** No journal read returns it. The minimal correct source is the open summary that the storage worker already returns to the service's `HistoryStorage`: main sends a main-only `{kind: 'database'}` query on the existing journal routing, and the service answers `{database, databaseUuid}` without a storage command. This touches `journal-contract.ts`, `journal-service.ts` and `history-storage.ts` and their unit tests, which are not in PR-5's owned files. The renderer has no channel for it, and `JOURNAL_CHANNELS` still lists the five reads; the export channel is the separate constant `JOURNAL_EXPORT_CHANNEL`.
- **The session origin** is derived from the database purpose: a database accepts exactly one plugin-session origin (the `database_info` CHECK and the `plugin_sessions_origin` trigger), so no read is needed. The storage test confirms it against `plugin_sessions.origin`.
- **`packages/contracts/src/index.ts`** (the `DesktopBridge` type) and **`journal-view.ts`** (the pure `journalExportText`) changed beside the owned files, because the bridge type and the result texts live there.
- **The default file name** uses the trip's start label in UTC; the plan does not name a zone, and UTC keeps the name independent of the computer's zone and daylight-saving changes.
- **`bounds.snapshot`** states J17's "bounds + trip.outcome `open`" explicitly.
- **Samples omit `tripUuid`:** every sample of the document belongs to its trip.
- **Trailers** are the detail's latest 10 configurations with the trip's total; there is no paged trailer read, and earlier configurations inside the window are in `events`.
- **Logging:** a write failure adds the fixed `step` and the system error code to `JOURNAL_EXPORT_FAILED {code}`; no path is logged.
- **The smoke's targets** are in the run's own output folder (`journal-export\`), inside the isolated run directory, and the dialog replacement records only the default file name and the filters, never the user's Documents path.
- **`docs/ci.md`** changed (not in the plan's PR-5 document list), because it describes the journal smoke.
- **The exit's combined idle wait** (settings save and export together) has no `main-boundaries.test.ts` case: main returns the single pending promise unchanged when only one exists, so the existing settings exit cases are unchanged, and the export's `idle()` is covered in `journal-export-writer.test.ts`.

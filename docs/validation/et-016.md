# ET-016 trip journal validation

## Scope and authorization

### Interpretations and deviations from the plan

- **Gap carrier.** The plan says `previouslyCoveredThrough + 1`. Storage uses `max(firstEventSeq, previouslyCoveredThrough + 1)`, the first eventSeq the gap newly covers: the two differ only for a gap that starts beyond coverage + 1, which the recorder's ordered FIFO does not produce. A dedicated case covers both shapes.
- **Carrier on an open trip.** Beyond "both NULL together", a CHECK keeps the carrier NULL while `outcome` is `open`, as J6 states it.
- **Checkpoint key range.** `checkpoint_next_event_seq` is a 20-digit key above zero, up to 2^64 − 1, because protocol v1 allows `nextEventSeq` up to that value.
- **`trip.close` without a carrier context** fails with `INVALID_INPUT` instead of writing NULL; no caller can reach it.
- **The orphan case.** The plan expected a failure inside 0002 to prove the rollback. A version 1 database with a broken foreign key never reaches 0002, because the verified backup refuses it; that case now asserts the refusal, and the rollback of 0002 is proven with an injected failing version 3 after it.
- **Existing tests changed because the requirement changed** (version 2 is current). `migrations.test.ts`, `backup-restore.test.ts` and `fixtures.test.ts` used a test-only version 2 step on top of `MIGRATIONS`; injected steps now start at version 3, and the cases that must read version 1 unchanged pass `MIGRATIONS.slice(0, 1)`. `worker.test.ts`, `open-durability.test.ts` and `recording-target.test.ts` expect a new database at version 2.
- **`tests/storage/failures.test.ts`** (not in the plan's owned list). Its `SQLITE_FULL` case caps `max_page_count` at the current page count. The 0002 rebuild leaves the old `job_configurations` pages on the freelist of a new database, so the event fitted into free pages and storage run 1 failed that case. The case now asserts a non-empty freelist, runs `VACUUM`, asserts an empty one, and then caps; the assertion on `DISK_FULL` is unchanged.
- **`RuntimeReceipt.ps1` and `tests/unit/runtime-receipt.test.ts`** (not in the plan's owned list, named in the task): the recording receipt rule accepted only `userVersion` 1; it now accepts only 2, and a negative case refuses a version 1 receipt.

## PR-2 journal reads in the storage worker (October 16, 2026)

### Changes

- `packages/contracts/src/journal.ts` (new, exported from `packages/contracts/src/index.ts`): the journal read contract. It holds the query and page types and the fixed bounds: 50 trips per page, events and intervals 100 or 500, samples 300 or 3,600, 50 intervals in a detail and 5,000 money amounts. The list row, detail, event, interval and money total shapes keep the protocol v1 availability and money shapes, every response carries `database: {purpose, schemaVersion}`, and cursors have a fixed format. The file also holds the strict request checks and answer validators. Event records, occurrences and job, truck and trailer values are checked with the protocol v1 validator itself, wrapped in an event envelope.
- `packages/storage/src/sqlite/journal.ts` (new): `journalTrips`, `journalTrip`, `journalEvents` and `journalIntervals`, with every statement in `JOURNAL_QUERIES` (J5, J7). `packages/storage/src/index.ts` adds them to `Storage` and exports `JOURNAL_QUERIES`; `api.ts` re-exports the contract types.
- `packages/storage/src/worker/protocol.ts`, `host.ts`, `client.ts`: four worker commands. The parser accepts a journal command only with exactly its listed fields and checked values; the host forwards only the parsed fields; the client copies queries and pages field by field and validates every answer, failing closed on a malformed one.

### Interpretations and deviations from the plan

- **Validators in the contract.** The plan names DTOs in `packages/contracts/src/journal.ts`. The strict request checks and answer validators live there too, so the storage client now, and main and the preload in PR-3, share one definition.
- **Limits are chosen by the caller.** `journalEvents` and `journalIntervals` take a required `limit` that must be 100 or 500. `journalTrips` takes no limit at all, and a `limit` field is refused.
- **Money totals.** Totals cover the fine, toll, ferry and train amounts of events attributed to the trip (`trip` or `trip-before-loaded`), grouped by category as well as SDK type and currency. With more than 5,000 amounts the lists are empty rather than partial.
- **Events of the trip's own session only.** Both the known and the unknown window list only events of the trip's plugin session.
- **Unknown-window plan.** SQLite first chose to walk the session's (session, eventSeq) index range for the referenced events. A unary `+` on those terms makes it look each referenced event up by primary key instead.
- **Statement cache.** Journal statements share the per-connection statement cache with the other reads, one of which plucks the same clock query, so the journal helpers set the pluck mode on every call.
- **`tests/measurement/storage-size.measure.ts`** records the journal medians of one run only and asserts none.

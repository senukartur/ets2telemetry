ET-017 implements the owner's [silent plugin installation](../../concept.md#silent-plugin-installation--october-12-2026) decision of October 12, 2026 in six PRs; see [game plugin setup](../plugin-setup.md). ## PR-3: atomic installer and install registry (October 17, 2026)

Branch `feat/et-017-plugin-installer`, based on `883f452` (PR-2 under review, merged with `main` `5e98b97`, which contains PR-1); implementation commit `1ac8449`. PR-3 adds three modules in `apps/desktop/src/plugin-setup/`:

See [algorithm](../plugin-setup.md#algorithm) and [install registry](../plugin-setup.md#install-registry).

### Deviations from the plan

- **Pending intent fields.** A pending intent also records `source`, `appVersion` and `createdPluginsDirectory`, beside P8's `{op, game, root, temp, fromSha256, toSha256, startedUtc}`. Recovery needs them to record an install whose rename completed before an interruption, with its source, version and created-folder flag.
- **Folder creation order.** A missing `plugins` folder is created after the pending intent is written (P8 step 6), not at step 2. Otherwise a failed intent write would leave a created folder that no record names, and P8 says the folder must stay untouched when that write fails. The intent records that this run creates the folder.
- **Read-only removal.** Removal also refuses a read-only target (`READ_ONLY_FILE`). Node's `unlink` clears the read-only attribute before it deletes, and P8 step 5 forbids clearing it.
- **Rename over an open file.** P7 expects `EBUSY` for a sharing lock. Measured on October 17, 2026, Windows refuses a rename over a target that another process holds open without delete sharing with `ERROR_ACCESS_DENIED`, which Node reports as `EPERM`. Such a lock is therefore `TARGET_LOCKED` at once, without retries. `EBUSY` from a sharing violation, for example while reading a target held with `FileShare.None`, is still `TARGET_LOCKED`, and the rename still retries `EBUSY` as P8 requires.
- **Quarantine timing.** The registry quarantines an invalid file at its first write, not at load, so that loading never writes, as in the settings store.
- **Registry bounds.** A write that would exceed the 16-install or 16-intent bound is refused with `REGISTRY_UNAVAILABLE`; no entry is evicted.

### Isolation

- Every unit case runs on fake game roots and a fake registry folder under the guarded temporary root, and fails if any path outside it was requested.
- The sharing-lock cases start a Windows PowerShell 5.1 child that opens only the fake target, through an environment variable, and is ended after each case.
- The ACL case asserts that the folder lies inside the guarded root before it runs `icacls /deny` for the current user's SID. It removes the deny in `finally` and checks that `icacls` no longer lists a deny entry.
- The image lock check runs the tests-only fake SDK host from the native build, with transport folders in its temporary root. Before it starts, it requires that `tasklist` shows no ETS2, ATS or TruckersMP process.
- `tasklist` showed no `eurotrucks2.exe`, `amtrucks.exe` or `truckersmp*` process before each plugin-lock run below.
- No real Steam library, game folder, `%LOCALAPPDATA%\ETS2Telemetry` or registry key was read or written.

### Deviations from the plan

- **Five channels, not six.** `diagnostics:export` is not registered yet. A stub that answers `NOT_AVAILABLE` would be a renderer-reachable channel and bridge method with a placeholder result type that PR-6 must replace, together with its tests; PR-6 defines the diagnostic bundle (P17) and its result, and appending one key to the bridge lists then is a small change. The plan's PR-4 step lists the six channels; this is the deviation the task brief allowed.
- **At most four folders per game.** P16 bounds a game's folders at four, while discovery keeps up to four Steam roots and P4 adds a manual folder. With a manual folder at most three Steam roots are listed and managed. Steam installs one copy per library, so a fourth Steam copy plus a manual folder is not expected; the case is documented in [setup run](../plugin-setup.md#setup-run).
- **Locked-file polling.** P13 polls while a folder is `TARGET_LOCKED`. A locked file that nothing detectable holds would be rewritten every 15 s (an intent and a failure in the registry each time), so the poll retries it at most three times in a row while the running games stay the same, and again whenever they change; Retry works at any time.
- **Extra codes.** The folder choice can also be refused with `SETUP_DISABLED` (disabled mode, before the dialog), `REGISTRY_UNAVAILABLE` (a read-only registry) and `BUSY` (a second dialog). `PLUGIN_ACTION` also carries the folder's `ordinal`, and setup logs `PLUGIN_REGISTRY_STATE`, `PLUGIN_BUNDLE`, `PLUGIN_RECOVERY_PENDING`, `PLUGIN_SETUP_TIMEOUT` and `PLUGIN_FOLDER_NOT_OPENED` beside P17's codes, all fixed codes and counts.
- **Test-root registry.** P15 does not place the install registry for the test-root mode. It is `<root>\LocalAppData\ETS2Telemetry\plugins\setup.json`, so every path the mode writes lies inside the root, and a bare drive (`C:\`) is rejected as a root.
- **Confinement probe.** The confinement resolves real locations with Node's `realpath` directly, not through the confined file system, so that probing where a junction points is not itself counted as an access by the code under test.

### Tasklist bound (October 17, 2026)

**Cause.** `tests/unit/game-processes.test.ts` "lists its own node.exe in a real run" failed in every full `npm test` during review round 1, at about 3,020 ms. That is the product's own 3 s `tasklist` deadline (`TASKLIST_TIMEOUT_MS`), not a test-only limit. Under the full parallel suite the host listed processes more slowly than 3 s, while a standalone `tasklist` took 0.6–0.7 s. A user machine under load would hit the same deadline, and setup would then report `RUNNING_CHECK_FAILED`. Before this change nothing polled such a folder, so the plugin stayed uninstalled until Retry, a new trigger or the next application start.

**Fix.**

- `TASKLIST_TIMEOUT_MS` is 10 s. It is still bounded.
- A run lists the running games before each folder's change, once more after a fresh install, and for recovery when intents are pending. A listing normally takes well under a second; three listings at the 10 s limit fill the 30 s run, and the run's own abort still bounds it.
- `RUNNING_CHECK_FAILED` now keeps the 15 s poll running, and so does a run that hit its 30 s limit. The poll starts a run as soon as its own listing succeeds; while the listing keeps failing it only goes on, and it writes nothing.
- The real-run test keeps its assertions. It now has a 20 s case limit, checked against the bound, so a slow listing fails as the product's timeout rather than as Vitest's default 5 s limit.
- Changed requirement: the stubbed call case now expects `timeout: 10_000`.

**New cases** in `plugin-setup.test.ts`:

- A failed listing marks both games' folders `missing` with `RUNNING_CHECK_FAILED` and arms the poll. A poll whose listing still fails starts no run. Once a listing succeeds, the poll's run installs both, and no poll remains.
- A run held until its 30 s limit before it reached any folder arms the poll, and the next poll's run installs the plugin.
- The 30 s abort case now also requires the poll to be armed.

**RED**, each applied alone and reverted:

| Mutation | Failing cases |
| --- | --- |
| `RUNNING_CHECK_FAILED` removed from the poll reasons | "retries a folder whose running check failed once the poll lists the running games again, and then stops polling" |
| The unfinished-run flag never set | "retries a run that hit its 30 s limit before it reached any folder" |
| The poll never retrying a failed listing (`continue` instead of `return true`) | both of the above |

`TASKLIST_TIMEOUT_MS` back at 3000 fails the stubbed call case, and the real-run case failed at that bound in every full suite above.

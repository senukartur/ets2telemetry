## PR-1: the protocol v1 minor-1 contract (October 25, 2026)

Based on main `43c634a`.

### Behavior

- `packages/contracts/src/protocol-v1.ts` implements minor 1. The envelope minor selects the state schema, so `state.gearbox` (B2) is required exactly in minor 1. The welcome's envelope minor must equal the minor it announces, and a hello is always version 1.0. `negotiateV1(input, {allowDurable, maxMinor = 0})` selects min(hello `maxMinor`, the server's own maximum).
- Every stateless entry point (`decodePayload`, `validateServerMessage`, `validateClientMessage`, `encodeFrame`, `FrameDecoder`, `negotiateV1`, `computeClockMapping`) defaults to minor 0. It accepts or writes minor 1 only when its caller passes `maxMinor: 1`, so every current caller behaves exactly as before.
- `packages/contracts/src/protocol-v1-delivery.ts` enforces one minor per connection:
  - `V1Consumer(durable, {maxMinor})` rejects a welcome above its `maxMinor` and any later message at another minor, and exposes the selected `minor`;
  - `DurableAckCursor.beginConnection(acked, minor)` builds ACKs at the connection minor;
  - `AckValidator(session, durable, minor)` rejects an ACK at another minor, and its `probe` method rejects a clock probe at another minor or before the checkpoint.

  Every new parameter defaults to 0.
- The live observation (`validateLiveObservationV1`, `LiveStateV1`) still validates the minor-0 state; the gearbox is projected only by PR-5.
- The plugin, broker, simulator and desktop application still negotiate minor 0. No v0, CAP0, storage, settings, IPC or native source changed, and `GAME_HISTORY_RECORDING` stays `false`.

## PR-2: gearbox-aware labels in telemetry-core (October 25, 2026)

Stacked on the PR-1 head `1577547`.

### Behavior

- `packages/telemetry-core/src/gear-labels.ts` adds the pure `deriveGearLabels(gearbox)`. It returns forward and reverse labels for a recognized layout and `undefined` for anything else, so the caller falls back to the GD2 formula. It follows the plan's seven steps; the stated interpretations are:
  - selector bits are classified from forward pairs only, because reverse labels are always R1…Rn (B4) and a range-only gearbox may number its reverse gears one apart across the range bit;
  - a pair whose two states hold the same gear carries no information and is not counted, so a cell whose splitter states repeat one gear gets no suffix (step 6); in the first round a bit with no differing pair was still unrecognized, which the review fix below amends;
  - a crawler exists only with a range bit: the one forward position without high-range gears;
  - a final check requires ascending gears to give strictly ascending labels (crawler first, then by number, L before H), which rejects a range or splitter direction that differs between positions and two gears that share a label.
- The crawler names are one constant, `CRAWLER_LABELS` (B5).
- `formatGear(index, mode, labels?)` uses a covered label in manual mode and the GD2 formula otherwise; automatic mode ignores the labels, and neutral is always `N`.
- The derivation is memoized per H-shifter layout object in a `WeakMap`, keyed together with the two counts.
- Nothing outside tests calls it yet; PR-6 wires it. No wire, contract, settings, IPC, storage or native change, and `GAME_HISTORY_RECORDING` stays `false`.

### Tests

Expected labels are written by hand from the plan's tables and the documented transmission names.

- `tests/unit/telemetry-core-gear-labels.test.ts`:
  - the CAP-01 DAF 12-speed from `minor1/checkpoint.json` gives 1L…6H, equal to the formula, and reverse R1…R4;
  - the CAP-01 Mack 18-speed from `minor1/checkpoint-ats-mack.json` gives LL, LH, 1L…4H, 5L…8H and reverse R1…R4;
  - a synthetic 13-speed gives L, 1–4, 5L…8H, also with splitter states that repeat the low-range gear; a 10-speed range-only gearbox gives 1–10 although its reverse gears are one apart across the range bit; the zero-selector fixture gives plain numbers; a split crawler gives LL/LH; a splitter-only gearbox gives 1L…2H;
  - fallback to `undefined` for forward or reverse counts above or below the slots, two crawler positions, a low-only position above other low-range gears, a mixed bit, two range bits, a range direction that differs between positions, a gear with two labels, a duplicate pair, selectors outside the selector count and each unavailable part. Since the review fix below, a bit without pairs and a bit whose pairs repeat the gear are no longer in this list: they give plain numbers;
  - manual mode uses the formula for uncovered gears (19 is `10L`), automatic mode ignores the labels, neutral is `N`;
  - memoization returns the same result for the same layout object and derives again when its counts change.
- `tests/unit/telemetry-core-format.test.ts` adds a hand-built label map case for `formatGear`.
- `tests/unit/telemetry-core-boundaries.test.ts` lists the new module; its imports are type-only contracts imports.
- Mutation checks, each restored afterwards:

  - counting every nonzero delta as a splitter failed seven derivation cases;
  - removing the explicit more-than-one-crawler check failed nothing, because step 5 then rejects the second low-only position for lacking a high range. The explicit check stays as the stated B5 rule.

### PR-2 review fix

The independent review requested changes with two accepted findings, fixed in one commit:

1. **Step-2 amendment (coordinator decision, applying B3 and B5 as written; not an owner B-decision).** The observed SDK shape always declares two selector bits, so a range-only or selector-less gearbox leaves a bit whose slots are neutral or repeat the gear. Rejecting that bit made such gearboxes fall back to the formula (a 10-speed showed `1L`…`5H`, a 6-speed `1L`…`3H`). Now a bit with no differing forward pair is unused and ignored, and a cell collision rejects: if the ignored bits fold slots with different gears into one cell state, the layout is unrecognized. A mixed bit and a second bit of the same kind are still rejected.
2. **Memoization note.** The doc comment states that the WeakMap is keyed by the layout object's identity, that a layout must not be mutated in place, and that a new object per update misses the cache and is derived again, which is cheap.

Tests:
- New cases in the observed two-bit shape: a 10-speed range-only gearbox with neutral splitter slots and with splitter slots that repeat the gear, both `1`…`10`; a 6-speed whose four selector states all repeat each gear, `1`…`6`; a bit used only on separate positions, plain numbers.
- The former fallback cases "a bit without pairs" and "a bit whose pairs repeat the gear" now expect plain numbers (`1`, `2`, `3` and `1`, `2`), because the requirement changed with the amendment.
- A new fallback case: two ignored bits that map different gears into one cell.
- The 12-speed, Mack 18-speed, 13-speed, zero-selector and every other fallback expectation is unchanged.

Mutation checks, each restored afterwards:
- Rejecting an unused bit again failed the six new or changed plain-number cases.
- Removing the cell-collision check failed nothing: a gear it overwrites is then missing a label, or gets a second label in another cell, and the ascending-label check rejects the layout. The collision check stays as the explicit rule.

## PR-4: the plugin's gearbox capture and minor-1 endpoint (October 25, 2026)

Written on the PR-3 head `928920fe`; rebased onto `main` after PR-1 (#186), PR-2 (#188) and PR-3 (#189) merged.

### Behavior

- **Capture.** `Adapter::v1_configuration` (`sdk-adapter.cpp`) handles the `hshifter` configuration callback in one pass over at most 256 attributes. It copies `selector.count` and the indexed `slot.gear`, `slot.handle.position` and `slot.selectors` by SDK slot index into a trivially copyable `GearboxPod` (`std::array<HShifterSlotRaw, 64>` with one seen bit per slot attribute, in `protocol-v1-records.hpp`). The pod lives beside the configuration and goes into `StatePod::gearbox` at the next publication. The `truck` branch also copies u32 `gears.forward` and `gears.reverse`, and a truck clear makes them `not-observed`.
- **No boundary.** The `hshifter` callback sets only the gearbox dirty flag. It changes no v1 configuration revision, calls no `v1_emit`, assigns no `eventSeq`, allocates nothing, waits for no lock and calls no SDK API. A contended publication keeps the copy pending. The layout survives truck changes until the next `hshifter` callback (B2).
- **Availability.** An empty list is `not-observed`. A null or unterminated list, a type mismatch, a slot attribute without an index or at index 64 or more, a repeated slot attribute, and disagreeing or missing `selector.count` copies are `invalid` in the adapter. The encoder (`protocol-v1-producer.cpp`) marks the whole layout `invalid`, never truncated, in these cases:
  - a selector count above 6;
  - an incomplete slot triple;
  - a gear outside −100..100;
  - a handle position above 255;
  - selectors not below 2^selectorCount;
  - a repeated (handle position, selectors) pair among the copied slots, neutral or not.

  Otherwise it omits gear-0 slots and keeps SDK slot order. Gear counts above 100 are `invalid`.
- **Minor per connection.** Every `Encoder` builder and `encode()` take the connection minor, which defaults to 0. `v1-server.cpp` negotiates with `negotiate(hello, true, 1)`, so it selects min(hello `maxMinor`, 1). The connection keeps that minor for every message it writes, for the `state.gearbox` of its checkpoints and snapshots, for its client `FrameDecoder`, and for `AckValidator` (ACKs and probes). Clock replies carry the same minor. A minor-0 state never encodes the gearbox, so minor-0 bytes are unchanged. `measure_event` stays at minor 0, because an event's encoded length does not depend on the minor.
- **Unchanged.** CAP0, v0, the broker relay, the service, the simulator and the desktop application are unchanged. The service still offers `maxMinor` 0, so every production connection still selects minor 0 until PR-5. The plugin DLL's bytes and hash change; `released-plugins.json` is not edited. `GAME_HISTORY_RECORDING` stays `false`.

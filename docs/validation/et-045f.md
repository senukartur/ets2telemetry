# ET-045f: animated Cluster speed arc

Date: October 24, 2026 (Europe/Warsaw). Task: item 3 of [ET-045](https://trello.com/c/OmNYTBsp), under the owner's decision D4 of October 24, 2026 ([ET-045 validation](et-045.md)). Branch `feat/et-045f-cluster-speed-arc`, from main `8bd6d8e` (ET-045e).

This record makes no game, display, DPI, readability or performance claim, and it neither passes nor waives an ET-044 assertion.

## Owner observation

During the owner-operated ETS2 single-player windowed run of ET-044 the owner noted that the Cluster's outer ring showed no speed: only the inner RPM arc moved (`cluster-rpm.png`, item 3, with item 2). The screenshot stays local evidence under `.local/validation/et044-s1-20261023-cca3e16/owner-findings/` and is not committed. The cause was by design: ET-028 kept the outer speed track decorative because the overlay payload carried speed only as formatted text. D4 authorizes a validated numeric overlay payload field for the speed arc.

## Decisions

The architect's decisions Y1–Y9, adopted by the coordinator under the owner's ET-045 delivery authorization, are in [concept.md](../../concept.md#et-045f-cluster-speed-arc--october-24-2026); the rules are in [the minimal overlay](../minimal-overlay.md#cluster-speed-arc-et-045f-october-24-2026).

- The speed section's value carries `speedRing`, the fraction in [0, 1] of the 130 km/h or 80 mph gauge scale of the displayed profile, only on a current, available, finite speed. It is 0 while the displayed integer is 0 (ET-045a) and in reverse, and capped at 1.
- One helper, `speedGaugeFraction` in `apps/desktop/src/speed-gauge.ts`, serves the overlay and the dashboard's Live instrument; the dashboard's behaviour is unchanged.
- Main attaches `speedRing` and the RPM `ring` only through `isGaugeFraction`; the overlay preload applies `overlayGauges` to every delivery, so a malformed or misplaced fraction is dropped without dropping the update, its credit or the channel.
- The arc lies on the outer track (radius 52, stroke 6) from 12 o'clock clockwise, eases its dash offset over 150 ms linear and has no transition under `prefers-reduced-motion: reduce`. The speed arc uses #60A5FA and the RPM arc the new `--yu-ov-rpm` #2563EB.
- No new IPC channel, bridge method, settings, window size, wire, storage, export or native change; `GAME_HISTORY_RECORDING` is unchanged.

## Hosted CI, first Ready run (October 24, 2026)

The first Ready run of PR #182 on `58c21f4` ([40139749258](https://github.com/senukartur/ets2telemetry/actions/runs/40139749258)) failed in the packaged UI overlay shard: `page.waitForFunction: Timeout 5000ms exceeded` at the reduced-motion step, in English, after the metric, US-customary, 0, −5 and 180 km/h steps had passed. Under `reducedMotion: reduce` the hosted overlay renderer kept the 0.15 s duration for 5 s, while the emulation works locally in packaged and development runs. The cause is not established.

First fix (`163786b`): the step required a loaded stylesheet rule `@media (prefers-reduced-motion: reduce)` with `.overlay-speed-arc` set to `transition: none` (`reducedMotionRule`, read from the CSSOM) and only recorded the emulation. Its Ready run ([40141031694](https://github.com/senukartur/ets2telemetry/actions/runs/40141031694)) failed one step later: after the emulation was cleared, the hosted renderer did not return to 0.15 s within 5 s. The emulated media feature evidently reaches the hosted overlay renderer late or not at all.

Second fix: the smoke no longer uses `emulateMedia({reducedMotion})`. It requires the loaded reduced-motion rule and the 0.15 s linear transition. Locally, the packaged `ui -UiCase overlay` smoke passed in EN and RU. Whether Windows "Animation effects" off removes the transition in a real session is an owner check; the emulation result seen locally in verifier and author runs (0 s under `reducedMotion: reduce`) stays recorded above as local evidence only.

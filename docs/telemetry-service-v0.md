# Prototype telemetry service and renderer bridge

ET-006a consumes the accepted [protocol 0.0](protocol/v0.md). It adds live ingestion and a functional speed/fuel display, with no production database writes, samples, trips, durable events or wire ACKs. The only SQLite operation remained the existing isolated temporary worker probe; since ET-013 PR-2 the service also opens the history database without recording anything ([below](#history-database)). Simulator success is not game compatibility evidence.

Electron main owns the window, authorization, fixed native artifact resolution and utility-process supervision. The utility process owns framing, ordering, source checks, freshness, subscriptions and the SQLite workers: the readiness probe and, since ET-013 PR-2, the history storage worker. React receives a frozen narrow preload API: `getStatus`, `selectSource`, and `subscribeLive`, followed since ET-011a by `getAppState`, `subscribeAppState` and `exitApplication` ([application lifecycle](app-lifecycle.md)). Since ET-010c an update from `subscribeLive` may carry the optional field `v1`, the whitelisted protocol v1 projection of the same selection, validated in main and in the preload and expired on its own 500 ms clock ([live projection](telemetry-service-v1.md#live-projection-et-010c)); the methods and IPC channels are unchanged. It receives no IPC object, Node access, filesystem path, native operation or database operation. Both sender identity and the main-frame identity authorize every main IPC request.

## Source selection and trust

The default `game` selection waits for an explicit target. `ets2` and `ats` select a game by enum. Multiple discovery records for the same selected game fail closed rather than choosing the first process. `synthetic` and `replay` require an explicitly configured isolated fixture endpoint; there is no fallback from a game source to a fixture. The main-owned environment configuration is `ETS2TELEMETRY_SOURCE_KIND` plus `ETS2TELEMETRY_SOURCE_PIPE`. Renderer commands cannot supply a path. The fixture endpoint must exactly match `\\.\pipe\ETS2Telemetry-SYNTHETIC-TEST-v0-{pid}-{uuid}`; the envelope origin must equal the selected fixture kind. The current ET-005a simulator produces synthetic data, so selecting replay against that simulator is rejected.

Node `net` is used only for the explicit fixture path. It does not authenticate game peers. The separate owned native client connects game sources using the [native transport boundary](native-transport-boundary-v0.md). Development uses the fixed `native/telemetry-client/build/Release/telemetry-pipe-client.exe`; packaged applications use `resources/telemetry-client/telemetry-pipe-client.exe`. Main compares the adjacent build receipt's source map with the desktop build receipt and hashes the executable before passing this fixed configuration to the service. This is build provenance within the same-user model, not a defense against a compromised account.

The client reads owner-only UTF-8 discovery records under `%LOCALAPPDATA%\ETS2Telemetry\transport\v0`, rejects unknown/duplicate keys, unsafe DACLs and reparses, sweeps validated records whose process is demonstrably gone or has a different creation lifetime, and bounds inspection to 256 non-stale directory entries/128 live records/16 KiB per record. It verifies the connected pipe server PID, retained process creation FILETIME, token SID and Windows session, and holds the game image and process handles. The executable basename must be `eurotrucks2.exe` or `amtrucks.exe` for the selected game. The record UUIDs bind discovery to the envelopes; they are not independently authoritative OS identities. Every envelope must match the native receipt's game, PID, session, process-instance UUID, plugin-session UUID and game origin. Reconnection launches a fresh verifier and consumer.

Before connecting, the broker publishes its own canonical held image path and SHA256 into the bounded protected `service-policy.json`, preserving valid existing entries (maximum four). A protected, exclusive, delete-on-close lock serializes this owned policy publication; contention fails closed. The plugin checks the actual connected broker process against this policy. The broker does not authorize Electron generally or infer role from command-line/ancestry claims. Other-user and remote connection evidence remains with the native transport acceptance record.

Broker-created security descriptors explicitly set the owner to the current `TokenUser` SID as well as a protected single-user DACL. They do not rely on `TokenOwner`, which can designate an Administrators group for an elevated token. The strict reader still requires the owner and sole allowed trustee to equal `TokenUser`; policy lock and atomic temporary publication use the same descriptor.

## Native broker control

The broker accepts only `--game ets2|ats --discovery-dir <main-owned-directory>` for v0, or the same arguments followed by `--capture cap0` for the separate opt-in [CAP0 evidence mode](protocol/cap0.md); the capture mode connects only to the CAP0 endpoint, marks its receipt with `"evidence":"cap0"` and accepts only a CAP0 hello. Its first stdout frame is a four-byte little-endian length followed by a JSON receipt of at most 4,096 bytes:

```json
{"type":"authority","schemaVersion":1,"source":{"game":"ets2","processId":123,"windowsSessionId":1,"processInstanceId":"00112233-4455-6677-8899-aabbccddeeff","pluginSessionId":"11112233-4455-6677-8899-aabbccddeeff","origin":"game"},"processCreationTime":"134000000000000000","userTag":"<64 lowercase hex characters>"}
```

No matching record produces `{"type":"waiting","schemaVersion":1}` and exit code 2. Authority failure exits 1. Source disconnect/cancellation exits 3. Exit code 4 reports contention on a project-owned file before any authority receipt: the policy lock held by another broker (`ERROR_FILE_EXISTS`) or still delete-pending (`ERROR_ACCESS_DENIED`), a policy replacement blocked by an open reader (`ERROR_ACCESS_DENIED`, `ERROR_SHARING_VIOLATION`, `ERROR_LOCK_VIOLATION`), or a sharing violation on the held broker/game image. A read-only policy also blocks replacement with `ERROR_ACCESS_DENIED` but never clears, so it stays exit 1. Exit 4 grants nothing, and exit 4 after a receipt is a hard rejection. The broker does not replace an identical policy, because every replacement races readers such as the plugin's per-connection policy check. On every exit the broker writes one stderr line `diag1 <stage> <win32-error> <elapsed-ms> <slowest-stage> <slowest-ms>`; stages are fixed names and timings cover startup and handshake stages only. The service keeps a 256-byte stderr tail, accepts only a known stage name (otherwise `unrecognized`/`unreported`) and logs a `NATIVE_BROKER_EXIT` record whose always-present `facts` hold the fixed outcome, exit code, stage, Win32 error number, broker timings and `serviceMs` (spawn to exit as seen by the service, so launch delay before the broker clock starts is visible). A run of identical outcome/stage/error is recorded at occurrences 1, 2, 4, 8 and so on with its `repeats` count, so a retry loop cannot fill the bounded service log. Routine waiting exits and owner cancellation are not logged; no path, identity, receipt or relayed byte reaches the log. The service sends one bounded framed v0 hello, then one byte `0x01` per relay credit. One credit permits one wire frame of at most 65,540 total bytes. The service returns a credit only after synchronous schema/order/identity validation and state application. Credits control this owned stdio boundary; they are not v0 or durable acknowledgements. An unsolicited frame, duplicate control credit, malformed frame, oversize payload or changed identity closes the connection.

There is one native client per service, including during automatic recovery and source switching. Both the retry backoff and actual previous-client completion must finish before a new verifier starts. An automatic retry captures its connection generation; stopping or selecting another source invalidates it even if completion arrives later. Switching requests coalesce into one pending selection. Native pipe operations have five-second deadlines and cancellation waits for actual completion. An input EOF monitor cancels outstanding overlapped reads. Synchronous stdio cancellation joins the owned I/O thread. The production executable uses the static MSVC runtime; optional ASan console targets are separate artifacts.

### Protocol v1 mode

ET-006b (coordinator decisions E3 and E4; see [ET-006b broker validation](validation/et-006b-broker.md#scope) for the authorization status) adds a third explicit mode: the same two arguments followed by `--protocol v1`, with `--discovery-dir` naming `%LOCALAPPDATA%\ETS2Telemetry\transport\v1`. It cannot be combined with `--capture`; another value or combination exits 1 at stage `arguments`. The v0 and CAP0 modes, their receipts and their control streams are unchanged. The broker implements the mode. Since ET-006b PR-3 the telemetry service starts it for every ETS2 or ATS selection, beside the v0 broker ([telemetry service v1](telemetry-service-v1.md#service-wiring)). The v1 mode differs from v0 as follows:

- **Discovery.** Records must carry `protocolMajor: 1` and the exact name `\\.\pipe\ETS2Telemetry-{game}-v1-{userTag}-{windowsSessionId}-{processInstanceId}`. Another major or name is a hard rejection (exit 1). The checks for collisions, process lifetime, token user, session and game image are unchanged.
- **Service policy.** The same bootstrap as v0 provisions `transport\v1\service-policy.json`: the same schema, the owner-only lock, the protected temporary file, `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`, and no replacement of identical bytes. It runs only when the plugin has already created `transport\v1`; otherwise the broker reports `waiting` and exits 2 without creating anything. The v0 policy is a separate file and is not touched. The plugin reads this file with the same reader as v0 ([native v1 transport](native-transport-v1.md#pipe-discovery-and-policy)).
- **Receipt.** The authority receipt adds `"protocolMajor":1`, so it has six keys. The v0 receipt keeps its five keys and the CAP0 receipt its `evidence` marker.
- **Hello.** The service sends one framed [protocol v1](protocol/v1.md) hello of at most 4,096 payload bytes. The broker validates it with the C++ v1 decoder and negotiation (`v1::negotiate(v1::decode_payload(hello, Sender::client))`). A v0 or CAP0 hello exits 1 before anything reaches the pipe.
- **Control stream.** After the hello, stdin is a stream of tagged records. `0x01` is one relay credit, as in v0. `0x02` is followed by a u32 little-endian length of 1–4,096 and exactly that many payload bytes, which must decode strictly as one v1 client message of kind `ack` or `clock.probe`. The broker writes each such frame, prefix and payload, to the pipe in stdin order and only after the hello, on its control reader thread with its own overlapped write beside the relay's pending read. Each write has a five-second deadline. A write that is not complete is cancelled with `CancelIoEx`, and its completion is observed before the buffer is released. The reader is joined before the pipe handle closes. Any other tag exits 1 like an invalid v0 credit. A length outside 1–4,096 or any other message exits 1 with stage `client-frame` and Win32 error 0, and nothing of it reaches the pipe. A write that misses its deadline or finds the pipe broken exits 3 with stage `client-write`; another write error exits 1 with the same stage. EOF inside a record is cancellation (exit 3) and forwards nothing.
- **Relay.** Server frames are relayed unchanged, one per credit, with the v1 bound of 65,536 payload bytes. The broker checks a client frame alone, not its order relative to other messages: the service owns ACK and probe ordering, and the plugin closes the connection on a client message it does not accept (protocol v1 §4, OD-5 S6). Credits remain stdio flow control and are never ACKs; the broker relays the service's `ack` and never creates one.

`client-frame` and `client-write` are new fixed stage names. The service's known-stage list includes them since ET-006b PR-3, which also starts this mode; its exits are logged as `NATIVE_BROKER_V1_EXIT` with the same fixed facts and coalescing as `NATIVE_BROKER_EXIT`.

## Current state and recovery

The service sends a single hello per connection and requires welcome followed by checkpoint. Welcome alone never creates a fresh reading. The accepted consumer rejects duplicates, regressions, unsupported versions, source/clock changes, regressing counters, malformed/split/oversize frames and partial EOF. A protocol failure closes the stream without scanning for another prefix. An explicit reselection is required after incompatibility. A selected game broker that granted no authority — the five-second startup deadline or exit 4 — is transient: the source reports `waiting` ("Native authority check did not complete; retrying") and retries on the same backoff after the broker has actually exited, without resetting it. Exit 1, receipt/relay violations and protocol or identity failures remain final `incompatible` states. Normal disconnects retry at bounded delays of 250, 500, 1,000, 2,000 and 4,000 ms; a hydrated checkpoint resets that backoff.

`waiting`, `connected`, `paused`, `stale`, `incompatible`, `disconnected`, `unavailable`, `service-failed` and `restarting` are visible. A service monotonic receive clock controls the 500 ms stale threshold. Source and receive clocks are never subtracted. A disconnect immediately clears freshness; an old observation may remain as context but the UI hides its speed/fuel values. Every update has `recording:false` and `coverage:"unknown"`; hydration is current-state replacement and never invents interval history.

Main authorizes one renderer subscription. The utility permits at most two port slots to bound replacement races. Each port holds one outstanding delivery and one replaceable latest update, receives at most 20 updates per second, and closes after five seconds without callback consumption. Delivery-ID exhaustion fails closed. The preload consumes the delivery only after invoking the narrow callback. Unsubscribe, navigation and renderer/service restarts retire old ports. A fresh authorized port hydrates from the new utility's state after a service restart.

Two service restarts are supervised, after 250 and 1,000 ms; exhaustion remains visibly failed until explicit application exit. Renderer recovery reloads at most twice. The opt-in diagnostic service-exit event exists only when `ETS2TELEMETRY_LIVE_SMOKE=1` and diagnostic/profile directories are configured; it targets the currently owned utility object, never a PID supplied by a renderer. Normal shutdown retains the original worker-probe cleanup and final deadlines. A deliberately killed service can leave its isolated probe directory; it is recorded separately from normal shutdown evidence. V0 has no recording. Since ET-011a, closing the main window hides it to the tray and leaves the service running; only an explicit exit stops it ([application lifecycle](app-lifecycle.md)). Recording-exit semantics remain ET-015 work.

Since ET-011a, the service stops through an ordered sequence: `intake` (ingestion and capture, 1000 ms each, in parallel), `flush` (empty until ET-015) and `storage` (the probe and, since ET-013 PR-2, `history-storage`, 1000 ms each, in parallel). Each step is bounded by its own budget, every step (including a successful one) is logged as a fact-only `SHUTDOWN_STEP` with its outcome, and a failed or late step does not stop the sequence, and the sum of phase maxima may not exceed 2500 ms, inside main's 3000 ms kill deadline. The service then sends one `{type: 'stopped', clean}` message and exits 0 when clean, 1 otherwise; a probe stop failure is still reported as `SERVICE_STOP_FAILED`. When a failed probe ends the service outside this sequence, the service closes the history database first (ET-013 PR-2, bounded by 1000 ms) and keeps its exit code. After first readiness this close is best effort, because the preceding `failed` report makes the supervisor kill the service at once; the killed-service rule (WAL replay on the next open) then applies. After first readiness, a service failure report or a restarted service's missed start deadline terminates the service and uses the same two supervised restarts instead of exiting the application; before first readiness both stay fatal. See [the application lifecycle](app-lifecycle.md#service-shutdown).

## History database

Since ET-013 PR-2 the service owns a second worker thread from the same `storage-worker.cjs` entrypoint, started in storage mode. At service start it opens `%LOCALAPPDATA%\ETS2Telemetry\data\telemetry.sqlite` through `StorageClient` without waiting for the result: readiness still comes only from the temporary probe, and live telemetry, subscriptions and the overlay never depend on the database. It logs `HISTORY_STORAGE_OPENED` (schema version, whether the file was created, the version it was migrated from), `HISTORY_STORAGE_UNAVAILABLE` with a fixed code (for example `DATA_PATH_INVALID` without a usable `LOCALAPPDATA`, `DATABASE_LOCKED` or `SCHEMA_NEWER`) or `HISTORY_STORAGE_CLOSED`, never a path. The `history-storage` shutdown step closes it before the single `stopped` report. The main process, the preload bridge, `ScaffoldStatus` and the renderers are unchanged and receive nothing from it. V0 still records nothing and sends no ACK; ingestion into history is ET-015a. See [storage](storage.md#history-database-in-the-telemetry-service) and [ET-013 validation](validation/et-013.md).

Validation and remaining evidence are listed in [ET-006a validation](validation/et-006a.md).

# Native Windows installer acceptance

**Retired on October 18, 2026 (ET-018 PR-1).** `Invoke-NativeInstallerAcceptance.ps1 -Run` and `native-installer-step.ps1 -Run` now throw `RETIRED_ET018_REAL_ROOTS`; without `-Run` each still prints its plan and launches nothing. Both installed into the real `%LOCALAPPDATA%\ETS2TelemetryDesktop` and seeded the real `%LOCALAPPDATA%\ETS2Telemetry`; once ET-018's uninstall removes the data root, a run would delete the user's real data. Installer checks now run only in a marked test root on a GitHub-hosted runner: [installer testing](../../docs/installer-testing.md). The text below describes the historical ET-001 procedure and is unchanged. `Test-UninstallResidue.ps1` and `Assert-UninstallResidue.ps1` are inert fixtures and stay in use.

**`Test-DeferredCleanup.ps1` (ET-018 PR-5).** It tests the deferred-cleanup executor `resources/uninstall/Complete-ETS2TelemetryUninstall.ps1` under Windows PowerShell 5.1 on temporary test-root scenes in `%TEMP%`, with its own per-run `HKCU\Software\ETS2Telemetry-Test-<id>\RunOnce` key. One scene, for the absolute `powershell.exe` form of the registered command, lives in a fresh `<system drive>\etd<8 hex>` folder instead, because the `%TEMP%` paths are too long for that form within 260 characters. It never writes the real RunOnce key and deletes its scenes, that folder and its key at the end. It plays every case of `tests/fixtures/uninstall/deferred-cases.json` as Windows starts a RunOnce entry, plus the executor's own cases (attempts, the 10th attempt, no intent, an installed application, an invalid intent, a base outside a test root, an unexpected error before and after the attempt is registered, the intent's 128 KiB bound, the absolute form, the Roaming userData on a stand-in inside the test root while the real Roaming folder is only compared before and after), and prints `DEFERRED_CLEANUP_PASS <cases>`. It starts no installer, game or application. Run it with `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File tests/windows/Test-DeferredCleanup.ps1`; `scripts/ci/Invoke-Extended.ps1` runs it too ([uninstall](../../docs/uninstall.md#deferred-cleanup-at-the-next-sign-in)).

The owner explicitly authorized current-user native runtime testing on October11,2026. These scripts use the unchanged `scripts/watchdog/BoundedProcess.cs` Job owner:16 processes,2GiB memory,25% CPU,45s installer steps and30s smoke/uninstall steps. The whole transaction has a300s budget. There are no retries. The default command reports a plan and launches nothing.

`Invoke-NativeInstallerAcceptance.ps1 -Run` requires reviewed absolute inputs and SHA256 parameters: `Manifest`, `ManifestSha256`, `Setup`, `SetupSha256`, `Feed`, `FixtureNugetSha256`, `FeedReleasesSha256`, `Node`, `NodeSha256`, `PlaywrightEntry`, `ObserverAssembly`, `ObserverAssemblySha256`, `ObserverBuildReceipt`, `ObserverBuildReceiptSha256`, `ObserverSourceSha256`, and a fresh `OutDirectory`. Run with Windows PowerShell5.1. The manifest supplies only the frozen runtime projection and installer/NuGet identities; its historical guest observer mapping is not reused. The separate reviewed DLL build receipt supplies the current assembly mapping.

Before an installation, execute `-Run -Control normal` and `-Run -Control linger`, each with its own fresh output directory and the same reviewed tool/projection inputs. They require an actual fixed child marker. Normal must finish with primary0, both streams drained, no remaining children, and whole Job0. Linger must reject with watchdog124/125 and a recorded child marker; it is never application acceptance. These controls use no application or installer.

The six steps are original Setup silent install, original Setup silent repair, installed0.1.0 smoke, Update local-feed synthetic0.1.1 upgrade, installed0.1.1 smoke, and silent uninstall. The synthetic NuGet changes installer version only; application bytes/version0.1.0 remain frozen. Each step verifies SQLite value42/synthetic1 and integrity with a real write/close/reopen followed by read-only reopen. Synthetic settings/log/archive/plugin metadata files are uniquely named and checked byte-for-byte. Existing files, logs and every existing shortcut are inventoried and preserved, including unrelated telemetry products.

The native root holds only its independently verified System32 console, waits for every other Job member to finish naturally, then exits. The immutable outer watchdog requires the remaining root console and entire Job to drain. This adapter does not assign application roles from ephemeral Chromium WMI records.

Automatic Squirrel operations are checked through actual installer exit, installed-file hashes, version selection, registration, shortcuts, preservation and absence of application/service diagnostics. Squirrel logs are retained as diagnostics; they do not establish automatic hook exit codes. Separate direct installed EXE hook regressions test exact `--squirrel-install`, `--squirrel-updated` and `--squirrel-uninstall` arguments/version, actual0, no application/service/probe startup, and natural Job drain. That evidence is explicitly labeled separately.

Pre-existing product binaries, registration, exact product shortcut name or any existing product data directory reject the transaction. Successful completion removes only the exact synthetic files and directories that this run created. Failure leaves owned fixtures and installed state for reviewed recovery; it never deletes an existing user root or recursively removes user data. Evidence and isolated profiles/TEMP remain in the new output directory.

Uninstall requires no product registration, product shortcuts or application payload. The pinned [Squirrel FullUninstall implementation](https://github.com/Squirrel/Squirrel.Windows/blob/eef37460ae/src/Squirrel/UpdateManager.ApplyReleases.cs) calls [DeleteDirectoryOrJustGiveUp](https://github.com/Squirrel/Squirrel.Windows/blob/eef37460ae/src/Squirrel/Utility.cs), which tolerates deletion failure, then writes a one-space `.dead` marker. The validator allows only that exact marker and optional `Update.exe`/`app-<tested-version>/squirrel.exe`, each matching the sealed vendor helper bytes. Every other file, unknown directory, reparse point or altered helper fails. The receipt records `vendorCleanupPending`; it does not claim an empty binary root. The authorized coordinator may separately restore the previously absent binary root after all Jobs have exited and exact residue ownership has been checked. The failed first-cycle receipt remains unchanged.
